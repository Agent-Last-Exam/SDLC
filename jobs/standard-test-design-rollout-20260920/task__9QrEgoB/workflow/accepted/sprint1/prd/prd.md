# PRD：Saleor 商家经营与应用接入升级

版本：1.0
责任：产品
状态：需求范围与验收条件已定义

## 1. 业务背景与目标

商家需要在不中断存量订单、账号、资产和已购权益的前提下，引入更多外部应用并升级经营能力。本轮同时覆盖 Saleor 核心 API 与商家 Dashboard，目标是：

- 让运营可靠维护经营资料、富文本内容、外部图片和现有搜索；
- 让仓储与渠道运营按渠道控制库存来源、外部运费缓存和配送过滤；
- 在退出旧数字内容业务接口后，继续保护已购下载权益，并保证新销售有明确履约路径；
- 将礼品卡纳入统一交易与退款账务，增加可分页、可定位、受权限和渠道隔离的交易入口；
- 安全退出 Dummy、DummyCreditCard、Braintree、Razorpay 四类旧支付插件，同时保留历史售后能力；
- 以部署配置执行 `ALL`、`CUSTOMERS_ONLY`、`DISABLED` 三种密码策略，并保障管理员恢复路径；
- 补齐五类详情 Widget、应用故障可视化，以及按事件、渠道和最小字段订阅的变化通知；
- 给实施与 QA 明确预检、迁移、对账、恢复和本地验收门槛。

成功不以“代码中存在字段或流程”为标准，而以第 4 章各可观察验收条件为准。任何切换都不得通过删除历史数据、扩大权限、暴露敏感数据、重复扣款/退款或重置订阅来换取便利。允许维护窗口，不承诺无停机升级；真实经营规模、生产使用情况和外部路径可用性尚未提供，均是部署前依赖而不是本 PRD 已验证的事实。

## 2. 用户与场景

- 商家管理员：统一维护店铺展示与公司资料；选择渠道库存模式和运费行为；配置安全登录；管理应用、Webhook 与升级切换；查看影响、恢复路径和审计结果。
- 内容运营：编辑商品、分类、集合、页面/模型、属性及翻译中的新旧 EditorJS 内容；导入外部图片；得到真实、分区的保存反馈；在异常内容存在时仍可读取和检索安全文本。
- 仓储运营：在兼容配送区域模式与仅按渠道仓库模式间逐步切换；理解仓库顺序、共享库存、预留、分配、补货与切换影响。
- 渠道运营：为每个渠道设置外部报价缓存时长和外部配送过滤；在报价或过滤应用故障时理解可售配送方式和恢复手段。
- 客服：从订单、交易和礼品卡查看真实资金来源、已付/已退/处理中金额；处理礼品卡或混合退款；继续协助顾客访问合法的历史数字权益。
- 财务：按交易、事件 PSP 参考号、订单/结账、渠道、时间、来源应用和礼品卡来源定位资金；迁移旧账、对账并处理部分成功或证据不足的项目。
- 账号管理与运维：实施密码策略、盘点受影响会话、验证外部管理员登录及恢复；观察应用投递和熔断状态；在维护窗口保护在途支付与通知。
- 集成方：声明并运行受权限控制的扩展；使用最小字段、渠道范围明确的新订阅；逐个 Webhook 验证并迁移，不被升级自动重置。
- 顾客：继续登录或使用外部身份、购物、退款，并按原次数和期限访问已购数字内容；密码策略之外的匿名购物与合法 token 不受误伤。
- 实施与 QA：依据目标 schema、迁移清单、异常矩阵、对账结果和恢复演练判定是否可交付，不把静态代码或受控模拟误作生产验证。

## 4. 需求条目

### R01 · 经营资料的统一维护与独立保存
- 来源：`query.md`「经营资料与检索」“统一维护展示名称、介绍/页头、公司名称与地址、邮件发件信息和公共/私有 metadata”；`business-conversations.md`「资料保存：未编辑不等于清空」“信息和地址分别保存、分别反馈”“省略就保留，显式清空与不合法空值要区分”。
- 优先级：P0
- 需求描述：API 与 Dashboard 应在经营设置中完整呈现并可靠更新店铺展示名称、介绍、页头、经营地址中的公司名称、邮件发件名称/地址和公共/私有 metadata；展示名称不得联动域名。设置与地址使用各自明确的更新、错误和成功状态，遵循已有字段约束与 API 已定义的 `null` 清空语义。
- 验收条件：
  - AC-01-1：有 `MANAGE_SETTINGS` 的用户只更新经营信息时，未提交的地址字段保持原值，且不会新增地址记录。
  - AC-01-2：有 `MANAGE_SETTINGS` 的用户只更新地址时，未提交的经营信息、发件信息和 metadata 保持原值。
  - AC-01-3：展示名称更新后店铺域名不变；公司名称读写经营地址的 `companyName`，不产生第二套公司名称来源。
  - AC-01-4：省略字段、显式清空和非法空值分别得到“保留”“按契约清空”和字段错误三种可区分结果。
  - AC-01-5：清空经营地址必须经独立显式操作和确认；清空后历史订单地址快照不变。
  - AC-01-6：经营信息与地址分别显示保存进度和结果；一方成功一方失败时不得显示整体成功，失败区保留用户输入并可重试。
  - AC-01-7：非法邮箱、发件名称换行、超长字段或不符合国家规则的地址在对应字段/区域返回错误，其他区域不被误报成功或清空。
  - AC-01-8：重复提交同一地址更新不重复创建地址，且最终读取值与首次成功提交一致。
  - AC-01-9：无 `MANAGE_SETTINGS` 的员工或应用不能修改上述设置；匿名 `shop` 查询和无私有 metadata 读取权限的订阅均不能获得私有 metadata。
  - AC-01-10：公共 metadata 的界面和契约明确警示不得保存敏感信息；私有 metadata 仍按既有对象权限读取和修改。

### R02 · EditorJS 新旧列表兼容与内容安全
- 来源：`query.md`「经营资料与检索」“兼容旧字符串列表与新嵌套对象列表，保留合法文字、层级、顺序和样式”；`business-conversations.md`「内容编辑：新旧内容都要可读」“空段落、空列表、空列表项……不能让后续合法内容失效”“非法结构的新提交应定位字段错误并保留旧值”。
- 优先级：P0
- 需求描述：商品、分类、集合、页面/模型，以及共用 EditorJS 处理的属性和翻译，应使用同一兼容、递归和安全处理规则读取、预览、保存并生成搜索纯文本。允许标签和协议白名单由后续契约明确，但不能降低本条安全与保真语义。
- 验收条件：
  - AC-02-1：旧版字符串 `items` 列表与新版包含 `content`、嵌套 `items` 和附加元数据的列表都可读取、预览、保存，合法内容的层级、顺序、列表样式和安全链接保持不变。
  - AC-02-2：空段落、空列表、空列表项或缺少可选字段时，处理继续到后续块和后续同级项，不导致保存、读取或索引任务崩溃。
  - AC-02-3：新提交含非法结构时，API 返回可定位到输入路径的字段错误，整个目标字段保持提交前值且不做部分覆盖。
  - AC-02-4：存量异常结构被读取时仅展示可安全解析部分并记录对象与内容路径可定位的告警，不因单个异常使整页或搜索任务失败，也不自动覆盖原文。
  - AC-02-5：文本、各级列表内容、图片 URL/说明和嵌入的 source/embed/caption 都统一移除或中和脚本、事件属性及危险协议，安全协议链接保留。
  - AC-02-6：编辑预览与保存后展示都不执行危险内容，输出到搜索的纯文本不含可执行 HTML。
  - AC-02-7：搜索纯文本按阅读顺序递归包含各层可见文字，不把结构字段、脚本或不可见元数据作为搜索文本。
  - AC-02-8：若实施需要重建派生文本或索引，必须保留原始内容备份和异常对象清单，不强制破坏性重写全库。

### R03 · 安全、可诊断的外部图片导入
- 来源：`query.md`「经营资料与检索」“支持带查询参数、无扩展名以及不支持 HEAD 但 GET 可用的合法图片源”“不能……访问内部资源或关闭安全过滤”；`business-conversations.md`「图片与搜索：失败可处理、更新可恢复」给出的 20 MiB、4000 万像素、20 秒、公网、无重定向等边界。
- 优先级：P0
- 需求描述：产品外部图片与应用品牌图的下载路径应以受限 GET 后的实际可解码内容为准，不依赖扩展名、HEAD 成功或声明的 Content-Type，同时维持 SSRF、资源消耗和原子写入保护。
- 验收条件：
  - AC-03-1：带查询参数、无文件扩展名或 HEAD 不支持但 GET 返回可解码受支持图片的公网直链可成功导入。
  - AC-03-2：错误扩展名或 Content-Type 不能单独否定合法图片，也不能让普通网页、损坏内容或不支持格式冒充图片；既有本地上传格式和视频/oEmbed 能力继续工作。
  - AC-03-3：默认单次下载上限为 20 MiB、解码像素上限为 4000 万、连接加读取总预算为 20 秒；部署可配置但必须为有限正边界。
  - AC-03-4：仅允许符合更严格生产策略的 HTTP/HTTPS 公网目标；回环、私网、链路本地、云元数据地址、非 HTTP(S) 协议及 DNS 解析/重绑定绕过均被拒绝。
  - AC-03-5：首版遇到 3xx 不自动跟随并返回要求最终直链的字段错误；需鉴权且没有公开直链的资源明确失败，不携带用户凭证进入内部系统。
  - AC-03-6：超时、非成功状态、非图片、损坏、不支持格式、体积或像素超限均返回可理解且可定位的错误，不留下成功媒体记录、临时孤立文件或替换既有图片。
  - AC-03-7：Dashboard 展示导入进行中状态；失败后保留原始输入和既有图片，用户可修改 URL 后重试。
  - AC-03-8：产品图片与应用品牌图使用等价的地址安全、重定向、预算和内容解码规则；日志隐藏 URL 中 token、签名等敏感查询参数。

### R04 · 现有搜索的可靠更新与恢复
- 来源：`query.md`「经营资料与检索」“改善已有商品、订单、顾客、礼品卡搜索及新增交易查询的更新可靠性，不引入新搜索产品”；`business-conversations.md`「图片与搜索：失败可处理、更新可恢复」“标准本地验收环境下……60 秒内可检索新值”“索引失败要可见、可重试，中断后能续跑”。
- 优先级：P1
- 需求描述：保留 PostgreSQL 等既有搜索方式、查询语义、权限、渠道隔离和空查询行为，提高商品、订单、顾客、礼品卡索引更新与重建的可观察性和并发正确性；交易定位由 R11 的精确查询承担，不引入独立搜索产品或新分词体系。
- 验收条件：
  - AC-04-1：商品的嵌套内容、富文本属性、关联属性/页面名称和 SKU，订单的既有可搜字段与交易参考号，顾客信息及礼品卡相关信息变化后，按既有搜索语义更新对应索引。
  - AC-04-2：在实施时声明配置与负载的标准本地验收环境中，单次正常更新成功提交后 60 秒内可用原搜索入口检索新值。
  - AC-04-3：标点、引号、中文和允许范围内的长输入不会导致服务端异常，并保持现有空查询、权限和渠道隔离行为。
  - AC-04-4：索引失败对运维可见且可按失败对象重试；作业中断后能从安全位置续跑，单个异常对象不会永久阻塞其他对象。
  - AC-04-5：全量重建覆盖已有非空旧索引，重建期间查询保持可用；并发编辑不会被旧快照覆盖，也不会丢失较新的待更新状态。
  - AC-04-6：迁移后的重建报告包含对象总数、成功/失败对象和重试结果，报告及索引均不泄露私有字段。

### R05 · 渠道库存模式与共享真实库存
- 来源：`query.md`「库存、运费与交付」“每个渠道可以选择‘兼容配送区域’或‘仅按渠道仓库’……共享仓库的真实库存不能按渠道复制”；`business-conversations.md`「渠道库存：有库存不等于可配送」对默认值、库存公式、切换和既有分配的决定。
- 优先级：P0
- 需求描述：为渠道增加可读写的库存模式。未显式设置的升级渠道和新渠道都默认“兼容配送区域”；新模式仅以渠道关联仓库作为库存来源。库存事实仍存于仓库库存，不按渠道复制。
- 验收条件：
  - AC-05-1：渠道 API 与详情页可读取两种模式；仅 `MANAGE_CHANNELS` 可修改，未设置值返回“兼容配送区域”。
  - AC-05-2：“兼容配送区域”继续要求仓库与配送区域的既有兼容关系，升级后未切换渠道的可售判断不改变。
  - AC-05-3：“仅按渠道仓库”中，可售数、库存校验、预留、订单分配及补货只使用当前渠道关联仓库，不以国家或配送区域关系选择库存来源。
  - AC-05-4：两种模式下国家仍参与合法配送、地址和税费判断；需配送结账没有可用配送方式时均不能完成。
  - AC-05-5：新模式的可售数继续按在库减已分配减有效预留计算，并保留库存跟踪、预售、仓库顺序、分配策略、本仓/全仓自提及私有仓资格约束。
  - AC-05-6：新模式没有关联仓库时，跟踪库存且不属于有效预售的商品不可购买；不跟踪库存及符合条件的预售按原规则处理。
  - AC-05-7：同一仓库关联多个渠道时，并发成交在同一真实存量上加锁/校验，不为每个渠道生成可重复消费的库存副本。
  - AC-05-8：切换模式或解除仓库关系不改写既有订单的有效分配、履约与退货回库来源。
  - AC-05-9：未完成结账在下一次报价、预留或完成时按当前模式重验；失效预留只释放一次，失败尝试不重复扣减。
  - AC-05-10：Dashboard 显示当前模式、关联仓库、仓库顺序及旧模式的配送区域要求；可能扩大可售区域的切换先展示变更摘要并要求确认。

### R06 · 渠道级外部运费缓存与过滤
- 来源：`query.md`「库存、运费与交付」“渠道还要能分别控制外部报价缓存时长和外部配送过滤”；`business-conversations.md`「外部运费：缓存和失败不能改变成交底线」给出的范围、默认值、缓存隔离和故障语义。
- 优先级：P0
- 需求描述：为每个渠道增加外部报价缓存时长与外部配送过滤开关，订单与结账使用自身所属渠道配置。配置只改变外部运费报价/过滤，不改变税费、支付通知或其他业务规则。
- 验收条件：
  - AC-06-1：缓存时长按秒读写，合法范围为 0—86400，0 表示不缓存，未指定时返回 43200；越界值返回字段错误。
  - AC-06-2：外部配送过滤默认开启；Dashboard 关闭前提示候选方式可能扩大，并提供独立校验和保存反馈。
  - AC-06-3：关闭过滤仅跳过结账和订单的外部过滤 Webhook，本地配送校验和外部报价调用仍执行，税费和支付通知不变。
  - AC-06-4：报价缓存至少按应用/Webhook、渠道和完整报价上下文隔离；地址、数量、金额、折扣、币种、订阅所选字段、应用身份或相关配置任一变化均不命中旧缓存。
  - AC-06-5：超时、错误和无效响应不作为成功报价缓存；符合契约的空列表可按渠道 TTL 缓存。
  - AC-06-6：外部报价仅接受渠道币种、非负金额、合法标识和币种精度；无效项不成为可选配送方式。
  - AC-06-7：报价失败时保留其他合法本地/外部方式；无方式时明确显示不可配送并可重试，不自动创建零价配送或无限沿用过期缓存。
  - AC-06-8：过滤开启且过滤请求失败或熔断时，受影响候选方式不能成交；只有商家显式关闭该渠道过滤后才可恢复为未经过滤候选。
  - AC-06-9：成交前重验所选配送方式和价格；涨价进入已有价格变更确认流程，不静默多扣，已生成订单保留原运费快照。

### R07 · 旧数字内容 API 退出与权益连续性
- 来源：`query.md`「库存、运费与交付」明确退出 `digitalContent`、`digitalContents`、创建/更新/删除/生成下载地址操作及关联字段和专属类型；`business-conversations.md`「数字交付：退出入口不退出已购权益」对兼容下载、导出、门槛和新销售的决定。
- 优先级：P0
- 需求描述：从目标 GraphQL schema 和 Dashboard 移除明确列举的旧数字内容业务入口，但保留数字商品、非配送类型、文件属性、礼品卡、普通订单履约、历史文件记录及已购权益。历史兼容下载服务不在本轮下线。
- 验收条件：

  - AC-07-5：兼容下载不公开受保护文件，不允许猜测 ID 或跨订单/顾客读取；下载成功的计数更新具备并发正确性。

  - AC-07-7：已付款未交付订单在切换前完成权益签发或经验证交接；新数字订单由商家选定且验证过的既有履约应用/外部服务处理。
  - AC-07-8：没有可用新履约路径时阻断相关新销售或整体切换，不影响已购下载和无关普通商品。

### R08 · 礼品卡统一交易记账与支付计算
- 来源：`query.md`「资金追踪与售后」“每张实际扣款的卡都有平台交易和扣款事件”“统一实付只计算一次礼品卡”；`business-conversations.md`「收款退款：每一笔都保留真实来源」对排序、有效性、税基、权限和完整卡码的决定。
- 优先级：P0
- 需求描述：将礼品卡视为平台支付来源。成功结账时为每张实际扣款礼品卡创建可追溯的 `TransactionItem` 与扣款事件，统一订单实付和支付剩余金额，消除旧补偿字段的二次计入风险。
- 验收条件：
  - AC-08-1：报价、加卡或失败结账不创建成功扣款事件且不减少余额；只有成功进入既有成交时点才落账。
  - AC-08-2：多卡按创建时间、再按唯一 ID 稳定排序消费；每卡扣款不超过其有效余额或结账剩余应付。
  - AC-08-3：仅激活、未过期且与结账币种一致的礼品卡可消费；不满足条件时结账返回明确错误且不部分扣卡。
  - AC-08-4：每张实际扣款卡对应独立平台交易及扣款事件，可追溯订单、结账、原卡、金额、币种和平台礼品卡来源；外部应用不能伪装成该来源。
  - AC-08-5：同一结账的重复完成、并发请求或异步重试返回既有资金结果，不重复扣卡或重复创建可操作交易；不同结账并发不能超用同一卡余额。
  - AC-08-6：订单统一实付只计入礼品卡实际扣款一次，不再叠加旧 `gift_card_compensation` 为第二笔；余额、礼品卡事件、交易事件、订单和结账结果一致。
  - AC-08-7：礼品卡作为支付不改变税基，支付应用只接收扣除礼品卡后的剩余应付；全额礼品卡按既有订单确认配置成交且不伪造 PSP 交易。
  - AC-08-8：API 与 Dashboard 仅展示掩码卡号和币种；无 `MANAGE_GIFT_CARD` 者不能修改余额/状态，无相应读取权者不能获得完整卡码或他人信息。

### R09 · 礼品卡及混合支付退款编排
- 来源：`query.md`「资金追踪与售后」“礼品卡部分或全额退款由平台退回原卡……混合支付按真实来源处理”；`business-conversations.md`「收款退款：每一笔都保留真实来源」对幂等、部分成功、状态和授权的决定。
- 优先级：P0
- 需求描述：在现有退款管理入口中按真实支付来源编排礼品卡、外部支付及混合退款。礼品卡份额由平台退回原卡，不向 PSP 发送该份额；每个来源保持独立而可汇总的事实状态。
- 验收条件：
  - AC-09-1：退款入口显示各来源的实扣、已退、处理中、剩余可退、原因、事件和最终状态；不同币种不相加。
  - AC-09-2：退款金额必须为正且符合币种精度；省略金额时取该来源剩余可退，累计成功加处理中不超过实际扣款。
  - AC-09-3：礼品卡退款只增加原卡余额并记录平台退款交易事件，不调用第三方 PSP；混合退款仅把外部资金份额发送给对应外部路径。
  - AC-09-4：退款申请要求稳定幂等标识；重复提交、并发或异步重试返回原结果，不多退余额或多发外部退款。
  - AC-09-5：混合退款一方成功一方失败时保留真实部分成功及失败原因，订单不被伪造成全成功，重试只处理失败来源。
  - AC-09-6：外部资金已成功但本地落账失败时保存外部资金事实并进入补偿或人工处理状态，重试不得再次请求外部资金动作。
  - AC-09-7：审批通过、处理中和退款成功可区分；只有余额恢复及成功事件确认后，礼品卡部分才显示成功。
  - AC-09-8：原卡过期或停用仍可接收退款，但不会被激活或延期，界面提示仍不可消费；找不到原卡时明确失败且不转现金。
  - AC-09-9：已有资金使用的礼品卡不能普通删除，系统引导停用；退货回库、取消订单和资金退款状态相互独立，取消不隐式重复退款。
  - AC-09-10：发起或登记退款要求 `HANDLE_PAYMENTS`，进入订单还需订单权限；任何卡余额或状态修改另需 `MANAGE_GIFT_CARD`。

### R10 · 历史资金归一、对账与不确定账务
- 来源：`business-conversations.md`「历史账务与资金定位：不把归一当作再次收款」“可信扣款/退款证据可形成带迁移标识的账务归一记录，不再次扣余额”“证据不足保留只读旧账和‘待核对’”。
- 优先级：P0
- 需求描述：提供可分批、续跑、幂等的历史资金盘点和归一机制，在不强制转换全部 `Payment` 的前提下，将可信礼品卡资金事实关联到统一交易视图，并隔离不确定账务。
- 验收条件：
  - AC-10-1：升级前按旧 `Payment`、`TransactionItem`/事件、礼品卡事件、订单补偿字段盘点扣款与退款，并区分已退、未退和证据不足。
  - AC-10-2：可信证据生成带迁移来源和审计映射的归一记录时，不再次扣减/增加卡余额，不重发消费或退款通知。
  - AC-10-3：旧支付与新交易并存时，同一资金事实只形成一笔可操作余额；不强制转换无礼品卡归一需要的全部历史 `Payment`。
  - AC-10-4：迁移支持分批、断点续跑和幂等重跑；同一订单在新记账启用后不会同时由新旧流程扣卡。
  - AC-10-5：对账按币种核对卡余额、订单实付/已退及来源关联，输出处理数、差异、审计映射和重试结果。
  - AC-10-6：证据不足项保留只读旧账并标为“待核对”，不能由当前余额反推成功交易，也不能开放不确定的自动退款。
  - AC-10-7：财务可用受权限控制的入口，依据可追溯线下证据登记经审核映射；登记保留审核人、时间和证据引用且不触发资金动作。

### R13 · 三态密码策略的端到端执行
- 来源：`query.md`「登录与账号连续性」三种策略定义；`business-conversations.md`「密码策略：按账号身份执行，不只按页面执行」「账号恢复：不能借旧链接或旧会话绕过」。
- 优先级：P0
- 需求描述：由实例部署配置提供 `ALL`、`CUSTOMERS_ONLY`、`DISABLED` 三态密码策略，API 与 Dashboard 按用户当前 `is_staff` 身份一致执行。首版 Dashboard 只读展示，不在线修改。
- 验收条件：
  - AC-13-1：新装和升级未设置配置时均为 `ALL`；未知值使启动或配置检查失败并列出合法值，不静默回退。
  - AC-13-2：`ALL` 允许所有符合既有校验的用户使用本地密码；`CUSTOMERS_ONLY` 仅允许当前 `is_staff=false`；`DISABLED` 禁止所有用户的本地密码入口。
  - AC-13-3：员工判定只依据当前 `is_staff=true`，包括超级管理员和有购物记录的员工；顾客升格员工后立即受员工限制。
  - AC-13-4：策略覆盖密码登录、设置/修改密码、重置邮件、带密码注册和员工密码邀请；被禁止的写入原子拒绝且不改变密码哈希或账号状态。
  - AC-13-5：受限账号的公开找回仍保持防枚举响应，但不发送重置邮件；策略收紧前签发的重置/邀请链接不能设置密码或建立可用本地会话。
  - AC-13-6：无密码顾客注册、外部身份创建/登录、授权应用 token 和匿名购物继续遵守原规则；激活、邮件确认、节流、CSRF 和权限校验不被绕过。
  - AC-13-7：匿名 `shop` 可查询密码策略和可用外部认证方式且不泄露账号是否存在；策略查询失败时 Dashboard 不默认开放密码入口。
  - AC-13-8：Dashboard 对受限员工隐藏密码与找回入口，并在无外部方式时提示联系管理员；后端仍独立拒绝直接 API 调用。
  - AC-13-9：收紧策略使受影响本地访问及刷新会话失效；来源无法辨别的旧会话安全失效并要求重登，但账号、密码哈希、订单归属和外部身份关联保留。
  - AC-13-10：放宽策略不复活已失效会话，但保留密码的用户可重新登录；外部身份不能仅凭可控邮箱匹配取得员工权限。

  - AC-15-8：凭证只发送到验证过的来源，不出现在 URL 或日志中，长期 token 不暴露给错误 iframe 来源。

### R16 · 应用故障状态、影响和安全恢复
- 来源：`query.md`「应用使用与变化通知」“区分安装失败、主动停用、投递失败及熔断”；`business-conversations.md`「故障管理：未知不等于健康」“首版沿用 Base 默认阈值及自动恢复语义”。
- 优先级：P1
- 需求描述：应用列表、详情及全局提醒用一致状态模型展示安装、主动停用、异步投递与同步熔断影响；沿用 Base 的默认阈值和自动恢复机制，不提供首版阈值自由调节或强制清零。
- 验收条件：
  - AC-16-1：界面可区分安装失败、主动停用、异步投递失败/耗尽和同步 Webhook 熔断，不用单一“不健康”状态混淆。
  - AC-16-2：每种状态展示最近变化时间、受影响同步事件、最近失败原因及有权用户可进入的投递详情。
  - AC-16-3：未启用监控、仅观察、数据未知和正常是不同状态；状态请求失败显示“未知”及刷新入口，不显示健康。
  - AC-16-4：升级不自动开启新的阻断；熔断继续使用 Base 默认阈值、半开观察和自动恢复语义，单一应用/事件故障不无差别停用该应用其他事件或其他应用。
  - AC-16-5：保留投递详情、既有异步重试及应用停用/启用能力；恢复操作不提供阈值编辑、强制清零或从故障页盲目重放同步资金动作。
  - AC-16-6：无详细日志权限者只看必要影响提示，不能越权读取或操作；日志与错误不包含密码、完整卡码、长期凭证或敏感 URL 参数。
  - AC-16-7：运费相关熔断按 R06 的候选方式和过滤规则处理，不以应用“恢复”绕过成交前重验。

### R17 · 经营、交易及 metadata 变化通知覆盖
- 来源：`query.md`「应用使用与变化通知」新增经营设置/地址、交易、八类 metadata 通知范围；`business-conversations.md`「变化通知：少给数据，不漏真实变化」“保留现有……事件”“不把建议名当现有接口”。
- 优先级：P0
- 需求描述：在保留现有事件与 metadata 专用通知的基础上，补充业务要求的变化覆盖。事件名称、枚举和错误码由后续契约规范化，本 PRD 中对象名称只界定业务范围。
- 验收条件：
  - AC-17-1：经营普通设置实际变化和经营地址变化均有可订阅通知；仅 metadata 变化仍触发既有 `SHOP_METADATA_UPDATED` 语义，不泄露私有字段。
  - AC-17-2：`TransactionItem` 创建以及金额、状态、退款事实变化可订阅，覆盖平台礼品卡交易与外部交易；既有 transaction metadata 专用通知保留。
  - AC-17-3：Attribute、Category、Menu、MenuItem、Page、PageType、ProductType、ShippingMethod 的 metadata 实际变化各有专用通知能力。
  - AC-17-4：不为 AttributeValue 新增 metadata 字段或 metadata 事件；其普通创建、更新、删除继续使用原有对象事件。
  - AC-17-5：Shop、订单、商品、变体、仓库、渠道、礼品卡等既有事件集合继续可用，本次补充不顺便删除其他弃用 API 或事件。

### R18 · 最小授权通知载荷与一致触发语义
- 来源：`query.md`「应用使用与变化通知」“只提供订阅者有权读取且选取的字段”；`business-conversations.md`「变化通知：少给数据，不漏真实变化」对创建、提交、批量、去重、顺序和删除快照的决定。
- 优先级：P0
- 需求描述：所有新增通知按已提交事实、对象权限、渠道范围和 subscription query 字段选择生成最小载荷，并在通用 metadata、对象内嵌和批量入口间保持一致逻辑事件语义。
- 验收条件：
  - AC-18-1：注册与投递都校验订阅应用的领域权限及渠道范围，载荷仅含合法 query 选择且当前应用可读的字段；撤权后不再提供被撤字段或对象。
  - AC-18-2：私有 metadata、员工信息和渠道隔离不因通知放宽；完整卡码、密码、密钥、长期凭证均不得进入新增通知、样例或日志。
  - AC-18-3：对象创建时的初始 metadata 包含在创建事件中，不额外伪造 metadata 修改事件。
  - AC-18-4：通用 metadata mutation、对象内嵌 metadata 更新和批量写入都覆盖专用通知；批量部分失败时只为成功对象登记事件。
  - AC-18-5：只有事务成功提交且值实际变化时产生逻辑更新；失败、回滚、同值写入或删除不存在 key 不产生新逻辑事件。
  - AC-18-6：同次业务提交内，同一对象同类变化最多产生一个逻辑事件；网络重试允许以同一稳定事件标识重复投递。
  - AC-18-7：事件提供对象标识、发生时间及可比较版本/序号供消费者排序，不承诺跨对象全局有序。
  - AC-18-8：删除或过期对象的通知携带足够快照或删除标识供订阅 query 解析，不因实时查不到对象而无限重试。
  - AC-18-9：过渡期保留原通用更新事件对 metadata 的既有触发，并文档化其与专用事件可能同时出现，消费者按事件类型去重/处理。

### R19 · 订阅契约、兼容迁移与可靠投递
- 来源：`query.md`「应用使用与变化通知」“按事件、支持的渠道和最少字段订阅”“存量订阅有过渡安排”；`business-conversations.md`「订阅过渡：先验证再切换」对 payload 模式、界面、至少一次投递和恢复的决定。
- 优先级：P0
- 需求描述：新增事件只使用 subscription payload，必须提供合法 query；旧事件继续兼容既有固定 payload 与自定义 query。所有契约入口一致暴露新增内容，并支持单个 Webhook 验证后切换。
- 验收条件：
  - AC-19-1：新增事件没有合法 subscription query 时拒绝创建/更新；旧事件仍可维持既有固定 payload 或已有自定义 query。
  - AC-19-2：升级不改变既有 Webhook 的事件集合、签名、目标 URL、启用状态、payload 模式或原字段含义，也不要求应用一次性重装。
  - AC-19-3：新增事件/字段在 App Manifest、Webhook 创建/更新、事件列表、subscription schema、样例和 Dashboard 编辑器中一致可见。
  - AC-19-4：创建/更新时校验 query 与事件匹配、字段存在、字段权限和渠道约束；失败返回可定位错误且不覆盖现有有效订阅。
  - AC-19-5：Dashboard 可查看事件、payload 模式、渠道、投递记录和迁移提示；管理要求 `MANAGE_APPS` 或既有应用所有者权限。
  - AC-19-6：可预览不含真实敏感数据的样例并用隔离事件验证连接，不以真实扣款、退款或其他资金动作测试。
  - AC-19-7：交付旧订阅清单、新 query 示例、影响、切换与恢复说明；每个 Webhook 可先验证后单独切换，旧固定格式最终停止日不在本轮硬定。
  - AC-19-8：异步变化在业务提交后可靠登记，worker 崩溃不丢已确认变化；投递按至少一次、失败有限重试，耗尽状态可见并允许授权重试。
  - AC-19-9：投递提供稳定事件 ID、时间、对象、验签和重试说明；排队不显示为送达。
  - AC-19-10：Webhook 停用后不登记新投递；重新启用只恢复明确未成功范围，不无提示重放全部历史。
  - AC-19-11：同步 Webhook 保持既有响应语义，任何平台或消费者重试都不得重复已成功资金动作。

### R20 · 受控升级、恢复与交付门槛
- 来源：`query.md`「范围与非目标」及“后续实施须先有影响报告……安排迁移、对账、恢复与开放后验证”；`business-conversations.md`「受控切换与恢复」全部固定决定。
- 优先级：P0
- 需求描述：实施交付必须包含可执行的影响评估、目标契约、维护窗口、备份、迁移/重建、对账、恢复和开放后验证方案。本条定义后续交付门槛，不表示本 PRD 阶段已执行。
- 验收条件：
  - AC-20-1：维护前影响报告不含明文密钥，并列出旧数字字段/固定 payload 消费者、四类插件使用渠道、受影响密码账号、账务不确定项及预计迁移对象规模。
  - AC-20-2：外部管理员登录、替代支付/售后、数字履约及所需受控通知端均由责任方真实验证；任一 P0 外部路径未验证即阻断切换。
  - AC-20-3：维护前完成可恢复一致的数据库、媒体、应用配置、必要密钥和构建版本备份，并记录恢复责任人、校验和与访问控制。
  - AC-20-4：维护时停止入口写入、暂停或排空相关任务，并盘点在途支付回调与待投递事件；外部回调由平台持久接收或由已验证发送方重试，不吞掉资金结果。
  - AC-20-5：API、worker 与 Dashboard 固定到本次交付源码或镜像摘要，Dashboard 生成代码与真实调用使用同一完整目标 schema，不用未知 `latest` 作为交付证据。
  - AC-20-6：迁移顺序覆盖 schema/数据变更、历史数字权益保护、资金归一与按币种对账、必要索引重建、订阅预检及开放前验证，每一步有失败停止和可恢复点。
  - AC-20-7：开放流量前所有 P0 验收通过，且无未解决的数据、权限、资金或管理员登录阻断；每条 AC 有结果或明确失败原因。
  - AC-20-8：开放后若已有新订单或外部资金动作，恢复时先暂停并保留增量对账，再前向修复或使用可重放恢复，不直接回滚旧数据库抹掉新增事实。
  - AC-20-9：本地交付环境包含 API、Dashboard、必要数据库/缓存/worker 以及受控身份、支付、运费、通知端；模拟数字履约仅用于接口验证且明确不证明生产外部路径可用。
  - AC-20-10：验收矩阵覆盖多渠道、共享/独立仓库、员工/顾客/无权应用、混合资金、旧账、新旧订阅、异常历史内容及不同数字权益，不能用单一正常样本替代连续性验证。
  - AC-20-11：维护时长和 RTO 只能用演练实测记录，不预设虚构生产承诺；无法达到产品参数时提交有证据的变更说明，不静默放宽。

## 5. 范围与非目标

本次范围包括：

- 核心 API 与 Dashboard 的经营资料、EditorJS、外部图片、现有搜索可靠性改进；
- 渠道库存模式、渠道级外部运费缓存和过滤；
- 明确范围的旧数字内容 GraphQL/Dashboard 退出、历史权益兼容与迁移门槛；
- 礼品卡交易化、退款编排、历史资金归一、分页交易查询和财务入口；
- Dummy、DummyCreditCard、Braintree、Razorpay 四类插件的受控退出；
- 三态密码策略的 API 执行、Dashboard 只读呈现、会话收紧及切换恢复；
- Category、Page、PageType、Menu、Promotion 五类详情 Widget；
- 应用故障状态、指定变化通知、最小字段/渠道订阅、旧订阅过渡和可靠投递；
- 配套目标 schema、兼容说明、迁移/预检/对账/恢复工具及本地交付验证依据。

明确不做：

- 顾客 Storefront、原生 App、支付服务商、身份产品、商家主体认证系统、应用市场结算分成；
- 任意 Dashboard 页面搭建器、跨币兑换、礼品卡转账/提现/利息/自动延期/退款转现金；
- 语义搜索、新增分词、推荐、全局搜索产品、独立媒体代理/CDN；
- 新数字分发产品、兼容下载服务最终下线，或强制终止无到期历史权益；
- 强制转换全部历史 `Payment`，删除未整体弃用的内置支付、Webhook 支付、OpenIDConnect、邮件、插件扩展框架、普通数字商品或文件属性；
- 除明确四类支付插件和旧数字内容契约以外的顺手弃用清理；
- 更多扩展挂载点、熔断阈值自助配置、强制清零、旧固定 Webhook payload 的最终停止日期；
- 在线修改密码策略或以外部服务故障为由自动放宽策略；
- 无停机承诺、虚构生产 SLA/RTO，或以本地模拟替代生产外部支付/身份/履约验证。
