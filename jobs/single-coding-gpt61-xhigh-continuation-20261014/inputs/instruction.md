# 业务委托：让 Saleor 的结账、收款与商户运营保持一致

## 背景与目标

这次 Saleor 3.23 交付以 Core 3.22.0 和 Dashboard 3.22.9 为升级起点，重点不是堆叠独立功能，而是打通客户结账、选择配送、支付、生成订单，再由商户履约和售后的商业链路。

Storefront 和支付集成方需要知道客户此刻能买什么、如何配送、支付是否有效；商户、客服和履约管理员需要看到相同的库存、金额和订单事实，并能在各自权限内采取行动。App 与 Webhook 集成方也需要明确的接口和事件约定，不能因为后台页面变化而失去兼容或读到错误状态。

请围绕这条链路完善本次交付：减少商户手工处理已支付结账的负担，让商品不可售、配送失效、资金不足、输入非法和权限不足都有可解释的结果。升级既要保护历史数据，也不能把失败、尚未保存的设置或尚未执行的后台工作显示成成功。

## 主要变化

### 从可售判断到订单生成，使用一致的条件

让 Storefront 能主动重新计算当前结账的配送选项，显示可用项和当前选择；结账状态变化后，更新配送和完成订单都要重新确认有效性，不能沿用失效选择。商品、结账、订单和履约应遵守一致的渠道与仓库库存规则，同时保护未切换库存策略商店的既有行为。

商户可以按渠道配置已支付结账的自动完成策略。自动化不能放松客户、地址、配送、库存和金额条件，失败后的重试也不能多生成订单、多扣款或重复发送完成事件。

### 把收款、礼品卡与售后放在同一笔账上

将礼品卡纳入统一的交易生命周期，让授权、取消、扣款、退款和余额有可追踪的对应关系。Dashboard 的订单金额分解、交易事件与剩余待付金额必须与服务端一致，普通交易和礼品卡不能重复计入。

商户需要安全地标记已支付、捕获授权款和退款：有权限不代表任何状态都能操作，可操作金额也必须以当前真实余额为限。客服和支付集成方应能通过基础业务关联与支付标识找到相关交易，而不是依赖本轮不交付的查询增强。

### 让运营人员找到对象、理解问题并准确执行动作

保留与主体业务相关的搜索，以及商品编辑页按渠道诊断可售性的能力。诊断要指出真正阻断销售的原因，区分警告和不适用检查，不能让正常依赖项淹没实际问题。

Dashboard 的列表、分配弹窗和层级导航要保持筛选与上下文一致。用户看到的对象范围，必须与导出、批量操作实际作用的范围一致；搜索、加载、空结果、权限和错误状态应清楚可辨。

### 统一身份策略，阻止危险内容和越权操作

商户应能控制客户和员工是否使用密码认证；服务端认证流程、后台登录入口和配置页面必须读取同一生效策略。外部身份关联不能留下旧密码绕过通道。

富文本和外链在保存前就要经过结构与安全校验。公开 API 同样需要明确的输入、权限和失败语义，不能把请求通信成功误认为业务操作成功，也不能在失败时留下部分危险数据或泄露敏感信息。

### 保持扩展、事件和历史订单数据可信

App 的安装、升级、扩展展示和表单交互需要一致且可迁移的约定，自托管商店也要有可用的扩展目录体验。Webhook 只做订阅实际需要的工作，允许异步处理的事件不要拖慢业务请求；一个接收方失败不应阻断其他接收方。

订单应保留创建时的配送元数据，不能因为后来修改或删除配送方式而改变历史事实。保留业务所需的基础读取和编辑，不为此扩展出独立的元数据管理功能。

### 让工作台根据最新事实展示和保存

配置加载、编辑、保存和缓存更新必须围绕用户当前操作，不能用迟到的数据覆盖正在输入的内容。重量、金额、媒体状态和订单时间展示应准确；草稿订单动作只在渠道和商品条件允许时可用，并说明不可用原因。

## 范围与非目标

范围覆盖上述 Core、Dashboard、Storefront 和外部集成的业务约定，以及为其必要的权限、历史数据迁移和客户端兼容。库存与金额等同一事实在不同入口应一致；升级既要能初始化新商店，也要保留既有订单、交易、扩展、库存和元数据的业务含义。

本轮不交付 App Problems、页面和用户的高级搜索、交易日期或事件筛选及专用排序、外链图片异步抓取与专用失败回退、独立变体生成器，以及订单、履约、仓库的独立元数据弹窗。排除这些增强不等于删除基础搜索、普通媒体与变体操作、基础交易查询、元数据编辑或 Webhook 失败告警。具体保留边界见补充沟通。

不另行增加与主体链路无直接关系的独立功能。依赖升级、CI、生成工具、遥测和内部重构不单独成为业务目标；只有影响上述业务约定的部分才属于本次交付约束。
