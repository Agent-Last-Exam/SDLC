版本：v1
责任：产品
状态：存在待确认项
输入：instruction.md；business-conversations.md；Core 3.22.0 与 Dashboard 3.22.9 现有项目代码、公开接口定义

## 1. 业务背景与目标

本次以 Core 3.22.0、Dashboard 3.22.9 为升级起点，面向 Saleor 3.23 打通“判断可售 → 更新结账与配送 → 收款 → 生成订单 → 商户履约与售后”的商业链路。现有项目已提供结账完成、渠道自动完成开关、Payment/Transaction、礼品卡、扩展和 Webhook 等基础能力；本次不是将这些能力重新建设为互不关联的功能，而是使各入口对同一业务对象的库存、金额、权限和状态采用相同事实。

业务问题及依据：

- Storefront 需要主动刷新配送选项；历史选择不代表当前地址、商品、渠道和配送服务条件下仍然有效（Instruction“从可售判断到订单生成”；BC-001、BC-002）。
- 渠道库存策略变化需要同时影响商品展示、预留、订单和履约，但不得令尚未切换策略的商店意外失去可售库存（BC-003）。
- 商户希望减少已支付结账的人工成单工作；自动任务必须具备与人工成单同等的资格校验，并在配置保存、任务等待、失败和实际成单之间明确区分（BC-005、BC-006）。
- 礼品卡、普通支付、新交易和退款必须能够对账，资金动作必须受实际余额与状态约束，不能在前后端或不同记录形式间重复计算（BC-007～BC-011）。
- 运营人员需要保留主体搜索、可售诊断和当前列表上下文，确保所见范围就是导出和操作范围（BC-004、BC-012～BC-015）。
- 身份策略、安全内容、对象权限、扩展合同、事件处理和历史配送资料应保持可信，不能依靠隐藏前端入口代替服务端约束（BC-016～BC-028）。
- 工作台不得将迟到数据、未保存设置、请求通信成功或排队成功呈现成已完成的业务事实（BC-029、BC-030）。

交付目标：

1. 可售、配送、支付与成单资格在 Core、Dashboard、Storefront 和集成路径中一致，正常客户能够可靠完成购买，失败能够定位原因且不产生半成品订单、超卖或部分危险写入。
2. 符合渠道策略的已支付结账可以按批次自动完成；重复请求、并发操作和重试不会增加订单、扣款、退款或逻辑完成事件。
3. 订单金额摘要、交易事件、礼品卡余额、可捕获/可退款额度和剩余待付金额可以互相解释，并以服务端当前事实为准。
4. 商户能够在权限与当前筛选上下文内定位对象、理解问题、配置策略和执行动作；加载、空结果、错误、等待和成功清楚可辨。
5. 升级可从空库初始化，也可保护既有订单、交易、扩展、库存和元数据的业务含义；公开 schema、客户端和弃用说明一致，明确不支持的能力不伪装为成功。

材料未提供现有转化率、人工处理量、吞吐量、响应时长或目标提升比例，本 PRD 不虚构业务收益、性能 SLA 或部署结果。验收以第 3 节的可观察行为与一致性结果为准；尚缺数值的合同参数列于第 5 节。

## 2. 用户与场景

| 用户类型 | 典型任务 | 必须看到或遵守的业务事实 |
| --- | --- | --- |
| 客户与 Storefront 集成方 | 查可售商品，修改结账地址/行项目，重算配送，选择配送或自提，付款并完成结账 | 当前渠道与库存策略、当前可用配送和价格、支付状态、可分支错误；合法旧标识的兼容不放松校验 |
| 商户、渠道管理员 | 设置库存模式与自动完成策略，查看订单金额，处理草稿订单和人工收款 | 已生效而非未保存的设置、真实订单/任务结果、允许执行的动作与最新金额边界 |
| 商品及内容运营 | 编辑商品，按渠道诊断可售性，搜索页面，保存富文本，维护普通媒体和变体 | 真实阻断/警告/不适用检查、安全内容校验、编辑内容不被迟到结果覆盖；不依赖本轮排除的独立增强 |
| 客服与售后人员 | 定位结账、订单、礼品卡及交易，检查支付事件，取消授权或退款，编辑基础元数据 | 有权读取的关联对象、支付方式、余额、历史事实；无权限与无结果分开，重试不重复占用资金 |
| 库存与履约管理员 | 分配仓库，预留/分配库存，处理履约，读取创建时配送资料 | 同一渠道库存语义、正确剩余库存、稳定层级与选择上下文、历史配送元数据快照 |
| 商店与身份管理员 | 配置密码登录模式，使用外部认证，管理员工 | 即时生效的统一认证策略、旧密码路径不能绕过外部身份关联、安全的员工实际删除与权限限制 |
| 支付、App、Webhook 集成方 | 按合法业务标识查交易，安装/更新扩展，回填当前表单，订阅事件与处理 delivery | 当前 schema 和扩展合同、对象与字段可见范围、逻辑幂等、订阅选择与异步边界、单接收方失败隔离 |
| 自托管商店管理员与只读人员 | 浏览筛选扩展目录，按权限查看或配置，诊断 Webhook 失败 | 不依赖不可用旧目录服务、空态与错误分开、无配置权限时只读；失败告警不等于 App Problems |

所有用户场景均受账户状态、业务权限、对象归属及适用的渠道/仓库范围限制。客户身份、员工身份和 App 身份不得因换成列表、弹窗、导出、关联查询或错误路径而扩大可见范围。

## 3. 需求条目

本节 R01～R31 与 BC-001～BC-031 对应。来源中的引文均来自 Instruction；BC 引文用于明确条件与例外。标明“推导”的规则是为实现原要求所作的产品约束，不作为已实现事实。

优先级按模板定义使用：P0 为主体目标、资金/库存/状态正确性、安全或升级可信性所必需；P1 为不移除主体能力但使明确使用者减少重复操作的体验要求。各条均属于本轮范围，不以优先级替代非目标边界。

#### 可售、配送与可靠成单

### R01 · Storefront 显式重算当前结账配送选项
- 来源：Instruction“让 Storefront 能主动重新计算当前结账的配送选项，显示可用项和当前选择”；BC-001“计算应使用当前结账的地址、行项目、渠道和同步配送服务结果”“不能用一次失败覆盖原有有效选择”。
- 优先级：P0
- 需求描述：
  - 提供可由 Storefront 显式调用的配送重算操作，不要求客户端通过偶然读取某字段触发刷新。重算基于当前结账的地址、行项目、渠道及适用的同步配送服务结果，返回可用项、每项展示价格/状态和当前选择信息。
  - 重算成功后，不适用的旧项不得继续标为可选；旧选择如已失效，应显示为失效或无有效当前选择，并要求重新选择，不擅自选择替代项。重算不等于完成结账。
  - 缺少必要地址数据、配送服务失败、结账不存在或调用方无权访问时返回可定位错误；本次失败不覆盖原有效选择，不保存部分结果。失败后保留的旧信息不能被客户端标为本次刷新所得的有效结论。
  - 使用现有 `shippingMethods`、`deliveryMethod` 的当前读取语义承接结果；新增操作的具体字段名由接口设计确定，不在本 PRD 假称已有新 API。
- 验收条件：
  - AC-01-1：给定可访问、地址完整且行项目合法的结账，调用显式重算后，返回当前适用配送项、各项价格/状态及当前选择；与相同事实下的结账读取一致，不生成订单。
  - AC-01-2：给定已选配送的结账，修改地址使原方式不再适用，再重算后，原方式不再显示为可选或有效当前选择，其他可用方式按新地址给出。
  - AC-01-3：给定已选配送的结账，修改商品/数量或切换有效渠道上下文，再重算后，选项及价格反映最新行项目与渠道，不复用上次结果。
  - AC-01-4：给定结账未变化但同步配送服务结果发生变化，再重算后，可选项与价格反映最新服务结果，失效旧项不能继续使用。
  - AC-01-5：给定已有有效选择的结账但必要地址不完整，重算返回地址相关字段错误，原保存选择及其他结账数据不被本次失败部分覆盖。
  - AC-01-6：给定已有有效选择且配送服务失败，重算返回可识别的服务错误，选择不被失败写入改变；客户端呈现刷新失败而非最新有效配送结果。
  - AC-01-7：使用不存在或不可访问的结账标识重算时，返回符合对象权限合同的错误，不泄露配送列表、地址或原选择，且不改变任何其他结账。

### R02 · 更新配送与完成结账再次校验有效性
- 来源：Instruction“结账状态变化后，更新配送和完成订单都要重新确认有效性，不能沿用失效选择”；BC-002“合法旧标识和新的配送标识都要按兼容约定处理”“只能选择属于当前结账的配送方式”。
- 优先级：P0
- 需求描述：
  - `checkoutDeliveryMethodUpdate`、兼容的配送更新入口及 `checkoutComplete` 均依据最新结账事实校验配送。内置、外部配送和现有自提方式遵守各自适用规则，不因接受旧标识而跳过渠道、地址、行项目或归属检查。
  - 更新成功仅保存当前适用选择。完成时所选方式缺失、失效、被停用、不属于当前结账上下文或服务无法验证时阻止成单，区分缺失、不适用、不存在和服务失败。
  - 合法旧配送标识按公开兼容合同处理；旧 `shippingMethod` 等配送读取字段保留明确弃用与替代说明，新客户端使用当前 `deliveryMethod` 约定。
  - 失败不改变原选择、不产生半成品订单、不扣取新的资金；是否需要配送依据行项目事实，不将纯数字商品强制要求配送。
- 验收条件：
  - AC-02-1：对当前适用方式提交合法新配送标识，更新成功并能从当前配送字段读回；提交合同允许的合法旧标识时得到同等有效业务结果。
  - AC-02-2：提交不属于当前渠道、地址或结账上下文的配送方式时，更新被拒绝，错误指向配送字段，原选择不变。
  - AC-02-3：给定已成功选择的方式，在完成前将其停用、移除或使其不适用，调用完成结账后返回失效原因，不创建订单或半成品订单。
  - AC-02-4：给定需要配送的结账但未选择配送，完成被拒绝并指明缺失；给定不需要配送且其余条件合法的结账，不因无配送方式被错误阻断。
  - AC-02-5：给定合法自提方式，更新与完成均遵守现有自提条件；仓库不适用后完成被拒绝，不把自提与普通配送的校验混为一谈。
  - AC-02-6：使用错误类型标识、不存在结账或越权请求更新/完成时，返回稳定且不泄露配送详情的错误，不改变原选择或他人结账。
  - AC-02-7：读取支持的旧配送字段时仍获得其弃用合同规定的数据，公开 schema 和客户端明确指向当前替代字段，不返回没有解释的成功空响应。

### R03 · 渠道库存策略跨入口一致且保留旧行为
- 来源：Instruction“商品、结账、订单和履约应遵守一致的渠道与仓库库存规则，同时保护未切换库存策略商店的既有行为”；BC-003“只有直接关联当前渠道且有可用库存的仓库参与计算”“失败不能造成超卖或部分预留”。
- 优先级：P0
- 需求描述：
  - 渠道支持保留旧库存可用性模式与显式切换为直接渠道—仓库关联模式。旧模式继续遵守既有配送区域、地址及仓库关联规则；升级、读取或缺省输入不自动切换。
  - 新模式只有直接关联当前渠道的仓库参与相应库存计算，可用量按现有库存追踪、有效预留与已分配扣减语义计算，不能把物理库存直接当可售库存。仓库分配排序策略与“哪些仓库参与”的可用性策略是不同概念，不以修改 `allocationStrategy` 偷换可用性模式。
  - 商品/变体查询、结账校验与预留、普通订单、履约、草稿订单使用同一模式；新模式下兼容接受的旧地址参数不改变直接关联决定的库存结果。库存可用性不替代 R02 的配送可达性校验。
  - 关系变化和库存变化在后续校验中生效。库存追踪关闭、受支持预售等既有例外仍按现行合同处理，不新增例外来绕过不足校验。
  - 预留/分配基于最新状态并具有原子性和幂等性，不能部分成功、重复扣减或并发超卖。配置和关系调整受对应权限约束。
- 验收条件：
  - AC-03-1：升级一个未切换策略的渠道后，使用原地址和配送区域组合查询、结账和履约，库存可用性结果与旧模式业务含义一致，不因迁移自动变为不可售。
  - AC-03-2：显式启用新模式且有一个关联仓库、一个未关联仓库时，商品/变体查询只计入关联仓库的可用库存；仅未关联仓库有货时不将其计为当前渠道可售。
  - AC-03-3：新模式下对同一商品使用不同合法旧地址参数查询，库存结果不随地址改变；配送选项仍按实际地址单独校验。
  - AC-03-4：在相同渠道模式和库存事实下，商品、结账、草稿订单、订单分配与履约对仓库资格使用相同判断，成功预留/分配后读取各入口反映相同剩余可用量。
  - AC-03-5：提交需求量超过可用量的多行结账预留时，返回库存不足相关错误，所有行均不留下部分预留，不影响他人已有有效预留。
  - AC-03-6：两个请求竞争同一有限库存时，成功结果总量不超过可用量；重复执行同一预留/分配请求不再次扣减。
  - AC-03-7：排队成单后解除相关渠道—仓库关系，实际成单重新检查并在库存资格不满足时拒绝，不能沿用排队时资格；无配置权限的关系/策略修改不改变已生效值。
  - AC-03-8：对既有不追踪库存或受支持预售商品，切换模式后仍按其现行库存合同处理，不引入误阻断或新的超卖豁免。

### R04 · 商品编辑页按渠道诊断真实可售问题
- 来源：Instruction“保留……商品编辑页按渠道诊断可售性的能力”“诊断要指出真正阻断销售的原因，区分警告和不适用检查”；BC-004。
- 优先级：P0
- 需求描述：
  - 在商品编辑上下文提供渠道可售诊断，支持按渠道名称或币种筛选与分页，展示相关渠道、问题数量及明细。
  - 结合渠道/商品/变体发布和可购买时间、价格等直接销售配置、库存、渠道仓库关联与配送区域事实判断。库存检查采用 R03 当前模式，不能因新模式不依赖配送区域计算库存而免除真实配送可达性检查。
  - 结果分为阻断错误、非阻断警告和不适用。问题数按实际问题去重，可识别阻断与警告数量；正常检查和不适用检查不计入错误数。不把上游未发布等原因导致的正常下游依赖重复列成多个销售错误，独立真实阻断仍可说明。
  - 不需配送商品只跳过不适用的配送区域检查，仍检查发布、购买资格和适用库存。
  - 诊断只使用有权读取的事实。区分首次加载、刷新中、编辑未保存导致诊断非最新、查询失败和最新结果；诊断不保存或覆盖商品表单。
- 验收条件：
  - AC-04-1：有商品及渠道读取权限时，用渠道名称或币种筛选并翻页，结果只含相应渠道，数量和问题明细对应同一商品及筛选上下文。
  - AC-04-2：商品在某渠道未发布或可购买时间未到时，诊断指出真实阻断及适用时间事实，不将正常依赖重复报成销售错误。
  - AC-04-3：制造库存不足、无符合当前策略的仓库或真实配送区域缺失中的任一情况，诊断分别给出对应原因，与结账可售/配送判断一致。
  - AC-04-4：对全部核心条件正常的渠道，诊断无阻断错误；存在仅警告项时可售结论不被误判为禁止销售，不适用项不增加错误计数。
  - AC-04-5：对不需配送商品执行诊断，配送区域检查为不适用，而发布、购买资格与适用库存检查仍执行。
  - AC-04-6：无权访问某商品或渠道的调用方不能从诊断数量、错误或细节推断其受限配置；返回相应权限状态而非虚假的无问题结论。
  - AC-04-7：编辑商品后刷新诊断或模拟请求失败时，页面保留未保存输入并清楚标识诊断状态，不将上次结果当作最新，也不将错误当作零问题。

### R05 · 已支付结账批量自动成单与幂等重试
- 来源：Instruction“减少商户手工处理已支付结账的负担”“自动化不能放松客户、地址、配送、库存和金额条件，失败后的重试也不能多生成订单、多扣款或重复发送完成事件”；BC-005。
- 优先级：P0
- 需求描述：
  - 根据 R06 生效渠道策略，分批发现和处理符合资格的结账。仅“收到过支付”或存在支付记录不代表合格。
  - fully paid 资格覆盖所支持的完整授权、完整扣款及受支持组合；Transaction 与兼容 Payment 各按自身合同识别，不将失败、取消、退款后不足或待处理资金当有效全额支付，不重复计算同一笔已从授权转成扣款的额度。
  - 同时要求客户或邮箱、账单地址、非空且可售行项目、有效渠道与库存、结账总额大于零；需配送时还要求有效配送地址和方式。人工流程允许未支付订单的设置不能放宽自动成单的 fully paid 条件。
  - 批次入选与实际提交前均校验最新事实，实际完成复用可靠成单规则。已完成、已被其他请求处理或不存在的结账不再次成单。
  - 失败留可关联结账、阶段和原因的诊断结果，允许在条件修复后按支持的重试流程再处理；一项失败不阻止批次其他合格项。无需新增独立任务管理页面，执行结果以实际结账、订单和任务记录为准。
  - 推导：重复任务、并发人工完成与自动完成须收敛到一个订单结果；幂等完成不能再次扣款、改写既有订单金额或额外产生逻辑完成事件。Webhook 同一 delivery 的合法传输重试不算新增业务完成事件。
- 验收条件：
  - AC-05-1：开启自动完成且满足时间范围的 Transaction 全额授权结账，其余资格全部合法时，批次执行最终形成一个订单；全额扣款结账在相同条件下也可形成一个订单。
  - AC-05-2：使用受支持的兼容 Payment 全额支付/授权流程且其余资格合法时，按该流程合同完成；不受支持或需要客户后续动作的支付不能被伪装为已完成。
  - AC-05-3：有支付记录但实际有效金额不足、仍待处理或退款后不足时，自动处理不创建订单，留下可识别的不满足支付资格原因。
  - AC-05-4：分别缺少客户及邮箱、账单地址、所需配送地址/方式、可售行项目，或总额不大于零时，自动处理被阻止，不生成半成品订单或新增资金扣取。
  - AC-05-5：入队时合格、执行前发生库存不足、配送失效、渠道停用或金额变化导致支付不足时，执行重新校验并拒绝，不沿用旧资格。
  - AC-05-6：同一结账重复投递任务或人工/自动并发完成时，最多存在一个关联订单、一份有效库存分配及一次应有逻辑完成通知，不重复扣款，既有订单金额不被重试改变。
  - AC-05-7：一个批次同时含合格项与不合格项，合格项正常完成，不合格项不成单且可以定位原因；修复其条件后重试只形成一次有效订单结果。
  - AC-05-8：渠道允许人工创建未支付订单但目标结账未 fully paid 时，自动任务仍拒绝；已完成或已处理结账被再次扫描时不产生新的订单或通知。

### R06 · 渠道自动完成开关、延迟与 cutoff 配置
- 来源：Instruction“商户可以按渠道配置已支付结账的自动完成策略”；BC-006“延迟从结账最近一次变化开始计算”“cutoff 是结账创建时间的下界”“设置状态与执行结果分开”。
- 优先级：P0
- 需求描述：
  - 渠道配置与 API 支持自动完成开关、明确单位的非负延迟和创建时间 cutoff；页面解释适用支付范围、资格限制和时间含义。
  - 记执行时间为 `now`、有效延迟为 `D`、结账最近变化时间为 `last_change`、创建时间为 `created_at`、cutoff 为 `C`：开启且 `now - last_change > D` 才达到延迟条件；存在 cutoff 时还须 `created_at >= C`。cutoff 不是任务执行截止时间，也不是最后修改时间下界。
  - 产品决策：`D=0` 表示无额外静置时长，但仍按上述严格时间边界检查；空 cutoff 不附加创建时间下界。更新未传字段保留其已生效值，旧渠道缺省继续关闭或其既有明确配置行为，不擅自开启或重置。未提供的延迟默认数值不在此编造。
  - 合法保存后能重新读回生效值；非法范围/组合、无权限或保存冲突返回明确错误并保留上一生效配置。配置并发保存不能静默覆盖不同上下文中的新值，冲突需可识别并重新读取。
  - 保存成功只表示策略已生效，不表示后台已扫描、已收款或已成单；显示当前策略与实际执行结果分离。
- 验收条件：
  - AC-06-1：有渠道配置权限者保存合法开关、延迟和 cutoff 后，再进入页面与通过 API 读取均得到相同生效值；其他渠道不受影响。
  - AC-06-2：关闭开关时，即便结账已全额支付且时间合格，自动任务也不因该设置产生订单；升级未配置旧渠道后保持关闭或既有明确行为。
  - AC-06-3：当 `now - last_change = D` 时尚不入选，超过 D 才可入选；修改结账使 `last_change` 更新后重新从最新变化计算，不沿用首次支付或创建时间。
  - AC-06-4：创建时间早于 C 的结账不入选，等于或晚于 C 且其他条件合法的可入选；任务在 C 之后继续运行，不将 cutoff 误作停止时间。
  - AC-06-5：保存空 cutoff 时没有额外创建时间下界，保存合法零延迟时按零延迟含义工作；仅更新开关不会清空其他已保存设置。
  - AC-06-6：提交负延迟、非法时间、违反公开输入组合，或无配置权限者保存时，返回可定位错误，原生效值和缓存均不被失败值覆盖。
  - AC-06-7：两个编辑上下文形成保存冲突时，冲突方获得明确反馈并可读取最新值，不能用迟到响应静默覆盖当前编辑；设置保存成功的界面不显示“订单已生成”。

#### 礼品卡、交易与安全资金动作

### R07 · 礼品卡统一初始化、授权与扣款生命周期
- 来源：Instruction“将礼品卡纳入统一的交易生命周期，让授权、取消、扣款、退款和余额有可追踪的对应关系”；BC-007。
- 优先级：P0
- 需求描述：
  - 结账与订单的支付链路支持可追踪的礼品卡初始化、授权和扣款，关联到当前业务对象和相应交易/事件，不再只留下无法解释的折扣减项。初始化、授权和扣款结果各自明确，初始化成功不冒充资金扣取成功。
  - 执行前校验卡存在、启用、未过期、币种与业务对象一致、可用余额足够，以及对象权限、支付状态和合法金额范围。失败不错误修改余额、业务支付状态或转为普通支付。
  - 产品决策：明确区分账面余额与授权占用后的可用余额。授权只能占用一次，取消释放占用，扣款消耗一次资金并消除对应占用；具体存储实现由研发确定，但对外可解释余额不得被并发重复花费。
  - 相同业务对象上的同一支付请求及其网络重试幂等。推导：使用相同幂等标识但不相同金额/卡/对象的请求须拒绝冲突，不以“重试”产生另一份授权；不同请求仍不能超出当前可用余额。
  - 历史礼品卡抵扣按原订单计价含义兼容读取，不重新计算历史应付总额或伪造旧资金事件，统一展示时遵守 R09 去重。
- 验收条件：
  - AC-07-1：合法礼品卡在可访问结账或订单初始化后，能定位相应支付关联，尚未发生授权/扣款时不产生错误扣款余额或已扣款状态。
  - AC-07-2：对账面余额 100、无占用的同币种礼品卡授权 30 后，可解释的可用余额为 70；扣取该授权 30 后账面余额为 70、该授权不再占用，事件及对象支付金额对应同一业务结果。
  - AC-07-3：分别使用不存在、停用、过期、币种不一致或余额不足的礼品卡请求支付时，返回对应可识别失败，余额和业务支付状态不变，不自动改走普通支付。
  - AC-07-4：重复提交同一初始化/授权/扣款请求后，只保留一次有效授权或扣款及一次应有余额变化，不生成冲突资金事件。
  - AC-07-5：使用同一幂等标识提交不同金额或其他业务对象时，得到冲突/非法请求错误，不复用他人资金结果，也不创建第二份授权。
  - AC-07-6：两个业务对象并发请求使授权/扣款总额超出卡可用余额时，不能都成功，不形成负余额或超额占用；无权限或状态非法请求不改变任何余额。
  - AC-07-7：升级后读取原礼品卡订单，原应付金额、已用金额和关联记录的业务含义保留；新链路能明确识别礼品卡资金而不重复计入旧抵扣。

### R08 · 取消礼品卡授权、退款与事件对账
- 来源：Instruction“把收款、礼品卡与售后放在同一笔账上”；BC-008“结账阶段可以取消礼品卡授权”“订单已经扣款的，只能在可退余额内退款”。
- 优先级：P0
- 需求描述：
  - 结账阶段取消尚有效的礼品卡授权，释放其占用；已扣款订单使用退款而非取消授权恢复已消费余额，退款不得超过当前可退余额，不跨卡或跨对象退回。
  - 交易事件、礼品卡账面/可用余额、结账/订单支付及退款状态表现相同结果；重复取消/退款不得再增加余额或重复产生资金变化。
  - Dashboard 与基础交易查询显示礼品卡支付方式、相关金额和事件，代码只按权限展示所需识别信息。事件为空是合法空列表，不据此认定整个读取失败；实际操作失败需显示原因。
- 验收条件：
  - AC-08-1：给定结账中礼品卡授权 30、未扣款且原可用余额 70，取消成功后授权占用释放、可用余额恢复为 100，取消事件和结账状态一致。
  - AC-08-2：给定订单已用礼品卡扣款 30、此前未退款，合法退款 10 后卡余额只恢复 10，当前可退额度相应减少，订单与交易退款状态一致。
  - AC-08-3：退款金额恰好等于当前合法可退余额时成功；超过余额、负金额、卡/订单不匹配或不合法状态时拒绝，原余额和资金状态不变。
  - AC-08-4：已扣款资金不能通过取消授权获得第二次恢复；重复取消或退款以及失败后同一请求重试均只产生一次应有资金变化。
  - AC-08-5：打开礼品卡支付订单详情并查询同一交易时，方式、金额、关联对象和事件可相互核对；无权限者不能通过事件或错误读到受限卡信息。
  - AC-08-6：合法交易读取返回空事件列表时，Dashboard 呈现“暂无事件”而非请求失败；操作失败时显示可识别原因，不刷新成成功资金状态。

### R09 · 订单金额分解、汇总与剩余待付统一
- 来源：Instruction“Dashboard 的订单金额分解、交易事件与剩余待付金额必须与服务端一致，普通交易和礼品卡不能重复计入”；BC-009。
- 优先级：P0
- 需求描述：
  - 订单摘要分别解释商品金额、折扣、税费、配送、礼品卡资金、已授权、已扣款、已退款和剩余待付金额；价格包含税与不含税展示遵守服务端合同，不能把税重复加到 gross 总额。
  - 兼容 Payment 和 Transaction 以及多笔支付；同一事件、同一份额度、礼品卡旧抵扣与新交易表示只能计入一次。授权转扣款后不可同时把已消耗授权当作新增支付；已退款与净已扣款的服务端含义不得再次相减。
  - 已授权不是已扣款。待处理金额如合同纳入余额计算，必须与已成功金额分开标识，不渲染成资金已到账。
  - 产品决策：以服务端 `totalBalance` 的“已付与订单应付之差”及其退款/待处理语义为基准，剩余待付显示取对应负差的非负值；正差展示为超付/余额而非负待付。不由前端重新叠加交易卡金额替代服务端事实。若余额字段合同调整，同步更新公开说明、客户端映射和验收样例。
  - 历史订单保留原总额与优惠含义，通过兼容映射解释礼品卡，不将历史抵扣再次当成新支付从原总额减去。
- 验收条件：
  - AC-09-1：给定同时含商品、折扣、税费及配送的订单，Dashboard 每项与 API 相符，组成关系可解释，gross/net 税费不重复相加。
  - AC-09-2：给定新模式订单应付 100、礼品卡成功扣款 30、普通成功扣款 50，且无授权余量、待处理或退款，服务端与 Dashboard 均解释已扣款合计 80、剩余待付 20，礼品卡 30 不再作为额外折扣重复扣除。
  - AC-09-3：给定授权 100 后部分扣款 40、剩余授权 60，摘要分别显示该状态，不累计为 140 已付，也不将剩余授权显示为已扣款。
  - AC-09-4：给定多笔交易及退款，摘要和交易事件按服务端当前净额与累计退款定义一致，不对已经净额化的扣款再减一次退款，不重复占用退款额度。
  - AC-09-5：读取纯兼容 Payment 订单、Transaction 订单和支持的混合记录订单时，采用各自合同及唯一业务资金关联汇总，同一资金不因两种记录形式重复计算。
  - AC-09-6：订单有待处理动作或超付时，页面明确区分待处理与已成功金额，超付不显示负的剩余待付；余额与当前 API 一致。
  - AC-09-7：读取升级前礼品卡订单后，原总额与已用金额不被新前端重算改变；交易展示和金额摘要一致，缺少事件不是余额计算成功的替代依据。

### R10 · 标记已支付、捕获授权与退款安全执行
- 来源：Instruction“有权限不代表任何状态都能操作，可操作金额也必须以当前真实余额为限”；BC-010。
- 优先级：P0
- 需求描述：
  - Dashboard 仅展示或启用当前订单状态、支付方式和权限允许的资金动作，Core 执行时再次检查；不能只依赖按钮隐藏。
  - 标记已支付仅适用于无现有 Payment/Transaction 支付记录、满足账单地址及现行订单状态规则的订单，按渠道配置的 Payment/Transaction 策略建立对应记录。存在记录的订单不能借该动作补记另一笔全额支付。
  - 捕获金额不得为负且不得超过当前可捕获授权；退款不得超过当前可退余额。合法上边界可成功，超过即拒绝。零金额仅按各动作已公开合同处理，不自行把空动作记为有效资金成功。
  - 多交易与并发请求以最新额度执行，已处理和仍有效占用的额度不得重复使用。相同资金请求重试幂等；相同幂等标识但不相同参数拒绝冲突。
  - 有关联订单及支付动作权限的员工/App 才能执行，渠道和对象范围仍生效。成功后从服务端刷新订单、交易事件和余额；失败保持原资金事实，允许诊断记录但不写入假成功，不通过错误泄露受限金额。
- 验收条件：
  - AC-10-1：对无支付记录、状态及账单地址合法的订单，有权用户执行标记已支付成功，按渠道策略形成对应 Payment 或 Transaction，订单和金额摘要刷新一致。
  - AC-10-2：订单已有任一 Payment 或 Transaction 记录，或缺账单地址/状态不允许时，标记已支付被拒绝，不生成另一笔全额支付；界面不提供可执行的非法动作。
  - AC-10-3：当前可捕获授权为 60 时，捕获 60 可成功且额度相应消耗；捕获超过 60 或负金额时被拒绝，不扣款或改变原授权余额。
  - AC-10-4：当前可退余额为 40 时，退款 40 可成功；超过 40 或负金额时拒绝，不改变原资金事实；同一额度不能在多笔请求中重复使用。
  - AC-10-5：两个请求或连续双击竞争相同捕获/退款额度时，不重复扣款、退款或写冲突事件；同一请求失败后重试只产生一次有效资金结果。
  - AC-10-6：界面加载后资金状态被其他操作者改变，提交仍按最新服务端额度与状态检查，非法请求拒绝后显示可区分错误而不是沿用页面旧额度。
  - AC-10-7：没有关联订单权限、相应支付动作权限或对象范围的员工/App 请求资金动作时被拒绝，不通过错误返回受限金额；成功刷新、失败不将失败金额写入成功缓存。

### R11 · 保留根级交易基础定位与权限分页
- 来源：Instruction“客服和支付集成方应能通过基础业务关联与支付标识找到相关交易，而不是依赖本轮不交付的查询增强”；BC-011。
- 优先级：P0
- 需求描述：
  - 保留单交易读取，并提供根级交易集合查询的基础筛选：订单或结账关联、交易 ID、支付服务商参考号（`pspReference`）和 App 标识。合法单值、列表或组合按公开输入类型处理，不把对象 ID、token、UUID 和 App identifier 任意混用。
  - 返回订单/结账关联、支付方式、状态、金额及事件展示所需且调用方有权读取的字段，适用于礼品卡、普通交易和多交易订单。
  - 分页稳定，员工、客户、App 的可见范围与对象归属生效；根级、对象关联与单交易入口不互为权限旁路。合法零结果可以为空 connection/事件列表，无权限、非法输入、过滤类型错误、非法分页不能伪装为成功空结果。
  - 不新增交易创建/修改日期、事件类型/日期过滤，不新增该查询的专用排序与索引；使用现行基础分页顺序，不为排除项引入别名。
- 验收条件：
  - AC-11-1：分别按合法订单、结账、交易 ID、`pspReference`、App 标识筛选，有权调用方能定位匹配交易，非匹配对象不出现。
  - AC-11-2：使用公开支持的合法数组/组合条件筛选多交易订单时，结果与各基础条件的组合合同一致，含礼品卡和普通交易所需字段，事件与订单展示一致。
  - AC-11-3：对稳定数据集合翻页，数量、游标及基础顺序稳定，无重复或漏项；合法无匹配结果返回正确空 connection，不被视为业务失败。
  - AC-11-4：提交错误对象类型、非法过滤值、数组 null 项、非法/超上限分页或无效游标时，返回稳定可分支错误，不用空结果掩盖非法请求。
  - AC-11-5：客户、员工及 App 分别查询越过自己对象/渠道范围的交易时，不泄露详情、金额或事件；无权限与合法零结果有可辨别的合同响应。
  - AC-11-6：公开 schema、Dashboard 操作和文档不存在本轮新增的交易日期、事件过滤或专用排序入口，基础交易定位仍可完成客服任务。

#### 运营搜索、筛选与操作上下文

### R12 · 主体增强搜索与 Page/User 基础搜索边界
- 来源：Instruction“保留与主体业务相关的搜索”“本轮不交付……页面和用户的高级搜索”；BC-012。
- 优先级：P0
- 需求描述：
  - 保留结账、礼品卡、商品、订单的主体增强搜索，按各对象合同支持关键词、前缀、组合词、短语与相关度行为。字段权重、匹配对象及排序必须可解释，不在此虚构统一权重算法。
  - 客户/员工继续采用基础 `search_document` 按空格拆分组合词匹配，每个有效词都需满足基础匹配，不升级为 User 向量、前缀或 RANK 增强。页面继续按标题、slug、内容基础查找，不恢复 Page 向量、前缀或相关度增强。
  - Page/User 不新增或重新暴露高级排序、专用索引、维护任务和相应迁移；普通基础搜索的已有维护不因排除增强被移除。
  - 页面引用名称改变后，相关商品搜索仍按商品增强搜索合同更新；这是商品更新依赖，不作为新增页面高级搜索。
- 验收条件：
  - AC-12-1：对结账、礼品卡、商品及订单各准备其支持的主体字段数据，关键词、前缀、组合词、短语与相关度查询按各自公开合同返回正确对象，主体增强未被整体关闭。
  - AC-12-2：以多词客户/员工基础搜索查询，结果满足空格组合词的基础匹配语义，未因改用高级向量或 RANK 产生新的匹配规则。
  - AC-12-3：分别以页面标题、slug、内容查询页面，基础搜索仍可用；不存在新暴露的页面前缀、向量相关度或 RANK 入口。
  - AC-12-4：修改被商品引用的页面名称并完成相关商品搜索更新后，商品按新引用名称可以定位，不要求启用页面高级搜索任务。
  - AC-12-5：检查公开 schema、客户端生成操作、路由和后台维护范围，Page/User 的被排除高级搜索、排序与专用任务/索引/迁移没有以别名重新出现，客户/员工隐私仍受权限保护。

### R13 · 搜索更新、稳定分页与异常状态
- 来源：Instruction“搜索、加载、空结果、权限和错误状态应清楚可辨”；BC-013“更新遵守约定的最终一致性窗口，这里没有提供该窗口的数值”。
- 优先级：P0
- 需求描述：
  - 对象创建、修改、归档及关联字段变化后，搜索按当前合同更新名称、编码、邮箱和主体标识；在约定最终一致性窗口内完成更新，不让旧值一直成为唯一索引结果，归档可见性遵守对象规则。
  - 大小写、重复关键词及同一合法组合的语义稳定；稳定数据与筛选下，数量、顺序、排序并列项和游标可解释且无重复漏项。不能承诺数据持续变化时游标提供未定义的强快照。
  - 空关键词表示无额外搜索条件，仍使用有权限、有限分页的普通列表，不触发无界扫描。过长/非法输入按公开限制校验；搜索服务失败明确报错并允许重试，不阻塞不依赖该次搜索的操作。
  - Dashboard 列表、弹窗、选择器和 Core 采用同一适用搜索语义；加载、空结果、权限错误、网络/服务错误分开，受限客户地址与身份信息不出现在列表或错误中。
- 验收条件：
  - AC-13-1：创建或修改对象的名称、编码、邮箱/主体标识后，当对应搜索更新已完成且在约定窗口内，新值可按合同搜索到，旧值不再作为过期唯一结果；归档对象按当前可见性处理。
  - AC-13-2：关联用户/地址/页面等被检索字段发生变化后，受影响主体的搜索结果同步反映新的关联事实，不要求引入已排除的高级搜索。
  - AC-13-3：对稳定数据分别使用大小写变化、重复词和合法组合词查询并翻页，匹配语义一致，顺序及并列项稳定，数量/游标无重复或漏项。
  - AC-13-4：空关键词、仅空格输入或清除搜索时，恢复当前权限和其他有效筛选下的分页列表，不触发不可控全量查询或清掉锁定范围。
  - AC-13-5：超公开长度限制或非法输入得到校验反馈；搜索服务/网络失败显示错误与可重试状态，合法零结果显示空态，两者不互相冒充。
  - AC-13-6：在列表与分配弹窗输入同一有效词及相同上下文，Core 适用匹配语义一致；无权限结果不泄露客户地址或身份信息，也不被解释为正常无匹配。

### R14 · 锁定筛选与导出、批量操作范围一致
- 来源：Instruction“用户看到的对象范围，必须与导出、批量操作实际作用的范围一致”；BC-014“普通筛选不能覆盖锁定条件”。
- 优先级：P0
- 需求描述：
  - 区分 URL、页面及弹窗上下文带来的锁定条件与用户可编辑的普通条件。有效范围为所有锁定约束与普通条件的共同限制，冲突时不能放宽锁定约束；清除、修改或切换普通筛选不清除锁定条件。
  - 搜索、分页、排序、礼品卡筛选、返回列表、导出和批量操作都读取当前有效条件，不引用旧闭包或旧缓存。显式选中操作只作用于当前有权且仍符合操作范围的对象，条件变化后的旧选择不得静默扩大范围。
  - “当前筛选全部结果”与“显式选中项”范围要清晰；导出遵守界面当前声明的范围。Core 再校验权限和对象资格，入口变化不改变权限。
- 验收条件：
  - AC-14-1：从锁定渠道或仓库的上下文进入列表后搜索、翻页或清除普通条件，列表及请求仍保留该锁定范围。
  - AC-14-2：普通筛选试图指定冲突渠道/仓库时，锁定范围不被覆盖或放宽，界面显示有效约束或无匹配结果，不展示范围外对象。
  - AC-14-3：连续修改礼品卡筛选、关键词和排序后立即导出，导出参数及所得对象集合使用最新有效条件，不使用前一次缓存范围。
  - AC-14-4：对“当前筛选全部结果”执行批量操作，实际处理对象与当前有效范围一致；对显式选中项操作不包含未选对象或已越过新范围的旧选择。
  - AC-14-5：导出或批量操作时权限/资格已变化，服务端拒绝不允许部分并按该操作既有原子/批量结果合同明确反馈，不通过入口变化放宽渠道、仓库或对象权限。
  - AC-14-6：刷新页面或从详情返回列表后，有效锁定与普通条件、排序和搜索与所见范围一致，用户不会操作与当前视图不同的隐含旧范围。

### R15 · 选择器、层级导航与长搜索输入保留上下文
- 来源：Instruction“Dashboard 的列表、分配弹窗和层级导航要保持筛选与上下文一致”；BC-015“仓库、分类和分配类层级结果去重”“返回列表都保留导航上下文”。
- 优先级：P1
- 需求描述：
  - 仓库、分类和分配选择器按对象标识去重，重复加载或选择/取消后不出现重复选项和残留选中值；正确显示父子关系与面包屑。
  - 加载、空态、权限/网络错误及其重试保持当前层级、关键词和返回上下文，详情返回列表时恢复适用的筛选、位置和分页，不要求用户重新定位。
  - 长关键词不撑破输入与列表宽度，不重叠或产生布局跳动；允许截断展示但能通过可访问方式确认完整关键词，清除操作可用。
  - 本条为减少运营反复定位的体验要求，不改变 R14 的强制作用范围和服务端权限正确性。
- 验收条件：
  - AC-15-1：反复选择、取消同一仓库并重复加载相同选项，最终列表不重复，取消值不残留，提交选择与当前实际选中一致。
  - AC-15-2：进入父分类、子分类再返回，父子列表及面包屑正确，重新加载后不混入其他父级对象。
  - AC-15-3：在当前层级遇到加载、空结果、权限错误或网络失败，页面分别展示对应状态；可重试错误重试后仍位于适用当前层级，不清掉无关输入。
  - AC-15-4：从分配页面/详情返回原列表，恢复当前可用的关键词、筛选、排序和分页/位置上下文，不产生跨锁定范围的选择。
  - AC-15-5：输入超过可视宽度但仍合法的长关键词，输入框和列表不重叠或跳动，可以确认完整内容且可正常清除；超业务长度限制按 R13 校验。

#### 身份、内容与接口安全

### R16 · 商店统一密码认证策略
- 来源：Instruction“商户应能控制客户和员工是否使用密码认证；服务端认证流程、后台登录入口和配置页面必须读取同一生效策略”；BC-016。
- 优先级：P0
- 需求描述：
  - 商店支持三种模式：`ENABLED` 允许符合账户状态与权限的受支持用户使用密码；`CUSTOMERS_ONLY` 仅允许客户身份的密码能力，员工不得凭密码取得员工会话或后台权限；`DISABLED` 禁止密码登录、重置、设置、修改及可绕过该策略的旧 token 路径。
  - 外部认证独立按自身配置与权限合同处理，密码策略不凭空启用 provider，也不将外部身份自动升级为员工。员工兼具客户资料也不能借“客户”名义取得后台权限。
  - 只有具备商店设置权限的身份可修改，保存成功后新的认证请求立即读取新生效值，所有密码入口与旧路径遵守同一策略。未保存、加载失败或保存失败仍保持原生效值。
  - 设置页展示当前模式及权限限制；后台登录页隐藏/禁用不适用的密码入口，只有可用外部方式时展示相应入口，无可用方式给稳定、可理解空态，不渲染坏表单。
  - 推导：升级原有未配置商店保持其受支持既有密码行为，不能默认关闭而造成无迁移说明的锁出；切换到禁用时提示员工所需替代方式，但不擅自增加可绕过策略的后门。
- 验收条件：
  - AC-16-1：`ENABLED` 下，状态合法客户及员工可按现行权限使用密码，停用/不合法账户仍被拒绝；密码模式不放宽账户资格。
  - AC-16-2：`CUSTOMERS_ONLY` 下，合法客户密码能力可用，员工密码请求不能获得员工会话或后台权限，包括兼有客户资料的员工。
  - AC-16-3：`DISABLED` 下分别调用密码登录、重置、设置、修改与受该策略约束的旧 token 路径，均返回明确拒绝原因，不颁发绕过策略的新密码会话或修改密码。
  - AC-16-4：有商店设置权限者保存模式后，随后的认证请求与后台登录入口立即采用同一生效模式；外部认证仍按自身允许合同处理。
  - AC-16-5：无设置权限者只读当前允许显示的设置，修改被服务端拒绝；加载/保存失败不改变原生效模式，也不把未保存值放入成功缓存。
  - AC-16-6：后台密码不可用且无可用外部方式时，登录页呈现稳定空态与说明，而非可提交的失效密码表单；升级缺省商店保持受支持原行为。

### R17 · OIDC 离线授权与旧密码路径处理
- 来源：Instruction“外部身份关联不能留下旧密码绕过通道”；BC-017“该场景使用 access_type=offline，而不是不兼容的 offline_access scope”。
- 优先级：P0
- 需求描述：
  - Google OIDC 在请求 refresh token 的场景使用 `access_type=offline`，不为该场景使用不兼容的 `offline_access` scope；其他 provider 使用各自合同，不一刀切改变。
  - 第一次将受验证外部身份关联到已有同邮箱本地用户时，清理或禁用可绕过该关联策略的旧密码路径；不能只隐藏登录按钮而保留可调用旧密码/token 能力。
  - 同一 OIDC 身份后续登录稳定关联已有用户，不重复创建身份或每次重复首次关联副作用；关联须遵守现行身份校验与权限，不能仅凭未验证邮箱任意接管账户。
  - 授权失败可区分但不回传 token、client secret 或敏感身份载荷，不把无需持久化的 token/身份信息写入不必要的前端持久化存储。
- 验收条件：
  - AC-17-1：Google OIDC 启用 refresh token 时生成授权请求包含 `access_type=offline`，不包含为此添加的 `offline_access` scope；关闭该需求时不错误强加离线授权。
  - AC-17-2：非 Google provider 请求仍按其现行 refresh token 合同构造参数，不因 Google 适配破坏原合法流程。
  - AC-17-3：首次合法关联已有同邮箱本地用户后，用旧密码或受禁用旧 token 路径不能绕过外部身份策略取得受保护会话。
  - AC-17-4：同一 provider 的同一受验证身份再次登录时稳定返回同一用户关联，不重复创建用户或重复执行首次关联副作用。
  - AC-17-5：授权、token 交换或身份校验失败返回可识别原因，响应及不必要的前端持久化存储不含 token、secret 或完整敏感身份数据。

### R18 · 富文本结构、链接与深度在保存前校验
- 来源：Instruction“富文本和外链在保存前就要经过结构与安全校验”；BC-018“未知或多余字段、非法 scheme、过深结构应被拒绝”“不允许配置扩展协议白名单绕过限制”。
- 优先级：P0
- 需求描述：
  - 所有接受 EditorJS 内容的相关写入入口先校验受支持结构、字段类型、block 数据和嵌套列表，再安全清理 URL 与链接属性；不能把结构不合法内容存下后依赖渲染时补救。
  - 合法正常富文本、受支持嵌套列表和常用链接可保存。JSON 未知/多余字段、不支持结构、非法 URL scheme 或超允许深度须拒绝整项写入并指出字段/链接/深度问题，不持久化部分危险内容。
  - 固定安全协议范围内按链接使用场景保留 `http`、`https`、`mailto`、`tel` 等明确支持协议；媒体地址仍遵守其类型限制，不能因普通链接允许 mailto/tel 而用作图片资源。不能通过配置追加任意协议逃逸。
  - 新窗口外链必须具备禁止 opener 控制来源页面的安全 rel；产品决策采用适用的 `noopener`/`noreferrer` 安全行为。危险链接属性不能在清理后残留。
  - 嵌套上限 L 和受支持 block/字段列表须在公开校验合同中明确，材料未提供 L 数值，见第 5 节；不得以待确认作为无限嵌套或放开未知字段的理由。
- 验收条件：
  - AC-18-1：符合受支持结构的正常文本与不超过 L 的嵌套列表保存成功，重新读取保留合法内容及层级。
  - AC-18-2：按允许使用场景输入 http、https、mailto、tel 链接，保存并读取后合法链接可用；不兼容媒体类型的 URL 不被当成合法图片资源保存。
  - AC-18-3：输入未知/多余 JSON 字段、错误类型或不支持 block 结构，执行前返回字段相关错误，原内容不变，不留下部分新内容。
  - AC-18-4：输入非法 scheme、变体编码/大小写形式的危险链接或不允许属性时，执行校验及安全处理后不存在可执行危险内容；非法 URL 导致整项保存拒绝，错误指明相关链接。
  - AC-18-5：在允许深度边界 L 的合法内容可保存，L+1 被拒绝并指出深度问题，不产生递归崩溃或部分写入。
  - AC-18-6：合法新窗口外链保存后带安全 rel，不能通过 opener 控制来源页面；配置尝试扩展非法协议白名单不能使危险链接通过。
  - AC-18-7：Core 直接 API 写入与 Dashboard 保存执行同等校验，失败不是业务成功，用户可在原编辑内容基础上修正后再试。

#### App、扩展与事件合同

### R19 · App 安装更新、扩展字段与历史迁移
- 来源：Instruction“App 的安装、升级、扩展展示和表单交互需要一致且可迁移的约定”；BC-019“适配 mountName、targetName、settings 的当前约定”“tokenTargetUrl 也属于可选安装信息”。
- 优先级：P0
- 需求描述：
  - 安装、更新、查询及渲染统一采用当前 `mountName`、`targetName`、`settings` 合同；对历史 mount/target/options 等实际旧表示提供必要迁移或读取适配，保留设置内容和默认行为，不要求重新安装。
  - 安装/更新前校验 identifier 唯一性、权限是否合法且可授予、mount/target 与 settings 类型/内容有效、URL 及必填信息合法。重复 identifier、非法权限/target、无法解析 settings 使操作失败，已有有效 App/扩展数据不被破坏。
  - `appName`、`manifestUrl` 为 App 安装必填；可选 manifest/安装信息缺省不令合法流程失败，包含可选 `tokenTargetUrl`。可选项与必填项不能混淆。
  - 新客户端只提交当前字段。仅在支持流程确有需要时交接/返回新建或安装 token，不因可选字段缺省就泄露 token；权限和字段可见性限制同时适用。
  - 安装/更新有 App 管理权限，读取仅返回调用方允许访问的扩展及字段。历史与空库迁移要求并入本条和 R27，不增加独立扩展重装功能。
- 验收条件：
  - AC-19-1：有 App 管理权限者用合法必填信息和当前扩展字段安装/更新后，可查询并按相同 mount、target、settings 渲染扩展。
  - AC-19-2：合法安装缺省可选信息及 `tokenTargetUrl` 时不因此失败，采用稳定默认行为；不需要 token 交接的响应不返回新建/安装敏感 token。
  - AC-19-3：缺少 `appName`/`manifestUrl`，或提交重复 identifier、非法权限、非法 target、无法解析 settings 时，明确拒绝，现有有效 App 和扩展数据不变。
  - AC-19-4：迁移含历史扩展及设置的商店后，无需重装即可查询、编辑并渲染，设置内容及行为含义保留，重复迁移执行不创建重复扩展。
  - AC-19-5：当前 Dashboard 不再提交旧扩展字段，Core 公开合同与生成客户端一致；历史读取适配不等于恢复未承诺的旧写入能力。
  - AC-19-6：无 App 管理权限者安装/更新被拒绝，读取不返回越权扩展、token 或设置；错误不泄露敏感安装信息。

### R20 · 扩展响应只作用于对应当前表单
- 来源：Instruction“App……表单交互需要一致……约定”；BC-020“多 frame、重复响应、未加载 frame 或未知 action 不能污染当前编辑状态”。
- 优先级：P0
- 需求描述：
  - 商品与翻译等受支持表单可以接收对应弹窗扩展的合法响应，处理字段缺省、成功、字段验证失败、权限错误及 App 关闭状态，并显示实际结果与未通过字段。
  - 响应须校验来源/frame、当前表单上下文、受支持 action 和数据类型；仅作用于对应当前编辑操作，不跨商品、语言、页面或已结束弹窗回填。
  - 重复响应不重复应用；多 frame 中非当前合法来源、未加载 frame、迟到/未知 action 明确拒绝或按合同忽略，不污染表单。字段错误不保存成成功，App 关闭不自动提交表单。
- 验收条件：
  - AC-20-1：当前已加载的合法扩展向其对应商品/翻译表单返回成功响应时，仅约定字段按当前上下文更新，用户可看到结果；缺省值按当前合同处理而不误清无关字段。
  - AC-20-2：响应含字段验证错误时，页面定位未通过字段，不提示保存成功或写入失败数据；权限错误有明确状态。
  - AC-20-3：同一合法响应重复到达时，表单与业务副作用只应用一次，不覆盖随后用户继续输入的内容。
  - AC-20-4：非当前 frame、未加载 frame 或未知 action 返回内容时，当前表单不被改变，并有合同规定的无效响应处理。
  - AC-20-5：切换商品、翻译语言或关闭 App 后收到前一操作迟到响应时，不回填新上下文，不自动保存或污染其他编辑状态。

### R21 · 自托管扩展目录可用且按权限操作
- 来源：Instruction“自托管商店也要有可用的扩展目录体验”；BC-021“目录不依赖不可用的旧地址”。
- 优先级：P0
- 需求描述：
  - 自托管部署可浏览和筛选可用扩展，目录来源不依赖不可用旧 marketplace 地址；有效目录数据与已安装/可配置状态按实际信息展示。
  - 区分加载、正常有数据、合法空目录、网络/配置/服务错误，支持适用重试，不把目录读取结果当成安装结果。
  - 有对应权限者可进行现行查看/配置/安装操作，无配置权限但有读取范围的用户保持只读。目录提供方及更新方式需由技术方案明确，不假定已有新服务部署成功。
- 验收条件：
  - AC-21-1：在没有旧 marketplace 服务的自托管部署，用可用当前目录来源加载后能浏览、筛选正确扩展，不请求不可用旧地址作为必要前提。
  - AC-21-2：合法空目录展示空态；网络失败、来源配置错误或服务错误展示可识别错误及适用重试，不能三者都表现为空列表。
  - AC-21-3：有读取而无配置权限的用户能在允许范围查看目录但不能配置/安装，直接请求也受权限校验。
  - AC-21-4：目录加载完成或失败均不会被展示成 App 安装成功；已安装状态与实际 App 安装记录一致。

### R22 · Webhook 按订阅解析与异步载荷边界
- 来源：Instruction“Webhook 只做订阅实际需要的工作，允许异步处理的事件不要拖慢业务请求”；BC-022。
- 优先级：P0
- 需求描述：
  - 同步订阅只解析所选择字段及其必要依赖，不因未选择字段而多调用税务、配送或无关同步通知。
  - 允许异步处理的订单、草稿订单和履约事件，完整异步载荷在后台任务边界构建，业务请求只完成必要的业务提交与异步安排，不等待完整异步载荷解析。纯异步订阅不提前触发无关同步通知。
  - 延迟生成内容仍遵守事件事实、关联数据和字段可见性合同，不能把未来源对象变化误当成历史事件事实；必要的事件上下文不得因异步安排丢失。
  - 沿用既有调用次数、超时、重试和熔断上限，复用允许的解析结果，不因重复解析或递归依赖放大负载。材料未另定性能或调用数值，不自行承诺新 SLA。
- 验收条件：
  - AC-22-1：同步订阅只选择不依赖税务/配送服务的字段时，解析不调用未需要的服务；选择确需服务的字段时仅在既有合同允许次数内调用必要服务。
  - AC-22-2：订单、草稿订单或履约仅有允许异步的订阅时，业务请求不执行完整异步载荷构建；后台任务随后生成满足订阅合同的内容。
  - AC-22-3：在异步工作等待/暂停时，正常业务请求不等待异步完整载荷，且不提前触发与该请求无关的同步通知；异步记录仍为等待而非成功。
  - AC-22-4：同时存在同步和异步订阅时，同步只按实际选择及依赖执行，异步按后台边界执行，不重复解析造成额外服务调用。
  - AC-22-5：延迟生成事件内容时，对订单金额、配送快照和权限字段仍符合该事件合同，不因源对象后改/删除改变历史事实或泄露字段。
  - AC-22-6：模拟慢服务、失败和重试时，既有超时、次数与熔断限制继续生效，未新增无限解析或重试循环；无订阅不构造无需求内容。

### R23 · delivery 失败隔离、准确通知与可见状态
- 来源：Instruction“一个接收方失败不应阻断其他接收方”；BC-023“无实质变化的保存不重复触发”“异步内容未生成不能当成成功”。
- 优先级：P0
- 需求描述：
  - 每个接收方 delivery 独立处理，某 App 载荷生成、发送或接收失败不阻断其他订阅，失败按既有策略只重试对应 delivery，不令已成功接收方重复获得新业务通知。
  - 已定义事件，包括商品变体折扣价更新，满足实质变化触发条件时产生合同正确的一次逻辑通知；无实质变化保存不重复触发。同一通知的网络重试保留原事件关联，不声称网络层 exactly-once。
  - Dashboard 显示等待、成功、失败、重试中及允许查看的错误/尝试信息；尚未生成异步内容为等待，不是成功。“重试中”可以由任务及尝试事实映射，不要求凭空新增状态枚举。
  - 有相关 App 或业务域权限且在对象范围内的身份可对允许失败 delivery 单条重试，其他无权限者不能操作或读受限载荷。保留既有 Webhook 失败告警，不扩展 App Problems。
- 验收条件：
  - AC-23-1：同一事件发送给三个接收方，其中一个失败，其余订阅仍执行并保持成功结果；重试只影响失败 delivery，不给成功接收方新增业务通知。
  - AC-23-2：单个订阅的载荷生成出错时，该失败有可识别状态/原因，其他有合法订阅的接收方不被一起阻断。
  - AC-23-3：商品变体折扣价发生实际更新时，有关订阅收到一次合同正确逻辑事件；保存相同值不新增重复事件，网络合法重试仍关联原 delivery。
  - AC-23-4：在内容尚未生成、正在发送、失败待处理、重试及成功的各阶段，Dashboard 状态与真实任务/尝试结果对应，排队成功不显示 delivery 成功。
  - AC-23-5：有相应 App 或业务域权限并满足范围者可单条重试允许失败项；无权限请求被拒绝，不从错误或载荷获得受限字段。
  - AC-23-6：失败告警仍可用于发现 Webhook 问题，但公开类型、操作与问题列表不新增 App Problems 能力。

#### 历史资产、公开接口与工作台事实

### R24 · 创建时配送 public/private 元数据快照
- 来源：Instruction“订单应保留创建时的配送元数据，不能因为后来修改或删除配送方式而改变历史事实”；BC-024。
- 优先级：P0
- 需求描述：
  - 结账完成成单和草稿订单完成两条路径保存当时配送方式的 public/private 元数据快照，供订单、履约及相关事件按合同读取；不能仅动态指向源配送对象。
  - 源配送方式后来修改、停用、删除不回写已创建订单快照。快照描述配送方式而非配送税类元数据，两者不可混用。
  - 公开与私有内容各按当前权限可见，不因创建快照将 private 内容公开。业务允许的基础编辑遵守 R25；只禁止源对象后改被动覆盖，不承诺额外独立快照管理 UI。
  - 历史数据迁移保留已有元数据，不丢失或重复生成记录，无数据时返回合同稳定空值；不能凭迁移时源对象的新值伪造无法证明的历史创建时事实。
- 验收条件：
  - AC-24-1：从结账创建含配送方式元数据的订单后，订单/履约读取和相关事件得到创建时 public/private 快照，字段访问遵守对应权限。
  - AC-24-2：完成含配送方式元数据的草稿订单后，同样保存并读取创建时快照，不因路径不同缺失。
  - AC-24-3：成单后依次修改、停用或删除源配送方式，已有订单及其履约读取的快照不随源对象改变或丢失。
  - AC-24-4：没有私有元数据读取权限的身份读取订单、履约或订阅内容时，不能获得私有快照；公开快照按其允许范围读取。
  - AC-24-5：迁移有既有元数据与无元数据的历史记录后，前者保留内容，后者获得稳定空值；重复执行适用迁移不增重复记录，不用新源值伪造旧事实。

### R25 · 基础元数据读写保留且不新增独立入口
- 来源：Instruction“保留业务所需的基础读取和编辑，不为此扩展出独立的元数据管理功能”；BC-025。
- 优先级：P0
- 需求描述：
  - 结账、草稿订单、订单、履约保留必要的基础元数据读取与业务允许写入；已有订单详情行内编辑和订单行元数据能力继续可用，仓库等既有基础能力不因排除独立弹窗被误删。
  - public/private 数据按对象及字段权限分开，合法键值按当前合同保存；非法输入、权限不足或保存失败不改变原值，不留下同一保存操作的部分写入。
  - 不新增订单、履约、仓库独立元数据弹窗、专用路由、菜单或隐藏入口，不用新管理入口代替已有行内/基础编辑。
- 验收条件：
  - AC-25-1：有适用权限者通过现有基础路径读取并保存合法结账、草稿订单、订单及履约元数据，重新读取得到保存值。
  - AC-25-2：已有订单详情行内编辑和订单行元数据保存仍可完成，不能因不交付独立弹窗移除这些能力。
  - AC-25-3：同一保存请求含非法键值时，返回可定位错误，全部原值保持，不出现部分键已写入的结果。
  - AC-25-4：无对象/私有字段权限或保存发生故障时，不修改原值，不泄露 private 内容，不在前端把失败当成功。
  - AC-25-5：检查路由、菜单及公开交互，不存在本轮新增订单/履约/仓库的独立元数据弹窗或专用入口，基础编辑仍可用。

### R26 · 公开 API 输入类型、失败语义与查询正确性
- 来源：Instruction“公开 API 同样需要明确的输入、权限和失败语义，不能把请求通信成功误认为业务操作成功”；BC-026。
- 优先级：P0
- 需求描述：
  - 数值、金额、时间、分页、枚举、必填和组合关系在执行写入前校验；分钟/小时/天数等时间量不得为负，金额为有限合法数值并遵守相应动作边界。非法类型/数组 null 项不得悄悄丢弃后执行其余部分。
  - Federation `representations` 不得为 null 或含 null 项，合法表示按合同解析。对象 ID、结账 token、UUID、渠道 slug 各用各自类型，不相互冒充。
  - 业务失败提供可分支的 `field`、`code`、`message`；schema/解析层失败保持 GraphQL 标准错误并提供约定的路径/错误标识，不能假称此时有成功业务 payload。HTTP 200、对象为 null、合法零结果和业务完成为不同状态，客户端必须读取业务错误与实际结果。
  - 订单条件查询、合法单值/数组/组合及用户关联订单查询返回准确对象并稳定分页，权限作用于所有入口。无权限、未知错误及非法过滤不转换成成功空列表。
  - 涉及金额、库存和状态的变更基于最新对象状态检查并幂等；失败不产生该操作部分写入。批量接口如已有逐项结果合同须明确逐项成功/失败，不将失败项整体伪装成功。
- 验收条件：
  - AC-26-1：给定公开支持的合法单值、数组和组合订单条件，查询返回准确订单；用户关联订单返回该用户可见关联对象与正确分页，不串到他人订单。
  - AC-26-2：分别提交负分钟/小时/天数、非法时间、非有限金额、错误枚举、缺必填或非法组合，在执行前拒绝并返回稳定错误，不发生部分写入。
  - AC-26-3：Federation representations 为 null、包含 null 项或错误类型时返回明确错误而非解析崩溃/成功空列表；合法表示保持可用。
  - AC-26-4：将对象 ID、token、UUID、slug 互换或提供错误对象类型时，按对应字段类型拒绝，不错误定位或修改另一个对象。
  - AC-26-5：负/超限分页、无效游标或不符合 nullability 的空分页输入产生稳定错误；合法已无后续结果的分页按合同返回空结果，不混同非法请求。
  - AC-26-6：mutation 返回 HTTP 200 但含业务错误或未产生业务对象时，Dashboard/集成示例不判定为完成成功，按 field/code/message 展示或分支处理。
  - AC-26-7：注入未知执行错误时，接口不返回成功空列表或成功变更；受影响操作无部分写入，修正后可按幂等合同重试。

### R27 · schema、弃用替代与空库/历史迁移一致
- 来源：Instruction“升级既要能初始化新商店，也要保留既有订单、交易、扩展、库存和元数据的业务含义”；BC-027“兼容不是继续默默执行已经退出的旧能力”。
- 优先级：P0
- 需求描述：
  - Core 公开 schema、Dashboard 查询/mutation、生成客户端、错误映射及使用文档作为同一接口合同交付；生成文件不能继续支持已退出操作或借生成类型暴露排除项。
  - 保留明确承诺的弃用读取及替代路径，已不支持能力返回 schema 不存在或明确迁移错误，不能成功空响应。旧 Adyen、NP Atobarai 插件、`Payment.partial` 和旧数字商品接口不再承诺；数字商品业务可通过 Apps 或现行方案继续提供。
  - 商品、礼品卡、voucher 使用当前查询导出合同；旧导出 mutation 按公开弃用约定处理，文档指出替代方式、权限及是否保留旧调用，不能无解释空成功。草稿订单新客户端使用 `voucherCode` 替代旧 `voucher` 输入。
  - 属性创建/适用更新的 `name`、`slug`、`type` 不能保存为空；按当前新输入合同声明必填约束，部分更新未提供的字段不因此错误清空。App 安装 `appName`、`manifestUrl` 必填，可选信息仍按 R19 处理。
  - 迁移可在空库执行，也覆盖有订单、交易、扩展、库存与元数据的旧库；保留关联与业务含义，不默认开启新策略，不重算已完成历史订单，不新增被排除能力专用迁移。跨前后端发布需要同步可用的合同与错误说明。
- 验收条件：
  - AC-27-1：对交付 schema 生成 Dashboard 客户端并检查其操作，所有本轮支持的当前查询、mutation 与错误映射匹配，不引用已不支持字段。
  - AC-27-2：调用明确保留的弃用读取时获得合同说明的数据及替代提示；调用已退出插件、`Payment.partial` 或旧数字商品接口时获得不存在/迁移错误，而非假成功。
  - AC-27-3：通过当前商品、礼品卡、voucher 查询导出路径有权导出正确范围；旧导出 mutation 按已公布弃用合同响应，不返回没有说明的成功空结果。
  - AC-27-4：新 Dashboard 草稿订单使用 `voucherCode` 完成合法优惠操作，客户端不继续提交旧 voucher 输入；非法 code/组合有明确错误且原订单不被失败部分改写。
  - AC-27-5：新建属性缺 name/slug/type 或试图将其保存为空时被拒绝，合法字段可保存；部分更新省略字段不清空已有合法值。App 安装缺 appName/manifestUrl 时执行前拒绝。
  - AC-27-6：在空库执行完整适用迁移后，必要表、默认值和支持链路可初始化，不依赖已有历史记录才能成功。
  - AC-27-7：在包含历史订单、Payment/Transaction、礼品卡、扩展、库存和元数据的旧库执行升级验证后，相关业务值与关联含义保留，不重复生成记录、不改既有订单金额、不意外启用新策略；适用重跑无额外副作用。

### R28 · 敏感操作、员工实际删除与对象范围
- 来源：Instruction“统一身份策略，阻止危险内容和越权操作”；BC-028“员工删除、属性更新、App 安装、导出和敏感税务字段读取，不能通过换查询入口绕过权限”。
- 优先级：P0
- 需求描述：
  - 员工、客户与 App 在列表、节点、关联查询、导出、mutation 和事件中遵守相应业务/字段权限及对象范围，渠道和仓库可见性按现行授权合同生效。
  - 有员工管理权限且满足既有目标管理限制的操作者删除合法员工时真正删除用户对象，而非只撤销员工标记；有历史订单也不得据此只做降级。关联订单/资金历史按现行保留规则保持可信，不连带删除业务历史。自删及无权限删除拒绝，保留现有不允许 App 执行员工删除的约束。
  - 属性更新、App 安装和商品/礼品卡/voucher 导出使用各自必要权限，不能借另一入口绕过。导出还必须满足 R14 范围。
  - 结账/订单相关 private 元数据、用户关联等税务敏感字段遵守 `HANDLE_TAXES` 等适用字段权限；错误、数量或列表结果不成为泄露旁路。
  - 权限不足与没有数据可区分，失败不呈现操作成功；不在无权错误中回传受限余额、地址或身份信息。
- 验收条件：
  - AC-28-1：有员工管理权限且符合目标管理规则者删除另一合法员工，重新查询用户对象不存在，而非仅 is_staff 变为 false；该员工历史订单及必要资金事实仍被保留。
  - AC-28-2：自删、无员工管理权限删除或原合同禁止的 App 删除请求被拒绝，目标账户及关联历史不变。
  - AC-28-3：没有所需属性/App/导出权限的身份分别执行属性更新、App 安装、商品/礼品卡/voucher 导出时均被拒绝，有权合法操作可实际成功。
  - AC-28-4：无适用 `HANDLE_TAXES` 等权限者通过结账、订单、关联用户或 Webhook 读取敏感税务字段/private 内容时无法取得，有权身份按合同可读。
  - AC-28-5：从列表改为节点、关联、弹窗、导出或另一查询入口后，对象、渠道及仓库限制保持一致，不能读写范围外数据。
  - AC-28-6：无权限响应与合法无数据响应可判别，错误不包含受限金额、地址或身份资料，Dashboard 不将拒绝显示为操作成功。

### R29 · 配置加载、编辑上下文与成功缓存
- 来源：Instruction“不能用迟到的数据覆盖正在输入的内容”“不能把失败、尚未保存的设置……显示成成功”；BC-029。
- 优先级：P0
- 需求描述：
  - 渠道、商店和商品设置明确区分未加载、加载中、已加载空数据、权限错误、网络错误和可重试状态；加载期间不显示误导默认生效值、不崩溃或闪烁错误值。
  - 异步数据到达只回填仍属于当前对象/渠道/表单上下文且未被用户修改的适用字段。已脏字段保持当前输入，切换上下文后旧响应不能回填新对象。
  - 保存依据业务成功而非 HTTP 成功：成功才更新相关缓存或重新读取已保存事实；失败不将失败值写入成功缓存，保留上一生效值及用户可修正输入，允许重试。
  - 成功响应晚到而用户继续编辑时，已保存快照与当前未保存编辑分开，不以旧成功结果覆盖新输入。保存冲突按相应配置合同明确处理。
- 验收条件：
  - AC-29-1：延迟加载渠道/商店/商品设置时，页面稳定展示加载状态而非错误默认生效值；合法空数据、权限拒绝与网络失败分别有正确状态。
  - AC-29-2：用户开始输入后初始/刷新数据到达，只有同一上下文未编辑的适用字段回填，正在输入的字段不被覆盖。
  - AC-29-3：切换到另一商品/渠道再收到上一上下文响应，当前表单不被旧对象数据污染。
  - AC-29-4：业务保存成功后，相关缓存/重新读取反映服务端生效值；业务错误、网络失败或冲突时，原生效值保持且失败值不进入成功缓存。
  - AC-29-5：保存失败后用户能修正当前输入并重试，不被重置成错误默认值；修正后成功结果按服务端事实展示。
  - AC-29-6：一次保存进行中用户继续编辑，旧成功响应晚到时不覆盖新的未保存输入，界面可辨别已保存事实与仍未保存内容。

### R30 · 正确展示重量、媒体、金额和日期并限制草稿动作
- 来源：Instruction“重量、金额、媒体状态和订单时间展示应准确；草稿订单动作只在渠道和商品条件允许时可用，并说明不可用原因”；BC-030。
- 优先级：P0
- 需求描述：
  - 商品重量按 API 实际单位与商店当前显示单位正确转换，保留业务所需精度，不仅替换单位文案；媒体正常/错误状态及折扣类型/金额与服务端一致。
  - 订单历史日期分组遵守当前适用 locale 和 timezone，先按相同时区事实归组再格式化展示，跨日/月/年边界不误归组；不凭展示格式改变原事件时间。
  - 草稿订单在渠道停用、无可售商品或缺少当前动作必要配置时，禁用不适用的添加商品、完成等动作并说明原因，不发送明知非法请求。添加与完成分别按动作前提判断，不将仅完成所需配置错误地阻断其他合法编辑。
  - 切换到正常合法渠道后恢复允许操作，清除旧上下文资格结论；服务端提交时仍按最新条件再校验。媒体错误状态展示不新增异步外链抓取或专用 fallback。
- 验收条件：
  - AC-30-1：同一合法重量在支持的不同显示单位间切换，数值按实际单位转换并反向保持原重量含义，不能数值不变仅改标签。
  - AC-30-2：媒体处于 API 正常/错误状态或折扣为不同类型时，页面显示相符状态及金额，不把媒体错误显示为成功，不误换折扣金额单位。
  - AC-30-3：事件发生在当前 timezone 的跨日边界时，日期分组与本地显示日期一致；切换 locale/timezone 后同一事件正确归组，不改变原时间事实。
  - AC-30-4：草稿订单渠道停用、无可售商品或缺当前动作配置时，对应非法动作禁用并解释原因，不发出已知非法请求；其他条件合法的基础编辑不被一并禁用。
  - AC-30-5：切换为满足条件的正常渠道后可执行适用添加/完成操作，不继续使用旧渠道的禁用或可售判断；提交前资格变化时由服务端拒绝并明确反馈。
  - AC-30-6：普通媒体失败显示和重试保持现行能力，不引入异步抓取 pending/503/proxy 或专用 Dashboard fallback。

#### 产品决策、假设与待确认项

已作出的产品决策：

- 不新增业务目标之外的独立 Storefront、App Problems、变体生成器、交易报表或元数据管理系统；必要基础能力与迁移不因排除增强被删除。
- 自动完成“时间达到”“支付足额”“业务资格合法”是并列必要条件，设置成功不是执行成功；cutoff 使用创建时间下界且包含等值，延迟从最后变化计算且超过才入选。
- 库存可用性策略与分配优先级分离；直接渠道—仓库模式不受旧地址参数改变，但并不免除配送可达性校验。
- 礼品卡作为可追踪资金来源；区分授权占用、账面余额和可用余额，历史订单金额不为新表示重算。金额示例只用于验收算术，不是商店实际业务数据。
- 所见筛选与操作范围同一来源；权限在服务端执行、错误和事件路径中同样约束，不依赖前端隐藏按钮。
- 一次业务完成只产生一次逻辑事件；合法传输重试可能多次送达原事件，接收方仍应按事件关联去重，不提出不现实的网络 exactly-once 承诺。
- 空数据、无权限、非法输入、任务等待和业务失败均不属于成功。GraphQL 解析错误与业务 payload 错误使用各自合同，不人为承诺所有 schema 层错误都有 mutation 的字段形状。
