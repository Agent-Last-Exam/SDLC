# PRD：Saleor 3.23 结账、收款与商户运营一致性交付

版本：v1
责任：产品
状态：需求范围与验收条件已定义
输入：instruction.md；business-conversations.md；现有项目代码
修订：首次交付。

## 1. 业务背景与目标

Saleor 3.23 以 Core 3.22.0 与 Dashboard 3.22.9 为升级起点。本轮交付的重点不是新增孤立功能，而是把「客户结账 → 选择配送 → 支付 → 生成订单 → 商户履约与售后」这条商业链路打通，使同一业务事实在 Storefront、支付集成方、商户后台、App 与 Webhook 集成方之间保持一致。

当前链路存在四类业务问题：

1. **结账侧的判断与最终成单不一致。** 配送选项是按页面读取被动计算的，客户换了地址、商品或渠道后仍可能看到上一轮的配送选择；提交时也不再确认配送方式是否仍然有效，容易留下半成品订单。商品、结账、订单与履约对「什么可卖、库存从哪里扣」可能各算一套。
2. **收款与售后无法对齐同一笔资金。** 礼品卡目前只是一次性的余额抵扣，授权、扣款、取消、退款没有可追踪的对应关系；订单金额分解、交易事件与剩余待付金额在后台与服务端之间可能对不上，普通交易与礼品卡可能重复计入。人工标记已支付、捕获授权与退款缺少状态与余额层面的边界。
3. **运营人员看不清对象、也无法判断自己动作的真实作用范围。** 商品编辑页缺少按渠道解释「为什么卖不出去」的诊断；列表、分配弹窗与层级导航的筛选上下文可能被普通筛选冲掉，导出与批量操作的范围可能与页面所见不一致。
4. **身份策略与内容安全依赖页面隐藏。** 密码认证策略没有统一的生效点；外部身份关联后旧的密码路径可能成为绕过通道；富文本与外链在保存前缺少结构与安全校验；部分公开 API 把传输成功当成业务成功。

本轮目标：

- 让「可售判断 → 配送选择 → 支付 → 成单 → 履约」使用一致的条件，并让已支付结账的自动完成成为可配置、可诊断、可幂等的后台流程，减少商户手工成单。
- 把礼品卡纳入统一的交易生命周期，使授权、取消、扣款、退款与余额变化可追踪、可对账，Dashboard 金额分解与服务端一致。
- 让运营人员能按渠道诊断商品可售性、能稳定检索对象，并保证列表、导出与批量操作的作用范围与权限一致。
- 统一客户与员工的认证策略，阻止危险内容与越权操作，并让公开 API 的失败语义可分支处理。
- 保持扩展、事件与历史订单数据可信：扩展安装与展示约定一致且可迁移，Webhook 不做订阅之外的工作、单个接收方失败不牵连其他接收方，订单保留创建时的配送事实。

成功以可观察的业务结果衡量：客户能拿到与当前结账一致的配送选项、结账不会因失效配送或库存条件产出半成品订单；商户能以真实余额为限完成收款、捕获与退款且不重复扣款；运营人员能解释商品为何不可售、能稳定检索到对象；升级后既有订单、交易、扩展、库存与元数据的业务含义不变。本委托未提供任何可用于量化基线的数据，因此不设数值化指标。

## 2. 用户与场景

| 用户类型 | 典型任务 |
| --- | --- |
| Storefront 集成方 | 主动重算当前结账的配送选项；提交前确认配送与库存仍有效；完成结账并处理可解释的失败 |
| 支付集成方 | 初始化、授权、扣款、取消与退款；在网络重试下保持幂等；按支付标识定位交易 |
| App 与 Webhook 集成方 | 按 mountName/targetName/settings 安装与展示扩展；接收与处理事件；在失败时区分「未生成」与「已失败」 |
| 商户运营 | 配置渠道级自动完成；在列表、分配弹窗与导出之间保持一致的作用范围 |
| 渠道运营 | 配置渠道-仓库关系与自动完成范围；判断商品在各渠道的可售性与阻断原因 |
| 商品运营 | 按渠道名或币种筛选、翻页查看商品可售性诊断与问题明细 |
| 订单运营 | 校验结账成单条件；处理人工成单、配送变更与历史订单事实 |
| 履约运营 | 依据订单创建时的配送事实安排履约；在库存变化后判断能否继续 |
| 资金运营 | 标记已支付、捕获授权、退款；核对金额分解、交易事件与剩余待付 |
| 客服 | 按订单/结账关联、交易 ID、服务商参考号与 App 标识定位交易；处理取消与退款 |
| 内容运营 | 保存正常富文本、嵌套列表与常用链接；在内容被拒绝时知道改哪里 |
| 安全管理 | 控制密码登录模式；确保外部身份关联不留旧密码后门；阻止越权与危险内容 |
| 商店管理 | 在自托管部署中浏览与配置扩展；在设置页看到与生效值一致的状态 |
| 平台维护 | 保证输入校验、弃用路径、权限与历史数据迁移的一致性 |

## 3. 需求条目

#### 业务域 A：结账配送与库存一致性

### R01 · 主动重算当前结账的配送选项
- 来源：instruction.md「让 Storefront 能主动重新计算当前结账的配送选项，显示可用项和当前选择」；business-conversations.md BC-001
- 优先级：P0
- 需求描述：提供以结账为主体的配送选项查询能力，使 Storefront 能自行决定何时重算，而不是依赖读取页面。计算必须使用当前结账的收货地址、行项目、渠道以及同步配送服务的当前结果；返回可用选项列表与当前已选配送方式，每项包含可展示的价格与状态。同步配送服务结果变化后可以重新计算；已经不适用于当前结账的旧选项不得继续出现在可用列表中。
- 验收条件：
  - AC-01-1：给定一个行项目非空、收货地址完整、渠道有效的结账，当集成方查询配送选项时，返回该结账当前可用的配送方式列表，且每项包含可用于展示的名称与价格。
  - AC-01-2：给定结账已选定配送方式，当集成方查询配送选项时，返回结果中的「当前选择」与结账的 deliveryMethod 指向同一对象。
  - AC-01-3：给定客户更换了收货地址、行项目或渠道，当集成方重新查询配送选项时，返回列表按新条件计算，先前条件下才可用的配送方式不再出现。
  - AC-01-4：给定结账地址缺失或同步配送服务返回错误，当集成方查询配送选项时，返回可定位到字段或原因的错误，且结账原有的有效配送选择保持不变，不写入半成品选择。
  - AC-01-5：给定结账不存在、不属于调用方或调用方权限不足，当查询配送选项时，返回明确错误且不泄露任何配送或地址信息。

### R02 · 更新配送选择与完成订单时重新确认有效性
- 来源：instruction.md「结账状态变化后，更新配送和完成订单都要重新确认有效性，不能沿用失效选择」；BC-002
- 优先级：P0
- 需求描述：更新配送选择与完成结账两个动作都必须重新校验配送方式对当前结账是否仍然有效，不能沿用上次看到的有效结论。完成前已过期或不可用的配送选择应阻止完成，并区分失效原因（未设置、地址缺失、方式不适用），不得留下半成品订单。归属错误、权限不足或不存在的结账不得借此泄露配送信息，也不得改掉原有选择。
- 验收条件：
  - AC-02-1：给定结账当前渠道或地址下已不适用的配送方式，当集成方更新配送选择时，返回「配送方式不适用」类错误，且结账原有配送选择不被改写。
  - AC-02-2：给定结账已选配送方式在提交时刻失效，当集成方提交完成结账时，阻止完成并返回可区分失效原因的错误，不创建订单。
  - AC-02-3：给定需配送的结账未设置收货地址或未设置配送方式，当提交完成结账时，分别返回地址未设置与配送方式未设置的错误，且不创建订单。
  - AC-02-4：给定一次完成结账失败，当再次提交时，校验以最新的结账、库存与支付事实重新执行，结账仍保持未完成状态。
  - AC-02-5：给定结账不属于调用方或调用方无权限，当请求更新配送方式或完成结账时，返回错误且不改变原选择、不泄露配送信息。

### R03 · 旧配送标识与旧字段的弃用读取兼容
- 来源：instruction.md「旧配送字段保留弃用读取语义，新客户端使用当前配送约定」；BC-002
- 优先级：P1
- 需求描述：合法旧标识与新的配送标识都要按兼容约定处理，但只能选择属于当前结账的配送方式。旧配送字段（结账与订单上的 shippingMethod）保留弃用读取语义，读取结果与当前配送约定一致并带弃用标记；旧客户端传入的地址类参数仍可被接受，但不得改变当前配送归属判断的结果。通过旧入口不得绕过渠道归属与权限校验。
- 验收条件：
  - AC-03-1：给定客户端使用旧的 shippingMethod 字段读取结账或订单，返回结果与 deliveryMethod 一致，且该字段带弃用标记。
  - AC-03-2：给定客户端使用旧的配送更新入口或旧的配送标识提交选择，若该配送方式属于当前结账则按兼容约定成功，若不属于则被拒绝。
  - AC-03-3：给定客户端通过旧入口提交，当配送方式不属于当前结账渠道时，返回与当前入口一致的不适用错误，不泄露其他渠道的配送信息。

### R04 · 渠道与仓库直接关联下的库存计算统一
- 来源：instruction.md「商品、结账、订单和履约应遵守一致的渠道与仓库库存规则，同时保护未切换库存策略商店的既有行为」；BC-003
- 优先级：P0
- 需求描述：商户可通过渠道与仓库的直接关联控制参与可售计算的仓库。未切换该方式的商店必须保留原有基于配送区域与地址关联的库存行为，升级后既有商品不会因此变得不可售。切换后，只有直接关联当前渠道且存在可用库存的仓库参与计算，且商品查询、结账、订单、履约与草稿订单使用同一语义。旧客户端传入的地址参数仍被接受，但在新方式下不改变直接关联决定的结果。仓库关系变化、库存不足、预留失败与权限不足都要有可解释的结果；预留或分配成功后各入口反映相同剩余量，失败不得造成超卖或部分预留。
- 验收条件：
  - AC-04-1：给定一个未切换库存策略的商店，当升级完成后查询既有商品的可售性与库存时，结果与升级前基于配送区域和地址关联的行为一致。
  - AC-04-2：给定已切换的商店，当查询商品可售性、结账可用量、订单与履约库存时，只有直接关联当前渠道且有可用库存的仓库参与计算，且各入口结果一致。
  - AC-04-3：给定已切换的商店且客户端仍传入地址参数，当查询可售性或预留库存时，直接关联的决定结果不因该参数改变。
  - AC-04-4：给定库存不足或预留失败，当提交结账或分配库存时，返回可解释的失败结果，不产生部分预留、不超卖，且各入口剩余量一致。
  - AC-04-5：给定调用方无权限访问某渠道或仓库，当查询可售性或库存时，返回权限错误，不以空结果掩盖。

### R05 · 已支付结账自动完成的前置条件与幂等
- 来源：instruction.md「自动化不能放松客户、地址、配送、库存和金额条件，失败后的重试也不能多生成订单、多扣款或重复发送完成事件」；BC-005
- 优先级：P0
- 需求描述：对已支付结账的自动完成，必须达到所支持支付方式的 fully paid 条件——受支持的完整授权、完整扣款，以及 Transaction 与兼容 Payment 流程各自按自身约定判定。同时必须具备客户或邮箱、账单地址，需配送时具备地址与配送方式，商品可售且总额大于零。已经完成或已处理过的结账不得再次成单。排队后库存或配送可能变化，真正完成前仍要重查支付、客户、地址、配送、库存与金额；任务按批次处理，失败留下可诊断、可重试的状态，条件修复后重试也只能形成一个订单结果，不得重复扣款、重复发送完成通知或改变已完成订单的金额。
- 验收条件：
  - AC-05-1：给定一个达到 fully paid 且具备客户或邮箱、账单地址、必要配送信息、可售商品且总额大于零的结账，当自动完成流程执行时，生成订单并发送一次完成通知。
  - AC-05-2：给定结账未达到 fully paid，或缺少客户/邮箱、账单地址、必要配送信息，或商品不可售，或总额为零，当自动完成流程执行时，不创建订单。
  - AC-05-3：给定结账已经完成或已被处理过，当自动完成流程再次触达该结账时，不生成第二个订单。
  - AC-05-4：给定结账在排队期间库存或配送条件发生变化，当真正执行完成时，重新校验后不合格的结账不创建订单。
  - AC-05-5：给定一次自动完成因条件不满足而失败，当条件修复后重试时，只产生一个订单结果，不重复扣款、不重复发送完成事件、不改变已完成订单的金额。
  - AC-05-6：给定自动完成失败，当商户查看该结账或任务状态时，能看到可诊断的失败原因与可重试的状态。

### R06 · 按渠道配置自动完成策略并与执行结果分离
- 来源：instruction.md「商户可以按渠道配置已支付结账的自动完成策略」；BC-006
- 优先级：P0
- 需求描述：自动完成按渠道配置开关、延迟与 cutoff，并明确适用范围。延迟从结账最近一次变化开始计算，只有超过延迟的结账才进入待处理范围；cutoff 是结账创建时间的下界，只考虑在该时间或之后创建的结账，不是任务停止执行的时间。未配置的旧渠道不得被意外改为自动完成，沿用关闭或既有默认行为，不改变历史手工流程。合法配置必须能保存并重新读到；范围或组合非法、无配置权限以及保存冲突都要明确报错并保留上次生效值。设置状态与执行结果必须分开：保存成功只表示设置已保存，页面不得据此显示订单已生成，订单是否完成以实际结账与订单状态为准。
- 验收条件：
  - AC-06-1：给定商户为某渠道配置开关、延迟与 cutoff，当保存后重新读取该渠道设置时，返回与保存一致的值。
  - AC-06-2：给定渠道未配置自动完成，当商户查看该渠道设置与结账处理结果时，该渠道沿用关闭或既有默认行为，既有手工流程不被改变。
  - AC-06-3：给定结账最近一次变化时间距今未超过配置的延迟，当批次任务扫描时，该结账不进入待处理范围；超过延迟后才进入。
  - AC-06-4：给定配置的 cutoff 时间，当批次任务扫描时，只考虑创建时间在该时间或之后的结账，早于 cutoff 的结账不进入处理范围。
  - AC-06-5：给定配置范围或组合非法、调用方无配置权限或保存发生冲突，当提交保存时，返回明确错误且渠道设置保留上次生效值。
  - AC-06-6：给定设置保存成功，当商户查看页面时，页面不显示任何订单已生成的结论；订单是否完成以实际结账与订单状态为准。

#### 业务域 B：商品可售性诊断与搜索

### R07 · 商品编辑页按渠道的可售性诊断
- 来源：instruction.md「保留与主体业务相关的搜索，以及商品编辑页按渠道诊断可售性的能力。诊断要指出真正阻断销售的原因，区分警告和不适用检查」；BC-004
- 优先级：P0
- 需求描述：商品编辑页可按渠道名或币种筛选、翻页查看各渠道的问题数量与明细。诊断结合发布与可购买时间、商品及变体库存、仓库关联、配送区域以及其他直接影响可售性的配置事实，区分阻断错误、警告与不适用。未发布或不可售时指出实际阻断原因，不把正常依赖重复报成错误。数字类（不需配送）商品只跳过不适用的配送区域检查，库存、发布与核心条件仍要检查。商品、渠道与员工权限仍然生效，不得从错误信息推断受限信息。编辑中、查询失败或刷新时应明确状态，既不把旧诊断当最新结论，也不覆盖正在编辑的内容。
- 验收条件：
  - AC-07-1：给定一个在多个渠道有不同可售状态的商品，当商户在商品编辑页按渠道名或币种筛选并翻页时，返回按筛选条件过滤的结果，并展示各渠道的问题数量与明细。
  - AC-07-2：给定某渠道因未发布、可购买时间未到、库存不足、无仓库关联或配送区域缺失而不可售，当商户查看该渠道诊断时，返回对应的阻断原因，并区分阻断错误、警告与不适用。
  - AC-07-3：给定某渠道的可售性依赖于正常满足的配置，当商户查看诊断时，该依赖不出现为阻断错误。
  - AC-07-4：给定一个数字类（不需配送）商品，当商户查看渠道诊断时，配送区域检查标记为不适用，库存、发布与核心条件仍被执行并报告。
  - AC-07-5：给定调用方无商品或渠道权限，当请求诊断时，返回权限错误，且响应中不包含受限信息。
  - AC-07-6：给定诊断请求仍在进行或失败，当商户查看页面时，状态明确区分加载中与失败，不把上一次诊断结论当作最新结果，也不覆盖正在编辑的内容。

### R08 · 主体对象搜索能力与范围边界
- 来源：instruction.md「保留与主体业务相关的搜索」；BC-012
- 优先级：P1
- 需求描述：结账、礼品卡、商品与订单保留各自的主体增强搜索能力，包括关键词、前缀、组合词、短语与相关度行为，不得整体关闭。客户与员工继续使用基础搜索文档，按空格组合词匹配；页面继续按标题、slug 与内容查找。不提供页面与用户的向量高级搜索、前缀或相关度增强、RANK 排序及其专用索引、后台维护任务与迁移。页面修改影响商品引用名称时，不得破坏商品的搜索更新。
- 验收条件：
  - AC-08-1：给定结账、礼品卡、商品或订单中存在匹配数据，当使用关键词、前缀、组合词或短语搜索时，返回按相关度排序的结果。
  - AC-08-2：给定客户或员工数据，当使用按空格分隔的组合词搜索时，返回按基础搜索文档匹配的结果；给定页面数据，当按标题、slug 或内容搜索时，返回匹配页面。
  - AC-08-3：给定查询接口与排序选项，当枚举可用能力时，不出现页面与用户的向量高级搜索、前缀或相关度增强、RANK 排序、专用索引、后台维护任务与迁移。
  - AC-08-4：给定某页面标题被修改且该页面被商品通过引用属性引用，当对商品执行搜索时，商品搜索结果反映更新后的引用名称。

### R09 · 搜索索引更新、分页与异常状态
- 来源：instruction.md「搜索、加载、空结果、权限和错误状态应清楚可辨」；BC-013
- 优先级：P1
- 需求描述：对象创建、修改、归档或关联字段变化后，名称、编码、邮箱与主体标识的新值应能被搜索到，旧值不能一直成为唯一结果；更新遵守约定的最终一致性窗口（本委托未提供该窗口的具体数值）。结果、数量、顺序与游标必须稳定且可解释，重复关键词、大小写变化、组合词与翻页不得让列表重复或漏项。空关键词不能引起不可控的全量查询；过长或非法输入、搜索服务异常应有空态、校验或错误状态，且不阻塞其他列表操作。客户与员工的隐私、地址与身份信息仍受权限保护，弹窗、列表与筛选器与 Core 使用一致的搜索语义。

  - AC-09-1：给定一个对象被创建、修改、归档或其关联字段发生变化，当在约定的最终一致性窗口之后搜索其名称、编码、邮箱或主体标识的新值时，能够检索到该对象，旧值不再成为唯一结果。
  - AC-09-2：给定包含重复关键词、不同大小写或组合词的查询，当连续翻页时，返回结果、数量、顺序与游标稳定，不出现重复项或漏项。
  - AC-09-3：给定空关键词查询，当请求列表时，不触发不可控的全量查询。
  - AC-09-4：给定过长或非法输入、或搜索服务异常，当请求列表时，返回空态、校验错误或错误状态，且其他列表操作仍可正常执行。
  - AC-09-5：给定调用方无权查看某客户或员工，当通过弹窗、列表或筛选器搜索时，返回与 Core 一致的结果范围，不泄露隐私、地址或身份信息。

#### 业务域 C：收款、礼品卡与交易

### R10 · 礼品卡纳入统一的交易生命周期
- 来源：instruction.md「将礼品卡纳入统一的交易生命周期，让授权、取消、扣款、退款和余额有可追踪的对应关系」；BC-007
- 优先级：P0
- 需求描述：礼品卡在结账与订单支付链路中要作为可追踪的支付方式统一处理，其初始化、授权与扣款能对应到具体交易记录，不能在订单详情里只留下一个无法解释的减项。使用礼品卡时必须满足：礼品卡存在、启用、未过期、币种一致且余额足够；不满足时明确失败，余额与支付状态不得被错误修改。权限不足、状态不合法或金额超限时不得静默改走普通支付。同一结账或订单的重复支付请求必须保持幂等：只形成一次有效授权或扣款、一次应有的余额变化，不形成冲突授权。
- 验收条件：
  - AC-10-1：给定一个结账或订单使用礼品卡支付，当商户查看其支付与交易记录时，礼品卡的初始化、授权与扣款可对应到可追踪的交易记录，而不是仅呈现为一个减项。
  - AC-10-2：给定礼品卡不存在、未启用、已过期、币种不一致或余额不足，当发起礼品卡支付时，返回明确失败，且礼品卡余额与结账或订单支付状态不被修改。
  - AC-10-3：给定调用方权限不足、礼品卡状态不合法或金额超限，当发起礼品卡支付时，操作被拒绝且不改为使用普通支付方式。
  - AC-10-4：给定同一结账或订单的同一支付请求被重复提交（如网络重试），当请求处理完成时，只形成一次有效授权或扣款与一次应有的余额变化，不产生冲突授权。

### R11 · 礼品卡授权的取消与订单退款
- 来源：instruction.md「将礼品卡纳入统一的交易生命周期」；BC-008
- 优先级：P0
- 需求描述：结账阶段取消与订单退款必须区分处理，不能混为同一种操作。结账阶段可以取消礼品卡授权，使授权与可用余额恢复到可解释状态；订单已经扣款的，只能在可退余额内退款。交易事件、礼品卡余额、结账或订单的支付及退款状态必须反映同一业务结果。Dashboard 要能区分礼品卡支付方式、金额与相关事件，并与交易查询一致，失败显示可识别的原因。没有事件时可以是空事件列表，不应因此认定整个请求失败。
- 验收条件：
  - AC-11-1：给定一个使用礼品卡授权但尚未完成的结账，当取消该礼品卡授权时，授权与可用余额恢复到可解释状态，且结账支付状态同步反映该结果。
  - AC-11-2：给定订单已通过礼品卡扣款，当发起退款且金额在可退余额内时成功，超过可退余额时被拒绝。
  - AC-11-3：给定一次礼品卡取消或退款完成，当对照交易事件、礼品卡余额与结账或订单的支付及退款状态时，三者反映同一业务结果。
  - AC-11-4：给定订单包含礼品卡支付，当客服在 Dashboard 查看时，能区分礼品卡支付方式、金额与相关事件，结果与交易查询一致；失败时显示可识别的原因。
  - AC-11-5：给定某交易没有相关事件，当请求其事件列表时，返回空事件列表且请求整体仍视为成功。

### R12 · 订单金额摘要的可解释分解与一致性
- 来源：instruction.md「Dashboard 的订单金额分解、交易事件与剩余待付金额必须与服务端一致，普通交易和礼品卡不能重复计入」；BC-009
- 优先级：P0
- 需求描述：金额摘要应分别呈现商品、折扣、税费、配送费、礼品卡、已授权、已扣款、已退款与剩余待付金额，组成关系可解释并与服务端一致。兼容的旧支付（Payment）与新交易（TransactionItem）都要处理；多交易汇总不能重复计入已经使用的额度或同一事件。同一订单同时存在折扣、税费、配送费、礼品卡与多笔支付时，各项之和不得多于或少于订单总额。
- 验收条件：
  - AC-12-1：给定一个含折扣、税费、配送费、礼品卡与多笔支付的订单，当查看金额摘要时，商品、折扣、税费、配送费、礼品卡、已授权、已扣款、已退款与剩余待付金额分别呈现，且与服务端返回一致。
  - AC-12-2：给定同一订单同时存在兼容旧支付与新交易记录，当汇总金额时，两类记录都被处理且不重复计入。
  - AC-12-3：给定同一订单有多笔交易，当汇总已授权、已扣款与已退款金额时，已使用的额度或同一事件不被重复计入。
  - AC-12-4：给定任一含礼品卡的订单，当核对金额摘要各项与订单总额时，礼品卡既不作为普通支付重复计入，也不被遗漏，各项之和与订单总额一致。

### R13 · 标记已支付、捕获授权与退款的状态与余额约束及幂等
- 来源：instruction.md「商户需要安全地标记已支付、捕获授权款和退款：有权限不代表任何状态都能操作，可操作金额也必须以当前真实余额为限」；BC-010
- 优先级：P0
- 需求描述：只展示并执行当前支付方式与状态允许的动作，输入金额不能为负。标记已支付要考虑已有支付记录：无记录且符合条件时可用；已有记录时按约定拒绝。捕获金额不能超过当前可捕获授权，等于合法边界可以成功，超过就拒绝。退款不能超过可退余额，多笔交易也不能重复占用额度。资金动作保持幂等，不重复扣款、退款或写入冲突事件。成功后显示刷新后的订单、交易事件与余额；失败保留原状态并给出可区分的错误。没有相关订单或没有支付权限的员工与 App 不能操作，也不能通过错误获得受限金额。
- 验收条件：
  - AC-13-1：给定订单当前的支付方式与状态，当客服查看可执行动作时，只展示该状态允许的动作；当提交负金额时，请求被拒绝。
  - AC-13-2：给定订单没有任何支付记录且满足标记条件，当执行标记已支付时成功；给定订单已有支付记录，当执行标记已支付时按约定被拒绝。
  - AC-13-3：给定订单存在可捕获授权，当捕获金额等于可捕获授权时成功，超过可捕获授权时被拒绝。
  - AC-13-4：给定订单存在多笔交易，当发起退款时，金额不超过可退余额，多笔交易不重复占用同一额度。
  - AC-13-5：给定同一资金动作被重复点击或失败后重试，当处理完成时，不重复扣款、不重复退款、不写入冲突事件。
  - AC-13-6：给定一次资金动作成功，当查看订单时，展示刷新后的订单金额、交易事件与余额；给定动作失败，原状态保留并返回可区分的错误。
  - AC-13-7：给定员工或 App 没有相关订单或支付权限，当尝试资金动作时被拒绝，且响应中不包含受限金额信息。

### R14 · 交易的基础查询与定位能力
- 来源：instruction.md「客服和支付集成方应能通过基础业务关联与支付标识找到相关交易，而不是依赖本轮不交付的查询增强」；BC-011
- 优先级：P0
- 需求描述：能够按订单或结账关联、交易 ID、支付服务商参考号与 App 标识筛选交易，礼品卡、普通支付与多交易订单都需要能定位。根级交易查询要能按这些主体条件筛选，并提供订单金额、支付方式、状态与事件展示所需字段。分页与客户、员工、App 的可见范围必须生效，不属于当前对象的交易不能泄露详情。本轮不做交易创建或修改日期、事件类型或日期筛选，也不做该查询的专用排序与索引。空分页项、越界分页、错误过滤类型及无权限请求要有稳定错误，不能用成功空结果掩盖非法请求。
- 验收条件：
  - AC-14-1：给定某订单或结账存在交易，当按订单或结账关联、交易 ID、支付服务商参考号或 App 标识筛选交易时，返回匹配的交易。
  - AC-14-2：给定订单使用礼品卡、普通支付或包含多笔交易，当执行上述筛选时，均能定位到对应交易。
  - AC-14-3：给定查询返回交易，当查看返回字段时，包含订单金额、支付方式、状态与事件展示所需的字段。
  - AC-14-4：给定调用方为某客户、员工或 App，当查询交易时，分页与其可见范围生效，不属于当前对象的交易详情不被返回。
  - AC-14-5：给定交易查询的筛选与排序参数，当枚举可用能力时，不出现按创建或修改日期、事件类型或日期筛选，也不出现该查询的专用排序与索引。
  - AC-14-6：给定空分页项、越界分页、错误过滤类型或无权限请求，当执行查询时，返回稳定错误，不以成功空结果掩盖非法请求。

### R15 · 锁定筛选与普通筛选的合并及作用范围一致
- 来源：instruction.md「Dashboard 的列表、分配弹窗和层级导航要保持筛选与上下文一致。用户看到的对象范围，必须与导出、批量操作实际作用的范围一致」；BC-014
- 优先级：P1
- 需求描述：从特定渠道或仓库的分配页面进入列表后，URL、弹窗或页面上下文带来的锁定条件应与普通条件分开合并，普通筛选不能覆盖锁定条件。搜索、翻页与清除普通条件都不能清掉原有限定范围。列表、礼品卡筛选、排序、导出与批量操作都读取当下有效条件，不能使用旧缓存；导出与操作范围必须与页面当前筛选一致；权限不能因为换入口而放宽。
- 验收条件：
  - AC-15-1：给定从某渠道或仓库的分配页面进入列表并带有锁定条件，当执行普通筛选时，锁定条件与普通条件同时生效，普通筛选不覆盖锁定条件。
  - AC-15-2：给定列表已带有锁定条件，当执行搜索、翻页或清除普通条件时，锁定范围仍然保留。
  - AC-15-3：给定页面当前的筛选条件发生变化，当执行列表查询、排序、导出或批量操作时，均读取当下有效条件而不使用旧缓存结果。
  - AC-15-4：给定页面带有筛选条件与锁定条件，当执行导出或批量操作时，其作用范围与页面当前可见对象范围一致。
  - AC-15-5：给定用户从一个入口换到另一个入口执行同类操作，其权限范围与在原入口一致，不因换入口放宽。

### R16 · 选择器、层级导航与返回路径的上下文保持
- 来源：instruction.md「Dashboard 的列表、分配弹窗和层级导航要保持筛选与上下文一致」；BC-015
- 优先级：P1

  - AC-16-2：给定在层级结构中切换层级并返回，当查看面包屑与父级关系时，层级关系与当前位置保持正确。
  - AC-16-3：给定列表出现加载、空结果、权限错误或网络错误，当从弹窗或层级页返回列表时，导航上下文被保留。
  - AC-16-4：给定输入框中出现很长的搜索关键词，当查看界面时，输入框与列表宽度稳定、不重叠跳动；长值可截断但可确认完整关键词；清除输入后功能正常。

#### 业务域 E：身份与内容安全

### R17 · 由商店统一控制的密码登录策略
- 来源：instruction.md「商户应能控制客户和员工是否使用密码认证；服务端认证流程、后台登录入口和配置页面必须读取同一生效策略」；BC-016
- 优先级：P0
- 需求描述：密码登录分三种模式：ENABLED 允许符合账户状态的受支持用户使用密码；CUSTOMERS_ONLY 只允许客户身份的密码能力；DISABLED 关闭密码认证及相关入口。外部认证独立按自身配置处理。CUSTOMERS_ONLY 下，员工不能凭密码取得员工会话或后台权限，需要使用允许的外部认证或其他管理入口。DISABLED 同时拒绝密码登录、重置、设置或修改密码，以及可绕过策略的旧 token 路径，并返回明确原因。只有具有商店设置权限的身份可以修改；保存后认证请求立即读取新值。设置页展示当前模式与权限限制，登录页不显示禁用入口，也没有外部方式时给出稳定空态。加载或保存失败保留原生效值，不把未保存值当作成功。
- 验收条件：
  - AC-17-1：给定商店设置为 ENABLED，当符合账户状态的受支持用户使用密码登录时成功；给定设置为 CUSTOMERS_ONLY，当客户身份的账号使用密码登录时成功。
  - AC-17-2：给定商店设置为 CUSTOMERS_ONLY，当员工账号尝试通过密码取得员工会话或后台权限时被拒绝，并可通过允许的外部认证或其他管理入口登录。
  - AC-17-3：给定商店设置为 DISABLED，当尝试密码登录、重置密码、设置密码或修改密码，或使用可绕过策略的旧 token 路径时，均被拒绝并返回明确原因。
  - AC-17-4：给定具有商店设置权限的身份修改密码登录模式，当保存后立即发起认证请求时，认证流程读取到新值。
  - AC-17-5：给定调用方无商店设置权限，当尝试修改密码登录模式时被拒绝；当配置页面展示时，显示当前模式与权限限制；当登录页没有任何可用外部方式时，显示稳定空态且不展示已禁用的密码入口。
  - AC-17-6：给定配置加载或保存失败，当查看生效行为时，仍使用上一次生效值，未保存的值不被当作成功。

### R18 · 外部身份关联后的旧密码路径清理
- 来源：instruction.md「外部身份关联不能留下旧密码绕过通道」；BC-017
- 优先级：P0
- 需求描述：Google OIDC 在需要 refresh token 时，要使用兼容的离线授权方式，即使用 access_type=offline，而不是不兼容的 offline_access scope；其他 provider 按自己的合同处理。授权失败要可识别，但 token 及敏感身份信息不能出现在错误响应或不必要的前端持久化存储中。当邮箱已经有本地用户时，首次关联后要清理或禁用能绕过外部身份策略的旧密码路径；同一 OIDC 身份后续登录应稳定，不能每次都被当作新身份。
- 验收条件：
  - AC-18-1：给定 Google OIDC 配置需要 refresh token，当发起授权时，请求使用 access_type=offline 且不使用 offline_access scope；其他 provider 按各自合同发起。
  - AC-18-2：给定一次外部授权失败，当查看错误响应与前端存储时，错误可识别，且 token 与敏感身份信息不出现在错误响应或不必要的前端持久化存储中。
  - AC-18-3：给定某邮箱已存在本地用户，当该用户首次通过外部身份完成关联时，原有的密码登录路径被清理或禁用，无法再通过旧密码绕过外部身份策略。
  - AC-18-4：给定同一 OIDC 身份已完成首次关联，当该身份后续再次登录时，被识别为同一用户，不被当作新身份创建。

### R19 · 富文本与外链在保存前的结构与安全校验
- 来源：instruction.md「富文本和外链在保存前就要经过结构与安全校验」；BC-018
- 优先级：P0
- 需求描述：继续支持正常富文本、嵌套列表与常用链接，但不允许一段内容控制来源页面。EditorJS 内容先校验结构，再清理 URL、链接属性与嵌套深度。未知或多余字段、非法 scheme、过深结构应被拒绝，不保存部分危险内容。http、https、mailto、tel 等合法链接按规则保留；新窗口外链具备安全的 rel 行为，不能通过 opener 控制来源页。不允许通过配置扩展协议白名单绕过限制。拒绝时错误要指向字段、链接或深度问题，不伪装成保存成功；合法内容仍能正常保存。
- 验收条件：
  - AC-19-1：给定一段包含合法嵌套列表与常用链接的富文本，当保存时，内容结构校验通过并正常保存。
  - AC-19-2：给定富文本包含未知或多余字段、非法 scheme 链接或超过允许深度的嵌套结构，当保存时被拒绝，且不写入任何部分危险内容。
  - AC-19-3：给定富文本包含 http、https、mailto 或 tel 链接，当保存并渲染时，链接按规则保留；新窗口外链带有安全 rel 行为，无法通过 opener 控制来源页。
  - AC-19-4：给定尝试通过配置扩展协议白名单，当提交原本被禁止的 scheme 时仍被拒绝。
  - AC-19-5：给定内容被拒绝，当查看错误时，错误指向具体字段、链接或深度问题，且不被表现为保存成功。

#### 业务域 F：扩展与事件

### R20 · 扩展安装约定与历史扩展数据适配
- 来源：instruction.md「App 的安装、升级、扩展展示和表单交互需要一致且可迁移的约定」；BC-019
- 优先级：P0
- 需求描述：扩展的安装、查询与展示要适配 mountName、targetName、settings 的当前约定，迁移后的历史扩展还要能查询、编辑与渲染。安装前要校验标识、权限、target 与设置；重复 identifier、无效权限、非法 target 或无法解析的设置要拒绝安装或更新，已有有效数据不能被破坏。可选安装信息缺省不能使合法安装失败，默认行为应稳定；tokenTargetUrl 属于可选安装信息，不需要时不要返回新建或安装 token。迁移与读取适配必须保留设置内容，新客户端不继续提交旧字段。安装与更新需要 App 管理权限，读取也只返回调用方允许的扩展数据。
- 验收条件：
  - AC-20-1：给定一个已安装的扩展，当通过查询接口读取并展示时，返回 mountName、targetName 与 settings 的当前约定字段，且取值可被客户端直接使用。
  - AC-20-2：给定升级前已存在的历史扩展数据，当升级后查询、编辑与渲染该扩展时，扩展仍可用，其设置内容被保留，且不要求用户重新安装。
  - AC-20-3：给定一次安装或更新请求带有重复 identifier、无效权限、非法 target 或无法解析的设置，当提交时被拒绝，且已有的有效扩展数据不被破坏。
  - AC-20-4：给定安装信息中缺省可选字段（含 tokenTargetUrl），当安装一个合法 App 时成功，且在不被需要时不返回新建或安装 token。
  - AC-20-5：给定新客户端提交扩展数据，当查看请求负载时，不再提交旧字段；当调用方缺少 App 管理权限时，安装或更新被拒绝，读取只返回其被允许的扩展数据。

### R21 · 扩展回应更新当前表单而非污染其他操作
- 来源：instruction.md「App 的安装、升级、扩展展示和表单交互需要一致且可迁移的约定」；BC-020
- 优先级：P1
- 需求描述：弹窗扩展返回表单内容时，用户要能看到返回结果，也要知道哪些字段未通过校验。需要处理缺省值、成功、字段验证失败、权限错误与 App 关闭状态，并按对应表单接收响应；错误不能保存成成功。多 frame、重复响应、未加载 frame 或未知 action 不能污染当前编辑状态，应被拒绝或明确处理为无效响应。
- 验收条件：
  - AC-21-1：给定弹窗扩展返回表单内容，当当前表单接收响应时，用户能看到返回的结果，且未通过校验的字段被明确标出。
  - AC-21-2：给定扩展回应为缺省值、成功、字段验证失败、权限错误或 App 关闭状态，当处理响应时，各状态被对应表单正确接收，错误不表现为保存成功。
  - AC-21-3：给定出现多 frame、重复响应、未加载 frame 或未知 action，当处理响应时，当前编辑状态不被污染，无效响应被拒绝或明确处理。

### R22 · 自托管商店可用的扩展目录
- 来源：instruction.md「自托管商店也要有可用的扩展目录体验」；BC-021
- 优先级：P1
- 需求描述：没有旧 marketplace 服务的自托管部署，也需要能浏览和筛选可用扩展，并按权限查看或配置。目录不依赖不可用的旧地址；能加载时展示可用数据，失败时明确区分空态与错误原因。没有配置权限的用户保持只读，不能把目录加载失败伪装为安装成功。
- 验收条件：
  - AC-22-1：给定一个未接入旧 marketplace 服务的自托管部署，当商户打开扩展目录时，可以浏览并筛选可用扩展。
  - AC-22-2：给定目录服务可加载，当打开目录时展示可用数据；给定加载失败，当打开目录时明确区分空态与错误原因，不依赖不可用的旧地址。
  - AC-22-3：给定用户没有配置权限，当浏览扩展目录时保持只读；目录加载失败不被呈现为安装成功。

### R23 · Webhook 只做订阅实际需要的工作
- 来源：instruction.md「Webhook 只做订阅实际需要的工作，允许异步处理的事件不要拖慢业务请求」；BC-022
- 优先级：P0
- 需求描述：同步订阅只解析实际选择的字段。允许异步处理的订单、草稿订单与履约事件，在后台任务边界构建完整内容，业务请求不等待完整异步载荷；纯异步订阅不提前触发无关的同步通知。订单业务请求不应因为构造大批异步通知内容而长时间等待，也不应顺带多调用未需要的税务或配送服务。继续遵守既有调用次数、超时、重试与熔断上限，不通过重复解析放大负载（本委托未另定新的数值上限）。
- 验收条件：
  - AC-23-1：给定一个同步订阅只选择部分字段，当触发该订阅时，只解析被选择的字段。
  - AC-23-2：给定订单、草稿订单或履约事件允许异步处理，当业务请求完成时，不等待完整异步载荷构建，完整内容在后台任务边界生成。
  - AC-23-3：给定订阅仅为纯异步，当相关业务请求执行时，不触发无关的同步通知，也不额外调用未需要的税务或配送服务。
  - AC-23-4：给定事件量增大，当观察调用次数、超时、重试与熔断行为时，仍遵守既有上限，不因重复解析放大负载。

### R24 · 单个接收方失败不阻断其他接收方
- 来源：instruction.md「一个接收方失败不应阻断其他接收方」；BC-023
- 优先级：P0
- 需求描述：同一事件通知多个 App 时，不能因为一个失败就让其他已成功的重来。失败只影响对应 delivery，其他订阅继续；失败按策略重试。包括商品变体折扣价更新在内的已定义事件，满足触发条件时产生合同正确的一次通知，无实质变化的保存不重复触发。后台需要能帮助判断是还没生成内容还是已经失败，显示等待、成功、失败、重试中状态以及错误；异步内容未生成不能当成成功。具备相关 App 或业务域权限时可单条重试，内容本身仍遵守 App 可见字段边界。既有 Webhook 失败告警保留，不扩展为 App Problems 功能。
- 验收条件：
  - AC-24-1：给定同一事件有多个订阅接收方，当其中一个投递失败时，其他订阅的投递不受影响、不被重做。
  - AC-24-2：给定一次投递失败，当重试策略执行时，仅该 delivery 按策略重试。
  - AC-24-3：给定商品变体折扣价发生实质变化，当保存时产生一次合同正确的通知；给定无实质变化的保存，当保存时不再重复触发通知。
  - AC-24-4：给定某投递处于等待、成功、失败或重试中，当商户在后台查看时，能看到对应状态与错误信息，异步内容尚未生成不被显示为成功。
  - AC-24-5：给定调用方具备相关 App 或业务域权限，当对单条失败投递执行重试时成功，且内容仍遵守 App 可见字段边界。
  - AC-24-6：给定存在 Webhook 失败告警，当查看后台时告警仍保留，且不呈现为 App Problems 类型的问题列表。

#### 业务域 G：历史数据、接口兼容与工作台

### R25 · 订单保留创建时的配送元数据快照
- 来源：instruction.md「订单应保留创建时的配送元数据，不能因为后来修改或删除配送方式而改变历史事实」；BC-024
- 优先级：P0
- 需求描述：结账成单与草稿订单成单两条路径都要保存当时的配送 public/private 元数据快照，供订单与履约读取。源对象后来被修改、停用或删除，不回写历史快照。公开与私有元数据的可见性仍按权限控制，相关事件内容与订单一致。迁移后已有元数据仍可读，不重复生成记录、不丢数据；没有元数据的历史记录给出稳定空值。
- 验收条件：
  - AC-25-1：给定一个结账通过结账流程成单，当订单创建时，保存当时的配送 public 与 private 元数据快照。
  - AC-25-2：给定一个草稿订单通过草稿订单流程成单，当订单创建时，同样保存当时的配送 public 与 private 元数据快照。
  - AC-25-3：给定订单已创建后，源配送方式被修改、停用或删除，当再次读取订单与履约的配送元数据时，内容仍为创建时的快照。
  - AC-25-4：给定调用方权限不同，当读取配送元数据时，公开与私有元数据的可见性按权限生效，且相关事件内容与订单一致。
  - AC-25-5：给定升级前的历史订单，当迁移完成后读取其配送元数据时，已有数据仍可读、不重复生成记录、不丢数据；原本没有元数据的记录返回稳定空值。

### R26 · 保留基础元数据读写，不提供独立管理入口
- 来源：instruction.md「保留业务所需的基础读取和编辑，不为此扩展出独立的元数据管理功能」；BC-025
- 优先级：P1
- 需求描述：结账、草稿订单、订单与履约保留必要的基础元数据读写；已有订单详情的行内编辑与订单行元数据能力继续保留。合法键值能按权限保存和读取，非法值、权限不足或保存失败不改变原值，也不能部分写入。本轮不交付订单、履约与仓库的独立元数据弹窗、专用路由或独立入口，也不通过隐藏入口把它们恢复。
- 验收条件：
  - AC-26-1：给定结账、草稿订单、订单或履约对象，当按其权限执行基础元数据读写时，合法键值能保存并被读取。
  - AC-26-2：给定订单详情页的行内编辑与订单行元数据操作，当执行时能力仍然可用。
  - AC-26-3：给定提交非法值、调用方权限不足或保存失败，当请求结束时，原元数据值保持不变，且不出现部分写入。
  - AC-26-4：给定订单、履约与仓库对象，当枚举其可用的元数据入口时，不出现独立的元数据弹窗、专用路由或独立入口，也不存在可恢复它们的隐藏入口。

### R27 · 输入校验与可分支的失败语义
- 来源：instruction.md「公开 API 同样需要明确的输入、权限和失败语义，不能把请求通信成功误认为业务操作成功，也不能在失败时留下部分危险数据或泄露敏感信息」；BC-026
- 优先级：P0
- 需求描述：接口调用方需要能区分传输成功、业务成功、没有结果与输入错误；GraphQL 返回 HTTP 200 不足以判断操作完成。数值、时间、分页、枚举、必填项与组合关系都在执行前校验；分钟、小时、天数等不得为负；Federation representations 不能是 null 或含 null 项；数组空项、错误类型与越界分页要有稳定错误。失败要返回可分支处理的 field、code、message，不产生部分写入，也不把未知错误转成成功空列表。合法的单值、数组与组合查询继续可用；订单条件查询与用户关联订单的查询返回准确结果与稳定分页；对象 ID、结账 token、UUID、渠道 slug 按各自类型使用，不能互换；金额、库存与状态变更依据最新对象状态执行幂等检查。
- 验收条件：
  - AC-27-1：给定一次接口调用返回 GraphQL 响应，当仅依据 HTTP 200 判断结果时无法区分业务结果，因此响应提供可区分传输成功、业务成功、没有结果与输入错误的信息。
  - AC-27-2：给定请求中包含为负的分钟、小时或天数，或缺少必填项、枚举取值非法、组合关系不成立，当提交请求时，在执行前返回校验错误。
  - AC-27-3：给定 Federation representations 为 null 或包含 null 项，当提交请求时，返回稳定错误。
  - AC-27-4：给定请求包含数组空项、错误类型或越界分页，当提交请求时，返回稳定错误。
  - AC-27-5：给定一次请求失败，当查看响应时，返回可按 field、code、message 分支处理的错误，且不产生部分写入；给定底层出现未知错误，不被转换成成功空列表。
  - AC-27-6：给定合法的单值、数组与组合查询，当提交时正常返回；给定订单条件查询与用户关联订单查询，返回准确结果与稳定分页。
  - AC-27-7：给定把对象 ID、结账 token、UUID 或渠道 slug 用于错误的参数位置，当提交请求时返回错误；给定金额、库存或状态变更，依据最新对象状态执行幂等检查，重复请求不产生二次变更。

### R28 · 弃用读取与迁移边界
- 来源：instruction.md「保持扩展、事件和历史订单数据可信」；BC-027
- 优先级：P0
- 需求描述：保留明确的弃用读取与替代路径，已不支持的能力则返回不存在或迁移错误，不能返回没有解释的成功空响应。旧 Adyen、NP Atobarai 插件、Payment.partial 与旧数字商品接口不再承诺；数字商品本身仍可通过 Apps 或现行方案提供。商品、礼品卡与 voucher 使用当前查询导出方式，旧导出 mutation 按弃用约定处理；草稿订单使用 voucherCode 替代旧 voucher 输入。属性的 name、slug、type 不能为空，App 安装的 appName、manifestUrl 必填。Core 的公开 schema、Dashboard 的生成客户端与错误映射、文档应一致，不能继续生成不支持的操作。迁移须能从空库执行，也要保留既有订单、交易、扩展、库存与元数据的业务含义（这不代表任何实际环境已经升级成功）。
- 验收条件：
  - AC-28-1：给定调用方使用仍被支持的旧用法，当发起请求时得到弃用读取结果与替代路径提示；给定调用方使用已不支持的能力，返回不存在或迁移错误，而不是无解释的成功空响应。
  - AC-28-2：给定调用方使用旧 Adyen、NP Atobarai 插件、Payment.partial 或旧数字商品接口，当发起请求时不返回成功结果；数字商品仍可通过 Apps 或现行方案获取。
  - AC-28-3：给定导出商品、礼品卡或 voucher，当使用当前查询导出方式时成功；给定使用旧导出 mutation，按弃用约定处理。
  - AC-28-4：给定草稿订单输入，当提供 voucherCode 时正常处理；旧的 voucher 输入按弃用约定处理。
  - AC-28-5：给定属性的 name、slug、type 为空，或 App 安装缺少 appName、manifestUrl，当提交请求时返回校验错误。
  - AC-28-6：给定 Core 公开 schema、Dashboard 生成客户端与错误映射及文档，当对照检查时三者一致，且不包含不支持的操作。
  - AC-28-7：给定一个空库，当执行迁移时能够完成，且既有订单、交易、扩展、库存与元数据的业务含义被保留。

### R29 · 权限不因查询入口而放宽
- 来源：instruction.md「用户看到的对象范围，必须与导出、批量操作实际作用的范围一致」；BC-028
- 优先级：P0
- 需求描述：员工删除、属性更新、App 安装、导出与敏感税务字段读取，不能通过更换查询入口绕过权限。有权限时合法员工应真正删除，而不只是撤销员工标记，包括有历史订单的情况；自删或无权限删除被拒绝。商品、礼品卡与 voucher 的导出受导出权限限制。结账与订单的相关私有元数据、用户等税务敏感字段遵循 HANDLE_TAXES 等权限，不向未授权身份泄露。客户、员工与 App 的对象范围、渠道与仓库可见性始终生效；没有权限不是「没有数据」，失败也不是「操作成功」。
- 验收条件：
  - AC-29-1：给定调用方缺少对应权限，当通过任一查询或操作入口执行员工删除、属性更新、App 安装、导出或读取敏感税务字段时，均被拒绝。
  - AC-29-2：给定具备权限的员工且目标员工有历史订单，当执行删除时该员工被真正删除而不是仅撤销员工标记；给定自删或无权限删除，被拒绝。
  - AC-29-3：给定调用方没有导出权限，当尝试导出商品、礼品卡或 voucher 时被拒绝。
  - AC-29-4：给定调用方不具备 HANDLE_TAXES 等税务权限，当请求结账或订单的私有元数据、用户等税务敏感字段时，不返回这些内容。
  - AC-29-5：给定调用方为某客户、员工或 App，当查询列表或读取错误信息时，其对象范围、渠道与仓库可见性始终生效；无权限不表现为「没有数据」，失败不表现为「操作成功」。

### R30 · 迟到的配置数据不覆盖正在编辑的内容
- 来源：instruction.md「配置加载、编辑、保存和缓存更新必须围绕用户当前操作，不能用迟到的数据覆盖正在输入的内容」；BC-029
- 优先级：P1
- 需求描述：打开渠道或商店设置后，数据可能晚到。页面必须明确区分加载中、已加载空数据、权限错误、网络错误与可重试状态；加载期间不崩溃、不闪烁错误值。渠道、商店与商品数据到达时只回填与当前编辑上下文仍有关的字段，不覆盖正在输入的值。成功才更新相关缓存或重新读取服务端事实；失败保留原状态，不把失败值放入缓存，修正后可以重试。
- 验收条件：
  - AC-30-1：给定打开渠道或商店设置且数据尚未到达，当查看页面时，明确区分加载中、已加载空数据、权限错误、网络错误与可重试状态。
  - AC-30-2：给定配置数据仍在加载，当查看页面时，页面不崩溃且不闪烁错误值。
  - AC-30-3：给定用户已在表单中输入内容，当渠道、商店或商品数据随后到达时，只回填与当前编辑上下文仍有关的字段，用户正在输入的值不被覆盖。
  - AC-30-4：给定一次保存成功，当查看缓存与服务端数据时，相关缓存被更新或重新读取；给定保存失败，原状态保留、失败值不进入缓存，修正后可以重试。

### R31 · 展示准确性与草稿订单动作可用性
- 来源：instruction.md「重量、金额、媒体状态和订单时间展示应准确；草稿订单动作只在渠道和商品条件允许时可用，并说明不可用原因」；BC-030
- 优先级：P1
- 需求描述：商品重量按实际单位转换，媒体状态和折扣金额与 API 一致，订单日期分组遵守 locale 与 timezone，跨日期边界不能归错组。媒体错误的正常状态展示不意味着重新引入异步图片专用回退体验。渠道停用、无可售商品或缺少必要配置时，草稿订单不能仍提供无效动作：应禁用不适用的添加商品、完成等动作并解释原因，不发送明知不合法的请求；切换到满足条件的正常渠道后仍可操作。
- 验收条件：
  - AC-31-1：给定商品重量数据与商店单位设置，当在界面展示重量时，按实际单位转换；当展示媒体状态与折扣金额时，与 API 返回一致。
  - AC-31-2：给定订单时间与用户 locale、timezone，当按日期分组展示订单时，分组遵守 locale 与 timezone，跨日期边界的订单不归错组。
  - AC-31-3：给定媒体处于错误状态，当展示时呈现正常的状态信息，不引入异步图片专用的抓取或回退体验。
  - AC-31-4：给定渠道已停用、无可售商品或缺少必要配置，当打开草稿订单时，不适用的添加商品与完成等动作被禁用并说明原因，且不发送不合法的请求。
  - AC-31-5：给定切换到满足条件的正常渠道，当执行草稿订单动作时功能可用。

### R32 · 交付范围边界：不恢复被排除能力并保留基础能力
- 来源：instruction.md「本轮不交付 App Problems、页面和用户的高级搜索、交易日期或事件筛选及专用排序、外链图片异步抓取与专用失败回退、独立变体生成器，以及订单、履约、仓库的独立元数据弹窗」；BC-031
- 优先级：P1
- 需求描述：本轮不交付 App Problems 的类型、字段、创建或关闭操作及问题列表，但 Webhook 失败告警仍在。页面和用户的高级搜索、交易日期或事件过滤及专用排序不借别名、隐藏路由或生成文件重新暴露。不做独立变体生成器页面、菜单、任务、状态或专用入口，但普通单变体创建、必填属性、hasVariants 兼容行为和普通批量创建保留。同步外链图片、本地上传和外部视频/oEmbed 保留，不做异步抓取、pending/503/proxy 状态和专用 Dashboard fallback。与主体链路无直接关系的专用 UI、后台任务、迁移或类型不新增；依赖升级、CI、运行器、生成工具、遥测与内部重构不另立业务需求，但必要的历史兼容、权限、交易一致性与可验证性不因此被取消。
- 验收条件：
  - AC-32-1：给定查询接口与后台页面，当枚举可用能力时，不出现 App Problems 的类型、字段、创建或关闭操作及问题列表，同时 Webhook 失败告警仍然可用。
  - AC-32-2：给定页面与用户的搜索、交易查询与排序入口，当通过别名、隐藏路由或生成文件检查时，不出现高级搜索、交易日期或事件过滤及专用排序。
  - AC-32-3：给定商品与变体操作入口，当检查时，不出现独立变体生成器页面、菜单、任务、状态或专用入口；同时普通单变体创建、必填属性、hasVariants 兼容行为与普通批量创建可用。
  - AC-32-4：给定媒体操作入口，当检查时，同步外链图片、本地上传与外部视频/oEmbed 可用，且不出现异步抓取、pending/503/proxy 状态与专用 Dashboard fallback。
  - AC-32-5：给定本轮交付物，当对照主体链路检查时，不包含与主体链路无直接关系的专用 UI、后台任务、迁移或类型；同时历史兼容、权限、交易一致性与可验证性能力仍然保留。

- **Dashboard 前端**：商品编辑页按渠道的可售性诊断、列表与分配弹窗的锁定筛选与作用范围一致、选择器与层级导航上下文保持、密码登录策略配置页、扩展目录与扩展表单回应处理、Webhook 投递状态与单条重试、迟到配置数据与编辑上下文、重量/媒体/金额/订单时间的准确展示、草稿订单动作可用性与原因说明、生成客户端与错误映射同 Core 保持一致。

## 5. 其他

### 5.1 事实依据

- 业务要求来自 instruction.md 与 business-conversations.md（BC-001 至 BC-031），两者共同表达业务要求。
- 代码事实用于确认基线与现状，不构成业务承诺：当前基线为 Core 3.22.0 与 Dashboard 3.22.9。基线中已存在 `Checkout.deliveryMethod` 与已弃用的 `shippingMethod`、`checkoutDeliveryMethodUpdate`、`ChannelWarehouse` 直接关联、`Channel.automatically_complete_fully_paid_checkouts`（仅布尔值，无延迟与 cutoff）、`automatic_checkout_completion_task`、礼品卡作为结账总额抵扣、`orderMarkAsPaid`/`orderCapture`/`orderRefund` 等人工资金动作，以及基于 Postgres 全文检索的商品/订单搜索。
- 基线中不存在、属于本轮新增的能力包括：以结账为主体的配送选项重算查询、商品渠道可售性诊断、密码登录模式（ENABLED/CUSTOMERS_ONLY/DISABLED）、扩展的 mountName/targetName/settings 后端约定与 `settings` 存储、礼品卡在交易生命周期中的可追踪记录、根级交易按主体条件筛选、订单配送元数据快照、自动完成的延迟与 cutoff 配置。

### 5.2 产品决策

1. **设置与执行分离。** 自动完成与密码登录模式的「保存成功」只表示配置已保存，页面不得据此推断业务动作已完成；业务结果一律以实际对象状态为准。
2. **弃用读取优先于静默成功。** 仍支持的旧用法给出弃用读取与替代路径；已不支持的能力返回不存在或迁移错误，不用成功空响应掩盖。
3. **同一事实单一来源。** 库存、金额、支付与退款状态在商品查询、结账、订单、履约与 Dashboard 之间必须来自同一计算语义；礼品卡不得作为普通支付被重复计入。
4. **失败可分支、不产生部分结果。** 校验在执行前完成；失败返回 field/code/message，且不产生部分写入、部分预留或半成品订单。
5. **权限与可见范围与入口无关。** 列表、弹窗、导出、批量操作与错误信息共享同一权限与可见范围。

### 5.3 假设

- Storefront 与支付集成方具备主动调用配送选项查询与交易查询的能力，并会按新约定迁移；旧客户端在弃用窗口内继续使用旧字段。
- 同步配送服务（列出配送方式、过滤配送方式）与税务、支付 App 的既有契约不变。
- 自动完成的批次调度沿用现有任务队列与重试上限；本委托未提供延迟、cutoff 与批次的具体默认数值，因此不设定数值化默认值。
- 搜索的最终一致性窗口数值未在业务材料中给出，按现有约定执行。

### 5.4 待确认项

- 自动完成配置的默认延迟、默认 cutoff 与批次规模的具体数值。
- 礼品卡在交易生命周期中的记录形态（是否复用统一交易模型还是新增可追踪支付记录）由研发在设计中确定，但必须满足 R10、R11、R12 的可追踪与不重复计入要求。
- 商品渠道诊断中「警告」与「阻断」的具体判定清单，需在实现时与渠道运营确认，但必须满足 R07 的区分与不淹没要求。
- 搜索最终一致性窗口的目标时长。
