# PRD：Saleor 3.23 结账、资金与商户运营一致性

版本：v1
责任：产品
状态：需求范围与验收条件已定义
输入：instruction.md；business-conversations.md；现有项目代码（Core、Dashboard）
修订：首次交付；根据业务委托、固定补充沟通及只读代码基线定义范围、规则与验收条件，未声明功能已经实现或环境已经升级。

## 1. 业务背景与目标

本次业务升级以 Core 3.22.0、Dashboard 3.22.9 为起点，目标版本为 Saleor 3.23。核心问题不是缺少若干独立页面，而是客户从判断商品可售、选择配送、支付到生成订单，以及商户履约、人工收款和售后时，可能使用不同时间、不同入口的库存、配置、金额和权限事实。

本次目标：
- **可靠成交**：当前结账可主动重算配送；选择更新、人工完成与自动完成均使用当前有效的客户、地址、配送、库存、支付及金额条件。错误不生成半成品订单，重试不重复成单或收款。
- **资金可解释**：礼品卡与普通支付具有可追踪的交易生命周期；金额摘要、事件、可捕获/可退余额及待付金额与 Core 一致，不把净额再次扣减或重复计入。
- **运营范围一致**：保留主体搜索及必要基础能力，诊断真实可售障碍；列表所见范围、导出范围、批量操作范围一致，筛选和导航不丢上下文。
- **策略与安全一致**：商店认证策略在 Core、登录入口与设置页同时生效；外部身份关联没有旧密码旁路；危险富文本和非法公开输入在执行或保存前被拒绝。
- **扩展与历史可信**：App 合同可迁移，Webhook 不做未订阅的工作，一个接收方失败不牵连其他接收方；订单保留创建时配送元数据，不因源对象后来变化而改写历史。
- **界面不制造成功**：配置保存、资金请求受理、后台排队与实际业务完成分别表达；失败或迟到响应不能覆盖生效事实及当前编辑内容。

没有提供现状转化率、人工处理时长、搜索一致性窗口数值或新的性能 SLA，本 PRD 不编造改善比例、绝对耗时或已运行结果。验收以状态、权限、金额、库存及副作用是否满足下列条件判定。

## 2. 用户与场景

| 用户类型 | 典型任务 | 必须得到的业务结果 |
| --- | --- | --- |
| 客户及 Storefront 集成方 | 修改地址/商品，重算并选择配送，使用普通支付或礼品卡，完成结账 | 当前可选配送和正确金额；失效、余额不足等有明确原因；一次有效成交 |
| 商户、商品及渠道运营 | 配置库存与自动完成，诊断渠道可售性，上架商品，筛选和导出对象 | 配置生效值可读；实际阻断可定位；操作不越过当前对象范围 |
| 库存与履约管理员 | 管理渠道仓库关系，预留、分配和履约，查历史配送信息 | 所有入口一致剩余库存；失败不超卖；历史配送资料保持创建时事实 |
| 客服及资金运营 | 定位交易，理解礼品卡和多笔支付，标记支付、捕获、取消或退款 | 合法状态和真实余额决定动作；重复提交不重复占用资金；事件与余额能对账 |
| 内容及翻译运营 | 保存富文本、使用 App 表单扩展、编辑允许的基础元数据 | 合法内容可保存，字段错误可修复，响应不会污染其他表单 |
| 商店及安全管理员 | 配置密码认证、外部身份、员工和 App 权限 | 后端实际拒绝禁用能力；敏感字段不从查询或错误旁路泄露 |
| App、支付及 Webhook 集成方 | 安装升级扩展，查询业务交易，接收和重试事件 | 当前 schema 合同明确，旧数据可迁移，delivery 独立，传输与业务成功可区分 |
| 自托管商店运维及后台使用者 | 使用扩展目录，处理加载/保存错误与渠道草稿订单 | 不依赖不可用旧服务；失败有稳定状态；满足条件的普通工作流程继续可用 |

## 3. 需求条目

以下条目的来源中，`instruction.md` 为业务委托原文位置，`BC-nnn` 为 `business-conversations.md` 片段标识；材料优先于基线实现。P0 表示删去会破坏某项委托目标、数据一致性或安全；P1 表示目标仍可完成但明确增加用户正常操作。本轮没有仅装饰性 P2 需求。金额、库存和异步状态的共通口径见第 5 节。

#### 结账、配送、库存与可靠成单

### R01 · 主动重算当前结账的配送选项
- 来源：instruction.md:15：“让 Storefront 能主动重新计算当前结账的配送选项，显示可用项和当前选择”；BC-001；依据 BC-001 的有效选择保护及 BC-002 的归属检查推导“不自动代选”。
- 优先级：P0
- 需求描述：提供 Storefront 可显式触发的配送重算能力，基于当前结账地址、行项目、渠道及同步配送服务结果，返回当前可用选项、当前选择、各项可展示价格与状态。成功重算不保留已失效选项作为可选项；如按当前字段合同仍返回被排除项，须明确不可选状态及原因。若原选择失效，其状态必须明确，不能假装仍可用于完成订单。重算计算失败与“成功计算但选择失效”分开处理：失败不覆盖原有有效选择，不保存部分计算结果。不自动代替客户选另一配送方式。
- 验收条件：
  - AC-01-1：有效结账具备所需地址和商品，调用重算后返回与当前渠道、行项目相符的选项、币种价格、状态及当前有效选择。
  - AC-01-2：客户修改地址或商品后再次重算，旧条件下才适用的选项不再作为可选项；失效原选择被明确标识，未自动替换成其他方式。
  - AC-01-3：同步配送服务可用项或价格发生变化后触发重算，结果采用本次服务结果，不继续展示上次价格为最新事实。
  - AC-01-4：需要配送而地址缺失或不完整时，返回可定位到地址的错误；已有选择及已保存数据不被失败覆盖。
  - AC-01-5：配送服务报错或返回无法使用的结果时，返回可识别服务错误，不保存半成品选项或伪装为成功空列表。
  - AC-01-6：结账不存在或调用方无对象访问权时，返回对应存在性/权限错误，不能泄露受限结账的地址、配送价格或选择，也不修改其他结账。

### R02 · 更新选择与完成结账重新验证配送
- 来源：instruction.md:15：“结账状态变化后，更新配送和完成订单都要重新确认有效性，不能沿用失效选择”；BC-002。
- 优先级：P0
- 需求描述：更新配送选择、人工完成和自动完成均验证选择属于当前结账且仍有效，覆盖地址、行项目、渠道、服务可用性及过期情况。需配送的结账没有有效配送不得完成。合法旧配送标识与当前 delivery 约定按公开兼容合同接受；旧字段保留弃用读取和替代说明，新客户端使用当前约定。不能通过兼容路径绕过归属或权限校验。
- 验收条件：
  - AC-02-1：选项在当前结账仍有效时，使用当前标识更新成功，随后读取的选择一致。
  - AC-02-2：使用兼容合同支持的旧标识选择合法方式时可成功；旧读取字段具有弃用信息，返回合同规定的结果，不要求旧客户端立即切断。
  - AC-02-3：输入其他结账的标识、非法标识或当前不适用方式，更新被拒绝并说明原因，原选择不变。
  - AC-02-4：已选方式在完成前过期、被停用或因地址/商品变化失效，完成被阻止并区分原因，没有新订单、资金重复动作或完成事件。
  - AC-02-5：无需配送的商品不因缺少配送选择被阻断，但仍执行客户、账单、支付、金额及库存等适用检查。
  - AC-02-6：不存在或无权限的结账经新旧两种入口得到稳定错误，不暴露受限配送数据，不改变原选择。
  - AC-02-7：当前合同支持的自提方式以 Warehouse 类型选择并由 deliveryMethod 正确读取；弃用 shippingMethod 按其语义不把自提伪装为配送方式。明确清除选择后读取为空，需配送结账仍不能无有效方式完成。

### R03 · 渠道库存策略在查询、预留、订单和履约一致
- 来源：instruction.md:15：“商品、结账、订单和履约应遵守一致的渠道与仓库库存规则，同时保护未切换库存策略商店的既有行为”；BC-003。
- 优先级：P0
- 需求描述：渠道可采用直接关联仓库的库存策略。未切换的渠道继续沿用原配送区域和地址关联行为；启用新策略后，仅直接关联当前渠道且有可用库存的仓库参与计算，旧地址参数仍接受但不改变该仓库集合。商品查询、结账、预留、订单分配、履约和草稿订单使用相同策略及当前关系，既有不跟踪库存商品等合法行为不因策略升级被无故改变。失败不得留下部分预留、分配或造成超卖。
- 验收条件：
  - AC-03-1：升级未切换策略的既有渠道，在相同库存、地址和配送区域配置下，可售数量及履约仓库行为与升级前一致。
  - AC-03-2：新策略下，当前渠道关联仓库库存为 3，未关联仓库为 10，相关商品、结账、订单及草稿入口只采用前者可用量；未关联库存不能补足订单。
  - AC-03-3：新策略下仅改变兼容地址参数、不改变渠道关联与库存，仓库集合和可用量不受该参数影响；配送本身仍按适用地址规则验证。
  - AC-03-4：仓库关联新增或移除后再次查询、预留和分配，均使用最新关系；已失去合法来源的新增操作返回可解释错误。
  - AC-03-5：预留或分配成功后，各入口按同一库存事实反映剩余量；并发或多行请求中任一必要库存不足时，不超卖、不遗留失败动作的部分预留/分配。
  - AC-03-6：权限不足、预留失败或仓库配置不合法时返回对应错误；受限渠道和仓库信息不从结果或错误中泄露。

### R04 · 商品编辑页按渠道诊断真实可售原因
- 来源：instruction.md:27：“诊断要指出真正阻断销售的原因，区分警告和不适用检查”；BC-004。
- 优先级：P1
- 需求描述：在商品编辑上下文提供渠道诊断，支持按渠道名称或币种筛选、分页、问题数量和明细。依据发布/可购买时间、商品与变体库存、渠道仓库关系、配送区域及直接影响可售性的配置判断，分别表示阻断错误、警告及不适用。未发布或不可售时突出实际阻断，不把正常依赖重复计为错误；数量与当前诊断明细一致。诊断不改变商品，也不替代 Core 成交检查。
- 验收条件：
  - AC-04-1：有多个可见渠道时按名称/币种筛选并翻页，展示正确范围、问题数量和对应明细，不重复或漏掉符合条件渠道。
  - AC-04-2：商品未发布或可购买时间尚未到时，指出真实时间/发布阻断；正常依赖项不被重复标为阻断错误。
  - AC-04-3：跟踪库存商品因变体缺货、仓库未合法关联或所需配送区域缺失而不可售时，分别指出可操作原因；警告不被误报为阻断。
  - AC-04-4：数字类无需配送商品的配送区域检查为“不适用”，发布、库存和核心条件仍正常检查，不能整体跳过诊断。
  - AC-04-5：员工无商品或渠道访问权时不展示受限诊断，也不借问题数量或错误披露受限配置。
  - AC-04-6：诊断加载、刷新或失败时状态明确；旧结果不标为当前结论，迟到响应不覆盖当前编辑字段或切换后的商品/渠道。

### R05 · 已支付结账按完整资格自动成单
- 来源：instruction.md:17：“自动化不能放松客户、地址、配送、库存和金额条件，失败后的重试也不能多生成订单、多扣款或重复发送完成事件”；BC-005。
- 优先级：P0
- 需求描述：对启用自动完成的渠道批次处理符合范围的结账。fully paid 按所支持流程判定：支持的完整授权、完整扣款，Transaction 与兼容 Payment 分别遵循其有效状态；部分支付、失败、待确认请求或仅有历史支付记录不足以成单。还必须有客户或邮箱、账单地址、所需配送地址与有效方式、可售商品、可用库存及大于零的总额。实际执行前重新核实全部条件。已完成或已处理的结账不得再次生成订单。失败有可诊断、可重试的结果，修复后重试仍只有一个订单结果。
- 验收条件：
  - AC-05-1：在支持完整授权的支付流程中，结账完整授权且其余资格和时间范围均满足，后台执行后生成一个对应订单，结账和订单的支付事实一致。
  - AC-05-2：在支持完整扣款的 Transaction 或兼容 Payment 流程中，结账 fully paid 且其他条件满足，自动完成遵守该流程合同，不再次向已支付额度扣款。
  - AC-05-3：结账只有部分支付、失败事件、待确认请求或支付额度不足时不成单，保留可解释的支付资格结果。
  - AC-05-4：缺少客户/邮箱、账单地址、适用配送条件，商品不可售或总额不大于零时，分别被阻止；没有半成品订单或完成通知。
  - AC-05-5：入队时合格、执行前库存不足或配送失效，任务重新检查后不成单，失败可以定位而不是显示执行成功。
  - AC-05-6：同一结账被重复入队、任务失败重试或与人工完成并发时，最多形成一个订单结果、一次有效资金动作及一次业务完成通知；已完成订单金额不被重试改变。
  - AC-05-7：批次中某结账不合格或执行失败，其他符合条件结账仍可处理；失败结账条件修复后可重试且不遗留上次失败的订单/库存副作用。

### R06 · 按渠道保存自动完成开关、延迟与 cutoff
- 来源：instruction.md:17：“商户可以按渠道配置已支付结账的自动完成策略”；instruction.md:9：“不能把失败、尚未保存的设置或尚未执行的后台工作显示成成功”；BC-006。
- 优先级：P0
- 需求描述：具有配置权限的用户可按渠道读取和保存开关、非负延迟及创建时间 cutoff。设执行时刻为 t、延迟为 d，仅当 `t - 结账最近一次变化时间 > d` 才符合延迟条件；有 cutoff 时须 `结账创建时间 >= cutoff`。cutoff 不是任务停止时间。界面与 API 明示时长单位、时间及时区语义。未配置旧渠道保持关闭或其明确既有默认，不擅自开启。范围、类型或组合非法、权限不足及保存冲突不覆盖上次生效值。自动完成设置不得混用“过期结账释放资金”的 TTL/cutoff。设置保存结果与实际任务及订单结果分别表达。
- 验收条件：
  - AC-06-1：有权限用户保存合法开关、延迟和 cutoff 后重新读取，同一渠道取得相同生效值，其他渠道不被改变。
  - AC-06-2：设延迟为 10 分钟，结账最近变化距执行时刻恰好 10 分钟时不进入待处理范围，超过 10 分钟才进入；再次修改结账重新计算等待时间。
  - AC-06-3：设 cutoff 为明确带时区时间 C，创建时间早于 C 的结账不处理，等于或晚于 C 的才继续资格检查；执行时间经过 C 后任务仍可运行。
  - AC-06-4：负延迟、错误时间/类型或非法配置组合被拒绝并定位字段；权限不足和并发保存冲突可区分，重读仍为最后成功生效值。
  - AC-06-5：升级未配置或未启用的既有渠道，不自动成单、不改变历史手工流程；关闭渠道不继续产生新的自动完成结果，执行前按最新开关复核。
  - AC-06-6：页面保存成功只表明配置生效；任务未执行或执行失败时不显示订单已生成，实际完成状态来自结账/订单事实。
  - AC-06-7：修改自动完成延迟/cutoff 不改变过期资金释放设置，修改释放资金设置也不被解释为自动完成范围修改。

#### 支付、礼品卡与查账

### R07 · 礼品卡纳入统一初始化、授权与扣款生命周期
- 来源：instruction.md:21：“将礼品卡纳入统一的交易生命周期，让授权、取消、扣款、退款和余额有可追踪的对应关系”；BC-007。
- 优先级：P0
- 需求描述：结账和订单支付链路可识别礼品卡支付，初始化、授权及扣款具有明确对象关联、金额和事件。验证礼品卡存在、启用、未过期、币种一致及可用额度充分；有效授权占用与最终扣款均须能解释余额变化，不能形成相互冲突的授权。错误不得悄悄切换为普通支付。重复同一业务请求须幂等。升级保留既有余额及历史扣卡事实，不把历史已扣卡重新扣一次；卡标识等敏感数据仅向允许的身份展示。
- 验收条件：
  - AC-07-1：合法礼品卡在结账初始化并授权后，可查到当前对象、支付方式、授权金额和相关状态，卡可用额度与授权占用一致。
  - AC-07-2：在允许扣款的状态完成礼品卡支付，形成有效扣款事件及一次应有的余额变化，结账/订单支付状态反映相同金额。
  - AC-07-3：卡不存在、停用、过期、币种不符或余额不足时，各返回可识别原因；卡余额、有效授权和支付状态保持失败前事实。
  - AC-07-4：无权限、状态不允许或申请金额超限时拒绝，不创建普通支付作为回退，也不泄露受限卡余额。
  - AC-07-5：同一结账或订单重复提交同一初始化、授权或扣款请求，只形成一次有效动作和余额变化，不创建冲突授权；并发不能超用同一卡额度。
  - AC-07-6：升级已有礼品卡及使用历史后，余额和历史金额仍可追踪；新交易展示不把旧抵扣再次记为新增扣款。

### R08 · 礼品卡取消、退款、余额和事件对账
- 来源：instruction.md:19：“把收款、礼品卡与售后放在同一笔账上”；instruction.md:21：“让授权、取消、扣款、退款和余额有可追踪的对应关系”；BC-008。
- 优先级：P0
- 需求描述：未完成结账的礼品卡授权允许按合同取消并释放占用；订单已扣款资金走退款，不伪装成授权取消。退款受当前可退余额约束，取消和退款同样幂等。Core 与 Dashboard 的事件、卡余额、对象支付和退款状态对应同一结果。Dashboard 区分礼品卡方式、金额和事件；查询成功但没有事件时使用空列表，不推断整个请求失败。
- 验收条件：
  - AC-08-1：未完成结账存在有效礼品卡授权，合法取消后授权状态和可用余额正确恢复，未形成订单退款或额外扣款。
  - AC-08-2：已扣款订单申请小于或等于可退余额的礼品卡退款，成功后卡余额、退款事件及订单退款状态对应同一金额。
  - AC-08-3：超额、负值或状态不合法的取消/退款被拒绝，原余额及有效状态不改变，并能与权限错误区分。
  - AC-08-4：同一取消或退款双击、网络重试或并发提交时，不重复释放/回充余额，不重复写有效资金事件。
  - AC-08-5：订单含礼品卡与普通支付时，Dashboard 与交易查询能分别识别方式、金额及各自事件；失败有原因且不展示为成功。
  - AC-08-6：可见交易无事件时查询成功并展示空事件列表；资金事件 pending、失败与实际成功分别呈现，不能以事件列表存在或 HTTP 200 判定成功。

### R09 · 金额摘要和剩余待付使用服务端同一口径
- 来源：instruction.md:21：“Dashboard 的订单金额分解、交易事件与剩余待付金额必须与服务端一致，普通交易和礼品卡不能重复计入”；BC-009。
- 优先级：P0
- 需求描述：摘要分别解释商品、折扣、税费、配送、礼品卡、授权、扣款、退款和剩余待付。区分总额、历史流水、当前净额及 pending；授权转扣款、退款或重复事件不能再次计入同一额度。Transaction 与兼容 Payment 按各自合同聚合，不盲目相加两套聚合结果。当前基线的 `chargedAmount`、`authorizedAmount`、`Payment.capturedAmount` 为相关动作后的剩余额度，不能再次减退款/已消耗授权。当前 `totalBalance` 欠款为负，正数待付是服务端余额口径的非负展示，不把 pending 或获批退款当成功收款。历史礼品卡已减入总额的订单不得再次减卡；新统一交易路径也必须只有一次礼品卡影响，明确总额与卡支付组成关系。
- 验收条件：
  - AC-09-1：订单同时有商品、折扣、税费及配送费，Dashboard 逐项金额和组成关系与服务端一致，不重复加税或折扣，币种及精度正确。
  - AC-09-2：订单商品等应付原始口径合计 100、礼品卡承担 20、普通成功支付 30 且无其他调整时，摘要能解释 20/30 来源并展示剩余 50，而不是重复扣卡得到 30；历史总额是否已扣卡按其服务端合同解释。
  - AC-09-3：多笔交易中授权已转扣款、同事件被重复收到或读取后，订单汇总不重复计入额度，当前授权/已收/可退款与 Core 一致。
  - AC-09-4：累计扣款 100、成功退款 20 且当前 `chargedAmount=80` 的交易，显示当前已收/可退依据 80，不再减 20 得到 60；历史退款仍可单独解释。
  - AC-09-5：使用兼容 Payment 的订单已退款后，按当前 `capturedAmount` 和其专属事件展示，不混用 TransactionItem 公式，也不将两套总额重复相加。
  - AC-09-6：Core 返回负余额、零余额、超付余额或包含 pending/获批退款的余额时，待付显示遵守 Core 口径且不为负，pending 与成功付款明确区分，超付不展示为还需支付。
  - AC-09-7：不同币种精度、零税或多笔部分退款场景中，摘要使用 API 金额与币种精度；不得固定两位或用客户端浮点重算覆盖服务端事实。

### R10 · 人工收款、捕获和退款受当前状态及余额限制
- 来源：instruction.md:23：“有权限不代表任何状态都能操作，可操作金额也必须以当前真实余额为限”；BC-010；由其金额和失败语义及基线 orderCapture/orderRefund 的正金额约束，推导“显式零值不能被当成缺省最大额”。
- 优先级：P0
- 需求描述：仅展示并执行当前订单、支付方式与状态支持的资金动作。标记已支付在无既有支付记录且满足当前流程条件时可用，不为有记录订单制造第二条冲突支付。捕获不得超出当前可捕获授权，退款不得超过当前可退余额；金额不能为负，现行要求大于零的动作继续拒绝显式零值，不将零误当“取最大金额”。超额须拒绝而非静默裁剪。缺省金额只有在接口明确支持时按合同采用当前额度。订单类动作和交易类动作分别校验其要求的订单/支付权限及对象、渠道范围，不用界面隐藏代替后端校验。请求、重试及多交易并发不得重复占用额度，受理不等于成功。
- 验收条件：
  - AC-10-1：有适用订单权限、无 Payment/Transaction 支付记录且满足账单等条件的订单，可按当前流程标记已支付；有任何冲突支付记录时按钮不可用且 Core 拒绝直接请求。
  - AC-10-2：可捕获授权为 50 时，合法捕获 50 可成功，捕获 50.01 或负值被明确拒绝，不能自动裁剪为 50；金额比较按该币种精度。
  - AC-10-3：可退余额为 30 时，合法退款 30 可成功，超出 30 被拒绝；多笔交易及退款 pending 占用按当前真实额度计算，不能重复退款。
  - AC-10-4：对要求正金额的资金动作显式输入 0 时返回金额错误，不默认为最大额度；未传金额的行为与该接口公开合同一致。
  - AC-10-5：在界面打开后额度被其他请求消耗，再提交原金额时 Core 以最新状态拒绝越限；双击或同一请求重试不重复扣款/退款或写冲突事件。
  - AC-10-6：请求仅受理或待服务商确认时显示 pending；成功后刷新订单、交易事件和余额；校验/权限失败保持原事实，外部资金失败按真实失败事件展示，不模拟成功。
  - AC-10-7：员工或 App 不具备相应动作权限或渠道/订单访问范围时，界面及直接调用均不能操作，错误不披露受限金额。

### R11 · 根级交易查询保留基础定位与受限分页
- 来源：instruction.md:23：“应能通过基础业务关联与支付标识找到相关交易，而不是依赖本轮不交付的查询增强”；BC-011。
- 优先级：P0
- 需求描述：提供根级交易查询及分页列表，可按订单或结账关联、交易 ID、支付服务商参考号、App 标识定位礼品卡、普通支付及多交易对象；支持这些条件合法组合。返回订单金额、支付方式、状态和事件展示所需字段。客户、员工和 App 只读取其被允许的对象及字段，不能将“允许看订单”等同于所有支付管理权限。列表使用稳定分页，不新增交易创建/修改日期、事件类型/日期过滤及本套查询的专用排序、索引。
- 验收条件：
  - AC-11-1：分别按订单、结账、交易 ID、PSP reference 和 App 标识查询，返回关联正确的交易；组合条件不泄露其他订单或 App 的交易。
  - AC-11-2：一个对象含多笔普通及礼品卡支付时，列表与详情具有方式、金额、状态及允许的事件字段，能与订单摘要对应。
  - AC-11-3：合法分页在固定数据集上游标稳定、不重复漏项；合法查询没有匹配时返回空结果/空事件，不被误报为错误。
  - AC-11-4：客户、员工和 App 使用各自可见范围查询，受限对象或字段不可见；无权限请求返回权限错误，不以成功空列表掩盖。
  - AC-11-5：分页参数中的 null 项、错误过滤类型或越界分页参数返回稳定可分支错误；合法的分页末尾无下一页仍是正常空页。
  - AC-11-6：公开 schema、Dashboard 查询和生成客户端不暴露本次排除的交易日期/事件筛选与专用排序，也不借别名形成相同能力。

#### 搜索、筛选与操作上下文

### R12 · 保留主体增强搜索和页面、用户基础搜索
- 来源：instruction.md:27：“保留与主体业务相关的搜索”；instruction.md:51：“排除这些增强不等于删除基础搜索”；BC-012。
- 优先级：P0
- 需求描述：结账、礼品卡、商品、订单继续提供主体增强搜索，保留对应关键词、前缀、组合词、短语及相关度合同，不因非目标裁剪一起关闭。客户/员工保留基础 `search_document`、按空格组合词匹配；页面继续按标题、slug、内容搜索。不引入 Page/User 向量高级匹配、前缀/相关度增强、`RANK` 及其专用索引、维护任务和迁移。基础搜索必要维护仍保留；页面修改影响引用商品名称时，仍更新商品搜索。现有各主体能力程度不同，本条是目标合同，不声称全部高级行为已在基线具备。
- 验收条件：
  - AC-12-1：分别搜索结账、礼品卡、商品和订单的主体关键词、支持的前缀、组合词及短语，结果和相关度遵守各自公开匹配合同，不能整体退化为关闭搜索。
  - AC-12-2：客户和员工以基础关键词及空格组合词搜索得到正确允许结果，隐私和身份字段依权限；不新增 Page/User 的前缀、向量相关度或 `RANK` 排序。
  - AC-12-3：按页面标题、slug 或内容查找正常可用，不因排除高级搜索返回固定空结果。
  - AC-12-4：页面名称修改影响引用商品后，商品搜索按更新机制可找到新名称；不能删除这一更新作为“不做页面高级搜索”的实现。
  - AC-12-5：列表、分配弹窗和筛选入口对同一主体使用一致 Core 搜索语义；无权限不能从搜索结果或错误获得受限对象信息。

### R13 · 搜索更新、分页和错误状态稳定可解释
- 来源：instruction.md:29：“搜索、加载、空结果、权限和错误状态应清楚可辨”；BC-013。
- 优先级：P0
- 需求描述：对象创建、修改、归档及关联字段变化后的名称、编码、邮箱及主体标识按约定最终一致性机制更新；旧值不能永久成为唯一检索结果。固定数据集下，大小写、重复关键词、组合词与翻页有稳定匹配、数量、顺序及游标。空关键词回到受权限、筛选及分页约束的默认列表或明确空态，不触发不可控全量查询。过长、非法输入与搜索异常有可恢复状态，不阻断其他列表操作；不引入材料未给出的数值 SLA。
- 验收条件：
  - AC-13-1：分别创建、修改名称/编码/邮箱、归档或修改关联主体字段，经过现行搜索更新机制后，新值可查，旧值不长期成为唯一结果，状态与对象事实一致。
  - AC-13-2：固定数据集使用大小写变化、重复关键词和组合词反复查询，结果、数量和顺序遵循同一匹配规则，不能因重复词产生重复对象。
  - AC-13-3：按稳定游标连续翻页并返回前页，在数据未变时不漏项、重复项；相关度相同的对象也有可解释稳定顺序。
  - AC-13-4：清空关键词后进入有界默认列表或清晰空态，分页、锁定筛选和权限仍有效，不发起无限量查询。
  - AC-13-5：过长/非法输入在适用输入约束处报校验错误；搜索服务或网络失败显示错误和重试，不伪装为“无匹配”，普通筛选和导航仍可操作。
  - AC-13-6：客户地址、身份及隐私信息，员工与 App 的可见对象范围，在搜索和结果数量/错误中均受保护。

### R14 · 锁定条件、导出与批量操作采用同一有效范围
- 来源：instruction.md:29：“用户看到的对象范围，必须与导出、批量操作实际作用的范围一致”；BC-014；依据所见与操作集合一致要求推导“不暗中使用筛选前的范围外旧选择”。
- 优先级：P0
- 需求描述：URL、页面和分配弹窗上下文形成的锁定条件与普通筛选分开管理，并以同时满足的方式合并。普通条件、清除筛选或缓存不能覆盖锁定范围。列表、礼品卡筛选、排序、导出和批量操作使用提交时当前有效条件及权限，而不是过时闭包或缓存。选中行操作与按全部筛选结果操作的范围明确，切换筛选后不能暗中操作范围外旧选中项。
- 验收条件：
  - AC-14-1：从指定渠道或仓库上下文进入列表，搜索、分页和清除普通条件后，锁定渠道/仓库仍存在且结果不越界。
  - AC-14-2：普通条件或可编辑 URL 参数与锁定条件冲突时，不替换锁定范围，也不能借此看到其他对象。
  - AC-14-3：修改礼品卡筛选/排序后立即导出，提交使用最新有效条件，导出对象集合与页面该范围一致，而不是只导出当前页或旧缓存范围。
  - AC-14-4：在选中行或全部筛选结果执行批量操作，确认范围与实际作用集合一致；切换条件后范围外旧选择不被暗中执行。
  - AC-14-5：从列表、弹窗、导出或直接 API 进入同一操作，使用相同业务权限和锁定/对象范围，不因入口不同放宽授权。
  - AC-14-6：列表筛选请求失败或旧请求迟到时，界面不把旧数据当当前筛选结果；导出/操作不会使用失败或失配范围。

### R15 · 选择器、层级导航与长搜索词保持上下文
- 来源：instruction.md:29：“Dashboard 的列表、分配弹窗和层级导航要保持筛选与上下文一致”；BC-015。
- 优先级：P1
- 需求描述：仓库、分类和分配层级结果按对象去重，重复选择/取消不残留值；父子关系、面包屑和返回路径正确。加载、空态、权限或网络错误后可保留当前位置及筛选，返回列表恢复合理原上下文。输入框/列表宽度稳定，长词可截断但有方式确认完整词，清除正常。
- 验收条件：
  - AC-15-1：同一仓库反复选择、取消、再次选择，候选和已选结果均不重复，取消值不出现在最终保存输入。
  - AC-15-2：进入分类子级、返回父级并搜索，层级结果及面包屑正确，不混入重复父子项或错误归属。
  - AC-15-3：加载、无匹配、权限错误或网络错误后恢复/重试，当前位置和允许的筛选上下文保留，错误与空态可区分。
  - AC-15-4：从详情或分配弹窗返回列表，恢复进入前的锁定条件、普通筛选和合理分页位置，不无故跳回无筛选首页。
  - AC-15-5：输入很长关键词，输入框和列表不重叠或跳宽，可查看完整词并正常清除，不误认为被截断显示的词就是实际提交词。

#### 身份与内容安全

### R16 · 商店密码认证三态统一生效
- 来源：instruction.md:33：“服务端认证流程、后台登录入口和配置页面必须读取同一生效策略”；BC-016；依据 instruction.md:49 的历史兼容目标推导“未配置商店不无故锁出既有管理员”。
- 优先级：P0
- 需求描述：商店提供 `ENABLED`、`CUSTOMERS_ONLY`、`DISABLED` 三种密码策略。ENABLED 允许账户状态合格的受支持用户使用密码；CUSTOMERS_ONLY 只允许客户身份的密码能力，员工不能凭密码获得员工会话或后台权限；DISABLED 拒绝密码登录及重置、设置、修改和可绕过策略的旧 token 路径。外部认证按自身配置独立处理，不能被密码策略误禁。仅具有商店设置权限的身份可改策略；成功保存后认证立即读新值。登录页按真实策略隐藏禁用入口，缺少外部方式有稳定空态，失败不改变生效值。
- 验收条件：
  - AC-16-1：ENABLED 下合格客户及员工按支持流程正常密码认证，停用或其他不合格账户仍被原账户条件拒绝。
  - AC-16-2：CUSTOMERS_ONLY 下客户受支持密码能力可用；员工直接调用密码登录或相关旧 token 路径不能取得员工会话/后台权限，返回明确策略原因。
  - AC-16-3：DISABLED 下直接调用密码登录、重置、设置或修改及旁路旧 token 入口均被拒绝；有效外部认证仍按其配置可用。
  - AC-16-4：有商店设置权限身份保存新模式后，重新读取一致，下一次认证请求按新值执行；未保存编辑不影响认证。
  - AC-16-5：无配置权限、加载失败或保存失败时，显示权限/错误，旧生效值不改变，失败编辑值不被写入缓存当成功。
  - AC-16-6：后台登录在 CUSTOMERS_ONLY/DISABLED 不提供禁用员工密码入口；没有可用外部方式时展示稳定无可用方式状态，不崩溃或显示虚假登录成功。
  - AC-16-7：升级未明确配置的商店保留现行密码行为，不无故锁出已有管理员；配置迁移的实际生效值可读且与登录页一致。

### R17 · OIDC 合同和首次身份关联关闭旧密码旁路
- 来源：instruction.md:33：“外部身份关联不能留下旧密码绕过通道”；BC-017。
- 优先级：P0
- 需求描述：Google OIDC 需要 refresh token 时使用 `access_type=offline`，不以不兼容 `offline_access` scope 替代；其他 provider 保持其自身合同。首次将已有本地邮箱用户与外部身份关联时清理或禁用可绕过外部身份策略的旧密码路径；后续相同 OIDC 身份稳定复用既有关联，不反复新增用户。授权失败可识别，但错误与不必要的前端持久化不含 token 或敏感身份信息。
- 验收条件：
  - AC-17-1：Google refresh token 场景的授权请求包含适用 `access_type=offline`，不因附加 `offline_access` scope 失败；其他 provider 参数不被一律改写为 Google 合同。
  - AC-17-2：已有本地用户首次合法关联外部身份后，旧密码无法绕过生效外部身份策略取得对应权限；用户和必要业务关联保留。
  - AC-17-3：同一 provider 的同一 OIDC 身份重复登录，稳定关联原用户，不重复创建身份或账户，也不每次重做首次关联。
  - AC-17-4：授权失败、无效身份或回调错误有稳定错误且无部分错误关联；响应、日志展示和不必要前端持久化不泄露 token 或敏感身份。
  - AC-17-5：全局密码模式变化后，已关联用户的外部登录及密码旁路处理仍遵循各自合同，不仅靠前端入口隐藏。

### R18 · 富文本结构与链接安全在保存前校验
- 来源：instruction.md:35：“富文本和外链在保存前就要经过结构与安全校验”；BC-018。
- 优先级：P0
- 需求描述：EditorJS 先验证结构，再清理 URL、链接属性及嵌套深度。合法富文本、嵌套列表及常用链接继续支持；未知/多余字段、非法 scheme、超出支持深度的结构拒绝整个保存，不部分写入危险内容。`http`、`https`、`mailto`、`tel` 等合法链接按允许规则保留；新窗口外链的 `rel` 必须防止 opener 控制来源页面，不能配置扩展协议白名单绕过固定安全约束。错误定位字段、链接或深度，页面和 API 使用同一规则。
- 验收条件：
  - AC-18-1：合法 EditorJS 富文本及支持深度内的嵌套列表可保存和重读，合法 http/https/mailto/tel 链接按规则保留。
  - AC-18-2：缺失必要结构、未知 block 字段或多余危险字段的输入被拒绝，错误指向结构/字段，原内容保持。
  - AC-18-3：非法 scheme、混淆或可执行链接输入被拒绝并定位链接问题，不保存部分内容；合法 URL 和属性按规则清理，不能通过可配置额外协议绕过固定约束。
  - AC-18-4：新窗口外链保存后具有防 opener 控制的安全 rel 行为，渲染时不能操作来源页面；合法链接不被全部删除。
  - AC-18-5：超过公开支持嵌套深度的输入返回深度错误；一次请求混合合法和非法内容时不保存部分危险或半成品内容。
  - AC-18-6：前端和直接 API 提交相同非法内容均失败并可定位修复，不显示保存成功，修复后合法输入可正常保存。

#### App、扩展与 Webhook

### R19 · App 安装、更新和历史扩展遵循当前合同
- 来源：instruction.md:39：“App 的安装、升级、扩展展示和表单交互需要一致且可迁移的约定”；BC-019。
- 优先级：P0
- 需求描述：安装、更新、查询及展示适配 `mountName`、`targetName`、`settings` 当前约定；校验 identifier 唯一性、请求权限、target 及可解析设置。安装输入 `appName`、`manifestUrl` 必填（同时见 R27），可选信息缺省不阻止合法安装，`tokenTargetUrl` 可选；不需要时不返回新建/安装 token。历史扩展迁移保留设置内容并可查、编辑、渲染，不要求重新安装。新客户端不再提交旧字段。修改须 App 管理权限，读取按调用方可见范围。
- 验收条件：
  - AC-19-1：有 App 管理权限的身份以合法 manifest/identifier/权限/target/settings 安装或更新成功，查询和 Dashboard 渲染同一 mountName/targetName/settings 合同。
  - AC-19-2：可选安装信息包括 tokenTargetUrl 缺省时，合法安装仍可成功且默认行为稳定；不需要返回 token 的路径响应不含新建/安装 token。
  - AC-19-3：重复 identifier、无效权限、非法 target 或无法解析 settings 时安装/更新被拒绝并有字段原因，现有有效 App 和扩展不被破坏或部分改写。
  - AC-19-4：基线历史扩展升级后，设置内容及业务含义保留，用户无需重新安装便可查、编辑和渲染；重复迁移不生成重复扩展。
  - AC-19-5：无 App 管理权限修改被拒绝，查询也只返回调用方获准扩展；token、受限设置不从结果或错误泄露。
  - AC-19-6：Dashboard 与生成客户端使用新合同，不继续提交不支持旧字段；旧读取适配与迁移说明明确而非静默丢 settings。

### R20 · App 响应只更新对应当前表单
- 来源：instruction.md:39：“扩展展示和表单交互需要一致且可迁移的约定”；instruction.md:45：“不能用迟到的数据覆盖正在输入的内容”；BC-020。
- 优先级：P0
- 需求描述：商品与翻译等弹窗扩展回应按已打开的对应表单及 frame/action 接收。缺省值、成功、字段验证失败、权限错误及 App 关闭分别处理，错误响应不得当成功保存。多 frame、重复响应、未加载 frame、未知 action 或已切换上下文的迟到消息不能污染当前编辑状态；无效消息拒绝或明确忽略。合法结果展示给用户，其写回和保存仍遵循表单校验与权限，不直接绕过 Core。
- 验收条件：
  - AC-20-1：当前已加载商品或翻译表单扩展返回合法内容，正确字段显示结果，缺省字段按对应表单合同处理，不写入别的对象。
  - AC-20-2：字段验证失败返回可定位字段错误，成功字段的显示与实际未成功保存明确区分，不把整次回应标为保存完成。
  - AC-20-3：权限错误或 App 关闭后，界面呈现对应状态，原已保存内容及其他表单编辑不被响应改坏。
  - AC-20-4：多个 frame 同时存在时，回应只作用于匹配的表单；重复响应不重复应用业务动作，未知 action 或未加载 frame 不修改状态。
  - AC-20-5：切换对象、关闭弹窗或用户继续编辑后收到过期响应，不覆盖当前操作；修复合法表单后仍可按权限保存。

### R21 · 自托管可使用扩展目录且区分加载失败
- 来源：instruction.md:39：“自托管商店也要有可用的扩展目录体验”；BC-021。
- 优先级：P1
- 需求描述：扩展目录不依赖不可用的旧 marketplace 地址；自托管商店可浏览、筛选可用扩展，按权限查看或配置。正常空目录、加载中和服务/网络错误分别表达；目录数据加载不等于 App 已安装，不因目录失败创建安装成功状态。没有配置权限保持只读。
- 验收条件：
  - AC-21-1：没有旧 marketplace 服务的自托管环境中，按当前目录配置加载可用扩展并可筛选，不请求必然不可用的旧地址作为唯一数据源。
  - AC-21-2：有效目录无匹配项时展示正常空态；数据源/网络失败展示错误及恢复方式，不伪装为“没有扩展”。
  - AC-21-3：有配置权限身份可按当前安装合同进入配置，无配置权限用户只读，直接调用受后端权限约束。
  - AC-21-4：目录加载成功、失败或重试均不表示安装已完成；只有实际安装结果可以更新安装状态。

### R22 · 按实际订阅解析，同步请求不等待完整异步载荷
- 来源：instruction.md:39：“Webhook 只做订阅实际需要的工作，允许异步处理的事件不要拖慢业务请求”；BC-022。
- 优先级：P0
- 需求描述：同步 Webhook 只解析订阅选择的字段；支持异步处理的订单、草稿订单及履约事件在后台任务边界构建完整载荷，业务请求不等待完整异步内容生成。纯异步订阅不提前触发无关税务、配送或其他同步通知。重复解析不放大负载；继续使用现行调用次数、超时、重试及熔断上限，不建立材料未给出的新数值标准。异步事实不可伪装为同步已完成。
- 验收条件：
  - AC-22-1：同步订阅仅选择部分字段，执行只解析实际选择内容，不为未订阅字段调用无关税务/配送服务。
  - AC-22-2：订单、草稿订单及履约的纯异步订阅，在业务请求完成时只完成必要入队/事件处理，不等待完整异步载荷构建；后台随后构建符合合同内容。
  - AC-22-3：纯异步订阅的事件不提前触发无关同步税务、配送或通知调用；混合同步/异步订阅分别遵循各自边界。
  - AC-22-4：重复读取、解析及失败重试不导致超出现行调用、超时、重试和熔断上限的额外循环；按既有策略出现稳定失败/熔断结果。
  - AC-22-5：异步任务尚未构建载荷或构建失败时，业务和 delivery 状态与实际一致，不显示通知成功；失败可通过 R23 的状态和重试定位。

### R23 · delivery 独立失败、重试与事件触发准确
- 来源：instruction.md:39：“一个接收方失败不应阻断其他接收方”；instruction.md:51：“排除这些增强不等于删除……Webhook 失败告警”；BC-023。
- 优先级：P0
- 需求描述：同一事件各接收方独立 delivery，失败仅影响该接收方并按现行策略重试，不让已成功接收方重新执行。已定义事件，包括商品变体折扣价更新，在满足实际触发条件时产生一次对应业务通知；无实质变化保存不重复触发。界面区分等待、成功、失败、重试中和错误，具备相关 App 或业务域权限可对单条 delivery 重试，载荷仍遵循 App 字段可见性。保留既有失败告警，不新增 App Problems 类型或管理流程。
- 验收条件：
  - AC-23-1：同一事件发送到 A/B/C，A 失败而 B/C 成功，B/C 不被阻断或因 A 重试重新通知；A 按策略独立重试。
  - AC-23-2：商品变体折扣价格实际变化时产生合同正确的一次业务事件/通知；未变化的保存不产生同样的新通知，delivery 重试保留原事件身份。
  - AC-23-3：载荷尚未生成显示等待，执行中或重试显示对应状态，确认投递成功才显示成功，失败显示可识别原因。
  - AC-23-4：获准身份单条重试失败 delivery，只重试目标条目，不改变其他 delivery 或重触发业务资金/订单动作。
  - AC-23-5：无相关权限不得重试或读取受限载荷；各 App 收到的载荷遵循其可见字段边界，错误不泄露敏感信息。
  - AC-23-6：Webhook 失败仍有现行告警/查看能力；不新增 App Problems 问题列表、创建/关闭操作或隐藏替代入口。

#### 历史资料、公开合同、权限及日常工作台

### R24 · 订单保存成单时配送 public/private 元数据快照
- 来源：instruction.md:41：“订单应保留创建时的配送元数据，不能因为后来修改或删除配送方式而改变历史事实”；BC-024；依据“创建时事实”与“没有元数据给稳定空值”推导“不用当前源值伪造无法恢复的历史”。
- 优先级：P0
- 需求描述：结账完成与草稿完成两条路径均保存当时配送方式的 public/private 元数据快照，订单和履约按该历史事实读取。源配送方式修改、停用或删除不回写快照，相关事件与订单一致。公开和私有可见性依权限；不能把配送税类快照或订单自身基础元数据当成配送方式快照。升级历史元数据仍可读，无数据给稳定空值，迁移不丢失或重复生成；不伪造无法从历史恢复的创建时值。
- 验收条件：
  - AC-24-1：结账完成时配送方式有 public/private 元数据，订单、履约允许的读取及对应事件取得相同创建时快照。
  - AC-24-2：草稿订单合法完成时，同样保存所用配送方式的当时快照，不遗漏此路径。
  - AC-24-3：成单后修改、停用或删除源配送方式，历史订单及履约快照不改变或消失；新订单取得其自身成单时事实。
  - AC-24-4：未授权身份不能读取 private 快照或从事件/错误旁路获取；public 按公开读取合同可见。
  - AC-24-5：既有历史元数据升级后仍可读，重复迁移不重复记录或丢数据；无历史数据对象返回稳定空值，不以当前源值冒充历史事实。
  - AC-24-6：基础业务元数据编辑或配送税类元数据变化不意外覆盖本条的配送方式快照；本条不新增独立元数据管理入口。

### R25 · 必要元数据基础读写与订单行内编辑保留
- 来源：instruction.md:41：“保留业务所需的基础读取和编辑，不为此扩展出独立的元数据管理功能”；BC-025。
- 优先级：P0
- 需求描述：结账、草稿订单、订单及履约保留当前业务允许的元数据基础读写，订单详情已有行内编辑和订单行元数据能力继续可用，包括现有用于订单行/商品变体编辑的交互，不因组件名含 Dialog 就误删。public/private 各自按权限执行，合法键值可读写；同一业务保存动作中的非法输入、权限不足或失败不部分写入、原值保持，不通过拆成多次请求把半成品结果当成整体保存成功。配送快照遵守 R24 的历史边界。订单、履约、仓库不新增独立元数据管理弹窗、路由、专用入口，也不借隐藏入口恢复。
- 验收条件：
  - AC-25-1：获准身份在结账、草稿订单、订单、履约基础接口保存合法键值并重读，得到相同结果及正确公开/私有可见性。
  - AC-25-2：订单详情原有行内编辑及订单行元数据读取/编辑正常可用，不因删除非目标入口而整体消失。
  - AC-25-3：同一业务保存动作含非法键值、权限不足或发生保存失败时，返回对应错误，其目标原元数据保持且不部分写入；动作内部即使使用多次请求也不能遗留部分保存或显示整体成功。
  - AC-25-4：切换查询、事件或编辑入口不能读取无权访问的 private 数据或改变配送历史快照。
  - AC-25-5：Dashboard 无新增订单、履约、仓库独立元数据弹窗、路由或隐藏入口；必要基础 API 与既有行内能力仍可访问。

### R26 · 公开输入执行前校验及业务失败语义统一
- 来源：instruction.md:35：“公开 API 同样需要明确的输入、权限和失败语义，不能把请求通信成功误认为业务操作成功”；BC-026。
- 优先级：P0
- 需求描述：执行前验证数值、时间、分页、枚举、必填与组合关系；分钟/小时/天等不得为负，金额由动作规定非负或正值。Federation `representations` 不允许 null 列表或 null 项；数组空项、错误类型和越界分页返回稳定错误。合法单值、数组、组合查询继续可用；订单条件查询、用户关联订单及分页准确。对象 ID、checkout token、UUID、channel slug 按各自类型使用，不随意互换。mutation 可处理错误具有 `field/code/message`，顶层 GraphQL 类型/权限错误按其合同定位并区分，不要求所有错误挤入同一 payload。无结果、业务失败、pending 与成功分开；未知错误不能转为成功空列表。金额/库存/状态动作基于最新对象做幂等和原子性检查。
- 验收条件：

### 共通判定与产品决策

1. **生效与编辑分开**：只以最后成功保存的配置作为生效策略。晚到数据只对当前未改动字段回填。保存冲突必须报错，不能以后到的旧值静默覆盖；实现采用何种版本机制由研发确定。
2. **等待不等于失败，更不等于成功**：设置保存、请求受理、后台入队、异步载荷构建、资金动作确认和订单创建分别有状态；确认成功后才刷新相应业务事实。读取合法空事件或无匹配不是请求失败。
3. **“失败不改变原状态”的边界**：输入/权限/状态检查失败不修改已保存业务数据；外部资金请求已发出后若明确失败或尚待确认，应忠实保留失败/pending 事件及追踪信息，但不虚增有效已付/已退额度。幂等保护不能只依赖前端按钮禁用。
4. **金额以 Core 为权威**：gross/net/tax 和币种精度采用 API；不把净额当累计额，不同时扣已包含礼品卡的总额及礼品卡交易。普通资金与礼品卡汇总须有无歧义合同，历史订单金额不为套用新展示口径被改写。
5. **权限以动作及字段为单位**：不是所有资金 API 都机械同时要求相同两项权限；订单操作、支付操作、配置、导出和税务字段分别遵循其合同，均检查对象、渠道/仓库范围。不因为能读某订单而自动拥有支付管理权。
6. **库存及历史资料分清对象**：新库存策略不由兼容地址重算仓库归属；配送方式元数据快照、配送税类快照及订单自身可编辑元数据是不同事实。快照读写不得互相覆盖。
7. **示例不是默认值**：验收中的 10 分钟、100/20/30 等是边界测试数据，不是自动完成默认配置、额度上限或实际业务统计。
