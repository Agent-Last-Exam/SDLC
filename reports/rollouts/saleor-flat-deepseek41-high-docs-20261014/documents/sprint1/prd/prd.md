# PRD：Saleor 3.23 结账、收款与商户运营一致性交付

版本：v1
责任：产品
状态：需求范围与验收条件已定义
输入：instruction.md；business-conversations.md；现有项目代码（saleor 3.22.0、saleor-dashboard 3.22.9）
修订：首次交付

## 1. 业务背景与目标

本次交付以 Core 3.22.0 与 Dashboard 3.22.9 为升级起点，目标不是堆叠独立功能，而是打通一条完整商业链路：客户结账 → 选择配送 → 支付 → 生成订单 → 商户履约与售后。这条链路上的每个参与者（Storefront、支付集成方、商户运营、客服、履约管理员、App 与 Webhook 集成方）必须看到同一份事实，并能按各自权限采取行动。

当前链路存在四类业务问题：

1. **同一事实在不同入口不一致。** 可售性判断、库存预留、配送选项、订单金额分解在商品查询、结账、订单、履约、Dashboard 之间可能各算一套；结账状态变化后仍可能沿用失效的配送选择，导致客户看到不可用的配送方式或成单失败。
2. **资金与订单事实缺少统一账本。** 礼品卡以无法追踪的余额抵扣形式出现，授权、取消、扣款、退款、余额之间没有可对应的追踪关系；Dashboard 的金额分解与服务端可能不一致，普通交易与礼品卡可能重复计入。
3. **运营人员难以定位对象与判断阻断原因。** 搜索、列表筛选、分配弹窗、层级导航的上下文容易丢失或被覆盖；商品按渠道的可售性诊断堆叠告警而不指出真正阻断销售的原因；导出与批量操作的作用范围可能与页面所见不一致。
4. **安全与兼容边界依赖页面隐藏或静默降级。** 密码登录策略未由商店统一控制，外部身份关联可能留下旧密码绕过通道；富文本与外链在保存后才补救；公开 API 把 HTTP 200 当作业务成功，失败时可能留下部分数据；已退出历史的能力以无解释的成功空响应返回。

本次交付要达成的业务目标：

- **G1** Storefront 能主动重新计算当前结账的配送选项，并在更新选择与完成结账时复核有效性；商品、结账、订单、履约与草稿订单遵守一致的渠道与仓库库存语义。
- **G2** 商户可按渠道配置已支付结账的自动完成策略，在不放松客户、地址、配送、库存与金额条件的前提下减少手工完成工作，且重试不会多生成订单、多扣款或重复发送完成事件。
- **G3** 礼品卡纳入统一交易生命周期；Dashboard 的金额分解、交易事件与剩余待付金额与服务端一致，人工收款、捕获与退款受权限、订单状态与真实余额三重限制。
- **G4** 运营人员能按主体条件检索对象、按渠道诊断可售性阻断原因，并确保列表、导出与批量操作作用于同一范围。
- **G5** 密码登录策略、外部身份关联、富文本与外链、公开 API 输入与权限由服务端统一执行，不依赖前端隐藏或事后补救。
- **G6** 扩展安装、事件投递与历史订单数据保持可迁移、可解释；升级不改变既有订单、交易、扩展、库存与元数据的业务含义。

**约束与边界：** 升级既要能初始化新商店，也要保留既有数据与既有行为（未切换库存策略的商店、未配置自动完成的渠道、旧客户端的合法旧标识、历史订单的配送元数据与已有元数据）。本 PRD 不编造任何未提供的量化指标、最终一致性窗口数值或调用次数上限；此类数值沿用系统既有约定。

## 2. 用户与场景

| 用户 | 典型任务 |
| --- | --- |
| Storefront 集成方 | 在地址、商品或渠道变化后主动重算配送选项；展示可用项、当前选择与价格状态；提交结账并处理字段级错误 |
| 客户（终端买家） | 选择配送方式、完成支付；在商品不可售、配送失效、资金不足或输入非法时得到可理解的失败结果 |
| 支付集成方 | 通过订单/结账关联、交易 ID、支付服务商参考号与 App 标识定位交易；按支付方式与状态执行授权、扣款、取消与退款 |
| 资金运营 / 客服 | 标记已支付、捕获授权、退款、取消结账阶段礼品卡授权；核对礼品卡余额、交易事件与订单金额分解是否指向同一笔资金 |
| 商户运营 | 配置渠道的自动完成策略；按渠道诊断商品可售性问题；从分配入口进入列表后继续搜索、翻页、导出与批量操作 |
| 履约运营 | 读取订单创建时的配送元数据快照；在配送方式被修改或删除后仍能解释历史订单 |
| 商店管理 / 安全管理 | 控制密码登录模式与权限；管理员工、App 安装与导出；确认失败不被显示为成功 |
| App 与 Webhook 集成方 | 按当前扩展约定安装、查询与渲染扩展；接收合同正确的同步/异步事件；单个接收方失败不影响其他接收方 |
| 平台维护 | 从空库执行迁移；确认公开 schema、Dashboard 生成客户端与文档一致；历史资产业务含义不变 |

## 3. 需求条目

**业务域：结账、配送与库存**

#### R01 · 结账配送选项的主动重新计算与当前选择
- 来源：Instruction「让 Storefront 能主动重新计算当前结账的配送选项，显示可用项和当前选择」；BC-001
- 优先级：P0
- 需求描述：提供可由 Storefront 主动发起的配送选项重算能力，基于当前结账的地址、行项目、渠道与同步配送服务结果，返回可用配送选项列表（每项含可展示的价格与状态）与当前选中的配送选项。计算必须使用服务端当前结账事实而非客户端缓存；同步配送服务（外部 shipping app 的同步 webhook）结果变化后重算应反映新结果。已不再适用于当前结账的旧选项不得继续出现在可用项中，也不得继续被标记为当前选择。失败语义：地址缺失或不完整、配送服务报错、结账不存在时返回可定位的字段错误；失败不得覆盖原有有效选择，也不得保存半成品选择。不破坏 `Checkout.shippingMethods`、`Checkout.deliveryMethod` 与已弃用的 `availableShippingMethods` 的既有读取语义。
- 验收条件：
  - AC-01-1：给定含行项目、收货地址与渠道的有效结账，当 Storefront 主动发起重算且结账地址已变化时，返回的可用配送选项与当前选择均基于新地址，价格与可用性与服务端当前计算一致。
  - AC-01-2：当结账的行项目或渠道发生变化后发起重算，返回的选项集合随之变化，不再包含因该变化而不适用的选项。
  - AC-01-3：当外部同步配送服务返回的选项发生变化后发起重算，返回结果反映新的服务结果，且不混入上一次结果。
  - AC-01-4：当结账已有有效配送选择时，重算结果同时给出可用项与当前选择；当原选择已不适用时，当前选择为空或明确标识为不可用，且不出现在可用项中。
  - AC-01-5：当结账地址缺失或字段不完整时发起重算，返回可定位到具体字段的错误，且结账原有的有效配送选择保持不变。
  - AC-01-6：当同步配送服务报错时发起重算，返回可识别的错误，且不写入任何部分配送选择。
  - AC-01-7：对不存在的结账发起重算，返回不存在错误，且响应不包含其他结账的配送信息。

#### R02 · 更新配送方式与完成结账时的有效性复核
- 来源：Instruction「结账状态变化后，更新配送和完成订单都要重新确认有效性，不能沿用失效选择」；BC-002
- 优先级：P0
- 需求描述：`checkoutDeliveryMethodUpdate` 与 `checkoutComplete` 在执行时都必须基于当前结账事实重新校验配送方式有效性（地址、行项目、渠道、库存、配送区域与外部配送服务结果）。只能选择属于当前结账的配送方式，不归属该结账的标识不得被接受。完成结账时若配送选择已过期或不可用，必须阻止完成并区分失效原因（未设置、不适用、地址缺失等），不能留下半成品订单。兼容：旧客户端使用合法旧配送标识（`shippingMethod` / `checkoutShippingMethodUpdate` 路径）按弃用读取约定继续可用，`Checkout.shippingMethod` 保留弃用读取语义，新客户端使用 `deliveryMethod` / `checkoutDeliveryMethodUpdate`。归属错误、权限不足或结账不存在的请求不得泄露配送信息，也不得改动原有选择。
- 验收条件：
  - AC-02-1：结账配送方式因地址或行项目变化而失效后调用 `checkoutDeliveryMethodUpdate`，返回可区分的失效错误，且不保存新的配送选择。
  - AC-02-2：结账在提交 `checkoutComplete` 前配送选择已失效时，完成操作失败并返回配送相关错误码，不创建订单。
  - AC-02-3：未设置配送方式、配送方式不适用、配送地址缺失三种情况分别返回可区分的失败结果。
  - AC-02-4：使用不属于该结账的配送方式标识调用更新，请求被拒绝且该结账原选择不变。
  - AC-02-5：旧客户端使用合法旧标识更新配送方式成功，服务端最终状态与使用 `deliveryMethod` 更新一致，且 `Checkout.shippingMethod` 仍可读取。
  - AC-02-6：无权限或不归属该结账的调用方请求配送信息或更新配送方式时被拒绝，响应不包含该结账的配送信息。
  - AC-02-7：完成结账因配送校验失败后，结账仍处于可重试状态，且不存在订单、库存预留或支付副作用。

#### R03 · 渠道与仓库直连的库存计算与既有行为保留
- 来源：Instruction「商品、结账、订单和履约应遵守一致的渠道与仓库库存规则，同时保护未切换库存策略商店的既有行为」；BC-003
- 优先级：P0
- 需求描述：提供通过渠道与仓库直接关联（`Channel.warehouses` / `ChannelWarehouse`）决定可售库存的方式；商店选择该方式后，只有直接关联当前渠道且有可用库存的仓库参与可售量与预留计算。未切换该方式的商店继续沿用既有配送区域与地址关联的库存行为，升级后未改设置的商品不因此变为不可售。商品查询、结账、订单、履约与草稿订单使用同一可售与预留语义。旧地址参数仍可被接受，但在新方式下不得改变由直接关联决定的结果。仓库关系变化、库存不足、预留失败与权限不足都要有可解释结果；预留或分配成功后各入口反映相同剩余量，失败不得造成超卖或部分预留。
- 验收条件：
  - AC-03-1：未启用渠道-仓库直连的商店，升级后商品可售性与预留结果与升级前一致（含仅有配送区域关联的仓库）。
  - AC-03-2：启用直连后，仅直接关联当前渠道且库存可用的仓库计入可售量；未关联该渠道的仓库即使有库存也不计入。
  - AC-03-3：同一变体在商品查询、结账可用性、下单、履约与草稿订单中得到相同的可售结论。
  - AC-03-4：在新方式下请求中传入地址参数，不改变由渠道-仓库直接关联决定的可售与预留结果。
  - AC-03-5：变更渠道-仓库关系后，新的可用量与预留计算立即反映新关系，不依赖旧缓存；已完成的预留不受影响。
  - AC-03-6：库存不足或预留失败时返回可解释错误，不产生部分预留、不超卖，剩余量保持不变。
  - AC-03-7：无权限调用方无法通过任何入口读取或改变预留结果。

#### R04 · 商品编辑页按渠道的可售性诊断
- 来源：Instruction「保留…商品编辑页按渠道诊断可售性的能力。诊断要指出真正阻断销售的原因，区分警告和不适用检查，不能让正常依赖项淹没实际问题」；BC-004
- 优先级：P1
- 需求描述：商品编辑页提供按渠道的可售性诊断，支持按渠道名或币种筛选与分页，展示问题数量与明细。诊断结合发布状态与可购买时间、商品及变体库存、仓库关联、配送区域以及其他直接影响可售性的配置事实。结论分为阻断错误、警告与不适用三类；未发布或不可售时指出实际阻断项，不把正常依赖重复报成错误。数字（非配送）商品只跳过配送区域检查，库存、发布与核心条件仍检查。商品、渠道与员工权限仍然生效，不能从错误信息推断受限信息。编辑中、查询失败或刷新时状态明确，不把旧诊断当作最新结论，也不覆盖正在编辑的内容。
- 验收条件：
  - AC-04-1：按渠道名或币种筛选诊断列表时，结果与筛选一致，分页稳定，问题数量与明细条目一致。
  - AC-04-2：商品在渠道未发布或不可购买时，诊断把发布状态或可购买时间标识为阻断项，且不把因此产生的库存或配送依赖重复报为错误。
  - AC-04-3：同一渠道下同时存在阻断、警告与不适用项时，三类分别标识，商户可据此判断哪些真正阻断销售。
  - AC-04-4：数字商品的诊断只跳过配送区域检查，库存、发布与核心条件仍给出结论。
  - AC-04-5：无权员工看不到受限字段的明细，也不能从错误信息中推断出受限数据。
  - AC-04-6：诊断查询失败时显示可重试的错误状态而非空结果；编辑中到达的旧诊断结果不覆盖正在编辑的内容，也不被标记为最新结论。

**业务域：已支付结账的自动完成**

#### R05 · 已支付结账自动完成的资格条件与幂等
- 来源：Instruction「商户可以按渠道配置已支付结账的自动完成策略。自动化不能放松客户、地址、配送、库存和金额条件，失败后的重试也不能多生成订单、多扣款或重复发送完成事件」；BC-005
- 优先级：P0
- 需求描述：自动完成仅针对达到所支持支付方式 fully paid 条件的结账；受支持的完整授权、完整扣款，以及 Transaction 与兼容 Payment 流程按各自约定判定。除支付条件外还必须满足：存在客户或邮箱、账单地址、需配送时具备配送地址与配送方式、商品可售、总额大于零。已经完成或已处理过的结账不得再次成单。任务按批次处理；失败保留可诊断、可重试的状态，条件修复后重试也只能形成一个订单结果。不得重复扣款、重复发送完成通知，或改变已完成订单的金额。
- 验收条件：
  - AC-05-1：结账达到 fully paid 且其余条件满足时，自动生成一个订单。
  - AC-05-2：只有完整授权而未扣款的结账按对应支付方式约定处理；未达到 fully paid 条件时不成单。
  - AC-05-3：缺少客户或邮箱、账单地址、配送地址或配送方式，存在不可售商品，或总额为零时，不创建订单并留下可诊断的原因。
  - AC-05-4：已完成或已处理过的结账再次进入处理范围时，不产生第二个订单。
  - AC-05-5：结账进入队列后库存、配送或支付条件失效时，在真正完成前重查并拒绝成单。
  - AC-05-6：条件修复后重试只形成一个订单，且不重复扣款、不重复发送完成事件。
  - AC-05-7：重试不改变已完成订单的金额与支付记录。
  - AC-05-8：任务按批次处理结账，单个结账失败不影响同批次其他结账的推进。

#### R06 · 自动完成策略的按渠道配置与状态呈现
- 来源：Instruction「商户可以按渠道配置已支付结账的自动完成策略」；BC-006
- 优先级：P0
- 需求描述：按渠道配置自动完成的开关、延迟与 cutoff，并明确适用范围。延迟自结账最近一次变化起算，超过延迟才进入待处理范围；cutoff 是结账创建时间的下界（只考虑在该时间或之后创建的结账），不是任务停止执行的时间。未配置的旧渠道不应被意外改成自动完成；未配置时沿用关闭或既有默认行为，不改变历史手工流程。合法配置能保存并重新读到；范围或组合非法、无配置权限、保存冲突都要明确报错并保留上次生效值。设置状态与执行结果分开，页面不能因为保存成功就宣称订单已生成；订单是否完成以实际结账与订单状态为准。
- 验收条件：
  - AC-06-1：新建或未配置的渠道，自动完成默认为关闭；配置后重新读取到与保存一致的值。
  - AC-06-2：结账最近一次变化早于配置延迟时进入待处理范围；变化时间晚于延迟的结账在延迟内不被处理。
  - AC-06-3：只处理创建时间在 cutoff 或之后的结账；cutoff 之后新建的结账仍可被处理（cutoff 不停止任务执行）。
  - AC-06-4：延迟为负或 cutoff 与适用范围组合非法时保存失败，返回可定位错误，渠道保留上次生效值。
  - AC-06-5：无渠道设置权限的身份无法保存配置，现有配置不变。
  - AC-06-6：并发保存发生冲突时明确报错，并保留上次生效值。
  - AC-06-7：保存成功只反映设置状态，界面不显示「订单已生成」；订单是否存在以结账与订单的实际状态为准。
  - AC-06-8：升级后未配置自动完成的渠道，其行为与升级前一致。

**业务域：收款、礼品卡与交易**

#### R07 · 礼品卡纳入统一支付生命周期
- 来源：Instruction「将礼品卡纳入统一的交易生命周期，让授权、取消、扣款、退款和余额有可追踪的对应关系」；BC-007
- 优先级：P0
- 需求描述：在结账与订单支付链路中统一追踪礼品卡的初始化、授权与扣款，订单详情不得只留下无法解释的减项。资格校验：礼品卡必须存在、启用、未过期、币种一致且余额足够；不满足时明确失败，不修改余额与支付状态。权限不足、状态不合法或金额超限时，不得静默改走普通支付。同一结账或订单的重复支付请求必须幂等，只形成一次有效授权或扣款、一次应有的余额变化，不形成冲突授权。
- 验收条件：
  - AC-07-1：满足条件的礼品卡用于支付时产生可追踪的授权或扣款记录，余额按扣款金额减少，结账或订单的支付状态一致更新。
  - AC-07-2：礼品卡不存在、已停用或已过期时支付失败并返回可识别原因，余额与支付状态不变。
  - AC-07-3：礼品卡币种与结账币种不一致时支付失败，且不改走普通支付。
  - AC-07-4：礼品卡余额不足时明确失败，不做部分扣减，余额不变。
  - AC-07-5：无支付处理权限的调用方无法使用礼品卡支付，且不能通过错误响应获得礼品卡余额信息。
  - AC-07-6：对同一结账或订单重复提交相同支付请求，只形成一次有效授权或扣款与一次余额变化，不产生冲突授权。
  - AC-07-7：订单详情与交易记录中礼品卡以支付方式形式呈现其金额与关联事件，而不是无法解释的减项。

#### R08 · 结账取消与订单售后的礼品卡对账
- 来源：Instruction「让授权、取消、扣款、退款和余额有可追踪的对应关系」；BC-008
- 优先级：P0
- 需求描述：结账阶段可以取消礼品卡授权，使授权与可用余额恢复到可解释状态；订单已经扣款的只能在可退余额内退款。一次取消或退款之后，交易事件、礼品卡余额、结账或订单的支付与退款状态应反映同一业务结果。Dashboard 要能区分礼品卡支付方式、金额与相关事件，并与交易查询一致；失败时显示可识别原因。没有事件时可以是空事件列表，不应据此判定整个请求失败。
- 验收条件：
  - AC-08-1：结账阶段取消礼品卡授权后，授权状态与可用余额恢复到与取消一致的状态。
  - AC-08-2：已扣款订单在可退余额内退款成功，礼品卡余额与订单退款状态同步更新。
  - AC-08-3：退款金额超过可退余额时被拒绝，余额与订单状态不变。
  - AC-08-4：一次取消或退款后，交易事件、礼品卡余额、结账或订单的支付与退款状态反映同一结果，不出现余额已变而事件未记录的情况。
  - AC-08-5：Dashboard 能区分礼品卡支付方式的金额与相关事件，并与交易查询结果一致。
  - AC-08-6：礼品卡相关操作失败时展示可识别原因，不显示为成功。
  - AC-08-7：某笔交易没有事件时返回空事件列表，页面正常渲染，不把空列表当作请求失败。

#### R09 · 订单金额分解的可解释性
- 来源：Instruction「Dashboard 的订单金额分解、交易事件与剩余待付金额必须与服务端一致，普通交易和礼品卡不能重复计入」；BC-009
- 优先级：P0
- 需求描述：摘要分别呈现商品、折扣、税费、配送、礼品卡、已授权、已扣款、已退款与剩余待付金额，组成关系可解释并与服务端一致。兼容旧 Payment 与新 Transaction 两条路径；多交易汇总不得重复计入已使用的额度或同一事件。礼品卡金额在分解中不得重复计入普通支付。
- 验收条件：
  - AC-09-1：订单详情同时展示商品、折扣、税费、配送、礼品卡、已授权、已扣款、已退款与剩余待付金额。
  - AC-09-2：同一订单在 Dashboard 展示的各金额与服务端计算结果逐一一致。
  - AC-09-3：存在多笔交易或支付时，汇总不重复计入同一事件或已使用额度。
  - AC-09-4：礼品卡金额在分解中只计入一次，不叠加到普通支付金额上。
  - AC-09-5：Payment 流程与 Transaction 流程的订单都能得到正确的金额分解。
  - AC-09-6：部分支付订单的剩余待付金额等于应付金额减去已有效支付金额，为零时显示为已结清。

#### R10 · 人工资金动作的权限、状态与余额限制
- 来源：Instruction「商户需要安全地标记已支付、捕获授权款和退款：有权限不代表任何状态都能操作，可操作金额也必须以当前真实余额为限」；BC-010
- 优先级：P0
- 需求描述：只展示并执行当前支付方式与订单状态允许的动作（`orderMarkAsPaid`、`orderCapture`、`orderRefund`、`transactionRequestAction`），输入金额不能为负。标记已支付要考虑已有支付记录：无记录且符合条件时可用。捕获金额不能超过当前可捕获授权，等于合法边界可成功，超过则拒绝。退款不能超过可退余额，多笔交易不能重复占用额度。资金动作保持幂等，点击两次或失败重试不重复扣款、退款或写冲突事件。成功后显示刷新后的订单、交易事件与余额；失败保留原状态并给出可区分的错误。没有相关订单或支付权限的员工或 App 不能操作，也不能通过错误获得受限金额。
- 验收条件：
  - AC-10-1：订单只展示当前支付方式与订单状态允许的动作，不允许的动作不出现。
  - AC-10-2：金额为负的标记已支付、捕获或退款请求被拒绝，返回可定位错误。
  - AC-10-3：订单已有支付或交易记录时不能标记已支付；无记录且满足条件时可以。
  - AC-10-4：捕获金额等于当前可捕获授权时成功；超过时被拒绝且订单与支付状态不变。
  - AC-10-5：退款金额等于可退余额时成功；超过时被拒绝；多笔交易不重复占用同一额度。
  - AC-10-6：重复提交同一资金动作只产生一次扣款或退款与一组对应事件。
  - AC-10-7：操作失败后订单金额、支付状态与事件保持原样，错误可区分。
  - AC-10-8：操作成功后展示刷新后的订单、交易事件与余额。
  - AC-10-9：无相关订单或支付权限的身份不能执行这些动作，且响应不泄露受限金额。

#### R11 · 交易的基础检索能力
- 来源：Instruction「客服和支付集成方应能通过基础业务关联与支付标识找到相关交易，而不是依赖本轮不交付的查询增强」；BC-011
- 优先级：P1
- 需求描述：根级交易查询支持按订单或结账关联、交易 ID、支付服务商参考号与 App 标识筛选，礼品卡、普通支付与多交易订单都能定位；提供订单金额、支付方式、状态与事件展示所需字段。分页与客户、员工、App 的可见范围必须生效，不属于当前对象的交易不泄露详情。明确不做交易创建或修改日期、事件类型或日期筛选，也不做本查询的专用排序与索引。空分页项、越界分页、错误过滤类型及无权限请求要有稳定错误，不能用成功空结果掩盖非法请求。
- 验收条件：
  - AC-11-1：按订单或结账标识查询时，能返回该对象的全部相关交易。
  - AC-11-2：按交易 ID、支付服务商参考号与 App 标识查询时，能定位到对应交易。
  - AC-11-3：礼品卡支付产生的交易可通过相同条件定位，并带有支付方式信息。
  - AC-11-4：多笔交易的订单返回其全部相关交易，结果稳定。
  - AC-11-5：查询结果包含订单金额、支付方式、状态与事件展示所需字段。
  - AC-11-6：客户、员工与 App 只能看到自身可见范围内的交易，越权查询不泄露详情。
  - AC-11-7：分页结果、数量与游标稳定；空分页项与越界分页返回稳定结果而非意外错误。
  - AC-11-8：错误过滤类型或非法参数返回稳定错误，不以成功空结果掩盖非法请求。
  - AC-11-9：按日期或事件类型筛选、专用排序等本轮不交付的能力不被提供，请求这些能力时行为明确，不静默忽略为成功空结果。

**业务域：运营检索与列表**

#### R12 · 主体搜索能力边界
- 来源：Instruction「保留与主体业务相关的搜索」；BC-012
- 优先级：P1
- 需求描述：保留结账、礼品卡、商品、订单、客户与员工的搜索入口，页面继续按标题、slug 或内容查找。结账、礼品卡、商品、订单保留各自的主体增强搜索行为（关键词、前缀、组合词、短语与相关度），不能一并关闭。客户与员工继续使用基础搜索文档，按空格组合词匹配；不恢复 Page/User 的向量高级搜索、前缀或相关度增强、RANK 排序及其专用索引、后台维护任务与迁移。页面修改影响商品引用名称时，不能破坏商品的搜索更新。
- 验收条件：
  - AC-12-1：结账、礼品卡、商品、订单能按关键词检索到预期对象，前缀、组合词、短语与相关度等增强行为保持有效。
  - AC-12-2：客户与员工按空格组合词匹配，结果符合基础搜索文档，不依赖向量高级搜索。
  - AC-12-3：页面可按标题、slug 与内容被找到。
  - AC-12-4：Page/User 不提供向量高级搜索、前缀或相关度增强与 RANK 排序，相关后台维护任务与迁移不新增。
  - AC-12-5：修改页面导致商品引用名称变化后，商品搜索仍能按新名称找到该商品。

#### R13 · 搜索更新、分页与异常的可解释性
- 来源：BC-013；Instruction「保留与主体业务相关的搜索」
- 优先级：P1
- 需求描述：对象创建、修改、归档或关联字段变化后，名称、编码、邮箱与主体标识的新值应能被搜索到，旧值不能一直成为唯一结果；更新遵守既有最终一致性窗口（本 PRD 不指定该窗口数值）。重复关键词、大小写变化、组合词与翻页不能让列表不断重复或漏项；结果、数量、顺序与游标稳定且可解释。空关键词不能引起不可控的全量查询；过长或非法输入、搜索服务异常要有空态、校验或错误状态，且不阻塞其他列表操作。客户与员工的隐私、地址与身份信息仍受权限保护；弹窗、列表与筛选器与 Core 使用一致搜索语义。
- 验收条件：
  - AC-13-1：修改对象名称、编码或邮箱后，在约定的最终一致性窗口内可按新值搜索到该对象。
  - AC-13-2：更新后旧值不再继续作为唯一命中结果。
  - AC-13-3：重复关键词、大小写变化与翻页不产生重复项或漏项，结果数量、顺序与游标稳定。
  - AC-13-4：空关键词不触发不可控的全量查询，行为明确可预期。
  - AC-13-5：过长或非法输入返回校验错误或明确空态，且不阻塞其他列表操作。
  - AC-13-6：搜索服务异常时返回错误或空态，不把异常转成成功空结果。
  - AC-13-7：无权限身份看不到客户与员工的隐私、地址与身份信息，弹窗、列表与筛选器与 Core 语义一致。

#### R14 · 锁定筛选与普通筛选的合并
- 来源：BC-014；Instruction「Dashboard 的列表、分配弹窗和层级导航要保持筛选与上下文一致。用户看到的对象范围，必须与导出、批量操作实际作用的范围一致」
- 优先级：P0
- 需求描述：从特定渠道或仓库的分配入口进入列表时，URL、弹窗或页面上下文带来的锁定条件应与普通条件分开合并，普通筛选不能覆盖锁定条件。列表、礼品卡筛选、排序、导出与批量操作都读取当下有效条件，不能使用旧缓存。导出与批量操作的作用范围必须与页面当前筛选一致，权限也不能因为换入口而放宽。
- 验收条件：
  - AC-14-1：从渠道或仓库分配入口进入列表后，继续搜索、翻页与清除普通条件，锁定条件仍然生效。
  - AC-14-2：设置与锁定条件同维度的普通筛选时，不会清除或替换锁定条件。
  - AC-14-3：导出作用于页面当前有效筛选（含锁定条件）所确定的对象范围。
  - AC-14-4：批量操作作用于页面当前有效筛选范围，不作用于被当前筛选排除的对象。
  - AC-14-5：筛选变更后列表、排序与导出立即使用新条件，不使用上一次的缓存结果。
  - AC-14-6：从任何入口进入都不放宽对象可见范围，越权对象不因筛选而出现。

#### R15 · 选择器去重与返回路径上下文
- 来源：BC-015；Instruction「Dashboard 的列表、分配弹窗和层级导航要保持筛选与上下文一致」
- 优先级：P1
- 需求描述：仓库、分类与分配类层级结果去重；取消选择后值不残留；父子关系与面包屑保持正确。加载、空结果、权限错误、网络错误以及返回列表都保留导航上下文。输入框与列表保持稳定宽度，不重叠或跳动；长值可以截断但要能确认完整关键词，清除输入仍然正常。
- 验收条件：
  - AC-15-1：反复选中再取消仓库或分类后，列表不出现重复选项。
  - AC-15-2：取消已选值后，该值不残留在筛选条件或选择状态中。
  - AC-15-3：切换分类层级时，父子关系与面包屑保持正确。
  - AC-15-4：加载、空结果、权限错误与网络错误状态下返回列表，仍保留原导航上下文。
  - AC-15-5：搜索词很长时输入框与列表宽度稳定、不重叠跳动，长值可确认完整关键词，清除输入后界面恢复正常。

**业务域：身份与内容安全**

#### R16 · 密码登录策略由商店统一控制
- 来源：Instruction「商户应能控制客户和员工是否使用密码认证；服务端认证流程、后台登录入口和配置页面必须读取同一生效策略」；BC-016
- 优先级：P0
- 需求描述：密码登录分三种模式：ENABLED 允许符合账户状态的受支持用户使用密码；CUSTOMERS_ONLY 只允许客户身份的密码能力；DISABLED 关闭密码认证及相关入口。CUSTOMERS_ONLY 下员工不能凭密码取得员工会话或后台权限，需要使用允许的外部认证或其他管理入口。DISABLED 同时拒绝密码登录、重置、设置或修改密码，以及可绕过策略的旧 token 路径，并返回明确原因。服务端认证流程、后台登录入口与配置页面必须读取同一生效策略；只有具有商店设置权限的身份可以修改。保存后认证请求立即读取新值；设置页展示当前模式与权限限制，登录页不显示禁用入口，没有外部方式时给稳定空态。加载或保存失败保留原生效值，不把未保存值当成功。外部认证独立按自身配置处理。
- 验收条件：
  - AC-16-1：ENABLED 模式下，账户状态允许的客户与员工均可使用密码登录。
  - AC-16-2：CUSTOMERS_ONLY 模式下，客户可以使用密码登录。
  - AC-16-3：CUSTOMERS_ONLY 模式下，员工凭密码不能取得员工会话或后台权限。
  - AC-16-4：DISABLED 模式下，密码登录被拒绝并返回明确原因。
  - AC-16-5：DISABLED 模式下，密码重置、设置或修改以及旧 token 路径同样被拒绝。
  - AC-16-6：修改并保存策略后，后续认证请求立即按新值处理。
  - AC-16-7：无商店设置权限的身份不能修改策略，返回权限错误且生效值不变。
  - AC-16-8：设置页展示当前生效模式与权限限制；登录页不显示被禁用的入口；没有可用外部认证方式时展示稳定空态。
  - AC-16-9：加载或保存失败时保留上次生效值，界面不把未保存值显示为成功。
  - AC-16-10：外部认证按自身配置继续可用，不因密码策略设置或失败而受影响。

#### R17 · 外部身份关联与 Google OIDC 离线授权
- 来源：Instruction「外部身份关联不能留下旧密码绕过通道」；BC-017
- 优先级：P0
- 需求描述：Google OIDC 在需要 refresh token 时使用兼容的离线授权方式，即使用 `access_type=offline`，而不是不兼容的 `offline_access` scope；其他 provider 按各自合同处理。授权失败可识别，但 token 与敏感身份信息不能出现在错误响应或不必要的前端持久化存储中。首次关联邮箱已有本地用户的场景时，清理或禁用能绕过外部身份策略的旧密码路径；同一 OIDC 身份后续登录应稳定，不被每次当成新身份。
- 验收条件：
  - AC-17-1：Google OIDC 离线授权请求使用 `access_type=offline`，且不发送 `offline_access` scope。
  - AC-17-2：其他 provider 的授权参数按其自身合同处理，不套用 Google 参数。
  - AC-17-3：授权失败返回可识别错误，错误响应与前端持久化存储中不含 token 或敏感身份信息。
  - AC-17-4：邮箱已有本地用户时首次关联后，可绕过外部身份策略的旧密码路径被清理或禁用。
  - AC-17-5：同一 OIDC 身份后续登录被识别为同一用户，不重复创建身份。

#### R18 · 富文本与外链的保存前校验
- 来源：Instruction「富文本和外链在保存前就要经过结构与安全校验」；BC-018
- 优先级：P0
- 需求描述：EditorJS 内容先校验结构，再清理 URL、链接属性与嵌套深度；未知或多余字段、非法 scheme、过深结构应被拒绝，不保存部分危险内容。http、https、mailto、tel 等合法链接按规则保留；新窗口外链具备安全的 `rel` 行为，不能通过 opener 控制来源页。不允许通过配置扩展协议白名单绕过限制。拒绝时错误指向字段、链接或深度问题，不伪装成保存成功；正常富文本、嵌套列表与常用链接仍能正常保存。
- 验收条件：
  - AC-18-1：正常富文本、嵌套列表与 http/https/mailto/tel 链接可以保存，并在读取时保持一致。
  - AC-18-2：`javascript:` 等非法 scheme 的链接被拒绝，保存失败且不落库。
  - AC-18-3：包含未知或多余字段的块被拒绝，不保存部分内容。
  - AC-18-4：超过约定嵌套深度的结构被拒绝，错误指向深度问题。
  - AC-18-5：新窗口外链带有安全 `rel` 行为，不能通过 opener 控制来源页。
  - AC-18-6：不存在可通过配置扩展协议白名单绕过校验的途径。
  - AC-18-7：拒绝时错误指向具体字段、链接或深度问题，界面不显示保存成功。
  - AC-18-8：校验失败时原有内容不被部分覆盖或部分写入。

#### R19 · 扩展安装、查询与历史数据迁移约定

  - AC-19-3：重复 identifier 的安装或更新被拒绝，已有扩展数据不被破坏。

#### R20 · 扩展表单响应的处理

#### R21 · 自托管商店的扩展目录

#### R22 · Webhook 同步与异步载荷的构建边界
- 来源：Instruction「Webhook 只做订阅实际需要的工作，允许异步处理的事件不要拖慢业务请求」；BC-022
- 优先级：P1
- 需求描述：同步订阅只解析实际选择的字段。允许异步处理的订单、草稿订单与履约事件在后台任务边界构建完整内容，业务请求不等待完整异步载荷。纯异步订阅不提前触发无关的同步通知，也不顺带多调用未需要的税务或配送服务。继续遵守既有调用次数、超时、重试与熔断上限，不通过重复解析放大负载（本轮不新增数值上限）。
- 验收条件：
  - AC-22-1：同步订阅只解析订阅中实际选择的字段，不构建未请求的内容。
  - AC-22-2：订单业务请求不因构造大批异步通知内容而长时间等待。
  - AC-22-3：异步事件在后台任务边界构建完整载荷并完成投递。
  - AC-22-4：纯异步订阅不触发无关的同步通知，也不多调用未需要的税务或配送服务。
  - AC-22-5：既有调用次数、超时、重试与熔断上限继续生效，不因重复解析而重复调用。

#### R23 · 事件投递的隔离、重试与状态展示
- 来源：Instruction「一个接收方失败不应阻断其他接收方」；BC-023
- 优先级：P0
- 需求描述：同一事件通知多个 App 时，单个 delivery 失败只影响对应 delivery，其他订阅继续，失败按策略重试。包括商品变体折扣价更新在内的已定义事件，满足触发条件时产生合同正确的一次通知，无实质变化的保存不重复触发。后台需要展示等待、成功、失败、重试中状态与错误；异步内容未生成不能当成成功。具备相关 App 或业务域权限时可单条重试，内容本身仍遵守 App 可见字段边界。保留既有 Webhook 失败告警，不扩展为 App Problems 功能。
- 验收条件：
  - AC-23-1：一个接收方失败时，其他已成功或进行中的订阅不被重做或阻断。
  - AC-23-2：失败的 delivery 按既有策略重试，重试过程与结果被记录。
  - AC-23-3：满足触发条件的已定义事件（含商品变体折扣价更新）产生一次通知；无实质变化的保存不重复触发。
  - AC-23-4：后台可区分等待、成功、失败与重试中状态，并显示错误信息。
  - AC-23-5：异步内容尚未生成时，其状态不显示为成功。
  - AC-23-6：具备相关 App 或业务域权限时可单条重试，无权限时被拒绝。
  - AC-23-7：重试与展示的内容不超出 App 可见字段边界。
  - AC-23-8：既有 Webhook 失败告警仍可用，且不引入 App Problems 的类型、字段、操作或问题列表。

#### R24 · 订单中的配送元数据快照
- 来源：Instruction「订单应保留创建时的配送元数据，不能因为后来修改或删除配送方式而改变历史事实」；BC-024
- 优先级：P0

  - AC-24-6：迁移后已有配送元数据仍可读，不重复生成记录、不丢数据；无元数据的历史记录返回稳定空值。

#### R25 · 元数据基础编辑保留，独立管理入口不交付

#### R26 · 执行前的输入校验与可分支的失败语义
- 来源：Instruction「公开 API 同样需要明确的输入、权限和失败语义，不能把请求通信成功误认为业务操作成功，也不能在失败时留下部分危险数据或泄露敏感信息」；BC-026
- 优先级：P0
- 需求描述：接口需要能区分传输成功、业务成功、没有结果与输入错误，GraphQL 返回 HTTP 200 不足以判断操作完成。数值、时间、分页、枚举、必填项与组合关系都在执行前校验：分钟、小时、天数等不得为负；Federation representations 不能为 null 或含 null 项；数组空项、错误类型与越界分页要有稳定错误。失败返回可分支处理的 field、code、message，不产生部分写入，也不把未知错误转成成功空列表。合法的单值、数组与组合查询继续可用；订单条件查询与用户关联订单查询返回准确结果与稳定分页。对象 ID、结账 token、UUID、渠道 slug 按各自类型使用，不能互换。金额、库存与状态变更依据最新对象状态执行幂等检查。
- 验收条件：
  - AC-26-1：业务成功、无结果与输入错误在响应中可区分，调用方不能仅凭 HTTP 200 判定操作完成。
  - AC-26-2：分钟、小时、天数等为负的输入被拒绝，返回可定位错误。
  - AC-26-3：必填项缺失或数组包含空项时请求被拒绝，返回稳定错误。
  - AC-26-4：Federation representations 为 null 或包含 null 项时返回稳定错误。
  - AC-26-5：越界分页返回稳定错误或稳定空结果，行为一致可预期。
  - AC-26-6：失败响应包含 field、code、message，调用方可分支处理。
  - AC-26-7：校验失败的请求不产生任何部分写入。
  - AC-26-8：未知错误不被转成成功空列表。
  - AC-26-9：合法的单值、数组与组合查询继续返回准确结果与稳定分页。
  - AC-26-10：对象 ID、结账 token、UUID 与渠道 slug 混用时返回稳定错误。
  - AC-26-11：金额、库存与状态变更依据最新对象状态执行幂等检查，重复请求不产生重复变更。

#### R27 · 弃用读取与已退出能力的明确错误
- 来源：Instruction「升级既要保护历史数据…不能把失败、尚未保存的设置或尚未执行的后台工作显示成成功」；BC-027
- 优先级：P1
- 需求描述：保留明确的弃用读取与替代路径；已不支持的能力返回不存在或迁移错误，不能返回没有解释的成功空响应。本轮不再承诺旧 Adyen、NP Atobarai 插件、`Payment.partial` 与旧数字商品接口，数字商品本身仍可通过 Apps 或现行方案提供。商品、礼品卡与 voucher 使用当前查询导出方式，旧导出 mutation 按弃用约定处理；草稿订单用 `voucherCode` 替代旧 `voucher` 输入。属性 `name`、`slug`、`type` 不能为空，App 安装的 `appName`、`manifestUrl` 必填。Core 的公开 schema、Dashboard 的生成客户端与错误映射、文档应一致，不能继续生成不支持的操作。迁移须能从空库执行，也要保留既有订单、交易、扩展、库存与元数据的业务含义。
- 验收条件：
  - AC-27-1：保留的弃用字段或输入仍可读取，并给出替代路径。
  - AC-27-2：旧 Adyen、NP Atobarai 插件、`Payment.partial` 与旧数字商品接口返回不存在或迁移错误，而非成功空响应。
  - AC-27-3：商品、礼品卡与 voucher 使用当前查询导出方式，旧导出 mutation 按弃用约定处理。
  - AC-27-4：草稿订单使用 `voucherCode` 输入；旧 `voucher` 输入按弃用约定处理。
  - AC-27-5：属性 `name`、`slug`、`type` 为空，或 App 安装缺少 `appName`、`manifestUrl` 时返回校验错误。
  - AC-27-6：Core 公开 schema 与 Dashboard 生成客户端及错误映射一致，不包含不支持的操作。
  - AC-27-7：迁移可从空库执行完成。
  - AC-27-8：迁移后既有订单、交易、扩展、库存与元数据的业务含义不变。

#### R28 · 查得出与改得动都要有对应权限
- 来源：Instruction「商户应能控制…服务端认证流程、后台登录入口和配置页面必须读取同一生效策略」与「不能在失败时留下部分危险数据或泄露敏感信息」；BC-028
- 优先级：P0
- 需求描述：员工删除、属性更新、App 安装、导出与敏感税务字段读取不能通过换查询入口绕过权限。有权限时合法员工应被真正删除（包括存在历史订单的情况），而不只是撤销员工标记；自删或无权限删除被拒绝。商品、礼品卡与 voucher 的导出受导出权限限制。结账与订单的相关私有元数据、用户等税务敏感字段遵循 `HANDLE_TAXES` 等权限，不向未授权身份泄露。客户、员工与 App 的对象范围、渠道与仓库可见性始终生效；没有权限不是「没有数据」，失败也不是「操作成功」。
- 验收条件：
  - AC-28-1：有权限时删除员工使该员工被真正删除（即使存在历史订单）；自删或无权限删除被拒绝。
  - AC-28-2：属性更新需要对应权限，更换查询或变更入口不能绕过。
  - AC-28-3：App 安装需要 App 管理权限，无权限时被拒绝。
  - AC-28-4：商品、礼品卡与 voucher 的导出受导出权限限制。
  - AC-28-5：未具备 `HANDLE_TAXES` 等权限的身份无法通过任何入口读取税务敏感字段与相关私有元数据。
  - AC-28-6：客户、员工与 App 的对象范围、渠道与仓库可见性在所有入口一致生效。
  - AC-28-7：无权限返回权限错误，不表现为空结果；失败不表现为成功。

**业务域：工作台一致性**

#### R29 · 配置加载与保存的上下文一致性
- 来源：Instruction「配置加载、编辑、保存和缓存更新必须围绕用户当前操作，不能用迟到的数据覆盖正在输入的内容」；BC-029
- 优先级：P1
- 需求描述：明确区分加载、已加载空数据、权限错误、网络错误与可重试状态；加载期间页面不崩溃或闪烁错误值。渠道、商店与商品数据到达时只回填与当前编辑上下文仍有关的字段，不覆盖正在输入的值。成功才更新相关缓存或重新读取服务端事实；失败保留原状态，不把失败值放入缓存，修正后可以重试。
- 验收条件：
  - AC-29-1：加载中、已加载空数据、权限错误、网络错误与可重试状态在界面上可区分。
  - AC-29-2：加载期间不显示错误的默认值，页面不崩溃或闪烁错误内容。

  - AC-29-5：保存失败时保留原状态，失败值不进入缓存，修正后重试可以成功。

#### R30 · 展示准确性与草稿订单动作可用性
- 来源：Instruction「重量、金额、媒体状态和订单时间展示应准确；草稿订单动作只在渠道和商品条件允许时可用，并说明不可用原因」；BC-030
- 优先级：P1
- 需求描述：重量按实际单位转换；媒体状态与折扣金额与 API 一致；订单日期分组遵守 locale 与 timezone，跨日期边界不归错组。媒体错误的正常状态展示不意味着重新引入异步图片专用回退体验。渠道停用、无可售商品或缺少必要配置时，草稿订单不能仍提供无效动作：禁用不适用的添加商品、完成等动作并解释原因，不发送明知不合法的请求；切换到满足条件的正常渠道后仍可操作。
- 验收条件：
  - AC-30-1：重量按实际单位正确转换与展示。
  - AC-30-2：媒体状态与折扣金额与 API 返回一致。
  - AC-30-3：订单日期按 locale 与 timezone 分组，跨日期边界不归错组。
  - AC-30-4：渠道停用或渠道内无可售商品时，草稿订单的添加商品、完成等不适用动作被禁用并说明原因，不发送请求。
  - AC-30-5：切换到满足条件的正常渠道后，相应动作恢复可用。
  - AC-30-6：媒体展示保留现有正常状态，不引入异步抓取与专用失败回退体验。

## 5. 其他

### 5.1 事实依据（基于现有代码仓库的核对结果）

以下为撰写本 PRD 时对 `/workspace/repos/` 基线的核对结论，用于说明需求起点与缺口，不代表任何已完成的交付结果：

1. **配送选项重算模型不存在。** 基线提供 `Checkout.shippingMethods`、`Checkout.deliveryMethod` 与 `CheckoutInfo.valid_delivery_methods` / `get_delivery_method_info()`，但没有「可用选项 + 当前选择」的统一重算返回结构；`checkoutComplete` 与 `checkoutDeliveryMethodUpdate` 通过 `clean_checkout_shipping` 做校验（`saleor/checkout/checkout_cleaner.py:24-63`），无独立的重算与失效原因区分步骤。R01/R02 为此新增能力，并保留 `shippingMethod`、`availableShippingMethods`、`checkoutShippingMethodUpdate` 的弃用读取语义。
2. **渠道-仓库直连的关系模型已存在**（`Channel.warehouses` / `ChannelWarehouse`，`saleor/warehouse/models.py:265-293`），但需要在商品查询、结账、订单、履约、草稿订单间统一语义，并保证未切换商店的既有行为不变（R03）。
3. **商品渠道可售性诊断不存在。** 基线只有 `ChannelsAvailabilityCard` 展示 `isPublished`、`publishedAt`、`visibleInListings`、`isAvailableForPurchase` 等字段，没有阻断/警告/不适用的分级诊断（R04）。结构化的先例是结账的 `Checkout.problems` 联合类型（`saleor/checkout/problems.py`）。
4. **自动完成已具备基础形态**：渠道已有 `automaticallyCompleteFullyPaidCheckouts` 布尔设置与 `automatic_checkout_completion_task`（`saleor/checkout/tasks.py:133-141`），但没有延迟与 cutoff 语义（R06）。
5. **礼品卡当前只是折扣式抵扣**：通过 `checkoutAddPromoCode` / `checkoutRemovePromoCode` 与 `Checkout.gift_cards`、`Order.gift_cards` 关联，`TransactionItem` 上没有礼品卡字段，也不存在把礼品卡作为支付方式的 mutation（R07/R08 为新增能力）。
6. **金额分解字段已存在但需保证一致性**：`totalAuthorized`、`totalCharged`、`totalRefunded`、`totalBalance`、`actions` 等字段与 Dashboard 的 `OrderPayment` / `OrderPaymentSummaryCard` 已在使用（R09/R10 要求一致性、边界与幂等）。
7. **根级交易查询不存在**：仅有单条 `transaction` 查询与订单/结账下的 `transactions` 子字段；现有 `TransactionFilterInput` 属于订单过滤，不支持按支付服务商参考号、交易 ID、App 标识筛选（R11 为新增能力）。
8. **搜索实现分散**：订单与商品使用全文检索与 RANK 排序，礼品卡使用 SearchVector，客户/员工使用 `search_document` + ILIKE，结账使用 ILIKE，页面使用 trigram；搜索更新存在「同步内联」与「dirty 标记 + 周期任务」两派做法（R12/R13 保留现状并明确边界）。
9. **EditorJS 清理偏弱**：基线仅以黑名单禁止 `javascript:`，无嵌套深度限制，也不处理 `rel`（`saleor/core/utils/editorjs.py:8`）；R18 要求结构校验、白名单 scheme、深度限制与安全 `rel`。
10. **扩展字段存在不一致**：Dashboard 的扩展查询请求 `mountName`/`targetName`/`settings`，而 Core 的 `AppExtension` 类型提供的是 `mount`/`target`，且没有扩展表单响应约定（R19/R20 要求对齐与迁移适配）。
11. **扩展目录依赖外部 marketplace 地址**，自托管部署需要不依赖该地址的可用体验（R21）。
12. **Webhook 载荷构建**：同步订阅在请求内构建载荷，异步在调用点构建并落库后由任务发送；投递状态仅有 `PENDING/SUCCESS/FAILED`，无「重试中」的独立状态（R22/R23）。
13. **配送元数据快照不存在**：订单以 `shipping_method` FK 与 `shipping_method_name` 去规范化字段记录配送方式，外部运费标识存放在 private metadata（`external_app_shipping_id`），没有 public/private 元数据快照（R24 为新增能力）。
14. **Dashboard 侧缺口**：无独立密码登录设置页；草稿订单在不适用时隐藏「添加商品」按钮而非禁用并说明原因，「完成」按钮不受渠道与商品条件限制；订单列表无日期分组，日期渲染只使用 locale；无重量单位换算工具；无媒体处理/失败状态展示（R16/R29/R30）。

### 5.2 产品决策

- **一致性优先于新增功能。** 同一事实（可售性、库存、金额、支付状态、配送选择）在不同入口必须一致；当一致性与局部便利冲突时，以服务端事实为准。
- **兼容与安全不可用「静默降级」换取。** 失败必须可区分，未保存的设置、未执行的异步工作与失败的操作不得显示为成功。
- **未切换/未配置即沿用既有行为。** 库存策略、自动完成策略、旧客户端标识、旧字段读取均遵循「未显式切换则保持原行为」的原则，避免升级即改变历史含义。
- **权限与状态双约束。** 有权限不代表任何状态都能操作；可操作金额以当前真实余额为限。
- **不新增数值约定。** 本 PRD 不引入新的最终一致性窗口、重试次数、超时或熔断阈值，一律沿用系统既有约定。
