# PRD：Saleor 商家经营与应用接入升级

版本：1.0
责任：产品
状态：需求范围与验收条件已定义

## 1. 业务背景与目标

商家需要在引入更多外部应用的同时，连续处理已有订单、账号、库存、数字权益和资金。本次升级覆盖 Saleor 核心 API 与商家 Dashboard，目标是：

- 让运营可靠维护经营资料、富内容、图片和搜索索引，避免未编辑字段被清空、危险内容进入系统或单条异常阻断任务。
- 让仓储和渠道运营按渠道选择库存来源规则，并独立控制外部运费报价缓存与过滤，且不复制共享仓库库存或改变税费、支付规则。
- 把礼品卡实扣与退款纳入统一交易追踪，提供独立交易查询，同时安全退出指定旧支付插件并保留历史售后能力。
- 通过实例级密码策略控制本地密码能力，保证外部身份、订单归属及管理员恢复路径连续。
- 补齐五类详情 Widget、应用故障状态和按需变化通知，使应用最小化取数、故障不阻断原生操作、旧订阅可渐进迁移。
- 在维护窗口内以影响盘点、备份、迁移、对账、恢复和开放后验证为门槛，避免丢失新事实、重复资金动作或中断历史数字权益。

本 PRD 定义目标行为与可判定验收条件，不表示能力已经部署、静态 Base 已通过测试或生产收益已经验证。

## 2. 用户与场景

| 用户类型 | 典型任务 |
| --- | --- |
| 商家管理员 | 维护经营资料与权限；查看密码策略、应用状态和升级影响；批准切换与恢复。 |
| 内容运营 | 编辑商品、分类、集合、页面、属性及翻译内容；导入外部图片；处理保存和索引失败。 |
| 仓储运营 | 为渠道选择库存模式、关联并排序仓库；在切换后继续分配、履约、退货与补货。 |
| 渠道运营 | 配置外部报价缓存和配送过滤；理解配置变更对候选配送方式的影响。 |
| 客服 | 从订单、交易或礼品卡定位实付来源与退款状态；保障顾客继续访问已购数字内容。 |
| 财务 | 对账礼品卡、外部交易、旧 Payment 和退款；处理部分成功、待核对及人工结果登记。 |
| 员工账号使用者 | 按当前账号身份和实例策略使用密码或外部身份登录，并获得明确恢复指引。 |
| 顾客 | 继续登录、购物、退款并访问合法已购数字内容；不因后台升级丢失账号或订单归属。 |
| 应用集成方 | 声明详情扩展；按事件、渠道和最少字段订阅；渐进迁移旧字段和固定 payload。 |
| 运维与实施 | 生成影响报告，验证外部路径，执行受控迁移、索引重建、对账、恢复和开放后检查。 |
| QA | 在受控本地环境覆盖多渠道、共享资源、混合资金、异常历史数据及新旧契约的可观察场景。 |

## 4. 需求条目

### R01 · 统一维护经营资料并防止误清空
- 来源：`query.md`「经营资料与检索」：“统一维护展示名称、介绍/页头、公司名称与地址、邮件发件信息和公共/私有 metadata”；`business-conversations.md`「资料保存：未编辑不等于清空」：“省略就保留，显式清空与不合法空值要区分”“信息和地址分别保存、分别反馈”。
- 优先级：P0
- 需求描述：在 API 与 Dashboard 统一提供 Shop 展示名称、介绍/页头、公司名称与经营地址、默认邮件发件名称/地址及公共/私有 metadata 的读取和维护。字段省略、显式清空和非法空值必须语义不同；资料与地址独立提交、独立反馈。展示名称不得改变域名，公司名称使用经营地址的公司名称字段。修改要求 `MANAGE_SETTINGS`，私有 metadata 不得向匿名用户或无权订阅者暴露。
- 验收条件：
  - AC-01-1：仅提交发件信息时，既有经营地址、展示名称、介绍及 metadata 保持不变，且不会新增重复地址。
  - AC-01-2：按 API 已定义的可空字段显式提交 `null` 时可清空；省略字段保留旧值；不允许清空的空值返回对应字段错误并保留旧值。
  - AC-01-3：资料保存成功而地址校验失败时，Dashboard 分区显示各自结果，保留失败输入，不把结果显示为整体成功。
  - AC-01-4：清空经营地址必须由显式操作和确认触发，且不修改历史订单地址快照。
  - AC-01-5：非法邮箱、含换行的发件名称和不符合国家规则的地址分别在对应字段或区域报错。
  - AC-01-6：无 `MANAGE_SETTINGS` 的主体不能修改；匿名 Shop 查询和无私有 metadata 权限的通知 payload 不含私有字段。

### R02 · 兼容并安全处理新旧 EditorJS 内容
- 来源：`query.md`「经营资料与检索」：“兼容旧字符串列表与新嵌套对象列表，保留合法文字、层级、顺序和样式”；`business-conversations.md`「内容编辑：新旧内容都要可读」：“非法结构的新提交应定位字段错误并保留旧值”“预览及保存后都不能执行危险内容”。
- 优先级：P0
- 需求描述：商品、分类、集合、页面以及共用 EditorJS 处理的属性和翻译须同时支持旧字符串列表与包含 `content`、嵌套 `items` 和元数据的新对象列表。解析、清理、展示、保存、翻译和搜索纯文本应遵循同一兼容规则，保留合法层级、顺序、样式、链接及可见文字；危险协议、脚本和事件属性在所有相关字段中一致清理。
- 验收条件：
  - AC-02-1：旧字符串列表和多层对象列表经保存再读取后，合法文字、层级、顺序、样式、链接及可选元数据保持一致。
  - AC-02-2：空段落、空列表、空列表项或缺少可选字段不会使其后的合法内容丢失，也不会导致详情、保存或索引任务崩溃。
  - AC-02-3：新提交结构非法时返回可定位字段错误，原值保持不变且 Dashboard 保留用户输入。
  - AC-02-4：存量异常内容只展示安全可读部分并产生可定位告警，不自动覆盖原文，也不阻断同页或同批次其他对象。
  - AC-02-5：文本、列表、图片地址/说明和嵌入内容中的脚本、事件属性及危险协议在预览与保存后均不可执行，合法链接仍可用。
  - AC-02-6：搜索纯文本按阅读顺序包含各层可见文字且不含可执行 HTML；重建派生内容时保留原文备份和异常清单。

### R03 · 安全兼容外部图片导入
- 来源：`query.md`「经营资料与检索」：“支持带查询参数、无扩展名以及不支持 HEAD 但 GET 可用的合法图片源，不能以兼容为由访问内部资源或关闭安全过滤”；`business-conversations.md`「图片与搜索」：“默认下载上限 20 MiB、4000 万像素、总下载预算 20 秒”“首版不自动跟随重定向”。
- 优先级：P0
- 需求描述：商品媒体及同一下载机制覆盖的应用品牌图，以受限 GET 返回内容的实际解码结果判定图片，不依赖扩展名、查询参数、HEAD 成功或单独的 Content-Type。保持 SSRF、协议、大小、像素、时间和重定向边界；失败不得替换既有图片或留下媒体记录、孤立文件。
- 验收条件：
  - AC-03-1：合法公网 HTTP/HTTPS 图片在 URL 带查询参数、无扩展名或 HEAD 不可用但 GET 可用时，仍可通过实际内容解码成功导入。
  - AC-03-2：回环、私网、链路本地、云元数据地址、DNS 解析绕过及非 HTTP/HTTPS 源均被拒绝；鉴权内部资源不会被代为访问。
  - AC-03-3：默认超过 20 MiB、4000 万像素或总下载预算 20 秒的响应失败；部署可收紧或有限调整，但不能配置为无限。
  - AC-03-4：3xx 不被自动跟随，并提示提供最终公开直链；普通网页、损坏内容和不支持格式返回可理解字段错误。
  - AC-03-5：超时、非成功响应、解码失败或超限后，不产生成功媒体记录或孤立文件，Dashboard 保留输入、既有图片和重试入口。
  - AC-03-6：日志中的 URL 敏感查询参数被隐藏；已有视频/oEmbed 和本地上传支持格式不因本改动失效。

### R04 · 可恢复地更新既有搜索和新增交易检索
- 来源：`query.md`「经营资料与检索」：“改善已有商品、订单、顾客、礼品卡搜索及新增交易查询的更新可靠性，不引入新搜索产品”；`business-conversations.md`「图片与搜索」：“单次正常更新提交后 60 秒内可检索新值”“索引失败要可见、可重试，中断后能续跑”。
- 优先级：P0
- 需求描述：沿用现有搜索技术和对象语义，可靠更新商品、订单、顾客、礼品卡索引，并为交易定位提供精确查询能力。任务须可观测、可续跑和幂等重试；异常单条不能卡住其他对象，并发编辑不得被旧快照覆盖。权限、渠道隔离、空查询行为和私有字段边界保持不变。
- 验收条件：
  - AC-04-1：标准本地验收环境中，正常提交嵌套内容、富文本属性、关联属性/页面名称、SKU、顾客信息或交易参考号变化后，60 秒内可按既有语义检索新值。
  - AC-04-2：标点、引号、中文及边界内长输入不会导致服务端错误，空查询保持对象原有行为。
  - AC-04-3：索引失败可查看失败对象和原因并重试；任务中断可续跑，单条异常不阻断其他对象。
  - AC-04-4：全量重建覆盖已有非空旧索引并在重建期间保持查询可用；并发新编辑不会被旧快照覆盖或遗失待更新状态。
  - AC-04-5：重建报告给出处理总数、失败对象和重试结果，索引及报告不泄露私有 metadata 或越权字段。

### R05 · 按渠道选择库存来源模式
- 来源：`query.md`「库存、运费与交付」：“每个渠道可以选择‘兼容配送区域’或‘仅按渠道仓库’的库存模式”；`business-conversations.md`「渠道库存」：“升级和未显式选择的新渠道默认‘兼容配送区域’”“共享库存的并发成交也必须受同一真实存量约束”。
- 优先级：P0
- 需求描述：为每个渠道新增可读写库存模式：`兼容配送区域` 保留现有经营规则，`仅按渠道仓库` 只从关联当前渠道的仓库计算可售、校验、预留、分配和补货。升级与未显式选择的新渠道默认兼容模式。Dashboard 展示模式、仓库关系、顺序和切换影响，保存要求渠道管理权限。
- 验收条件：
  - AC-05-1：既有渠道升级后及未指定模式的新渠道均为兼容模式，并继续要求原配送区域关系。
  - AC-05-2：渠道管理员可在 API 和 Dashboard 读写模式；无权主体被服务端拒绝而不只是隐藏控件。
  - AC-05-3：仅渠道仓库模式下，库存来源不受配送区域或国家关系决定，但国家、税费、地址、配送方式及自提资格规则继续生效。
  - AC-05-4：可售数量继续遵守在库减分配减有效预留，并保留库存跟踪、预售、仓库顺序、分配策略和私有仓规则；无关联仓库时，跟踪库存且非预售商品不可购买。
  - AC-05-5：切换模式或解除仓库关系不重写已有订单有效分配、履约和退货回库来源；未完成结账在下次报价、预留或完成时按新规则重验。
  - AC-05-6：多个渠道共享同一仓库时不复制库存，并发成交共同受真实存量约束，不重复扣减或释放预留。
  - AC-05-7：切到仅渠道仓库模式前展示可能扩大可售区域的摘要并要求确认。

### R06 · 渠道级外部运费缓存与过滤
- 来源：`query.md`「库存、运费与交付」：“渠道还要能分别控制外部报价缓存时长和外部配送过滤”；`business-conversations.md`「外部运费」：“范围 0—86400，0 表示不缓存；未指定时为 43200 秒”“过滤开启但失败或熔断时，受影响方式不能成交”。
- 优先级：P0
- 需求描述：每个渠道独立配置外部报价缓存秒数和外部配送过滤开关。缓存范围 0 至 86400，0 为不缓存，未指定默认 43200；过滤默认开启。订单和结账使用所属渠道配置。关闭过滤只跳过外部过滤，不跳过本地校验、外部报价、税费或支付通知规则。
- 验收条件：
  - AC-06-1：API 与 Dashboard 可读取和保存两项配置，越界缓存值返回字段错误，保存结果明确；无渠道管理权限时服务端拒绝。
  - AC-06-2：新建或无显式配置渠道使用 43200 秒和过滤开启；设置 0 后成功报价也不跨请求缓存。
  - AC-06-3：缓存按应用/Webhook、渠道及报价上下文隔离；地址、数量、金额、折扣、币种、订阅所选字段、应用或相关配置变化均不命中旧报价。
  - AC-06-4：超时、错误和非法响应不作成功缓存；合法空列表可缓存；报价必须符合渠道币种、非负金额、标识和精度要求。
  - AC-06-5：报价故障时保留其他合法方式；无方式时明确不可配送并可重试，不自动变成免费运费，也不无限续用过期报价。
  - AC-06-6：过滤开启且过滤请求失败或熔断时，受影响方式不可成交；只有商家显式关闭过滤才恢复未被本地规则排除的候选方式。
  - AC-06-7：成交前重验所选方式，涨价进入既有价格变更确认；已生成订单保留原运费快照。

### R07 · 退出旧数字内容 API 并保留历史权益
- 来源：`query.md`「库存、运费与交付」：“退出范围为 `digitalContent`、`digitalContents` 及其创建、更新、删除、生成下载地址的旧操作……历史文件和权益不随接口退出而删除”；`business-conversations.md`「数字交付」：“已购内容仍要通过只服务历史权益的兼容下载路径访问”。
- 优先级：P0
- 需求描述：从目标 schema 删除明确列出的旧数字内容查询、mutation、变体和订单行旧字段、旧下载默认设置及无引用专属类型，并移除 Dashboard 对应入口和调用；不删除普通数字商品、非配送类型、文件属性、历史文件或已购权益。提供只服务历史权益的兼容下载路径和新销售切换门槛。
- 验收条件：
  - AC-07-1：目标 schema 不再暴露 `digitalContent`、`digitalContents`、旧创建/更新/删除/下载地址操作及明确关联字段和专属类型，Dashboard 构建产物不再请求它们。
  - AC-07-2：普通数字商品、非配送类型、文件属性、礼品卡、订单履约及未整体弃用 API 仍保留。
  - AC-07-3：维护前输出旧字段消费者清单、替代流程和 schema 差异；仍有未迁移消费者时不得越过删除门槛。
  - AC-07-4：历史有效下载按原剩余次数和期限访问；过期或耗尽继续拒绝，无到期权益不被新增期限，且不能猜 ID 越权或形成永久公开文件。
  - AC-07-5：受控导出与恢复覆盖文件、校验和、商品/变体/订单行关联、token、期限及使用次数；核对不一致时阻断切换，恢复不重复发权益或重置已用次数。
  - AC-07-6：已付款未交付订单在切换前签发权益或完成经验证交接；新数字订单仅在已验证的既有履约应用/外部服务可用时销售，否则阻断相关新销售而不影响历史下载和无关商品。

### R08 · 将礼品卡实扣纳入平台交易账本
- 来源：`query.md`「资金追踪与售后」：“成功支付时，每张实际扣款的卡都有平台交易和扣款事件”；`business-conversations.md`「收款退款」：“多卡按创建时间、再按 ID 排序消耗”“支付应用只处理扣除礼品卡后的剩余应付”。
- 优先级：P0
- 需求描述：保留加卡、移卡入口和成交扣减时机，在成功支付时为每张实际扣款礼品卡创建平台来源 `TransactionItem` 和扣款事件，关联订单、结账、原卡及来源。礼品卡按确定顺序消耗，是支付而非折扣；余额、事件、订单实付和结账结果须原子一致。
- 验收条件：
  - AC-08-1：报价、加卡或失败结账不产生成功扣款交易；成功成交后，每张实际扣款卡恰有一条平台交易和对应扣款事件。
  - AC-08-2：多卡按创建时间、再按唯一 ID 稳定排序；单卡扣款不超过有效余额或剩余应付，且仅激活、未过期、同币种卡可消费。
  - AC-08-3：同一结账重复请求、并发完成或异步重试不会重复扣款或重复创建逻辑交易；不同结账并发不能超用同一卡余额。
  - AC-08-4：支付应用只收到扣除礼品卡后的剩余应付；全额礼品卡按现有订单确认配置成交，不伪造 PSP 交易。
  - AC-08-5：统一实付只计一次礼品卡金额，不再叠加旧补偿字段；礼品卡不改变税基。
  - AC-08-6：Dashboard 展示掩码卡号、币种及平台来源；外部应用不能冒充平台礼品卡来源，无权主体不能获得完整卡码或他人信息。

### R09 · 按真实资金来源执行幂等退款
- 来源：`query.md`「资金追踪与售后」：“礼品卡部分或全额退款由平台退回原卡，不向第三方支付服务商请求该部分退款；混合支付按真实来源处理”；`business-conversations.md`「收款退款」：“混合退款须明确各来源金额”“重复请求返回原结果”。
- 优先级：P0
- 需求描述：把礼品卡退款整合进现有订单交易与退款入口。退款按原实扣来源拆分：礼品卡部分由平台恢复原卡余额，外部部分才请求对应支付服务；全过程以稳定幂等标识跟踪请求、处理中、部分成功、成功和失败。
- 验收条件：
  - AC-09-1：客服可查看各来源实付、已退、处理中、剩余可退、原因与事件；省略金额取剩余可退，显式金额必须为正且符合币种精度。
  - AC-09-2：累计已退加处理中不超过各来源实扣；不同币种不相加，礼品卡部分不会向第三方支付服务发退款请求。
  - AC-09-3：重复提交、并发请求或异步重试使用同一幂等标识时返回原结果且不多退；取消订单不会隐式重复退款。
  - AC-09-4：混合退款一方成功另一方失败时保留真实部分成功，重试只处理失败部分；外部成功而本地落账失败进入补偿或人工处理状态，不重复请求外部资金。
  - AC-09-5：只有余额恢复并记录成功事件后礼品卡退款才显示成功；审批通过或排队不等于成功。
  - AC-09-6：原卡过期或停用仍可退回余额但不激活、不延期；找不到原卡则明确失败且不转现金，有资金记录的卡不能普通删除。
  - AC-09-7：退款要求 `HANDLE_PAYMENTS`，查看订单另校验订单权限；修改卡余额或状态要求 `MANAGE_GIFT_CARD`。

### R10 · 提供分页交易查询与财务定位入口

### R11 · 归一历史账务而不重复资金动作
- 来源：`business-conversations.md`「历史账务与资金定位」：“可信扣款/退款证据可形成带迁移标识的账务归一记录，不再次扣余额或发消费/退款通知”“证据不足保留只读旧账和‘待核对’”。
- 优先级：P0
- 需求描述：升级前盘点旧 `Payment`、`TransactionItem`、礼品卡事件和订单补偿；仅依据可信证据建立带迁移标识的归一映射。迁移支持分批、续跑和幂等重跑，不强制转换全部历史 `Payment`，不把同一资金事实变成两笔可操作资金。
- 验收条件：
  - AC-11-1：盘点报告按订单、来源和币种区分已扣、已退、未退及证据不足，并保留旧记录引用。
  - AC-11-2：可信记录归一时不再次扣/加礼品卡余额、不请求外部资金、不发送新的消费或退款业务通知。
  - AC-11-3：同一订单的旧支付和新交易并存时，同一笔钱只能有一个可操作来源；维护窗口后不会双轨扣卡。
  - AC-11-4：任务可分批、续跑并幂等重跑，输出审计映射，并按币种核对卡余额、订单实付/已退和来源关联。
  - AC-11-5：证据不足记录保持只读和“待核对”，不得根据当前余额推断成功交易或开放自动退款；审核后的人工映射保留操作者、依据和时间。

### R13 · 实例级三态密码策略
- 来源：`query.md`「登录与账号连续性」：“`ALL` 允许所有用户使用密码，`CUSTOMERS_ONLY` 只允许非员工使用密码，`DISABLED` 禁用所有用户本地密码登录”；`business-conversations.md`「密码策略」：“策略由实例部署配置控制，首版 Dashboard 只展示及说明、不在线修改”。

- 验收条件：

  - AC-13-2：限制覆盖登录、设置/修改密码、重置邮件、带密码注册和员工密码邀请，禁止写入时原子拒绝且不产生局部更新。

  - AC-13-4：Dashboard 对受限用户不显示密码和找回入口，无外部方式时提示联系管理员；服务端对直接调用同样拒绝。
  - AC-13-5：授权应用 token、外部认证、无密码顾客注册及匿名购物不因密码策略禁用，原有激活、确认、节流、CSRF 和权限规则继续生效。
  - AC-13-6：未知配置值导致启动或配置预检失败并列出合法值；Dashboard 只读展示当前值和影响。

### R14 · 策略切换时保持账号连续性并阻断绕过

- 验收条件：

  - AC-18-5：现有 Shop、订单、商品、变体、仓库、渠道、礼品卡等事件继续可订阅；新增事件名在 schema、Manifest、创建/更新、事件列表、样例和 Dashboard 中一致。

### R19 · 保证通知语义、安全与可靠投递
- 来源：`query.md`「应用使用与变化通知」：“私有 metadata、员工信息及渠道隔离不因通知放宽，完整卡码、密码和凭证不得进入新增通知”；`business-conversations.md`「变化通知」「订阅过渡」：“失败、回滚、值未变……不产生新的逻辑更新”“异步投递按至少一次处理”。
- 优先级：P0
- 需求描述：所有新增和受影响通知以已提交事实为准，按最小领域权限和渠道隔离生成 payload；异步投递采用可追踪的至少一次语义，同一逻辑事件具有稳定标识。过渡期保留 metadata 触发的原通用更新，并说明可能与专用事件并存。
- 验收条件：
  - AC-19-1：失败、回滚、值未变或删除不存在 key 不产生新逻辑事件；批量部分失败只通知成功对象，同次提交同对象同类变化仅一个逻辑事件。
  - AC-19-2：payload 不包含订阅者无权字段、越权渠道、私有 metadata、无关员工信息、完整卡码、密码或凭证。
  - AC-19-3：事件包含稳定标识、发生时间、对象及可比较版本/序号；不承诺全局有序，网络重试可重复投递同一事件标识。
  - AC-19-4：提交成功后可靠登记异步事件，worker 崩溃不丢已确认变化；失败有限重试，耗尽后可见并可由有权用户重试，排队不显示为送达。
  - AC-19-5：停用后不登记新投递，重新启用只恢复明确未成功范围，不无提示重放全部历史；同步重试不得重复资金动作。
  - AC-19-6：删除或过期对象的通知可由快照或删除标识解析，不因当前对象不存在无限重试。
  - AC-19-7：过渡期 metadata 变化仍触发既有通用更新，并可同时产生专用事件；文档要求消费者按事件类型和稳定标识处理。

### R20 · 受控迁移、对账、恢复与开放
- 来源：`query.md`「范围与非目标」：“先有影响报告和外部登录/支付/履约路径验证，备份数据库、媒体、应用配置及必要密钥”；`business-conversations.md`「受控切换与恢复」：“维护时停止入口写入、暂停或排空任务”“不可直接回滚旧数据库抹掉新资金”。
- 优先级：P0
- 需求描述：以允许停机的维护窗口交付，不承诺无停机。实施必须提供不含明文密钥的影响报告、外部路径预检、完整备份、可续跑迁移、对账、恢复演练和开放后验证；维护中保护写入、回调和待投递事件，版本固定到交付源码或镜像摘要。
- 验收条件：
  - AC-20-1：切换前报告覆盖账号、四类插件及渠道、数字字段/固定 payload 消费者、历史资金、数字权益、索引与外部登录/支付/履约路径；未知实际规模和证据明确标为依赖而非推定通过。
  - AC-20-2：备份覆盖数据库、媒体、应用配置、必要密钥和构建版本，并验证可恢复一致性；报告和日志不含明文密钥。
  - AC-20-3：维护期间停止相关入口写入，暂停或排空任务，记录在途支付回调和待投递事件；回调可持久接收或已验证发送方重试，不吞资金结果。
  - AC-20-4：API、worker、Dashboard 及生成代码固定到同一目标 schema 和可追溯版本/摘要，不以未知来源 `latest` 作为交付证据。
  - AC-20-5：迁移、历史权益核对、按币种资金对账、必要索引重建及 P0 验收完成后才开放流量；每项有结果或明确失败原因。
  - AC-20-6：开放后出现新订单或外部资金动作再发现故障时，先暂停、保留增量并对账，再前向修复或可重放恢复，不回滚旧数据库抹除新事实。
  - AC-20-7：恢复记录责任人、检查、日志与验证；维护时长和 RTO 通过后续演练测量，不在本 PRD 虚构生产承诺。
