# QA Rubric Step 1：固定基准与读取候选

## 这一步是做什么的

第一步的目标不是判断候选测试是否覆盖 Golden，也不是判断候选是否写出了相反预期，而是先把后续评测所依赖的输入和基准固定下来。

本步骤包含两项工作：

1. 从 Golden 测试材料中整理、去重并固定稳定的业务检查点，形成后续覆盖评测使用的 `G` 编号；
2. 对候选 `test-cases.csv` 做轻量读取、定位和可理解性检查，确认哪些测试用例可以可靠地交给后续步骤评估。

本步骤的产出是：

- 一份固定的 Golden 检查点表；
- 一份候选测试用例读取和定位表；
- 一份格式、读取范围和参考问题清单；
- 一份追加到 `evaluation-worklog.md` 的可追溯记录。

本步骤完成后，下一步才能检查候选是否覆盖 Golden，以及是否存在相反预期。本步骤本身不计算覆盖率、不判断冲突、不输出最终结论。

# QA Rubric Step 2：覆盖检查与相反预期检查

## 这一步是做什么的

第二步的目标是基于第一步已经固定的 Golden 检查点和已经完成读取定位的候选测试用例，分别回答两个问题：

1. 候选测试是否真正覆盖了 Golden 要求的业务场景；
2. 候选测试是否在相同条件下写出了与 Golden 相反的预期结果。

本步骤合并原 Rubric 中的：

- W3：检查 Golden 测试是否覆盖全面；
- W4：检查是否写出了相反预期。

本步骤的关键原则是：

- W3 从 Golden 检查点出发，逐项寻找候选覆盖证据；
- W4 从候选全部测试用例出发，反向检查是否存在冲突；
- 找到一条正确测试，不能抵消另一条相同条件下的相反预期；
- 条件不同不构成冲突；
- 少写副作用属于覆盖缺项，不自动判定为相反预期；
- 新增但不在 Golden 范围内的场景记录为参考范围外，不因未被 Golden 收录而扣覆盖分；
- 本步骤只形成覆盖初判和冲突记录，不做最终复核、最终计数或最终报告。

本步骤完成后的产出是：

- 每个 G 检查点的覆盖初判；
- 每个覆盖初判的候选证据和缺失说明；
- 全部候选用例的审阅去向；
- 去重前的相反预期冲突记录；
- 参考范围外用例和未决问题清单；
- 追加到 `evaluation-worklog.md` 的可追溯记录。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

按照 G 编号逐个检查固定的 Golden 检查点。

对每个 G，审阅候选中所有可能相关的测试用例，并核对以下三件事：

1. 条件是否对应；
2. 是否真正执行了需要验证的业务操作；
3. 是否检查了全部关键结果和必要副作用。

一、条件对应性

核对至少包括：

- 身份；
- 权限；
- 模式；
- 对象状态；
- 数据状态；
- 关键时序；
- 资源或对象范围；
- 正常、异常、越权、边界等场景区别。

函数名、接口路径、内部对象名或具体数值不同，不要直接判定为不等价。只有当这些差异改变了业务对象、关键边界、身份、权限、状态或结果时，才影响等价性。

二、操作真实性

确认候选是否真的触发了 Golden 要求验证的行为，而不是只：

- 查看按钮；
- 检查页面是否存在；
- 检查错误消息；
- 检查对象 ID；
- 声称覆盖某个 AC；
- 读取一个与业务变化无关的字段。

必须确认候选实际执行了对应业务操作。

三、关键预期完整性

确认候选是否验证了 Golden 要求的全部关键结果和必要副作用，例如：

- 成功或拒绝；
- 返回值；
- 状态变化；
- 数据保存；
- 数据不变；
- 权限边界；
- 金额变化；
- 快照稳定性；
- 资源最终可读取；
- 必要的持久化、回读或关联对象变化。

“结果正常”“处理成功”“返回正确”等笼统表述，如果无法知道观察对象和判断条件，不足以证明完整覆盖。

四、允许一对多和多对一

- 一个候选 TC 可以覆盖多个 G；
- 多个候选 TC 可以共同覆盖一个 G；
- 多个 TC 联合覆盖时，必须具有相同场景的兼容前提和真实验证关系；
- 不能把不同身份、不同权限、不同对象状态或不同操作拼成一个覆盖结论；
- 重复 TC 不增加覆盖信用。

例如：

- 无权请求返回拒绝；
- 有权请求成功保存数据；

不能拼成“无权请求数据不变”，除非候选确实在无权条件下检查了数据不变。

五、W3 初判状态

每个 G 必须记录以下五种状态之一：

- 完整覆盖（初判）；
- 部分覆盖；
- 遗漏；
- 明确冲突；
- 不可判定。

状态含义：

完整覆盖（初判）：

- 条件对应；
- 操作真实发生；
- 全部关键预期和必要副作用都有实质证据；
- 但仍须经过 W4 冲突检查。

部分覆盖：

- 有对应测试；
- 但缺少必要条件、操作或关键结果；
- 必须明确写出已覆盖内容和缺失内容。

遗漏：

- 审阅完整可靠读取范围后，没有任何实质测试该场景；
- 只有主题、编号、标题或 AC 引用，不算覆盖；
- 必须记录查阅范围和最接近但不成立的用例；
- 没有对应 TC 时写“无”。

明确冲突：

- 已发现候选在相同条件下写出与 Golden 相反的预期；
- W4 统一记录冲突后，不能因为存在另一条正确 TC 而恢复为完整覆盖。

不可判定：

- Golden 参考问题或候选不可读范围妨碍判断；
- 必须说明具体缺失或冲突证据；
- 不得擅自当作遗漏、部分覆盖或完整覆盖。

六、W3 记录格式

对每个 G 至少记录：

| 字段 | 内容 |

| G 编号 | 固定的 Golden 检查点编号 |
| Golden 条件/操作/预期 | 保留关键业务含义及来源 |
| 对应 TC | 一个、多个或无 |
| 候选位置 | 文件和 CSV 逻辑记录序号/TC 标签 |
| 条件判断 | 是否对应及理由 |
| 操作判断 | 是否真实触发及理由 |
| 结果判断 | 已验证和缺失的关键预期 |
| W3 初判 | 五种状态之一 |
| 证据 | Golden 与候选原文 |
| 问题 | 缺项、歧义或限制 |

完成 W3 后，不得只围绕已匹配的 TC 继续判断。必须从候选 CSV 的全部可靠读取用例出发，逐条审阅，包含：

- W3 已匹配的用例；
- W3 未匹配的用例；
- 额外新增的用例；
- 只填写了主题、AC 编号或覆盖编号的用例；
- 可能属于参考范围外的用例。

W4 的目的，是发现 W3 从 Golden 出发容易漏掉的反向冲突。

例如：

- TC001 正确写明无权读取被拒绝；
- TC004 却在相同无权条件下要求返回完整私有值；
- 不能因为 TC001 正确，就忽略 TC004 的冲突。

一、确认明确冲突必须具备四项证据

每个明确冲突必须同时记录：

1. Golden 的条件和预期原文；
2. 候选的条件、操作和相反预期原文；
3. 为什么双方属于同一身份、模式、对象状态和操作；
4. 为什么两种预期不能同时成立。

如果缺少其中任何一项，不得直接判定明确冲突，应记录为不可判定或待复核。

二、区分冲突与非冲突

按以下规则处理：

| 情况 | 处理 |
|---|---|
| Golden 规定无权读取私有信息不泄漏，候选要求相同条件下返回完整私有值 | 明确冲突 |
| Golden 规定无权拒绝，候选规定有权身份可读 | 条件不同，不冲突 |
| 候选少写一个必要副作用检查 | 回到覆盖缺项，不因漏写自动判相反预期 |
| 候选新增 Golden 未涉及的业务场景 | 记录为参考范围外，不因未收录扣覆盖分 |
| 候选新增用例引入 Golden 已禁止的权限例外 | 仍需检查，不能以“新增场景”逃避冲突判断 |
| Golden 对同一场景自身存在冲突 | 记录参考问题，不得任选一句惩罚候选 |
| 候选条件、身份、模式或对象状态不同 | 默认不冲突，但必须写明差异 |

三、冲突去重原则

如果同一种业务冲突重复出现在多个 TC：

- 合并为一个冲突记录；
- 为冲突分配稳定的 X 编号，例如 X01、X02；
- 列出全部相关 TC；
- 记录受影响的全部 G；
- 不按重复行无限增加冲突数量。

只有不同业务义务、不同适用条件或不同相反结果，才分别记录不同冲突。

四、参考范围外用例

对不属于 Golden 固定检查点范围、且没有违反 Golden 明确约束的候选用例：

- 标记为参考范围外；
- 记录 TC 位置和业务摘要；
- 不因 Golden 未收录而扣覆盖分；
- 不把它算作 Golden 覆盖；
- 不保证该用例本身正确；
- 如果它违反 Golden 已明确禁止的条件，仍然记录为冲突。

五、全部候选用例审阅去向

每条可可靠读取的候选用例必须有一个审阅去向：

- 匹配一个或多个 G；
- 记录为参考范围外；
- 记录为冲突证据；
- 记录为内容不足；
- 记录为不可判定；
- 记录为重复用例。

不能只审阅检索返回的少数 TC，就宣称整份候选无冲突。

# QA Rubric Step 3：证据复核、最终计数与分项报告

## 这一步是做什么的

第三步是 QA Rubric 的收尾步骤。它不重新设计 Golden，也不重新发明覆盖判断，而是对前两步已经形成的记录进行证据复核、冲突去重、状态回写、计数和报告整理。

本步骤合并原 Rubric 中的：

- W5：复核证据、合并结论与计数；
- W6：输出分项评价报告。

本步骤的核心目标是：

1. 确认每个 G 的最终状态能够由 Golden 和候选原文复算；
2. 将 W4 的明确冲突回写到相应 G，避免正确用例抵消相反预期；
3. 对重复冲突去重，但不把不同业务义务错误合并；
4. 只有在发布条件满足时才计算最终覆盖率；
5. 输出覆盖、冲突、格式问题、范围外用例和未决项分开的报告。

本步骤完成后，得到的是 **QA 测试用例文档相对于 Golden 的评测报告**，不是软件实现结果、测试执行结果或生产发布结论。
