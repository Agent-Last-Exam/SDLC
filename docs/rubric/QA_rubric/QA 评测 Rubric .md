# QA 评测 Rubric 



## 1\. 评价目标



**输入 Agent 提交的 ****`test-cases.csv`**** 和评测方私有的 Golden 测试材料，**回答以下两个问题：

- **B1：golden测试是否覆盖全面？** 对照 Golden 的业务检查点，判断候选是否完整覆盖、部分覆盖或遗漏。

- **B2：有没有写出与 Golden 不一致的预期结果？** 检查同一条件下，候选是否把应当拒绝写成成功、应当保持不变写成发生变化。



## 2\. 输入、职责与产物



### 2\.1 最小输入



|输入|用途|边界|
|---|---|---|
|Golden 测试材料及其版本|明确应该验证哪些业务行为|只在评测方可见；可以是测试用例文档，不必逐行对应候选 CSV|
|候选`test-cases.csv`|唯一被评产物|保留原文，不替 Agent 补写或修正用例|
|test\-cases Schema|帮助识别列和基本结构|不恢复全量 Schema 合规量表|



## 3\. 总体流程



```Plain Text
准备一次，供同一任务的不同候选复用
Golden 测试材料 → W1 整理并固定业务检查点
                              │
逐份评价                       ↓
候选 test-cases.csv → W2 轻量检测schema与定位
                              ↓
                     W3 检查该测的有没有测到
                              ↓
                     W4 检查有没有相反预期
                              ↓
                     W5 复核证据、合并结论与计数
                              ↓
                     W6 输出分项报告
```



## 4\. W1：整理并固定 Golden 检查点



**执行者：** LLM Judge 提取草稿，评测维护者审核固定。

**输入：** Golden 原文及版本、Rubric；不输入候选用例。

**输出：** 固定检查点表及参考问题清单。



### 怎么做



1. 通读 Golden，区分目标业务要求、历史脚本实际断言、已有覆盖缺口和执行说明。只有确认的目标要求才用于判候选对错。

2. 按“条件、操作、关键预期”拆出完整业务场景，保留权限、模式、时序、对象范围、否定和例外。

3. 合并重复出现的同一业务义务，同时保留所有来源位置。不按段落数、脚本数或句子数增加权重。

4. 给检查点分配稳定的私有 G 编号；记录来源是否充分。含糊、相互矛盾或无法明确结果的部分列入参考问题，不默默删去。

5. 维护者确认范围、粒度和来源后固定版本；同一任务的全部候选使用同一版本。

    

|检查点字段|要保存的内容|
|---|---|
|G 编号|用于私有判分定位，不要求候选填写|
|来源|Golden 的位置及支撑原文|
|条件|身份、模式、对象状态、数据和必要时序|
|操作|实际触发什么业务行为|
|关键预期|本场景必须验证的全部结果与副作用|
|参考问题|无则注明无；有则说明缺什么，不能猜答案|



例如，“无权限修改被拒绝且数据不变”保留为一个完整检查点，不临时拆成两点给部分分；“新订单快照”和“旧空快照兼容”前提不同，可以分为不同检查点。



函数名、内部对象名称可以抽象为业务含义；决定权限、金额或状态变化的路径和时序不能抽掉。Golden 没要求的组合，不凭空扩成参数矩阵。



**交接条件：** 检查点有来源、范围稳定、重复已合并；未解决的参考问题仍有记录。若参考范围尚无法完整确定，可继续做局部诊断，但不能生成正式覆盖率。参考以后修订时，更新版本并重新评价受影响候选，不只为某一个候选改答案。



## 5\. W2：Schema检测



**执行者：**LLM Judge 解析和定位辅助识别明显无法理解的步骤与预期（目前不设计程序解析）。

**输入：** 候选原文件、Schema。

**输出：** 带原文定位的候选用例表、格式问题清单及无法读取的范围。



只检查三项：



|项目|检查内容|对后续的影响|
|---|---|---|
|可读取|CSV 能解析、必要列齐全；多行单元格不被拆成多条用例|确实无法识别的部分标未完成，不猜测恢复内容|
|可定位|TC 编号非空、唯一，具体记录可定位|空号或重号列为问题；仍可通过逻辑记录序号定位时继续评价|
|可理解|有可辨认的操作与预期，二者能对应|明确缺失的内容按内容不足处理，不一概当成过程失败|



每条候选保留文件、CSV 逻辑记录序号、原 TC 标签、条件、步骤和预期原文。不能只传标题或 AC 编号给 Judge；写了覆盖编号，不代表用例实际测到了相应业务。



**交接条件：** 能可靠读到的用例继续 W3/W4，不因普通格式问题阻断。若只读到部分文件，后续结果只能说明已读范围，不能据此宣称整份文件没有遗漏或冲突。只有表头但没有用例是可确认的空候选，不等同于文件读取失败。



文件命名、列顺序、版本说明、名称逐字相同、历史编号和需求优先级上限不另设评分项。预检不打分，也不计算合规率。



## 6\. W3：检查golden里测试是否覆盖全面



**执行者：** LLM Judge。

**输入：** 固定检查点表、Golden 原文、可读候选的完整内容、W2 的读取范围。

**输出：** 按 G 编号排列的覆盖初判，每条带候选定位、证据和理由。



### 怎么判断



逐个检查点查找对应候选 TC，核对三件事：



1. **条件对不对？** 身份、权限、对象状态、模式和关键时序是否对应。

2. **真的做了那个操作吗？** 有没有触发需要验证的行为，而不是只看按钮、消息或对象 ID。

3. **关键结果都检查了吗？** 有没有可观察的预期及必要副作用检查，而不是只写“结果正常”。

    

用例可以一对多、多对一。多个 TC 联合覆盖时，必须指向相同场景的兼容前提和真实验证关系；不能把无权请求的报错和有权请求的数据保存拼成“无权请求数据不变”。重复 TC 不增加覆盖信用。



候选换了函数名、接口路径或数值，不直接判错；判断差异是否改变业务对象、边界和结果。仅当数值或路径是场景关键条件时，变化才影响等价性。



### 记录初判



|状态|含义|
|---|---|
|完整覆盖（初判）|条件、操作、全部关键预期都有实质支持；仍须经过 W4 冲突检查|
|部分覆盖|有对应测试，但少了必要条件、操作或关键结果；写清已测到和缺失内容|
|遗漏|审阅完整候选后，没有实质测试该场景；只写主题或编号不算覆盖|
|明确冲突|已发现同条件相反预期，交给 W4 统一核对与记录|
|不可判定|参考缺口或确实无法消除的歧义妨碍判断；说明原因|



每条判断引用 Golden 和候选原文。遗漏时写明查阅范围及最接近但不成立的用例，没有对应 TC 就写无，不编造引文。



**交接条件：** 固定检查点逐个有记录，没有漏掉难判的点。W3 不发布最终覆盖率；候选未读全时，不把局部“未找到”升级为全局遗漏或最终完整覆盖。



## 7\. W4：检查有没有写出相反的预期



**执行者：** LLM Judge。

**输入：** 完整候选内容、Golden、固定检查点表、W3 初判。

**输出：** 冲突记录、受影响 G 编号、参考范围外用例及未决问题。



W3 从 Golden 找候选，容易找到一条正确用例就停止。W4 从候选出发，检查**全部用例**，包括 W3 没有匹配的额外用例。这样才能发现：一条要求无权读取被拒绝，另一条却要求相同无权读取成功。



不是每个未匹配 TC 都有错，也不是只查预期文字是否相反。每个明确冲突必须有四项证据：



1. Golden 的条件和预期原文。

2. 候选的条件、操作和相反预期原文。

3. 为什么双方是同一身份、模式、对象状态和操作。

4. 为什么两种预期不能同时成立。

    

|情况|怎样处理|
|---|---|
|Golden 规定无权读取私有信息不泄漏，候选要求返回完整私有值|明确冲突|
|Golden 规定无权拒绝，候选规定有权可读|条件不同，不冲突|
|少写一个副作用检查|回到覆盖缺项，不因漏写就判相反|
|新增场景不在 Golden 中|记为参考范围外，不因未收录扣分，也不增加覆盖分；不保证其正确|
|新增用例引入 Golden 已禁止的权限例外|仍是受参考约束的内容，不能以“额外用例”逃过冲突检查|
|Golden 自己对同一场景相互矛盾|参考问题，不能任选一句惩罚候选|



同一种业务冲突重复出现在多个 TC 时合并记录，列出全部 TC，不按重复行无限增加冲突数量。不同业务义务的冲突分别说明。



**交接条件：** 候选记录都有审阅去向；明确冲突有双方证据，其他未匹配用例说明是范围外还是尚未判清。不能只看检索返回的少数 TC 就宣称整份候选无冲突。



## 8\. W5：复核证据、合并结论与计数



**执行者：** 程序核对定位和计数；LLM Judge 复核有分歧的语义判断。参考定义有问题时交评测维护者处理，不让 Judge 自行改 Golden。

**输入：** W2 读取范围、W3 覆盖初判、W4 冲突与未决项、原始材料。

**输出：** 最终覆盖明细、去重冲突清单、汇总计数及结果完整性说明。



### 先核对，再合并



- 核对引用确实来自对应原文、TC 和 G 编号能定位、固定检查点没有漏项；引文存在不等于语义正确，后者仍需 Judge 判断。

- W4 发现明确冲突时，关联检查点最终标为“明确冲突”，不能因为 W3 找到过正确 TC 就继续给完整覆盖。

- 无冲突且证据成立时，保留完整覆盖、部分覆盖或遗漏；无法可靠判断的项保留不可判定。

- 已证实冲突不能被其他未知项抹掉；同时保留反例与未完成范围。尚未审完或工具失败的部分标评价未完成，不伪装成业务遗漏。

- 若复核发现判断错了，修正结论并保留原因；不能通过调整 Golden 来迁就候选。争议仍未消除时不强行判分。

    

这一步是结果复核，不要求部署第二个独立 Judge 或多模型投票。若由同一模型复核，应如实称为自复核，不宣称已经获得独立验证。



### 最终状态与覆盖率



最终每个检查点的主状态仍为：**完整覆盖、部分覆盖、遗漏、明确冲突、不可判定**。只有完整覆盖计入覆盖分子，部分覆盖不任意给 0\.5 分。



```Plain Text
完整覆盖率 = 完整覆盖的检查点数 / 固定、去重的 Golden 检查点总数 × 100%
```



只有同时满足以下条件才发布最终比例：Golden 非空且范围已经固定；候选已完整可靠读取和审阅；全部检查点都有最终判断；没有未解决的不可判定项或过程失败。



条件不足时，保留固定总数、已确认的各状态计数和未决/未完成数量，明确不发布最终覆盖率；不删除困难项重新归一化。没有完成判断的点不能因计数方便直接填遗漏或 0 分。



例外要区分：候选可读且只有表头、Golden 有明确检查点时，可确认全部遗漏并得到 0%；Golden 为空或候选读取失败时不能这样处理。



**交接条件：** 汇总与明细一致、冲突已经回写相应覆盖状态、结果是否完整有明确说明。冲突另列，不在覆盖率上再额外扣一次分，也不合成总分。



## 9\. W6：输出分项评价报告



**执行者：** 程序从确定的记录汇总，LLM Judge 可整理解释文字，但不得在汇报时重新编造结论或改变计数。

**输入：** W5 的最终记录与评价对象身份。

**输出：** 一份维护者可追溯的报告，而不是要求 QA Agent 增加的交付物。



报告按以下顺序组织：



|部分|必须说清楚什么|
|---|---|
|评价对象与范围|哪个候选、哪个 Golden/检查点/Rubric 版本，评价是否完成|
|结论摘要|主要冲突和遗漏、覆盖率能否发布；不写未经规定的“总分合格”|
|格式问题|三项预检发现的位置、问题和阅读影响；没有格式分|
|Golden 覆盖|每个 G 对应哪些 TC、最终状态、双方证据、缺项与理由|
|相反预期|每个冲突的双方原文、相同适用条件、涉及 TC 和受影响 G|
|参考范围外与未决项|哪些新增用例未被参考涵盖、哪些参考缺口或过程问题尚未解决|



覆盖明细采用以下最小结构即可，不再另建一套复杂量表：



|G 编号|Golden 条件/操作/预期及来源|对应 TC 与原文位置|最终状态|判断理由、缺项或冲突编号|
|---|---|---|---|---|
|稳定检查点标识|必须保留关键业务含义|可为一个、多个或无匹配|五种状态之一|用证据解释，不只给标签|



冲突记录用 X 编号，不混同于 QA 测试报告的 D 缺陷编号。同一问题可同时出现在覆盖明细和冲突清单中，但共用记录，不重复扣分。



**交付条件：** 每个结论可追溯；数值可由明细复算；未知没有被写成通过；没有把用例文档质量结论说成软件实现通过或生产可发布。报告含私有参考信息，不自动回传到正在进行的待测任务中。



## 10\. 用一个 Saleor 小例子走完流程



以下是合成教学片段，不是正式 Golden、完整 CSV 或真实模型评价结果。为说明流程，假定维护者已确认下列四个检查点的参考含义，且候选文件全部可读、全体用例均已审阅。



### 10\.1 W1：固定四个检查点



|G 编号|条件、操作与关键预期|
|---|---|
|G01|后台修改元数据，重开页面并独立回读同一对象，值保持一致|
|G02|新成交订单已有配送快照，修改当前配送配置，原订单快照不变|
|G03|无权身份读取私有信息，私有信息不得泄漏|
|G04|提交可获取的外部图片，除请求被受理外，还要验证最终资源可读取|



### 10\.2 W2：读取五条候选用例



|候选|操作与预期摘要|
|---|---|
|TC001|保存元数据，重开页面并通过另一个查询接口回读同一对象，值与保存值一致|
|TC002|查看新订单的配送快照，预期等于成交时配置；没有修改当前配置|
|TC003|无权身份请求私有信息，预期被拒绝且不返回私有值|
|TC004|同样无权身份请求相同私有信息，预期成功返回完整私有值|
|TC005|Golden 未涉及的浏览器快捷操作场景，没有引入上述业务规则的例外|



实际文件若有普通格式问题，只在问题清单说明；本表仅展示语义摘要，不声称它本身满足 CSV 预检。



### 10\.3 W3–W5：先查覆盖，再检查反向冲突



|检查点|W3 初判|W4 发现|W5 最终状态|
|---|---|---|---|
|G01|TC001 完整支持；查询接口名称不同不影响业务含义|没有相反预期|完整覆盖|
|G02|TC002 只看当前快照，没触发“修改当前配置”|没有相反预期|部分覆盖，缺少修改后仍不变的验证|
|G03|TC003 提供正确验证|TC004 在相同条件下要求泄漏私有值|明确冲突 X01，不能靠 TC003 抵消|
|G04|没有外部图片终态测试|没有相反预期|遗漏|



TC005 记为参考范围外，不因未收录扣分，也不增加覆盖分；没有发现它与参考相反，不等于证明其在所有意义上正确。



### 10\.4 W6：形成结果



- 固定检查点 4 个：完整覆盖 1、部分覆盖 1、遗漏 1、明确冲突 1、不可判定 0。

- 完整覆盖率：`1 / 4 × 100% = 25%`。

- 明确冲突：X01，涉及 TC004 和 G03；报告列出 Golden 禁止泄漏、候选要求返回私有值及相同身份条件。

- 主要缺项：TC002 缺少触发快照稳定性验证的操作；G04 未测。

- 不给综合总分，不评价是谁在上游造成这些问题，也不声称软件本身发生了泄漏。

    

若 G02 的参考预期后来被发现含糊到无法可靠判断，应保留参考问题，将受影响结果标不可判定，最终覆盖率暂不发布；不能把分母改成 3。若候选有不可读部分，则只能报告已确认诊断，不能假装已完成整份评价。
