# Harbor Golden PRD + 配对代码 → Query 单次长程构造工作流

## 1. 直接执行的任务指令

你是**出题方的输入构造 agent，只有阅读本文档指定目录和文件的权限**。完整读取本文件及指定设计文档后，在一次任务中完成 Golden → Query 的六步构造、证据化自审、必要修正和最终交付。不要只返回计划，不要在阶段末尾等待用户确认或要求用户继续发送 prompt。

本轮最终产物是：

- 可提供给后续待测 agent 的 `OUTPUT_ROOT/query.md`。
- 启动即提供、不可运行时补答的 `OUTPUT_ROOT/business-conversations.md`。
- 与输入逐字节一致的 `OUTPUT_ROOT/prd-schema.md`。
- 私有 `reduction-ledger.json`、`worklog.md` 和最终审核报告。

**本工作流只构造 Query 和业务沟通材料，不生成 PRD、不启动模型试评。** 不规定后续 agent 的 PRD 结构、优先级、AC 编号、工具权限或执行方式；这些属于独立的下游任务编排。保留出题方的事实忠实性、来源追踪与避免直接泄漏参考答案的质量检查。

核心目标：保留必要业务事实与不可推断的决定，同时留下需求理解、现状调查、信息关联和验收条件组织工作。既不能把 Golden 换成聊天口吻直接当输入，也不能靠隐藏必要信息让待测 agent 猜题。

本轮正式输入是同一 Harbor 包的完整 Golden 文档集与配对实现，不是旧的本地 PRD 副本。由当前 PRD 界定范围，结合 TDD、接口契约、测试设计、剪枝记录和验证证据理解需求，再定向核对 code patch；有获准的可读 Base 时才调查源码现状。默认仅有包文件也可开展构造，不依赖外部仓库。出题方可读完整文档不等于可以把技术设计、测试答案或实现代码公开给待测 agent。

执行路线：

```text
S0 核对身份、版本、输入与输出边界
→ S1 拆分可核对的业务命题
→ S2 先判断公开必要性，再选择信息载体
→ S3 按业务目标组织主题
→ S4 生成 Query 和固定业务沟通记录
→ S5 登记实际信息去向与恢复记录
→ S6 全量双向自审
→ 有可修复问题：返回对应阶段修正，再执行 S5/S6
→ S7 最终复核、冻结与一次性交付
```

S1–S6 对应设计文档的六步；S0/S7 是运行入口与交付环节。原 `promt.md` 的 step1 是初始化，step5 合并了生成与记账，step6 是审核，不能按其编号误认为设计六步已全部完成。

### 2.3 Harbor 包内的基线身份与可访问性

Base 是任务起始代码及环境状态，不是一个必然存在的本地仓库目录。其身份、构建方式和环境适配以包内配对清单、`env/manifest.json`、`environment/Dockerfile` 与 `task.toml` 为依据；不得去旧工作区搜索替代 Base。

- `package_only`：只有包文件。登记清单声明的基线身份和准备方式，`read_path`、`agent_path` 未确认时为 null。允许基于完整 Golden 文档及配对 Patch 构造，但 Base 源码现状标为未调查，不宣称已挂载或已复现。
- `readable_baseline`：运行方明确提供基线环境和读取权限后，核验实际路径、HEAD/tree、环境适配、工作区及证据指纹；不是只核对一个 upstream SHA。版本或内容不符时禁止使用该证据，并报告相关命题的阻塞，不静默换仓库。
- 出题方 `read_path` 与待测 agent `agent_path` 分别登记，不能自动互相复制。未来挂载映射只能标“待运行前验证”；包内配置路径不等于实际可访问路径。
- 不自动 clone、fetch、checkout、reset、构建镜像、运行容器或应用 Patch。需要实际基线环境时，列出最小授权及输入请求。
- 没有可读 Base 不自动阻塞文案构造；但不能把任何必要事实分配到未经验证的 `base` 去向。应从正式文档中保留必要公开信息；若其依据缺失或存在冲突，仍须标 `BLOCKED`，不能靠猜测或隐藏信息继续。
- Query 不得包含虚构的本地 Base 路径或要求待测 agent 访问未提供材料。文案可独立成立时，未来基线挂载仅列运行依赖；若任务可解性必须依赖该调查而访问尚未确认，则不能宣布可投喂。

### 2.4 Harbor 代码身份与证据边界

- 分别登记 `upstream_base`、`agent_baseline_commit/tree`、code/test/combined tree 及 evaluation tree；不能把评测用 `environment + test patch` 当作待测 agent 可见 Base，也不能把 upstream target SHA 当作剪枝目标树。
- 最终 code patch 取 `solution/`，最终 test patch 取 `tests/`；校验实际 SHA-256 与包根 manifest 及 Golden 配对清单一致。环境 patch 的实际路径为 `environment/harbor/saleor-3.23/env/`。`env/manifest.json` 保留的原始 code/test 路径与哈希只用于历史环境说明，不替代最终剪枝 patch，也不因与最终 patch 不同而误判配对失败。
- 包提供的是差分，不是完整目标源码树。默认按文档命题定向读取指定 code patch；仅在有获准可读 Base 时结合其上下文。Patch 上下文和删除行不能证明完整 Base 行为，新增行也不能单独证明完整目标行为；不足时记录证据限制。
- 不自动应用 patch、创建 worktree、构建容器或启动服务。需要物化目标树时，另行申请独立位置与操作授权；不得改现有仓库来便于阅读。
- 只有待测 agent 实际可见的固定 Base 事实可以分配到 `base`。仅在私有目标代码发现的新业务决定若为解题所必需，必须按既定范围公开其业务含义；实现算法、代码片段、私有路径及补丁内容不能泄漏。
- 完整 Golden 文档均为出题方正式私有材料：全文读取当前 PRD、前后端设计、接口契约、测试设计与双向追踪审计；阅读 references 中的剪枝流程、完整性审计和阶段决定，历史 PRD 仅作差异追踪，不合并其已剪枝范围。
- `target-schema.graphql`、详细运行日志及大型 evidence JSON 按命题、字段、场景定向检索，登记已读范围和未读范围，不以目录扫描或校验和通过冒充全文审核。身份、配对及验证摘要必须读取；历史运行结果不算本轮实测。
- Golden `Test/` 文档可用于核查必要业务条件，但 `tests/` 中隐藏测试执行代码、评分实现不默认开放语义读取；最终 test patch 仅计算配对哈希。不得将测试实现、私有断言或参考技术方案直接改写成公开答案。
- PRD 决定当前范围，TDD/契约解释实现与约束，测试设计检查场景充分性，references 解释剪枝，evidence 证明身份与历史状态。材料间实质矛盾记为 `conflict`；不自动选边或扩题。公开的是有依据且必要的业务条件，不是全套 Golden 的压缩副本。

## 4. 长程执行与检查点

每个阶段结束，先做本阶段完成检查，再自动进入下一阶段，不要求用户发送“继续”。阶段内保持证据摘要，不输出内部思维链。

在 `PRIVATE_ROOT/worklog.md` 追加检查点：

- run_id、实际时间、mode、当前阶段与阶段状态。
- 本轮输入身份、SHA-256、Base 提交和已读证据索引。
- 已覆盖的 Golden 章节／命题范围、已完成和剩余工作。
- 命题原始数、去重末项数、拆分父项数及其统计定义。
- 当前输出版本与指纹、台账是否与公开文本同步。
- 未决问题、阻塞项、修正轮次和下一步。

使用 `pending / running / completed / blocked / not_run` 区分阶段状态。`completed` 只表示该阶段已执行且产物可追溯，不代表审核通过。不得沿用旧日志“第四步完成”就跳过本轮调查或自审。

上下文不足前写入检查点。继续同一运行时，先核对输入、输出与快照指纹，读取最后有效检查点和待办，再继续未完成部分；不能仅凭记忆或历史分数跳步。实际中断且无法继续时交付 `INCOMPLETE` 与恢复入口，不声称任务完成。

不要全盘读取工作区来寻找上下文。先读指定文档，再按命题调查明确 Base。大文件分段读取直至需要的范围完整；工具截断不能视为已读全文。工作量过大时保留未读范围，不以抽样冒充全量。

## 5. S0：初始化与输入冻结

1. 先解析 Harbor 包身份和 `active_prd`，核验 Golden 文档校验和及最终 code/test patch 的配对；建立完整文档清单，按第 2.4 节读取 PRD、TDD、契约、测试设计、追踪审计、剪枝记录及验证摘要，同时完整读取构造设计和 Schema。必需文档缺失、错配或路径越出授权包时停止，不回退到旧 PRD。候选输出、旧 Query、日志都不能反向证明 Golden 正确。
2. 确认 mode、WORKFLOW_DIR、HARBOR_TASK_ROOT、OUTPUT_ROOT、PRIVATE_ROOT、REVISION_ROOT 与 Base 状态。核验私有记录目录已获授权；记录文件字节数、SHA-256、编码、可读性及异常，不继续沿用旧提示“文件为空”的假设。
3. 用第 2.3–2.4 节登记 `base_access`、包版本、SDLC 提交、工作区状态、文档/patch 哈希、各树语义及 agent 可见边界。仅有包时标 `target_view=docs_plus_patch_static`；有已核验 Base 但未物化目标时标 `base_plus_patch_static`。都不代表已验证目标树或运行行为。
4. `construct` 模式不要求提供旧产物或历史修订目录。公开文档结构直接遵循第 9.0 节内嵌模板，不查找旧版本学习格式；如提供历史背景，不继承其命题总数、授权、结论或业务规则，所有新判断仍要从本次输入重建和核验。`revise` 仅要求明确指定的父版本，不要求更早历史。
5. `revise` 模式必须冻结旧公开文件和已有台账，记录父版本。旧 JSON 无法解析时不覆盖；保留原文件并报告缺口，不能声称可追溯修订已成立。
6. 核验只读 Golden 和 Schema 的指纹；在私有日志记录本文件、设计文档、父版本路径（如有）、快照映射及版本指纹。只做版本准备时记录 `SNAPSHOT_READY_GENERATION_NOT_STARTED`，不将旧台账状态当成本轮完成状态。
7. 写入 S1–S7 的执行计划及初始风险，立即进入 S1，不把计划作为最终回答。

若业务范围、权限或输入身份不清到无法继续，可先登记可确认的部分，但不能自行制定新的业务决定或发布最终公开输入。最终按第 12 节报告阻塞。

## 6. S1：拆分业务命题并调查可恢复事实

从 Golden 全文处理背景、目标、用户、范围、需求、验收、其他约束与未决项，不只遍历 R/AC 编号。

每个业务命题建立“当前 PRD → 设计/契约 → 场景/边界 → 剪枝目标改动 → 公开信息去向”的来源链。Base 可读时补充现状对照，不可读时明确未调查。跨仓命题记录两侧实际证据；纯业务政策可标 `policy_only`。实现证据不足与实质矛盾分别记 `missing/conflict`：前者评估是否影响业务表达，后者阻塞相关命题；不冒充语义核验完成，也不要求逐行阅读整个 Patch。

命题粒度以“可独立核对并决定信息去向”为准。每条保留主体、前提、动作、结果、否定、例外和适用范围；一个段落混合不同性质时拆分，同义项可合并但保留全部来源。

每条命题至少记录：

| 字段                      | 内容                                                                                       |
| ------------------------- | ------------------------------------------------------------------------------------------ |
| id / parent_id / children | 稳定私有 ID、拆分或合并关系；不投喂给待测 agent                                            |
| source                    | Golden 文件身份、章节／行号、精确原文、源片段指纹                                          |
| meaning                   | 不改变条件与边界的业务含义                                                                 |
| information_type          | 目标、角色、规则、优先级、AC、范围、非目标、现状事实、实现暗示、迁移兼容、运行运维、未决项 |
| nature                    | 新业务决定／Base 已有事实／分析或验收组织／实现方法／共用交付规程／待确认                  |
| base_recoverability       | 能否从固定 Base 恢复、实际证据及限制；未调查不能写已核实                                   |
| target_code_evidence      | 仓库、配对 patch SHA、文件、hunk/符号、短证据、`supported/policy_only/missing/conflict`；仅私有 |
| golden_document_evidence | PRD/TDD/契约/测试设计/剪枝记录的角色、路径、位置、原文及指纹；标明必需公开的业务条件和不公开的参考方案 |
| omission_test             | 省略后是否仍可合理得到、是否产生多个同样合理但不同的答案                                   |
| uncertainty               | 缺失材料、矛盾、风险和需后续决定的信息                                                     |

Base 调查必须以当前固定版本的文件、符号、配置、接口、测试或文档为证据，记录仓库、提交、路径、位置、短原文、哈希，以及它能证明和不能证明什么。

- 区分“存在代码”“可能的行为”“已验证运行结果”；不把静态材料说成运行成功。
- 跨仓事实应记录各仓的证据与关系，不能用单仓猜完整链路。
- 发现接口名不等于证明所有权限、默认值或异常路径；需要核对相关上下文。
- 新业务选择不能只因 Base 旧行为相似就标为可调查得到。
- 不读取或执行秘密、凭据或生产数据；遇到此类依赖记录限制。

缺口使用可追溯标签：`base_evidence_missing`、`business_decision_missing`、`runtime_evidence_missing`、`scope_ambiguity`。未提供运行事实不等于需求本身无效。

完成条件：全文有覆盖索引；所有命题有来源与性质；拆分父项和末项可区分；不能判断的部分已显式记录。不要在此阶段生成公开文案。

## 7. S2：先判断公开必要性，再选择载体

逐条完成两个独立判断：先判断是否必须公开，再判断如何分配到 Query、固定记录、Base 或私有材料。**必须公开不等于必须进入 Query。** 不能把所有剩余 Golden 细节自动塞进沟通记录，也不能因“范围／非目标／业务规则”的标签自动放进 Query。

| 主去向                               | 条件                                                                                       |
| ------------------------------------ | ------------------------------------------------------------------------------------------ |
| `OUTPUT_ROOT/query.md`                  | 业务背景、目标、主要变化、范围类别、非目标及关键保护边界；以界定任务的最低必要精度表达主干 |
| `OUTPUT_ROOT/business-conversations.md` | 主体不宜展开但不能省略的精确业务选择、有限集合、条件与例外；允许必要技术政策，不模糊其含义 |
| `base`                             | 已在固定版本找到、待测 agent 确实可访问且调查成本合理的现状事实                            |
| `private`                          | 参考措辞／编号、加工依据、提前分析、非强制实现或验收组织，不是隐藏必要业务义务             |
| `out_of_scope`                     | 原始范围已明确排除，或本轮有明确批准；不能因缺证据、难度大或无运行环境自行排除             |

每个末项只设一个主去向用于统计，可有多个辅助承载位置。私有细节若承载必要业务含义，必须说明公开信息或已核实 Base 如何仍支持该义务；“只保留私有”本身不是充分性证明。

每条分配记录：主去向、公开载体、Base 证据、公开／省略理由、预期待测工作、信息不足风险、过度公开风险、评分依赖、是否需后续试评及决定状态。

分别登记 `public_necessity`、`carrier`、`carrier_reason`、`query_without_detail_test`、`conversation_necessity`、`over_specification_risk`、`under_specification_risk`。Query 去掉精确细节后若仍能完整表达任务主干，而该细节是不可推断的必要决定，优先由固定记录承载，并保留关联。Base 只能证明现状，不能代替本轮新的业务选择。

接口、类型、字段、配置标识、精确集合及高密度规格是载体适配复核信号，不是自动删减依据。逐项用本项目证据说明去掉精度的影响、能否下沉、剩余分析工作与公平性；不用固定正例、接口数量或长度阈值代替 case-by-case 判断。

判断规则：

- 核心目标、关键权限、金额和数据不变量、兼容边界、非目标、不可推断的新业务选择，不能靠省略来制造难度。
- 对分析、验收组织和非强制实现方案可以抽象或省略，但必须保留支撑业务结果的事实；不能隐藏验收中的独有规则。
- 省略后有多个合理答案而评分只认一个时，保留必要决定或登记评分边界阻塞；不得静默修改 Golden 或评分。
- `not_recoverable_from_base` 的事实不能伪装成“留给调查”；若是明确新决定，应公开；若决定本身缺失，标 `requires_public_decision`。
- `requires_runtime_evidence` 需区分“PRD 可写成有条件依赖”和“缺失后连需求范围都无法确定”。前者保留明确义务与依赖，后者阻塞，不编造数据。
- 不设统一删减率、主题数或命题数。文本变短不等于信息减少，条目多也不等于覆盖完整。

完成条件：每个末项有去向及载体理由；Query 独立说明主干，联合固定记录保留所有必要决定；每项必要义务有公开／Base 支撑链；每个载体风险项已复核。未支持链和未经批准的排除都标为问题。对可由现有证据消解的问题自行修正，不等待中间批准。

## 8. S3：围绕业务目标形成提纲

仅在私有 worklog 中形成：

1. Query 提纲：背景与目标（含角色和场景）、主要变化、范围与非目标、补充业务材料；与第 9 节四个二级标题一致，不加入下游产物要求或运行入口。
2. 沟通主题：每个主题的业务关切、通用职能角色、回应关系、必要选择及条件；明确拟安排的每轮发言是在提出关切、说明背景、回答、澄清、限制还是确认，以及它与前文的关系，不预设固定角色或轮数。
3. 主题与命题关联：公开片段拟用标识、来源及需保留的条件／否定／例外。
4. 剩余分析工作：待测 agent 还需调查、关联或组织什么，不能只笼统写“保留分析空间”。

先组织 Query 主干，再围绕实际业务关切组织固定记录中的精确决定。检查必要重复与回应关系；下沉不等于删除，不能丢失条件、集合边界、例外、否定或兼容要求，也不能借对话补回已省略的实现清单。

不按 Golden 编号逐项换说话人，不强制按仓库或技术层划主题。使用通用角色可以，不编造真实人物、公司、事故、会议或访谈经历。不主动制造噪声、虚构冲突或加入新的业务决定。

检查 Query 能独立说明任务、沟通是必要补充而非第二份完整 PRD；分散的信息有足够联系、不会互相矛盾；被抽象的实现清单不会借对话重新泄漏。

完成后自动进入 S4。原 prompt 中“停止等待确认”不再是此处的门禁；但新业务决定、扩大范围或额外权限仍不能自行批准。

## 9. S4：生成业务委托与沟通材料

### 9.0 内嵌产物模板与格式契约

以下两份模板完整定义公开文档的结构，不依赖历史产物、修订目录或外部格式样例。它们只定义本轮两份业务文案，不规定后续 PRD 如何生成。模板中的 `{{…}}` 是填写说明，成稿须全部替换；只输出填写后的 Markdown，不保留外围代码围栏或模板说明。

#### Query 模板

保留以下四个二级标题及顺序。“主要变化”下按本项目实际业务目标重复三级主题块，主题名称、数量及排列由材料决定，不复制固定项目分类。标题表达业务含义，不能用 Q 编号替代；需要引用标识时可辅助标注，但不能牺牲标题可读性。

```markdown
# 业务委托：{{本轮业务目标}}

## 背景与目标

{{现有业务背景、受影响角色及工作场景、希望解决的问题和目标。}}

## 主要变化

### {{业务主题}}

{{该主题希望发生的变化、业务结果及必要保护边界；需精确补充的决定由固定沟通记录承载。}}

## 范围与非目标

{{本轮包含与明确排除的范围、兼容和资产保护边界、延期事项；不要混入下游 agent 的产物格式或执行限制。}}

## 补充业务材料

{{相对本文件引用 business-conversations.md，说明它补充的业务条件与边界，不添加下游 PRD 生成指令。}}
```

Query 应是可独立理解的业务委托，不是编号摘要或附件目录。不把多个不同业务方向压成一个长段，也不为追求短而把业务主干移到沟通记录。精确接口、集合和例外是否进入 Query，仍须按 S2 判断，模板不授予额外公开权限。

#### 固定业务沟通记录模板

保留文档标题与材料性质说明；按项目需要重复“业务主题 → 具体讨论事项 → 角色发言”的结构。下列两轮只演示排版位置，不规定每个事项必须两轮、必须问答或固定角色顺序；不能为了凑轮次虚构确认、争议或历史事件。

```markdown
# 固定业务沟通记录

以下是任务启动前一次性提供的合成需求材料。角色仅代表业务相关职能，不对应真实人物、公司或已经发生的访谈，也不是待测 agent 的调查结果。运行中不安排追问或补答。各片段补充业务委托的条件和边界，与委托共同使用；未提供的实际部署和运行结果不得据此推定。

## {{业务目标或实际关切}}

### {{具体讨论事项及其关键关切}}

片段标识：{{稳定公开标识}}

**{{职能角色}}：** {{围绕当前事项提出关切、说明必要背景或表达有依据的业务决定。}}

**{{相关职能角色}}：** {{承接前文作出回答、澄清、限制或确认，保留必要条件和例外。}}
```

- 角色标签加粗，每轮独立成段；标题可陈述也可提问，不强制全部改成问题句。公开标识放在独立行，便于引用但不取代语义标题。
- 每轮发言必须围绕当前关切发挥明确作用，不把不相关的权限、异常、配置与验收条款一并塞入回答，也不只是轮换角色宣读规格。暂时去掉角色名后，若一段仍像多个独立验收条款的拼接，就触发重写检查；这是复核信号，不是自动判错、删信息或禁止必要技术政策的依据。
- 允许表达必要技术政策，但不添加寒暄、虚构冲突或无信息量的确认来制造“自然感”。不能为口语化模糊精确决定。
- 精简顺序固定为“去重复 → 重组 → 改写”，不是“删决定”。先合并反复出现的共同说明，为每项业务事实安排主要承载位置；其他位置只有在理解确有需要时才简要重述或引用，引用必须可定位且不能把读者引入循环查找。再按实际关切重组主题和发言，最后改写表达。不按字数、轮数或主题数硬裁剪；下沉的必要信息不得删除或降格，仅换行拆短长段或轮换角色不算解决。

### 9.1 Query

写入本轮 `OUTPUT_ROOT/query.md`，应独立说明业务背景、目标、主要变化、角色与场景、范围和非目标，不得只有附件阅读指令。

Query 追求完整清晰，不追求最短。按业务主题说明主要变化，让读者理解各主题的目标、变化与保护边界，避免把多领域信息压成编号摘要。“最低必要精度”约束的是细节展开程度，不是压缩业务主干或限制篇幅。每项精确清单和代码层标识须通过载体适配复核；保留理由不能仅为“属于范围”或“必须公开”。不能省略但主干不宜展开的精确集合、接口细节和例外放入固定记录，不以去技术化为由抹去业务决定。

业务正文之后仅写“补充业务材料”：相对 Query 所在 `query docs/` 引用 `business-conversations.md`，说明其承载精确条件、例外和业务决定。若提及附带的 `prd-schema.md`，只说明它是原样附带的模板，不要求读者采用。

不写下游 PRD 生成指令，不指定章节、优先级分类、AC/需求编号、状态或文件交付格式，也不设置待测 agent 的访问、工具和执行权限。确属业务范围的安全、兼容、数据保护与非目标仍保留，不能与 agent 操作规则混淆。不编造 Base 访问入口。

### 9.2 固定沟通记录

写入本轮 `OUTPUT_ROOT/business-conversations.md`：

- 开头明确“预先提供的合成业务材料，启动即公开，非真实访谈，运行中不追加回答”。
- 每段有稳定公开片段标识，如 `BC-001`；标识不复用 Golden R/AC 或私有命题编号。
- 发言之间澄清、确认、限制或推进同一业务问题，不成为多人机械宣读 Golden。
- 保留适用角色、条件、例外、否定及兼容边界，不让口语化模糊必要选择。
- 承接从 Query 下沉的必要精确选择与集合边界；不得降格为可选建议，不逐字重复主干，不变成另一份逐项换皮 PRD。
- 不把假设写成事实、建议写成强制、Base 旧行为写成新政策；无依据阈值、例外和功能不新增。
- 不包含完整 R/AC 列表、验收矩阵、参考实现、私有映射、删减原因或审核结论。

### 9.3 成稿后检查

先对第 9.0 节验收：Query 的四个二级标题及顺序完整，业务主题具有语义；沟通记录保留材料说明、主题层级、稳定标识及加粗角色；占位符全部替换，成品不依赖历史版本才能理解。再逐话题检查发言是否回应、是否堆砌互不相关规格、是否跨文件无意义重复。可由现有材料解决的表达问题必须重写并核对语义，不只登记为人工审阅风险。

联合阅读两份公开文本，检查是否仍是 Golden 的同义重排、是否直接给出完整参考设计，以及是否遗漏必要业务事实。附带 Schema 仅核验复制一致性，不作为文案内容约束。

额外复核 Query 中保留的精确细节是否有载体理由，以及所有下沉内容的联合语义是否完整。公开必要性与载体适配分别验收，不能用一般泄漏扫描代替后者。

所有可确认问题写入私有问题清单，S5 登记实际版本，继续 S6；不要在生成结束停下来，也不要在未审核时宣布可交付待测 agent。

## 10. S5：登记实际信息去向与可恢复记录

### 10.1 台账内容与 JSON 契约

`PRIVATE_ROOT/reduction-ledger.json` 是实际成品的权威结构化依据，不再手工维护另一份权威 Markdown 台账。前期计划可以留在 worklog，但台账必须按成品修正位置与文本。

新建台账使用明确 `schema_version`，顶层至少包含：

| 字段              | 类型及含义                                                                                |
| ----------------- | ----------------------------------------------------------------------------------------- |
| schema_version    | 字符串，说明本轮字段约定，不冒称旧台账自动升级                                            |
| run               | 对象：run_id、mode、阶段、状态、修正轮次、时间及时区                                      |
| inputs            | 数组：角色、实际路径、字节数、SHA-256；含设计、工作流、Golden、Schema及明确批准的补充输入 |
| base_repositories | 数组：base_access、包内声明的基线身份、read_path、agent_path、实际提交/tree、工作区状态、核验范围和限制；package_only 时未核实的实际字段为 null |
| parent_version    | revise 时记录业务修订起点及 parent_run_root；construct 为 null，但不意味着磁盘上没有旧文件 |
| preexisting_snapshot | 新一轮写入前既有产物的快照清单及指纹；construct 遇到旧文件也须登记，与业务父版本分开 |
| public_versions   | 当前三份公开文件的路径、字节数和 SHA-256                                                  |
| evidence_registry | Golden 文档、Base 与目标代码证据 ID 到文件、位置、原文、指纹和证明边界的映射；每条标 `golden_document/base/target_patch/policy`、文档角色和 agent 可见性，私有文档及目标证据不得用于声称 Base 可恢复 |
| entries           | 全部命题记录，父项和末项身份明确                                                          |
| changes           | 实际改写／修正记录、版本关系和恢复说明                                                    |
| issues            | 未决、阻塞、已修正问题，含证据和影响                                                      |
| audits            | 追加各轮自审结果，保留历史，不把建议记成已完成                                            |
| counts            | 从 entries 计算的原始数、父项数、末项数和主去向统计                                       |

旧版台账只在明确修订时作为输入。保留原版本和原字段，新增关联记录；字段映射或能力升级必须说明，不能将缺失的原文／恢复数据自动声称为已有。无法解析的输入不得覆盖。

每条末项至少包含以下语义字段，ID 引用必须可解析：

- `id`、`record_kind`、`parent_id`、`children`、`related_ids`。
- `golden_sources`：准确位置、精确原文和片段哈希；不能只有摘要或 R 编号。
- `information_type`、`meaning`、`public_necessity`、`carrier`、`carrier_reason`、`primary_destination`、`secondary_destinations`。
- `query_without_detail_test`、`conversation_necessity`、`over_specification_risk`、`under_specification_risk`。
- `public_refs`：实际文件、稳定章节／片段标识、精确当前文本及哈希；未公开时说明计划补入的位置或不适用原因。
- `base_evidence`：已核实证据 ID；无证据时明确未核实，不能填“Base 可恢复”。
- `target_code_evidence`：配对目标代码的证据 ID、命题对应状态与冲突；与 `base_evidence` 分列，不能互相代替。
- `golden_document_evidence`：设计、契约、场景与剪枝依据的证据 ID；公开必要性、实现方案和历史状态分别标注，不把设计或测试文档中的每个细节自动升级为业务要求。
- `operation`：保留、压缩、抽象、载体移动、省略、合并、拆分、交给 Base 调查等；组合操作保留关系。
- `reason`、`risk`、`expected_agent_work`、`decision_status`。
- `score_status`：有无未解决的评分依赖，不是分数或模型实验结论。
- `restore_when`、`recovery`：什么情况下考虑回补、回补方式与当前验证状态。

统计只数末项，每个末项一个主去向；父项是索引，不再次计数。一个命题可以在多处公开，多个命题也能合并成一段，不能强求一对一。

### 10.2 首次构造与修订恢复

**首次构造或重新构造：** 仅当磁盘上没有旧文件时，`before` 才为 null 或明确不存在；construct 遇到已有产物时，业务 `parent_version` 仍为 null，但必须保存其快照、完整 before 文本及指纹，不能假装首次落盘。保存 Golden 精确源文、实际公开表达、拟补充文本、目标文件、唯一锚点及插入前／后约定。若补充措辞尚未确定，标 `pending_review`，不能声称自动回补已经可用。

**修订既有公开文本或本轮自动修正：** 保存父版本哈希、目标文件、完整 `before`／`after`、唯一位置、关系组和恢复规则。`before` 是旧公开文本，不是 Golden 原段；逆向替换恢复的是旧输入，不保证恢复 Golden 全部信息。

- 完全删除时 `after` 为空，必须用唯一锚点插入，禁止把空字符串作为全局替换条件。
- 拆分／合并／交叠修改记录共同版本和依赖顺序，不假定各组恢复互不影响。
- 声称可逆的替换须在内存或私有验证副本实际验证正向产生新稿、逆向恢复旧稿，比较哈希；匹配零处或多处立即停止该恢复验证。
- 首次语义回补只验证源、拟补文本和插入位置，不冒充字节级回退，也不自动把所有删减补回公开包。
- 公开文本一旦修正，更新 public_refs、changes 和文件指纹，并重做相关审查；台账不能还指向旧稿。
- Query 与固定记录间的移动登记为 `move_carrier` 或等价明确操作，记录旧新载体、完整 before／after、联合语义映射及关联关系；不得误记为省略、范围删除或新增业务。

## 11. S6：全量自审与有限修正

### 11.1 八项审核

明确标注这是**同一 agent 的证据化自审，不是独立盲审**。从原始材料重新核查，不仅复读自己先前写的清单。

| 审核项         | 必须核对的内容                                                                                                                                                 |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 正向充分性     | Golden 全文的必要目标、决定、条件、例外、权限、资金数据、兼容和非目标，有公开表达或真实可恢复 Base 证据；没有无授权删题                                        |
| 反向忠实性     | 两份公开文本的每个实质业务承诺，有 Golden 或本次明确批准决定的来源；没有新增阈值、功能、例外或强制方案                                                         |
| 未改题         | 业务目标、范围和关键边界不变，必要业务信息不依赖临时补答；不审核下游 PRD 格式或执行方式                                                                                               |
| 分析空间与泄漏 | 未暴露答案结构、完整技术方案、模块映射、私有台账或隐藏评测；正常业务事实不一概当泄漏                                                                           |
| 载体适配       | 对所有精确集合、接口／类型／字段／配置标识、例外矩阵与高密度规格分别检查 Query 去细节后主干、固定记录必要性、Base 可恢复性、剩余分析空间和保留理由；下沉不丢义 |
| 台账可追溯     | 精确源文、当前表达、版本、Base 证据及恢复记录可核验；counts 与末项实际一致                                                                                     |
| 输出契约       | 两份公开文档遵循第 9.0 节内嵌模板及回应关系要求，无残留占位符或历史模板依赖；业务表达与来源一致，不夹带下游 PRD 的章节、优先级、AC 编号或工具约束 |
| 访问与路径     | 公开文件位于 Harbor `query docs` 且互引有效，私有记录/快照位于任务目录，未将未知路径写成事实；不配置或验收下游 agent 权限 |

另做公开文件的静态泄漏扫描：私有路径、Golden 文件名、私有命题 ID、参考 Patch／Target／Oracle／隐藏测试、源 R/AC 映射与台账字段。搜索命中只产生候选问题，结合上下文区分真实泄漏、一般禁止性说明、业务术语，以及 Schema 必需的空 R/AC 模板；不按词命中机械删文，也不把未命中当完整安全证明。

载体适配必须独立给出证据，不能由“有来源”“必须公开”或“无泄漏”推定通过。风险信号不构成数量／长度阈值；判断依据是当前项目任务主干、不可推断的决定、整体公平性和预期分析工作，不加入固定项目正例。

在“输出契约”审核中逐话题执行对话质量检查，不因格式符合模板就判通过：

1. 是否围绕同一业务关切推进，是否夹带应另行组织的独立规格。
2. 每轮发言的作用及与前文的回应关系是否明确，角色是否只是装饰，是否重复宣读已经表达的内容。
3. 去掉角色名后是否出现独立验收条款拼接的风险信号；若保留当前表达，记录项目内理由，而非机械拆段或删信息。
4. 共同说明是否有主要承载位置，必要重述或引用是否有助于理解，而非把重复转成难以跟随的跳转。
5. 对已确认且可由现有材料解决的自然度问题，按“去重复 → 重组 → 改写”实际修正；不能仅列为剩余风险后宣布审核通过。

重写后将修改前后的公开表达与来源逐项对照，核对条件、例外、否定、精确集合、保护及兼容边界是否完整，决定是否被降格或新增。更新 S5 的表达位置、变化记录和指纹，再执行完整 S6。自然度改善与语义保持必须同时成立；无法在修正上限内解决的实质问题按第 11.2 节处理，不用文风理由掩盖信息损失。

每个问题记录 ID、类型、严重影响、原文位置、依据、修复建议和状态。对“没有泄漏”“没有遗漏”的结论说明检查范围，不以检查表打勾代替证据。

### 11.2 自动修正范围

遇到可由已冻结证据明确解决的问题，不把它留给用户再发一条 prompt。先保留旧稿，再回到对应阶段修正：

- 漏写已有明确业务条件、例外或非目标：补回必要含义，不复制完整答案结构。
- Query 过细但信息必须公开：保留任务主干，将精确选择下沉固定记录，按载体移动记账；每次修正后重新执行完整 S5/S6，不能只核对改动段落。
- Query 过度压缩、发言作用不明、角色装饰化或重复宣读规格：回到 S3/S4，按业务主题恢复清晰主干，去重复、重组并改写，不新增或删除业务决定；修正后逐项验证语义保持并完成全量复审，不只把问题记为风险。
- 无依据新增、身份误述、强制方案、私有泄漏：删除本轮输出中的无依据承诺或改成来源支持的表达；保留旧版本，不能删除源文件。
- 公开文件相互冲突、引用错误、编号重复、台账过时：修正本轮产物并同步更新来源和版本。
- 命题遗漏、错误归类或去重问题：回到 S1/S2，更新所有受影响统计，不只改报告数字。

一次修正轮次包含：问题集冻结 → 私有旧版快照 → 最小修正 → S5 更新 → S6 全量复审。最多 3 轮；连续无进展或到达上限仍有阻塞时，保留问题并结束为 `BLOCKED`，不无限循环、不宣称通过。若无需修正，可直接进入 S7。

不能自动修正的事项：选择尚未确定的新业务政策、扩大／缩小范围、改 Golden 或 Schema、改变评分依据、获取新权限、替换 Base、补造运行结果或启动试评。对这类问题保留明确阻塞及最小决策请求；不为了“完成”猜答案。

## 12. S7：最终复核、状态与交付

### 12.1 实际复核

交付前重新执行并记录：

1. Harbor 包 manifest、Golden 配对清单、Golden、code/test patch、Schema、设计文档与工作流输入 SHA-256 未变化；文档与最终 patch 仍配对。`REVISION_ROOT/<revision_id>/` 快照与修改前记录一致，当前产物与最新台账指纹一致。
2. `readable_baseline` 时核验 Base HEAD/tree 及证据内容指纹未变化；`package_only` 时记录源码核验不适用、基线仅为包内声明，确认没有命题被错误分配到 `base`，也没有未经确认的访问路径。
3. JSON 可解析，必须字段和 ID 引用齐全，父子关系无循环，主去向统计与去重末项数一致。
4. 所有命题的来源、公开表达、Base 依据、目标代码对应状态与未决项可定位；未决实现冲突阻塞相关命题；不能将私有目标事实当作 Base 可恢复事实，不能恢复已剪枝范围。
5. 三份公开文件位于 `OUTPUT_ROOT`，Query 与沟通记录非空、Schema 副本与 `schema_path` 逐字节一致；私有记录/快照位于任务目录，快照清单可核验，互引路径以声明的根解析有效。包内受保护输入未变化，新增 query docs 的 manifest 登记状态如实说明。
6. 每轮公开修正有旧稿、变化记录和新指纹；声称已验证的可逆改动具有实际正逆验证结果。
7. 最终自审覆盖正向、反向、改题、泄漏、载体适配、台账、契约与可访问性；所有载体风险项有证据，修正后经过全量复审。
8. 未生成候选 PRD，未启动模型、应用测试、服务、部署或外部试评；不把静态检查说成运行验证。

不把日志自身的最终哈希写进该日志后再声称仍然一致。需要日志指纹时注明它对应哪个检查点前缀或最终关闭后的文件，由最终回复／外部记录引用。

### 12.2 终止状态

| 状态                            | 含义与交付方式                                                                                                |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `COMPLETED_FOR_REVIEW`        | 六步、自审、必要修正及复核完成，未发现构造阻塞；可以提交人工审阅，不等于已获实验发布批准                      |
| `COMPLETED_WITH_DEPENDENCIES` | 构造完成，仅保留不妨碍业务文案成立的明确依赖，例如尚未实际部署；不把下游 agent 编排当作本轮验收条件 |
| `BLOCKED`                     | 有影响任务可解性、公平性、范围或权限的未决问题，或修正达到上限仍不合格；已有文本仅为草稿，不宣布公开包可投喂  |
| `INCOMPLETE`                  | 上下文／工具／时间限制导致未做完；说明已完成、未检查和恢复入口                                                |
| `PROCESS_FAILED`              | 必需文件无法读取、输入运行中变化、写入失败等过程错误；不虚构已完成产物或审核结果                              |

仅有 Harbor 包不自动导致构造阻塞。只有必要业务信息已公开、未以不可访问 Base 隐藏义务且相关审核通过时，才可按实际情况标 `COMPLETED_FOR_REVIEW` 或 `COMPLETED_WITH_DEPENDENCIES`；这些状态不代表基线已部署或可直接投喂。无法消除的必要信息缺口、文档/代码冲突或必须依赖但未获准的 Base 调查仍为 `BLOCKED`。不得静默降低原义务。

现有状态写进本轮日志、台账和报告并保持一致。不要因文件都已生成就标 completed，不继承旧台账的 `generated_pending_human_review` 作为本轮自审结果。

### 12.3 最终报告

写入 `PRIVATE_ROOT/final-report.md`，按以下顺序：

1. **结论**：终止状态、是否完成构造、是否可提交人工审阅、是否存在阻塞；明确未经真实试评。
2. **输入与边界**：run_id、mode、完整 Golden 文档清单与已读范围、输入指纹、base_access、包内声明/实际核验的基线身份、路径映射和访问限制；两类状态不得混写。
3. **产物**：公开三份文件和私有台账／日志路径及各自职责。
4. **信息分配摘要**：原始数、父项数、去重末项数、各主去向计数；不把当前历史样例的 523／550／576 等数字硬编码为新结果。
5. **保留的分析空间**：实际留给待测 agent 的调查、关联与验收组织工作；没有隐藏的必要业务决定。
6. **审核和修正**：八项审核结论、载体适配风险与理由、重要证据、问题及修正轮次，承认同一 agent 自审限制。
7. **未决与限制**：业务信息缺口、文档/代码冲突、尚未核验的基线事实、Schema 复制状态及新增 query docs 未纳入包发布清单的情况；不额外制定下游 PRD 或 agent 约束。
8. **交接**：列出 Harbor 包 query docs 三份文件的绝对路径、包版本与私有报告位置；后续 agent 如何使用、生成 PRD 或执行实验由独立流程决定，本轮不配置。

最终回复面向运行方，一次性给出结论、实际产物入口、关键信息分配与审核摘要、未决事项。不逐阶段索要确认，不自动启动待测 agent，也不将需要用户的新业务决定伪装为已经解决。
