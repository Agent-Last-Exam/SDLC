# 完整 Base → Target 的未剪枝 PRD 反向提取 workflow

## 1. 任务与执行约定

执行者负责从版本变化中重建产品需求，输出未剪枝 PRD，以及证明范围和证据关系的审计材料。最终结果回答：改变前支持什么、改变后支持什么、谁受影响、哪些条件下行为改变，以及怎样判断这些行为成立。

完整执行本文各阶段，在本阶段完成检查通过后继续。常规目录、拆分、命名和写作选择自行处理；缺失的实质业务决定、输入身份冲突或无法恢复的材料缺口才作为阻塞登记。不要依赖历史聊天推进任务，也不要把一个执行计划当成文档交付。

所有 case 采用相同阶段和数据契约。技术栈相关的准备、接口对比、测试解析和生成命令通过配置接入。不强制存在前端、后端、数据库、GraphQL、Docker 或 Harbor。

## 2. 范围与事实边界

### 2.1 本轮包含的变化

- 新增用户能力、公开接口能力和业务配置。
- 既有流程、状态、权限、错误、默认值、数据和兼容行为的变化。
- 用户可观察的缺陷修复、可靠性和安全边界调整。
- 弃用、删除旧能力和升级过程对使用者的影响。
- 支撑这些行为的跨仓库关系和必要运行约束。

本轮不按某个业务主体筛选需求。不能因为功能偏离主线、代码少、没有评分测试或实现昂贵而略过。

纯重构、依赖更新、工具链、CI、测试基础设施、格式和生成文本变化要登记归属；只有存在产品可观察的影响时，才将该影响提取为需求。不得为了覆盖所有文件而把内部函数、生成步骤或每个 migration 写成独立需求。

### 2.2 已有材料的角色

代码、测试和接口是事实证据；业务说明是意图证据；Git 历史是背景证据。已有 PRD 只作为明确版本的参考，不能覆盖本次完整变化清单，更不能用剪枝后的 PRD 反推未剪枝范围。

本流程重建的是“此升级实际表达的需求”。实现存在不等于原产品意图已被证明；意图与实现冲突时保留两侧证据，不能静默选择其中一侧。疑似实现缺陷不写成正常业务规则。

## 3. 输入、身份与工作目录

### 3.1 输入契约

配置定义见 [data-contracts.md](data-contracts.md)，入口模板见 [inputs.json](templates/inputs.json)。运行方必须提供：

- `case_id`、`run_id`、运行根目录、最终包内证据位置和模板身份。
- 每个仓库的完整基线身份与完整目标身份，或足以恢复两者的 patch 和准备方法。
- 环境适配 E、生产变化 G、测试变化 T 的角色与实际指纹；没有相应层时明确为空。
- 可读源码/包的位置，跨仓库配对关系，以及本次允许使用的准备和验证能力。
- 业务说明与已有文档的位置；没有时明确标记缺失。

代码与测试差异可以来自已拆分 patch，也可以从明确源码快照提取。尚未拆分的差异要根据实际内容分类；不能假定某个目录中的全部内容都属于同一职责。

### 3.2 分开登记四种身份

| 身份 | 含义 |
| --- | --- |
| upstream baseline | 环境适配前的源码起点 |
| production baseline B | 本次新增业务能力的比较起点，可能已经包含环境适配 E |
| full target | 完整、未剪枝的目标生产/测试状态及各自组合身份 |
| evaluation composition | 某次测试对比所使用的两侧组合，不自动等同于生产起点 |

每层登记实际 commit/tree 或等效内容指纹、patch SHA、应用顺序与准备命令。已包含 E 的镜像或工作树不能再次盲目应用 E。Git HEAD 相同但工作树不同也不能当成同一快照。

反向提取比较的是生产起点与完整目标的行为变化。本流程不规定 F2P/P2P 的评测组合，不重新校准评分清单。若引用既有运行结果，必须同时引用其测试组合、test patch、选择集、运行器和被测树身份。

### 3.3 运行目录

```text
RUN_ROOT/
├── inputs.json
├── sources/                         # 冻结输入、原始差异、方法/模板、引用证据及报告
├── inventory/
│   ├── evidence-index.csv
│   ├── change-inventory.csv
│   ├── requirement-catalog.csv
│   └── traceability.csv
├── artifacts/
│   └── prd.md
├── audit/
│   ├── audit-report.md
│   ├── run-status.json
│   └── artifact-manifest.json
├── worklog.md
├── scratch/                         # 临时工作树、依赖缓存等可再建内容
└── revisions/                       # 输入或产物修订前的不可覆盖快照
```

`RUN_ROOT` 是执行期间的独立暂存目录。最终必须将其冻结记录放入最后交付的 Harbor 包，默认位置为：

```text
HARBOR_TASK_ROOT/
└── golden-docs/evidence/reverse-extraction/
    ├── index.json                   # case/run/阶段、运行 manifest 哈希及发布归属
    └── <run_id>/                    # RUN_ROOT 的冻结记录，保留原目录结构
        ├── inputs.json
        ├── sources/
        ├── inventory/
        ├── artifacts/prd.md
        ├── audit/
        ├── worklog.md
        └── revisions/
```

最终包尚未生成时，第一条 workflow 交付 `archive_status=staged` 的冻结目录。第二条 workflow 必须归档并验证它，再完成 Harbor 包发布；不能只在包内记录宿主机路径。各运行目录按 run_id 保存，旧运行不覆盖，包内索引明确哪个未剪枝运行是本次剪枝依据。

`scratch/` 中的临时工作树、依赖、数据库和缓存不要求打入包；其中用于结论或复现的原始 diff、路径母集、命令输出和报告，必须先转存 `sources/` 并登记指纹。包内应保留完整输入 patch、环境与准备方法、模板及所引用的文件或上下文片段；大仓库以固定身份和恢复方法登记，不把临时工作树当成唯一来源。

证据的原始宿主机路径保留为来源记录，归档副本使用包内相对路径。片段副本须保存原来源身份、定位和片段哈希；原文件哈希与片段哈希不能混用。移到另一台机器后，应能在包内审核需求、变更及结论；只能依赖宿主机临时目录的证据不算完成归档。

输入、原始仓库和已发布包作为只读来源。必要的 patch 应用、代码生成和验证在运行目录的隔离副本执行。遵守实际授权范围；不要为了阅读改动原仓库或重新打包输入。

仅有 patch 也可开始索引和分析，但不足以确认基线或目标行为时，登记缺口。不能把删除行等同于完整 Base 行为，也不能把新增行等同于完整 Target 行为。

## 4. 全流程

```text
S0 输入核验与冻结
→ S1 完整变更盘点
→ S2 行为分析与候选需求
→ S3 需求聚合、边界与关系
→ S4 PRD 与 AC 编写
→ S5 双向充分性和必要性审计
→ 修复：回到最早受影响阶段，再执行下游检查
→ S6 冻结和交付
```

每阶段保存检查点、输入/输出指纹、已读范围、剩余项与下一步。结构检查成功和语义审计通过分别记录。下文的检查均为完成条件；现有工具未实现自动检查时，按同一规则逐项核对并留证据，不声称已经存在自动化检查器。

## 5. S0：核验并冻结输入

1. 解析配置路径，确认仓库、完整目标、环境、测试和文档属于同一个 case/版本。不要从旧目录自动寻找“看起来相近”的替代包。
2. 核对实际哈希、commit/tree、dirty 状态及已有 manifest 声明；声明不符时登记冲突。标签、目录日期和历史分数不能替代指纹。
3. 根据声明的组合在隔离位置恢复所需视图，或确认现有快照。记录哪些视图只有静态差异、哪些已经物化、哪些已有配对运行证据。
4. 多仓库分别确认身份，登记版本配对和可观察调用关系。未知配对不能按版本号相近推定。
5. 冻结 PRD 模板。优先使用本次指定模板；没有时使用目录内模板。模板修订也应留版本和来源。
6. 建立证据索引、初始运行状态和日志，将冻结输入和引用材料存入 `sources/`，记录原来源与归档副本的映射。输入不足时仍可完成可独立进行的索引，但相关行为不能标成已确认。

**完成检查**：所有输入角色明确；完整目标没有被剪枝目标替换；可访问性与声明身份分别核验；无法恢复或相互矛盾的必需输入已登记为阻塞。

## 6. S1：完整盘点变化

### 6.1 建立覆盖母集

以实际快照差异或全部 patch 为母集，枚举新增、修改、删除、重命名、文件类型/权限变化和二进制资源。Git 分支可能并行发布；提交列表和 merge-base 不能替代准确起点到准确终点的内容差异。

为每个仓库建立路径清单，再将变化划分为可解释的变更单元 `C-*`。一个单元表示一个内聚行为或内部目的，可以跨文件；一个文件混合多个目的时拆开。每个单元保留源路径、hunk/符号或等效定位，以及增、删两侧证据。

生产、测试、接口、迁移、生成配置、派生结果、资源、环境和文档分别分类。目录和文件名只是线索，内容才决定分类。混合 patch 必须登记跨职责内容，不强行按文件全部归入 G 或 T。

### 6.2 大型差异的处理

- 人工维护的生产变化逐单元分析；大文件分段读取，明确已读和未读范围。
- 接口使用语义差异盘点类型、字段、默认值、错误、权限、弃用和删除；文本重排不能掩盖合同变化。
- 生成物追溯权威输入、生成配置、工具版本和消费者。输入及合同分析完整后，允许合并登记机械输出，不要求逐行解释重复生成文本。
- 依赖、lockfile、资源和格式变化可合并，但要说明运行影响和合并依据；不能将未调查的大目录统一写成“自动生成”。
- 迁移区分模型结构、数据转换和升级任务，分析使用者可见的数据与兼容影响；不能全部视为工具产物。

没有代码生成或运行能力时记录限制。静态分析能够解释的部分继续进行；“生成命令成功”也不证明未声明输出可重新生成，需检查生成配置与产物的关系。

### 6.3 防止长尾遗漏

路径清单必须逐项关联变更单元。检查删除文件、低行数改动、错误分支、权限、配置默认值、异步副作用和调用方；不能只根据行数排序调查。

每个变更单元最终必须得到 `product / internal / derived / resource / no_semantic_change / unresolved` 之一。类别定义见数据契约。分类理由和证据必填，未调查项保持 `unresolved`，不能先填排除再算覆盖完成。

**完成检查**：来源路径全部登记；人工变化的所有 hunk 或等效变化范围有归属；派生物和批量内容的聚合可解释；未读和未映射范围可定位。

## 7. S2：还原变化前后的行为

对每个可能具有产品意义的单元，按同一问题表调查：

| 问题 | 要保存的事实 |
| --- | --- |
| 谁触发？ | 用户、调用方、集成方或运维角色；避免凭空扩展人群 |
| 何时发生？ | 前置状态、输入、配置、权限与适用范围 |
| Base 如何处理？ | 已有能力、限制、错误或确实不存在的能力；附基线证据 |
| Target 如何处理？ | 成功、失败、边界、状态变化、数据和外部副作用 |
| 谁会受影响？ | 页面、API、外部系统、数据升级和跨仓库消费者 |
| 属于什么变化？ | 新增、行为调整、用户可见修复、弃用/移除或兼容变化 |

证据核对顺序为：生产实现及上下文 → 测试输入/断言 → 接口、迁移与调用方 → 业务说明 → Git 背景。该顺序用于调查，不是冲突时自动覆盖其他材料的优先级。

测试帮助识别场景、边界与预期；只验证测试工具的用例不成为业务需求。缺少测试不自动排除实现支持的行为。测试与实现冲突时记录两侧证据，必要时在配置允许的环境里定向验证。

缺少可靠 Base 证据时，写“Base 状态未确认”，不能宣称新增。未被代码、合同或测试支持的业务目的标记为推导；存在数个同样合理的规则时登记待决，不能挑一个编成事实。

验证按证据需要执行，不默认构建所有镜像或跑全量套件。复用兼容的既有环境；历史报告只有在身份与条件匹配时才能引用，且标明“历史验证”。未执行验证不得写通过。

**完成检查**：每个产品候选都有前后行为、角色、触发条件与证据状态；异常、安全、兼容和跨仓关系已调查；缺口与冲突可追踪。

## 8. S3：聚合需求并建立边界

### 8.1 聚合规则

按独立用户目标、业务规则和公开合同聚合候选，不按文件、函数、commit 或测试数量生成需求。

- 同一需求横跨多个仓库时合并，保存两侧证据和责任边界。
- 一个条目出现独立用户目标、独立适用范围或不同兼容政策时拆分。
- 同义候选去重，保留所有来源，不删除来源链。
- 修复、移除和兼容行为可成为需求或已有需求的子行为，不能因为“不是新功能”消失。
- 纯实现方式登记为内部变化；若支撑产品行为，关联该需求，避免重复写成另一项需求。

发布 `Rnn` 与 `AC-nn-m` 后不重排、不复用。后来拆分或合并在目录中保留旧 ID 和继承关系，新项使用新 ID。未剪枝需求不因后续剪枝而从历史目录中消失。

### 8.2 需求关系

记录 `depends_on`：完成该需求必须满足的其他需求，以及 `related_to`：共享用户/数据但未证明必需的关系。依赖关系循环时核查是否应合并或拆出共享合同；不要人为切断真实关系。

这份关系用于后续剪枝分析，本阶段不确定主体，不计算删除顺序，也不因弱关联删除需求。

### 8.3 来源、必要性与优先级

有业务原文时引用原文和出处；没有时明确写“由版本差异反向提取”，引用 `C-* / E-*`，不得伪造 Instruction。

这里的必要性是：该条目是否必须出现在完整升级 PRD 中，是否与其他条目重复，是否错误提升了实现细节。它不证明该能力在产品战略上绝对必需。

优先级遵守输入提供的定义。已明确的优先级与分析者推定的优先级分别登记。没有依据但模板必填时，标记“暂定”并给出理由；若优先级将作为后续剪枝/评分依据，必须在使用前确认，不能将推定当成产品决定。

**完成检查**：业务单元都有需求归属；内部单元都有理由；重复和混合条目已处理；ID、来源、关系和推定决定均显式登记。

## 9. S4：按模板写 PRD 与 AC

PRD 以业务语言表达背景、角色、场景、需求、范围和非目标。没有证据的商业动机、成功率、性能阈值和优先级不能补造。背景推导应与明确事实区分。

每条需求说明：要改变什么、解决什么可证实的问题、触发与适用条件、主要业务规则，以及必要的异常与兼容行为。完整范围包含所有产品行为变化；内部实现排除写在范围说明中，其详细理由保存在台账。

AC 使用 Given/When/Then 或等价的条件—动作—结果结构，一条对应一个可判定的场景。按适用性覆盖成功、输入边界、状态、权限、错误、默认值、兼容、异步完成和副作用；不为了凑数量为所有需求机械套同一组场景。

- 函数、类、文件、migration 编号、索引算法和生成命令放在证据清单，不规定为产品验收条件。
- API 名称、公开字段、错误码、事件和弃用版本可以保留，前提是它们本身属于使用者依赖的合同。
- “已实现”“代码存在”“测试全通过”不能替代业务 AC。
- 异步操作区分请求被接受与业务完成，描述使用者能观察到的完成条件。
- 不编造毫秒、条数、容量或时间阈值；有证据的限制才写入。
- 技术证据不足的 AC 保持草稿并登记缺口，不能用更含糊的措辞隐藏不确定性。

同步更新需求目录和追踪清单，保证正文的所有 R/AC ID 与台账一致。指定模板没有技术附录时，证据文件单独交付，不擅自改模板章节。

**完成检查**：模板章节与字段完整；无占位符和未注明的推定；AC 可观察且不锁定内部实现；正文与目录一致。

## 10. S5：双向充分性与必要性审计

### 10.1 变化 → PRD：充分性

逐项检查覆盖母集：

1. 每个产品单元都映射到实际 PRD 条目，必要场景有 AC。
2. 每个接口、持久化、迁移、权限、默认值和用户可见删除行为都能定位需求；不只核查新增接口。
3. test patch 中表达产品行为的新增/修改/删除测试都有解释；共享回归、内部适配和无变化测试不伪装成独立新需求。
4. 派生结果能追溯输入，输入中的合同变化已覆盖；不能通过给生成文件贴标签跳过公开行为。
5. 每个非产品单元有分类理由和证据；抽查可以发现问题，但不能替代逐项归属。

### 10.2 PRD → 变化：必要性与忠实性

逐条检查 R 与 AC：

1. 有确切变化及事实证据，或有明确来源的产品决定；既有能力作为上下文而不是冒充新增。
2. 角色、前提、否定、例外和结果忠实于材料，没有扩大或缩小适用范围。
3. 没有重复条目、纯函数级条目、未证实的能力或把疑似缺陷正常化的规则。
4. 测试确实验证所引用的行为，不能只因测试名相关就标已覆盖；多个 AC 可以共享测试，一个 AC 也可以由多个测试支持。
5. 没有自动化测试覆盖时明确登记 `test_gap`；如静态依据充足，可以完成需求提取，但不能称已自动验证。

### 10.3 三个独立结论

审计报告分别给出：

- **范围覆盖**：输入母集是否盘点完整、产品变化是否都有归属。
- **语义忠实**：需求与 AC 是否符合证据，是否存在未解决冲突。
- **验证强度**：静态支持、历史运行、本轮运行及缺少测试的实际范围。

哈希一致、CSV 可解析、映射比例和 reward 只支持各自结论，不能互相替代。全量文件归属不等于行为空间 100% 被证明；“未发现遗漏”须附实际分析范围和限制。

### 10.4 修正与结束

将发现写入 `audit-report.md`，附定位、影响、处理决定与证据。格式错误、引用错误和可证实遗漏直接修正。输入错配、意图冲突、关键行为不可确认保留为阻塞；不能通过删除需求、改分类或缩小母集消除问题。

修复后重查受影响的上游和下游关系，再重做全局 ID、路径、分类、R/AC 与追踪完整性检查。配置中的修复轮数用于防止无限重写；耗尽仍不通过则交付草稿及恢复入口，不能宣称冻结成功。

**完成检查**：无未归属单元、无无依据条目、无未解决阻塞；所有验证限制明确；可接受的非阻塞缺口有影响说明和处理依据。

## 11. S6：冻结与交付

输出：

- `artifacts/prd.md`：未剪枝 PRD。
- 四份 inventory 清单：证据、变更、需求和追踪关系。
- `audit-report.md`：范围、语义和验证三个结论，以及全部发现。
- `run-status.json`：阶段状态、交付状态、计数、限制和恢复入口。
- `artifact-manifest.json`：本次输入与产物身份、模板/流程版本、父运行、内容指纹及最终包内归档位置。
- `worklog.md`：实际操作、失败与修正、读取和验证范围、检查点。

交付状态：

| 状态 | 条件 |
| --- | --- |
| `ready` | 范围和语义检查通过，约定验证完成，无阻塞或需说明的验证缺口 |
| `ready_with_limits` | 范围和语义检查通过，仍有已明确影响的非阻塞验证限制；不能表述为全量运行通过 |
| `draft_blocked` | 输入身份、产品决定、关键证据或语义冲突未解决，不能作为最终需求基线 |
| `incomplete` | 尚有未执行分析或未完成审计，附检查点和剩余工作 |

在 manifest 中记录相对路径、字节数和 SHA-256；manifest 本身不包含自己的哈希，外部发布绑定另行处理。冻结前核对只读输入未改动。修订已冻结结果时创建新版本与父关系，保留旧版，不直接覆盖历史。

冻结顺序为：完成正文与清单 → 完成审计 → 写入最终状态和最后检查点 → 计算产物哈希 → 写 manifest → 只读复核。复核失败则修正并重新执行冻结顺序；成功后不再追加会使已登记哈希失效的日志。最终 manifest 必须登记全部约定交付文件，不能只挑已通过的文件。

### 11.1 随最终 Harbor 包归档

1. 冻结前将所有结论引用的输入、差异、报告和修订依赖转入 `sources/` 或包内已有的固定来源，补齐证据清单的归档路径及哈希。原始输入配置保留来源语义，归档文件的可移植位置由 manifest 和证据索引解释。
2. 首次提取时包通常尚未生成，运行状态登记 `archive_status=staged`，目标位置登记为 `golden-docs/evidence/reverse-extraction/<run_id>`。PRD 的 ready 状态不等于最终包已归档完成。
3. 第二条 workflow 把冻结目录中的 `sources/、inventory/、artifacts/、audit/、revisions/、inputs.json、worklog.md` 逐字节复制进最终包。所有保留运行和父修订均有包内位置；不在复制后静默改写已冻结内容。
4. 归档后重算全部文件哈希，与运行 manifest 一致；从包内相对路径核对证据、父修订和 PRD 追踪关系。引用包内已有文件时核对其固定哈希，不因为最终剪枝 patch 的文件名相同就替代原始完整 patch。
5. 在包内 `index.json` 登记归档状态 `archived_verified`、run 路径、运行 manifest 哈希、case_id、run_id、`full_unpruned` 范围、父运行和本次剪枝依据。归档状态记录在包内索引，不回写冻结 run-status 的 staged 状态。
6. 将证据目录和索引纳入包的证据清单与完整性校验，由后续打包流程通过指定 exporter/发布工具登记。不能绕过 exporter 手改已发布 Harbor 根 manifest。避免运行 manifest 与包根 manifest 相互包含哈希形成循环；包级清单引用运行 manifest，运行 manifest 只登记归档位置。

未剪枝 PRD 和原始完整 patch 在此目录属于历史审计材料，不能被第三条 workflow 当成剪枝后的活动需求。证据目录属于出题方/审核方资料，遵守最终包的 Golden 可见性规则。

第二条 workflow 读取本次 `prd.md`、需求目录、关系、变更清单和审计状态。`draft_blocked/incomplete` 不能当成已确认剪枝依据；`ready_with_limits` 必须携带限制及其对后续决策的影响。

## 12. 批量执行、恢复与变更失效

每个 case 使用独立运行目录和稳定身份。批处理可调度不同 case；同一 case 的变更分析可按领域拆分，但必须合并去重、检查跨域调用，再统一分配和冻结需求 ID。是否使用多 agent 由运行方配置，本流程不要求特定会话或协作工具。

共同流程负责盘点、证据关系、写作和审计；项目配置只提供仓库、物化命令、接口提取、生成、验证和模板。新协议可通过配置命令产生可定位的合同差异；不支持的适配能力记录缺口，不能返回空结果并算完成。

### 12.1 中断恢复

核对配置、输入指纹、产物指纹和最后检查点；从最早未完成或失效阶段继续。阶段上下文必须可由清单和日志恢复，不能依靠模型记忆。输入未变化时复用已有有效证据，避免重复读取和运行昂贵验证。

### 12.2 输入变化后的失效范围

| 变化 | 至少重做 |
| --- | --- |
| baseline、环境或目标身份变化 | S0 起重新盘点、行为对比及全部下游；明确内容不变的来源可核验后复用 |
| code/test/接口/迁移/生成输入变化 | 核对身份；重做相关 S1/S2，传播至聚合、PRD 和全局审计 |
| 业务说明或已确认产品决定变化 | S2 起重查受影响行为、来源和冲突，再更新 PRD/审计 |
| 模板变化 | S4 起重写结构并重做审计；模板新增字段所需事实回到 S2 补证 |
| 文案或证据路径修正 | 核验语义是否变化，重查引用及全局一致性，生成新交付指纹 |

缓存以内容身份及分析方法版本为依据。若命令、解析器、环境或测试条件变化，旧运行结果需重新判断适用性；不得仅因同一个 case_id 就继承已通过状态。

## 13. 通用异常处理

| 异常 | 处理 |
| --- | --- |
| 完整目标未提供，只有剪枝结果 | 登记输入缺口；不能恢复不存在的需求或声称未剪枝 PRD 已完成 |
| patch 不能应用、树不匹配 | 保留错误及身份，修正准备方法或输入；不修改业务 patch 来凑目标树 |
| 生成物缺少输入/入口 | 登记派生链缺口，核查合同及消费者；能静态确认的继续，关键行为不明则阻塞 |
| 意图、代码、测试互相矛盾 | 分别记录材料和影响；证据不足时保持待决，不自动选边 |
| 缺少产品测试 | 登记 test_gap；区分需求支持与运行验证，不能删除该需求 |
| 验证受网络、服务、数据或工具限制 | 保留失败事实，区分环境问题与产品问题；不随意修改断言或超时 |
| 业务背景/优先级缺失 | 显式记录推导或暂定；影响后续决定的内容等待明确确认 |
| 输入太大、时间不足 | 保存未读范围和恢复检查点，交付 incomplete；不把抽样改称全量 |

## 14. 最终检查清单

- [ ] 输入是完整未剪枝版本，所有仓库和环境身份配对。
- [ ] 生产基线、测试树和评测组合分别登记。
- [ ] 全部变化路径和变化单元有证据及归属，包括删除和长尾。
- [ ] 内部、派生和资源分类有理由，公开行为没有被分类隐藏。
- [ ] 每个 R/AC 都有依据，来源与推定不混淆，编号稳定。
- [ ] 成功、异常、权限、默认值、兼容及异步边界按适用性覆盖。
- [ ] PRD 按指定模板写成业务文档，技术追踪独立保存。
- [ ] 双向审计完成，阻塞、测试缺口和验证限制如实登记。
- [ ] 结构检查、语义审核和运行证据的结论没有混用。
- [ ] 交接材料可以独立恢复，产物指纹和父版本可追踪。
- [ ] 冻结记录可按包内相对路径审核；第一条 workflow 已交付待归档目录，最终 Harbor 发布前已逐文件归档验证并登记包内索引。
