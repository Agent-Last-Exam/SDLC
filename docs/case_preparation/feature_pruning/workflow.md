# 功能剪枝 → 标准 Harbor 包 workflow

## 1. 目标与执行方式

执行者将完整升级裁剪为一个明确、关联性强且可验证的产品范围，生成标准 Harbor task，并保留从未剪枝需求到最终实现的完整证据链。

按本文阶段连续执行。已有范围授权覆盖的候选、常规实现、隔离工作树、验证和导出无需逐轮再确认。新增主体、更改保留政策、突破兼容边界或测试排除政策，属于实质范围决定：登记待决，继续不依赖它的工作。证据不足不等于授权删除。

执行配置与字段见 [data-contracts.md](data-contracts.md)。任何仓库数量、测试数量、镜像名和 exporter 路径都来自配置，不从历史 case 复制。

## 2. 输入与不可混用的身份

### 2.1 必需输入

- 第一条 workflow 的 PRD、变更/需求/追踪清单、审计、运行 manifest 和归档材料；状态为 ready 或已评估限制的 ready_with_limits。
- 完整生产基线、未剪枝目标及生产/测试差异；持续剪枝时还提供上一轮已验收父树和累计差异。
- 已确认的主体目标、保留政策、外部合同及历史数据库支持范围。
- 环境、生成与迁移方法、原评测选择及其校准来源、测试 ID/报告适配方法。
- 指定 Harbor schema、builder/exporter、执行命令、目标目录、运行权限与资源配置。

没有可信父验证时，先恢复原始目标并运行原冻结合同，或按 P6 方法建立父校准；无法证明起点可用时登记阻塞，不能通过剪枝消除原输入的未知错误。

### 2.2 身份模型

```text
U = upstream baseline
B = U + 环境适配 E                # 制作/Agent 的生产起点
F = B + 完整 G + 完整 T           # 完整未剪枝组合目标
W0 = F 或上一轮已验收剪枝树
Wk = W(k-1) + 第 k 轮剪枝增量

Gk/Tk = 相对固定 B 导出的累计生产/测试 patch
Ck = B + Tk                       # 评测 Base/C
Dk = B + Gk + Tk                   # 评测 Target/D，与 Wk 内容一致
```

B 与 C 是不同身份。环境镜像若已经包含 E，不再应用一次 E。两侧使用同一 Tk，只有 D 额外包含 Gk；测试与适配工具不能把目标生产实现带入 C。

每仓库分别记录 U、B、code-only、test-only、C、D 和阶段父树，使用实际 tree 或等效内容身份。`U + T` 不自动等于 `B + T`。上游目标 commit 不自动等于剪枝后的 D。

本流程采用上述共同 T 的 C/D 合同；不得中途换成 environment-only C。生产环境本身是否健康，另用 B 的构建/启动/迁移检查回答，不能把 C 的预期 F2P 当成环境全部失效。

## 3. 运行与包内目录

```text
RUN_ROOT/
├── inputs.json
├── sources/                          # 原始输入、方法、模板与引用材料
├── decisions/
│   ├── scope-policy.md
│   ├── scope-decisions.csv
│   ├── impact-inventory.csv
│   └── stage-plan.csv
├── stages/<stage_id>/
│   ├── stage-record.md
│   ├── snapshots.json
│   ├── incremental/                  # 父树 → 本轮树的 code/test 差异
│   ├── cumulative/                   # 固定 B → 本轮结果的 patch
│   ├── reports/                      # 原始检查、测试、失败与重跑记录
│   └── test-ledger.csv
├── artifacts/
│   ├── prd-golden.md
│   ├── patches/
│   ├── patch-manifest.json
│   └── builder/                      # 冻结 builder 配置与输入清单
├── calibration/
│   ├── selection.json
│   ├── calibration.json
│   ├── test-ledger.csv
│   └── reports/                      # C/D 原始报告、解析、评分及选择复核
├── audit/
│   ├── final-audit.md
│   ├── run-status.json
│   └── artifact-manifest.json
├── worklog.md
├── revisions/
└── scratch/                          # 临时工作树、容器和可再建缓存
```

执行期间使用隔离 RUN_ROOT；最终冻结记录进入 `golden-docs/evidence/feature-pruning/<run_id>/`。第一步记录进入 `golden-docs/evidence/reverse-extraction/<run_id>/`。sources、decisions、stages、artifacts、calibration、audit、日志和必要修订均随包交付；scratch 中用于结论的输出先转存，临时工作树和缓存不打包。

原始路径可保留作 provenance；实际审核引用须有包内相对副本、固定哈希和原定位。第一步材料按其冻结版本复制，不能修改历史 PRD 或哈希来与最终范围“对齐”。

原仓库、输入包和已发布版本只读。开发修改与重置只作用于本次隔离工作树。环境复用采用持久容器和挂载；镜像不是可原地修改的源码交付，不能用 docker commit 替代可复现构建。

## 4. 阶段与完成检查

```text
P0 输入配对、父结果与能力检查
→ P1 主体与逐需求决定
→ P2 影响面、聚类及执行顺序
→ P3 一轮生产与测试剪枝
→ P4 本轮完整性、保留合同及快照验收
→ P3/P4 处理下一轮
→ P5 最终范围与累计 patch 冻结
→ P6 共同 T 下的 C/D 校准和选择复核
→ P7 标准 builder/exporter 导出
→ P8 归档、包级验证与交付绑定
```

各阶段保存输入身份、输出身份、实际命令、报告、发现和恢复入口。校准发现实现问题返回最早受影响阶段，不能在评分环节修改选择来掩盖问题。完成检查可以工具化，但本目录只提供契约与模板，不宣称自动检查器已经实现。

## 5. P0：核验起点与准备能力

1. 校验第一步文件、指纹、完整范围和审计结论。影响本次删除判断的缺口必须先解决；非阻塞限制记录到本次交接。
2. 恢复 U/B/F 或明确的父 W，核对实际 patch、tree、dirty 状态和环境。持久容器要核对当前挂载、文件指纹和服务状态，不能按旧容器名认定版本。
3. 原选择集只有在 E/G/T、C/D 组合、ID 归一化、报告解析和环境匹配时才能作为父验收证据；不把其他版本数量或旧 selection 继承成当前标准。
4. 固定生成输入/输出、migration 支持范围、应用顺序政策、测试 ID 解析及排除政策。原输入的未解决非通过测试仍留痕，不假定全仓库全绿。
5. 核对 exporter 的真实版本、输入布局、模板与所需依赖目录；先检查命令/能力，不因旧案例用过某路径就认定可用。
6. 冻结输入、方法、原报告及第一步材料，建立本轮状态。缺少工具或关键数据时，继续可独立完成的范围分析，无法生成最终包时登记阻塞。

**检查**：起点可恢复，第一步与完整实现配对，原验证适用范围明确，必需工具及真实路径已核验。

## 6. P1：主体、保护规则与逐项决定

### 6.1 先明确主体

用用户目标、参与角色、完整业务链和成功条件定义主体，记录决定来源。产品主体不能从代码行数、测试数量、PRD 优先级或 agent 偏好自动推出。第一步暂定的优先级不是本步的删除授权。

固定默认保护范围：主体及其必要上下游、数据完整性、权限/安全、可靠性修复、共享公开合同、必须维持的兼容行为，以及目标版本已有的旧能力移除。撤销安全修复或恢复已淘汰代码不能作为普通剪枝。

需要突破保护规则时，要求明确的产品决定和变更方案，不自动按“主体外”操作。复杂度、收益和风险可支持保留决定，但不能单独证明每行代码具有绝对必要性。

### 6.2 按 R/AC 判断

为完整 PRD 的每个活跃需求和必要子行为登记决定：

| 决定 | 依据 |
| --- | --- |
| retain | 主体、必要依赖、保护行为，或明确决定保留 |
| remove | 独立新增能力，与主体无必要依赖，可完整分离，且在已确认删除范围内 |
| partial | 混合需求中某些子行为可移除，其余保留；列出具体 AC/合同边界 |
| pending | 主体关联、授权或可分离性仍不明确，不实施删除 |

审查直接业务贡献、上下游依赖、共享协议/数据、跨仓闭环、独立入口和可分离性。需求同处一个目录不证明相关；共用底层模块也不证明不可拆。

决定关联第一步稳定 R/AC/C/E ID，并保留来源与理由。删除不重排 R/AC 编号。部分保留必须列出被删与保留的行为，不能只写“删掉 UI”而忽略仍被客户端消费的合同。

**检查**：每个需求有决定和依据；没有未授权删除；必要依赖已纳入保留集合；pending 不能混入删除计划。

## 7. P2：影响面、聚类与顺序

### 7.1 全链路影响面

每个删除子行为先建立完整影响清单：入口/路由、领域模型、服务与任务、权限、配置默认值、数据迁移、API/事件、前端和其他消费者、生成输入与配置、生成结果、依赖、测试/fixture/factory/story、资源和文档。

用符号、公开合同、引用和依赖调查两侧及跨仓消费者。共享文件标明确保留部分，不能整文件回退。分类为 exclusive_remove/shared_keep/shared_split/derived_update/unresolved，并登记处理方法和验证方法。

### 7.2 按依赖聚类

根据需求与调用依赖构图；把必须一起修改的消费者/提供者和合同变更聚成原子批次。优先低耦合、可独立验证的叶子，随后处理共享合同；确有循环依赖时合并批次或先建立兼容中间状态。

顺序由依赖与风险决定，不固定为“前端 → 后端”或某组 R 编号。共享底层能力等最后消费者处理后才能移除。每批声明父快照、删除范围、保留范围、关联仓库、检查和回退方法。

### 7.3 迁移策略

在“重新制作升级目标，从未引入被删能力”的场景，可删除仅属于该能力的新 migration，并重接仍保留的迁移图。支持已经运行完整目标的数据库时，不能改写其已执行历史，需明确补偿迁移和数据处理方案。

是否需要空库、B 数据库升级、完整目标数据库升级和反向迁移，依据声明支持范围与受影响数据决定。工具生成的 migration 骨架不自动证明数据转换正确。

**检查**：影响面无 unresolved 删除项，生成链和共享消费者有归属，阶段依赖有效，迁移策略与部署场景一致。

## 8. P3：实施一轮剪枝

1. 从上一轮已验收 W 创建只读父快照和本轮隔离工作树。首次从已核验 F 开始；不要重新应用完整目标覆盖前轮修改。
2. 按阶段影响清单移除独立入口和调用，处理提供者、任务、模型、持久化和公开合同；保留共享最小行为。
3. 恢复 B 已有且保留范围需要的行为；新增适配代码逐项说明必要性。删除功能不意味着 diff 中只有删除行。
4. 更新配置与声明支持的 migration。不要为了省事删除整个共享测试、migration 链或接口文件。
5. 修改权威接口/operation/模型/文案输入，使用配置的工具重建受影响 schema、client、factory、locale、lockfile 和其他派生产物。
6. 生成输入、配置、结果和消费者一起检查。删除 output 配置而保留消费方与旧结果是生成链缺陷；“命令成功且文件仍在”不能证明可再生。必要时在干净输出位置重建并比对。
7. 同步测试：删除仅验证被删能力存在的测试；拆分共享测试并保留回归；按需求增加删除合同守卫，确认能力缺失且共享能力仍成立。
8. 将本轮测试变化登记到 test-ledger，区分 removed_for_scope/shared_rewritten/id_changed/added_guard/unchanged/unknown；关联明确产品决定和源码差异。失败不构成删除测试的理由。

本轮不修改测试断言、超时、重试或 skip 来制造通过；合理的框架兼容适配要单独记录理由，并核对未改变行为标准。

删除守卫可纳入共同测试全集或作为 Target-only invariant，分类由声明合同与实际 C/D 结果决定。后者单独运行、单独报告，不伪装成 F2P/P2P；也不能用它替代保留需求的回归覆盖。

**检查**：生产与测试边界清楚，保留能力未被误伤，派生链可解释，所有测试变更有理由与证据。

## 9. P4：本轮验收与快照

### 9.1 结构与合同

按影响面执行 patch、残留符号、完整 API/事件合同、类型/构建、生成一致性、服务启动和声明范围内的迁移验证。普通性能或网络测试不因名单外失败扩大正式验收，但若暴露了保留合同错误，必须调查并登记影响。

先执行本轮受影响测试和守卫，再执行最新有效累计 F2P/P2P 选择；直接按精确 ID 运行，避免模糊标题选择和重命名漏选。setup/seed 是运行依赖，单独登记，不计评分数。

当 T、E、ID 或测试语义变化使父选择分类失效时，必须按 P6 相同规则做本轮校准或重新分类，再验证；不能只删除失效 node 后沿用旧分母。改变运行器或 fixture 也需核对可比性。

### 9.2 两类 patch

导出父 W → 当前 W 的增量差异，用于审查本轮；另从固定 B 导出累计 G/T，用于最终交付。处理新增、删除、重命名、二进制、链接、权限和文件模式，不能只保存修改过的已跟踪文本文件。

分层按内容职责和消费关系判断，不能机械认为所有生产文件属于 G、所有 tests 目录文件属于 T。E 的环境变更不重复进入 G；测试支撑不得偷偷实现待评业务。生成配置与产物的分层应保证声明视图可构建和再生成。

在干净 B 上应用累计 patch，核对实际结果等于 W。默认要求 code→test、test→code 得到相同目标；若标准工具明确采用固定顺序且确实不能交换，配置 ordered 并提供理由，验证每个声明顺序，不能冒充双顺序成功。使用的零上下文/二进制 patch 能力必须与正式 applier 一致。

### 9.3 推进条件

所有保留的有效选中 ID 通过，无 missing、未收集、非预期 skip 或报告异常；本轮结构/迁移/生成/守卫检查通过；增量准确还原父→本轮，累计准确还原 B→W。只有完成这些检查的 W 才成为下一批父快照。

失败时保留日志、报告与试验树，不变更已验收父树；修正本轮或重新决定边界。遇到未预见的主体/保护依赖，停止该删除并标 pending/retain，不顺手扩大删除范围。

**检查**：父/子身份、增量/累计差异和报告配对；测试变化逐项审计；快照清晰且下一轮可恢复。

## 10. P5：最终范围与累计实现冻结

### 10.1 最终 PRD

从第一步完整 PRD 派生 `prd-golden.md`，保持指定模板和稳定编号：retain 保留，remove 不作为活动条目，partial 只保留批准的活动行为及 AC。历史删除和原 ID 存在 scope-decisions 与原 PRD 中。

保留的 AC 若因兼容行为变化确需修订，保留旧 AC 和继承关系并分配新 ID，不能用旧编号承载相反语义。没有证据的新增业务规则不得在这一阶段补入。

检查最终范围 → 实现/测试、实现/测试 → 最终范围：删除入口、数据、合同、生成符号和专用测试有清理证据；仍保留的源码变化有活动需求或合理内部归属。评分通过不证明删除决定正确。

### 10.2 环境升级的迁移

若制作过程中换用架构/环境升级后的新 B，冻结旧成果，以共同来源做语义合并。生产工具链以已确认 E 为依据，业务范围以已确认剪枝结果为依据，已删除功能不能复活。

直接 diff 新 B 与旧 W 只有在重叠环境实现相容且无反向覆盖时才成立。核查依赖、生成配置、migration、接口和共同改动文件，重新生成派生结果；不能拼接两个 patch 或按 ours/theirs 粗选。

新 B 意味着新的输入身份，累计 G/T 重新从新 B 导出，评测组合与选择按 P6 重校准；旧测试报告不能仅凭“业务没变”自动继承。

### 10.3 冻结身份

冻结 E、最终 G/T、B/code-only/test-only/C/D 树、环境身份、生成器输入、测试运行器/ID/报告解析版本、数据初始化方法和范围。patch manifest 是真实文件与树的记录，不能用元数据修正掩盖应用结果不符。

**检查**：最终 PRD 和实现闭环、删除结果完整、保护能力存在；最终 patch 可从正确 B 干净复现；不存在未记录的环境替换。

## 11. P6：校准与冻结评测选择

### 11.1 明确候选全集与政策

校准候选全集由事先声明的业务/回归测试范围及最终 T 的有效测试确定，不直接等于原 selection，也不要求所有 case 都跑整个源码仓库。覆盖正式测试相关的全集；名单外测试、基础设施、setup 与 Target-only invariant 的处理各自声明。

若缺少可信全集，需要 collection/枚举调查；它与最终仅执行 F2P/P2P 的验收不同。不能只运行通过的测试再称完成校准，或将未执行测试从候选分母移走。记录 universe 哈希及候选数。

排除政策在读取本轮结果前固定。政策可允许已说明原因的不稳定外部测试或环境限制，但每个排除都要保存原 ID、状态、证据、影响和审核决定。运行中发现的保留业务回归必须修复；不能自动把所有 D 非通过项排除后得到 reward=1。

### 11.2 C/D 构造与运行

在干净隔离视图构造 C=B+T，D=B+G+T，两侧同一 T、环境和必要 seed。记录实际组合与各仓库树，防止 prepare/reset/mount 指向其他包。

按配置的适配器执行 collection 和候选测试，保存原始报告及归一化结果。可复用身份、条件与覆盖范围一致的历史报告；明确引用原报告和理由，不称本轮重跑。

pytest/Jest/Playwright 或其他框架的 ID 通过结构化映射归一化，保留参数、文件、suite、重名和运行上下文。解析器状态使用实际框架语义；成功、预期失败、expected、skip、timeout 和错误不能靠词面猜测。

### 11.3 分类规则

| C | D | 处理 |
| --- | --- | --- |
| pass | pass | P2P |
| 可靠的行为失败 | pass | F2P |
| 已证明由目标能力缺失造成的可归属 missing | pass | 按固定政策纳入 F2P，保存具体归属证据 |
| skip/基础设施异常/无法解析/未执行 | pass | 无法直接分类，调查或按明确政策审计，不冒充业务 F2P |
| 任意 | fail/error/missing/非预期 skip | 阻塞或逐项政策排除；保留失败及影响，不能当成通过 |

整文件 import/collection 失败不等于其中每个 node 有可靠的 Base 行为失败。只有适配器能证明具体 node 缺失原因、目标能力归属且 D 真正通过时，才可按 missing 政策分类。报告丢失或 selector 漏选始终是运行问题。

共同 T 保证比较同一测试语义，不保证测试数量等于历史版本。测试重命名、参数变化、分拆/合并要有证据映射，不能靠相似标题自动判断同一 node。

### 11.4 重跑与报告合并

重跑政策固定：触发条件、次数、seed/worker、选择方式和合并规则。不得反复挑通过结果替换失败；符合声明环境重置政策的有效重跑可按精确 identity 合并，保留全部尝试和作废理由。改断言、T、超时或行为配置后，属于新版本，不是原报告的重跑。

### 11.5 变化审计与冻结复核

对每个历史候选/选择 ID 登记 retained、removed_for_scope、renamed、reclassified、added、policy_excluded 或 unresolved。指出对比两套选择是否同口径，不能把校准方式变化误称剪掉了大量测试。

生成 selection，F2P/P2P 不重叠，counts 与节点数组一致，每个选中项有 C/D 证据；计算 SHA。测试 ID 排序规则固定，不按任意报告顺序得到漂移指纹。

冻结后使用实际 verifier 执行选中测试或同身份的完整有效报告，复核 C 的 P2P 全通过、F2P 没有通过，D 的两类全通过，无选中项缺失/skip/解析错误；并单独验证 Target-only invariant。正式验收仅以冻结 F2P/P2P 和声明必需守卫为准，额外检查的结果如实披露。

保存已排除项与覆盖缺口，不将分数当成全仓库全绿。F2P 为空时不编造数量；按配置的 case 有效性条件判断是否还能作为目标评测案例。

**检查**：全集和排除政策可追溯；分类/重跑有证据；选择、配置、报告和 grader 配对；无未解决校准项或保留合同回归。

## 12. P7：标准 builder 与 exporter 导出

1. 新建独立 builder 或版本，不覆盖原输入与已发布包。以指定 schema 和 exporter 模板组装环境、每仓库 G/T、patch manifest、selection、配置和 runtime/verifier。
2. 核对 exporter 的全部相对依赖、fixture、共享 payload 与输入来源。package.yaml/等效配置引用的文件必须实际可用；不能只复制 builder 根而漏掉相对目录。
3. 适配 selection 到 exporter 所需格式，逐项核对 canonical ID、分类和计数，保留源格式与转换后格式各自哈希；格式转换不重新选择用例。
4. 环境 fingerprint 与现有镜像内容匹配时复用；B、系统依赖、lockfile、Dockerfile 或生成/验证必要环境变化时重建相关层并记录。功能剪枝本身不要求逐轮重建镜像。
5. 检查实际 prepare：pre 只应用共同 T；post 使用待测 Agent 的生产改动和共同 T。Golden 验证可以注入 G，但普通评测不能自动应用参考 G 或复制 Golden/制作证据到 Agent 空间。
6. 执行配置中的官方 exporter，保留命令、版本、源 fingerprint、共享 payload fingerprint、release 状态和日志。Exporter 管理文件通过正式来源生成，不手动伪造根 manifest 或把旧校准数字改成新数字。
7. 从导出目录用正式 applier/prepare 构造 C/D 和所有声明顺序，验证真实树；校对 environment、patch、selection、config、grader、task.toml 的路径和语义一致。
8. 用导出包内的 runner/grader 完成冻结选择复核。源码制作脚本通过不等于导出 verifier 通过；若导出改变了运行器/准备/解析语义，重新执行受影响运行与校准。

**检查**：标准导出成功，文件和共享内容完整，实际 verifier 使用正确版本、C/D 与参考解注入边界，评分与声明配对。

## 13. P8：归档、完整性和发布绑定

### 13.1 冻结记录并随包归档

将第一步归档及本步 sources、decisions、各阶段差异/报告、最终范围、patch/builder、校准、审核、状态、日志和修订转入证据目录。所有相关失败尝试和政策排除留痕，不只复制成功报告。

先完成 P0–P7 审核，写本步最终检查点和 archive_status=staged，冻结 run manifest，再逐字节复制。包内 index 标 archived_verified；不要回写冻结运行的 staged 状态。RUN_ROOT/artifacts/builder 只保存 builder 输入/配置和来源指纹，不把含同一 run 的最终交付包递归复制进去。

归档后从包内路径重算全部文件哈希，核查证据、修订父关系与第一步绑定。运行原路径是 provenance，包内必须有可审核副本；最终 G 与原完整 G 即使文件名相同也不能相互替代。

### 13.2 清单职责与防循环

| 文件 | 管理内容 |
| --- | --- |
| Harbor 根 manifest | exporter 管理的运行文件、来源和构建身份 |
| `golden-docs/evidence/manifest.json` | 第一步/本步 run、索引、报告等证据文件；也登记活动 PRD 的包内路径与哈希 |
| 各 run 的 artifact-manifest | 该运行的冻结输入/输出；不包含最终包或外层清单哈希 |
| `release-binding.json` | release/case、运行包 manifest SHA、证据 manifest SHA、最终 PRD、E/G/T/目标/选择/环境及验证结论 |

证据 manifest 不包含自身或 release-binding 的哈希；release-binding 不包含自身哈希。运行包 manifest 管理范围默认不含这些附加证据。若 exporter 要求根清单覆盖附件，则从 builder 明确登记附件并按无环依赖生成；发布绑定放在该根清单哈希管理范围外，不能形成 root↔binding 循环。

绑定中声明每份清单的覆盖范围及未纳入哈希的绑定文件；归档包可用外部文件哈希、Git commit/tag 或发布系统校验绑定文件。不能宣称根 manifest 校验通过就覆盖了它不管理的证据。

### 13.3 包级终检

- 从标准准备入口重现正确 B/C/D 和最终 patch，选择与报告身份一致。
- manifest 内全部文件可读且哈希一致，层职责、应用顺序、资源和 schema 合法。
- 第一条与第二条冻结记录实际存在，所有引用可在包内审核，无宿主机临时目录作为唯一证据。
- 活动 PRD、范围决定与最终目标相符，历史未剪枝文档明确标为证据。
- Agent 工作区准备只注入声明输入和 B；不会注入 Golden、参考 G、隐藏测试或制作证据。Verifier 的独立视图按任务约定接收 T。
- 所有选中 F2P/P2P 和必需守卫通过，排除/重跑/限制已登记，无未解决回归。

发布状态只有全部必需检查通过才能为 ready。incomplete 表示未完成；blocked 表示关键输入/范围/验证无法解决。允许的非选中限制在 ready 的 limitations 中说明，不能声称全仓库全绿。

本流程默认交付展开后的标准包；压缩包、Git commit/push 或外部发布按实际任务指令执行，不在记录中假设已做。第三条 workflow 从 release-binding 查找活动 PRD和最终实现，不按目录日期寻找最近版本。

## 14. 失败、恢复与规模化

| 触发 | 至少重做 |
| --- | --- |
| 主体或范围决定改变 | P1/P2 及受影响轮次，再重做最终范围、校准和打包 |
| E/B 或环境身份改变 | P0，语义迁移及 patch 重导出，C/D 校准和包级验证 |
| G/T 改变 | 受影响实现/生成/结构检查，校准适用性判断及导出验证 |
| ID/selector/解析/seed/grader 改变 | 核对原始报告适用性，重做受影响运行、分类及选择复核 |
| exporter/template/schema 改变 | P7/P8；运行语义变化传播回 P6 |
| 仅文案/路径改变 | 核对语义、引用和哈希，生成新发布绑定；不无理由重跑测试 |

输入未变化时复用有效阶段与报告。恢复先核对最后已验收父树、配置、patch、运行 manifest 和未决项；不能只凭上次输出“reward=1”跳过身份检查。

批量 case 使用独立 run，配置提供主体与工具差异。实现可按独立领域工作，但共享合同批次必须统一验收；统一入口汇总范围、ID、测试变化、manifest 和发布绑定。语义决定与确定性解析/哈希/导出分别记录，失败 case 留下可操作恢复入口，不以空列表算成功。
