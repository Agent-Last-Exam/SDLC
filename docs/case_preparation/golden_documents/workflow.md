# 最终范围与配对实现 → Golden 技术设计和测试设计

## 1. 任务与边界

执行者负责生成可作为参考答案交付的技术设计、接口合同、目标接口描述和测试设计，提供对最终 PRD、实现及 test patch 的充分性与必要性双向审计。

按阶段连续执行，常规写作和定位不逐步等待确认。输入错配、关键合同矛盾或产品决定缺失时登记阻塞，继续不依赖该问题的工作。不能通过改 PRD、删 AC、改测试或缩小审计母集把问题藏起来。

本流程针对出题方的 Golden 制作。待测 Agent 模板中“仅从 Base 和设计推导、不得读取目标源码”等执行指令不适用于出题方；模板的产物结构、字段和编号约束仍然适用。明确区分角色与模板，不把给待测 Agent 的项目专有路径原样复制进通用流程。

## 2. 输入与身份

配置见 [data-contracts.md](data-contracts.md)，入口为 [inputs.json](templates/inputs.json)。必需输入：

- 第二条发布绑定、运行包/证据清单、最终活动 PRD及范围决定。
- 每仓库 B/G/T/C/D、完整目标接口、生成输入/配置/消费者的配对身份。
- 冻结选择、校准、原始或引用测试报告、有效守卫及所有已接受限制。
- 文档模板、模块角色、接口边界、测试用例格式、允许的准备和检查能力。

```text
B = 已包含环境适配 E 的生产起点
G = 最终参考生产代码 patch
T = 最终官方 test patch
C = B + T
D = B + G + T
```

技术文档描述 B 到最终生产行为的变化；最终技术和测试证据绑定实际目标 D，测试支撑与生产实现的职责分别登记。C 用于评测比较，不能当成待测 Agent 的生产起点。

仅按已核验的 release-binding 定位 active_prd 与 implementation，不按日期、旧 PRD 或相近目录选输入。历史未剪枝 PRD和剪枝记录用于解释来源，不恢复已移除需求。

若第二条没有可核验的 ready 发布，允许先做适用性和差异盘点，但不得冻结为已配对 Golden 文档集。

## 4. 执行路线

```text
DOC0 输入配对与模板冻结
→ DOC1 模块、接口、行为与测试盘点
→ DOC2 技术设计
→ DOC3 接口合同与完整目标描述
→ DOC4 Golden 测试用例设计
→ DOC5 test patch 的双向覆盖和必要性审计
→ DOC6 全文档、范围与实现一致性审核
→ 修复：返回最早受影响阶段并重查下游
→ DOC7 冻结运行与文档集
→ DOC8 随包归档和发布绑定更新
```

所有阶段保存实际读取范围、输入/输出指纹、检查、失败和恢复入口。结构检查、语义审计和运行验证分别记录。本文定义流程与契约，不假设通用自动检查器或每种协议适配器已经实现。

## 5. DOC0：配对检查与模板冻结

1. 核对第二条发布绑定、根运行清单、证据清单、PRD、范围决定、G/T、目标树和选择指纹。输入元数据与实际内容不一致时不能只改文档中的数字。
2. 确认 active_prd 是最终范围。保留的 R/AC、移除边界、部分保留行为及原限制分别登记；历史版本不能作为活动范围混用。
3. 核对实际源码/环境视图和报告身份；必要时在隔离目录物化 B/D，并记录 test-only 支撑。仅 patch 静态视图不足以解释合同和上下文时，登记证据缺口。
4. 冻结所用模板文件及来源。项目专有业务内容不是空模板；模板中待测执行权限与 Golden 制作职责分别解释。
5. 固定模块/协议适配和输出位置。模板必交项无法满足时阻塞，不擅自删除文件。模板可选项按实际系统不适用时登记 not_applicable 和理由。
6. 保存旧发布绑定与清单副本、方法/模板和已接受限制，建立文档计划、证据指纹与状态。

**检查**：最终范围与实现配对；模板和职责明确；缺口、限制与可读性真实登记。

## 6. DOC1：盘点适用文档、行为和测试

### 6.1 文档适用性

按实际系统组成规划输出：服务端、网页/移动客户端、CLI、插件、数据任务或其他模块可以独立成文。使用模板指定的名称与 ID 前缀；默认前端 FD、后端 BD、工程任务 BT、接口 I。更多角色通过配置提供前缀，不强行塞进 BD/FD。

每个文档登记适用理由、承接 R/AC、模板指纹、输出位置及完成检查。无前端的 case 不编造页面；若模板要求前端文件，则保留结构并解释不适用。纯内部变化可以在相关设计单元中说明，不把它提升成新 PRD 需求。

### 6.2 行为与接口母集

从最终 PRD、范围决定、B→D 差异、公开接口/事件、数据迁移、任务、副作用和消费方建立行为单元 `DU-*` 与边界 `I* / GU*`。接口盘点包括新增、调整、弃用、移除、默认值、错误、权限和兼容；不能只清点新增 mutation 或 endpoint。

人工维护生产变化逐行为归属；派生输出关联其权威输入和消费者；环境/工具链变化解释其约束，不伪装成业务设计。共享或不变能力记录 baseline_context，不能冒充本次新增。

### 6.3 测试母集

建立两个来源：最终 T 中的全部变化范围，以及冻结 selection/守卫引用但 T 没有修改的现有测试。两者分别登记，去重后形成自动测试审计母集。

按输入、断言和真实行为建立 `TU-*` 单元。语义一致的参数测试可成组，但要列完整成员及证据；异质用例不能仅因在同一文件而成组。文件重命名、测试删除、fixture/mock/factory 和框架适配也有去向。

大文件分段读，记录已读/未读范围和原 diff 定位。未知单元保持 unresolved，不将整个目录归为“回归”后宣称审核完整。

**检查**：适用文档、行为/接口、T 变化及选中既有测试均可定位，未分析范围明确，不凭抽样宣布全量。

## 7. DOC2：生成技术设计

按配置模板写方案概述、需求覆盖、详细设计、接口清单、工程依赖/验证和其他约束。只列本模块承接的需求；跨模块需求由多个设计单元共同承接，不要求每份文档都机械覆盖全部 R。

设计单元至少说明：

- 目标行为与覆盖 R/AC、B 的相关现状、最终实现落点与职责。
- 数据/状态变化、权限、校验、事务、并发和失败语义，按实际关联展开。
- 同步/异步边界、持久化、外部副作用及使用者可观察的完成条件。
- 配置、迁移、生成链、消费方、运行和兼容约束。
- 工程任务与依赖、验证方法及已知限制。

这是已实现目标的参考技术方案，设计说明须由最终实现支持。可以给出有依据的实施顺序，但不能把未采用的架构建议写成目标事实。无法证实的设计待决；实现缺陷不正常化成合同。

内部函数、路径、数据结构适合技术定位，但不以逐函数清单代替系统设计。前端写交互、状态、数据流和异常，后端写服务/数据/任务职责；共享接口完整语义集中在 interface-contract，其他文档只引用 I ID。

设计单元、接口与工程任务 ID 发布后不重排、不复用，继承 PRD 名称。后续拆分合并保留旧 ID 和继承关系。

**检查**：每个活动 R/AC 有实际模块承接或明确理由；设计有实现证据，无虚构模块或遗漏必要依赖。

## 8. DOC3：合同与完整目标接口描述

### 8.1 接口合同

每个改变的对外/跨模块边界登记 I ID、所属设计单元、提供者、消费者和原生定义位置，并按模板说明：

- 输入/输出、可空、默认值、列表与列表项、ID 和枚举的语义。
- 身份、对象权限、可见性和敏感状态的返回边界。
- 参数、权限、业务失败和传输错误的形式，不能把 HTTP 成功等同业务成功。
- 状态/数据/事件变化、请求接受与完成判定、适用的幂等/重试。
- 相对 B 的差异、弃用/移除与旧消费者过渡。

权限、动态默认值和副作用通常不能由 schema 单独证明，结合实现、调用方与测试核验。文档片段必须真实且可解析，不能用省略号替代关键字段。

### 8.2 原生目标描述

按每个真实协议边界提供完整目标描述：GraphQL SDL、OpenAPI、proto、事件 schema、CLI 参数/输出合同或项目原生格式。不强制将所有协议转为 GraphQL；描述单位是声明的完整接口边界，不是整个组织的所有服务。

包括未变更的 Base 定义和本次最终变化，不能只交 diff。生成文件优先从固定目标的权威输入导出，保存工具/配置/输入/输出身份及实际检查。配置要求完整 schema 时不可用片段代替。

多套 schema 或生成输入分别登记供应者、版本、用途和消费者。不能因文件名为 main/staging 就假定相同；也不能把历史客户端快照描述成最终后端 schema 的同步副本。

比对生产者、目标描述和消费者：验证 operation、字段、类型、权限和错误语义。字节不同不自动表示不兼容；有意的兼容快照/超集需有明确规则和消费者实际使用范围证据。仍被调用的缺失/矛盾合同是阻塞，不能借“现有选择通过”略过。

若生成入口缺失、schema 与冻结实现冲突，记录发现并返回第二条修复实现，第三条从新绑定重新进入。不得仅在文档目录生成一个“修好”的 schema 冒充现有目标接口。

**检查**：合同完整且与原生定义/实现/消费者一致，描述可解析且版本明确；生成链与限制如实记录。

## 9. DOC4：生成 Golden 测试用例

### 9.1 活动产品用例

按指定 CSV 模板设计可重复执行的用例。默认九列为用例编号、一级模块、二级模块、用例标题、覆盖、优先级、前置条件、操作步骤、预期结果。版本和依据写在 Test/README，不在 CSV 前插标题。

每个产品 TC 至少覆盖一个当前活动 AC，必要时引用设计/接口 ID。需求名称和业务域与 PRD 一致，步骤有明确数据、身份、状态和操作，预期与步骤对应。步骤不得依赖未提供的外部系统或数据；无法独立运行的场景明确环境要求。

按适用性覆盖成功、边界、权限、错误、默认值、状态、异步、副作用和兼容。一个 TC 可聚合多个 AC，但每个 AC 必须有明确触发与对应预期；多个 TC 也可共同覆盖同一 AC。不要求 TC 数量等于 AC 数量。

优先级遵守模板和最终 PRD。风险提示可独立登记；不能借测试优先级修订未确认的产品优先级。既有共享回归若不属于新增 AC，在审计中说明依据，不为了 CSV 关联编造新 AC。

### 9.2 删除边界与非目标守卫

已移除的历史 R/AC 不作为活动 AC 再出现在产品 TC 中。最终非目标、公开接口缺失和保留基础能力的边界，登记到 boundary-register 的 GU ID。

若某守卫已由当前活动 AC 明确表达，可作为产品 TC；否则在独立 guard-cases 中设计，不篡改九列模板的“至少一个活动 AC”要求。关联实际 invariant/断言，缺少自动化时写计划和 gap，不声称测试已经存在。

**检查**：活动 AC 设计覆盖明确，TC 可执行且非机械一对一，历史删除与产品验收分开，设计不冒充执行。

## 10. DOC5：对 test patch 做双向审计

### 10.1 PRD/AC/TC → 自动测试：充分性

逐 AC 和关键场景读取测试输入与断言，定位 TU 与节点。判定 full/partial/gap/conflict，并指出哪些前提、输出、异常或权限已经验证、哪些没有。

文件名相关、schema 存在、某个 suite 通过，不能单独证明完整 AC 覆盖。mock 中手工构造的结果不证明真实提供者生成它；单元、集成、端到端证据按各自边界解释。

活动产品 TC 的设计充分性、T/现有测试自动覆盖、实际执行状态三个维度分别记录。缺少自动化时可以在非阻塞政策下交付 ready_with_limits 文档，但不能把手工计划变成自动测试证据；输入规定必需自动覆盖的合同缺口是阻塞。

### 10.2 自动测试 → 范围/基线/执行依赖：必要性

逐 TU 分类：active_behavior、baseline_regression、execution_support、pruning_guard、removed_history 或 unresolved。每类都有断言目的、源码/合同/数据风险及来源；测试不直接属于新增 PRD，不自动表示不必要。

P2P 是运行分类，不能单独证明产品必要性；回归依据来自保留的旧行为、共享风险和兼容合同。fixture、测试工具与生成 factory 的必要性来自明确消费者和执行依赖，不写成独立产品需求。

若最终 T 中仍有要求被删能力存在的正向测试，或有无法解释的行为测试，登记冲突并返回第二条；文档流程不删除测试。removed_history 条目仅解释 diff 中已经删除的测试，不能把仍在目标收集的测试归入此类掩盖矛盾。

### 10.3 运行证据

从第二条引用实际 C/D、F2P/P2P、invariant、排除和重跑记录，核对选择、节点、环境、解析与目标身份。引用历史报告明确标历史，不自动重跑已匹配的冻结验证。

若为澄清证据而本轮定向运行，记录实际命令和条件。只有确实执行过 TC 的步骤并观察结果，才能称该 TC 执行通过；相似自动节点通过不能直接转换为手工 CSV 的执行报告。

不重新分类 F2P/P2P、不改 T/G/选择/评分。发现需要实现修复或新守卫时形成上游修复请求，并等待配对新版本。

**检查**：所有活动 AC 和测试母集有去向，full 的断言依据充足，回归与执行依赖解释明确，缺口/冲突和运行范围未混用。

## 11. DOC6：全套一致性与必要性审查

### 11.1 需求到文档

活动 R/AC → 承接设计单元 → 接口/数据/交互 → TC/守卫 → 自动测试/实际证据。并非每条都有接口或前端，not_applicable 要有理由，不产生虚构 ID。

### 11.2 文档/实现到需求

每个设计、接口、目标定义变化和 TC 有活动范围、公开约束或基线/执行目的；每个实际生产行为及 T 变化有归属。排除纯机械生成内容要追溯输入，而非略过合同变化。

检查字段、状态、空值、权限、错误、异步完成、默认值、兼容、迁移和配置在 PRD、各模块设计、接口描述、消费者与测试中的表达一致。不得把更详细的技术文本当作自行扩大的产品范围。

### 11.3 结构检查

核对模板章节、必填字段、ID 唯一/引用、TC 列名与 CSV 转义、覆盖映射、原生协议语法/类型引用、相对链接、来源与产物哈希，以及已删除符号是否被误写成活动能力。

检查设计覆盖和接口引用的实际内容；字段齐全、映射比例或测试总数不是语义审核结论。问题按格式/证据/设计缺口/合同冲突/自动化缺口分别处理。

修复局部写作后重查受影响链和全局引用；达到修复轮数仍不通过时交付草稿和恢复入口。不能通过忽略少量未映射变化就宣称全量审计。

**检查**：活动范围、技术合同、TC 和实际行为一致，双向关系完整，所有未决项及限制真实可定位。

## 12. DOC7：冻结运行与文档集

输出实际适用的 TDD/Test、document-plan、行为/测试/边界母集、traceability、审计、检查报告、日志与文档 manifest。

文档审核状态：

| 状态 | 含义 |
| --- | --- |
| ready | 文档完整且语义审计通过，约定覆盖/检查均满足 |
| ready_with_limits | 文档范围/语义通过，存在已说明影响的非阻塞自动化或验证限制 |
| blocked | 输入或关键语义/合同冲突、必需覆盖缺口不能解决 |
| incomplete | 尚有未分析、未写或未审的部分 |

运行的 delivery_status 先为 staged，表示可归档，document_status 保留上述审核结论；最终归档/绑定状态由包外层记录。DOC8 在冻结时为 running，完成结果写外层索引和包级审核，不回写冻结日志。

先冻结输入及来源、完成所有产物和审计，再写最终状态/检查点、计算哈希、生成文档 manifest 和 run manifest，最后只读复核。文档 manifest 只管理文档及其输入配对身份，不引用自身、外层证据清单、当前发布绑定或本 run manifest 哈希；run manifest 可引用文档 manifest，避免循环。

本流程默认不生成测试执行 CSV、QA verdict、开发提测或部署报告。输入报告可归档；只有另行实际完成对应任务时才产生新的执行结论。

## 13. DOC8：归档与新发布绑定

1. 在独立包候选版本中放入 TDD/Test 与新的 golden-docs/manifest。active_prd 原样保留，B/G/T/选择及 exporter 管理内容核对不变。
2. 冻结 run 逐字节归档到 golden-documents/<run_id>；更新该目录 index 为 archived_verified，登记审核状态、运行 manifest、父运行和文档版本。
3. 保留第一、第二条全部已交付证据；更新 `golden-docs/evidence/manifest.json` 的覆盖范围为三条运行记录、索引、活动 PRD、TDD/Test、文档 manifest 和包级文档审核。
4. 新发布绑定保留 runtime manifest、B/G/T/目标/环境/选择及已核验运行证据，绑定新 evidence manifest 与 golden manifest，并登记父发布来源及 document_status。仅文档变化不虚构新 F2P/P2P 执行。
5. 文档 ready_with_limits 时，外层绑定明确 document_status 与 limitations；只有所有必需包检查和文档语义通过才能让发布 status=ready。文档 blocked/incomplete 的候选不能替代活动已就绪版本。
6. 在包级 documentation-audit 中核对全文档/三条证据归档、相对引用、清单无环及 Agent 可见性。Golden 与制作记录不能进入待测 workspace。

证据 manifest 不包含自身或当前 release-binding 的哈希；Golden 文档 manifest 不反向引用外层清单；run 不包含最终包副本。引用输入旧绑定使用 sources 中的冻结副本，不能形成“当前绑定引用 run、run 又引用当前绑定”的循环。

若 exporter 根清单覆盖附加文档，通过其正式输入重新生成，遵守第二条的无环策略；不能直接手改已发布根清单。归档包、Git 或外部发布按实际授权执行，本流程默认交付展开后的包候选。

**检查**：文档、实现和运行证据版本配对；三步记录随包且可移植；当前绑定和清单覆盖明确，无循环，无参考答案泄漏。

## 14. 恢复、变更失效与规模化

| 变化 | 最早重查范围 |
| --- | --- |
| 活动 PRD/剪枝决定 | DOC0/DOC1 及受影响设计、接口、用例、双向审计 |
| B/G/T/目标/接口输入 | 返回第二条确认新发布；DOC0 起核对行为、测试和所有下游 |
| 仅运行器/选择/校准报告变化 | DOC0 身份、DOC5 运行适用性及覆盖状态，再更新审核/绑定 |
| 模板或模块/协议适配变化 | 适用性/对应写作阶段，缺新字段证据时补盘点，再重查引用 |
| 仅文案/链接/路径变化 | 语义与引用检查、manifest 和发布绑定，不无理由重跑功能测试 |

恢复读取最后有效检查点、输入/输出指纹、未读范围和发现，不能凭历史聊天或旧测试分数继续。批量 case 使用独立 run；模块设计可独立加工，但共享合同、ID 分配、双向审计和最终版本统一复核。无前端/数据库/接口等能力由配置声明，不以空文件算完成。
