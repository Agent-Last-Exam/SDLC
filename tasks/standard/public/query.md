# 业务委托：商家经营与应用接入升级

## 背景与目标

商家希望引入更多外部应用支持经营，同时继续处理已有订单、账号和资产。请为 Saleor 核心 API 与商家 Dashboard 的配套升级形成一份 PRD：让运营更可靠地维护资料和内容，让仓储人员控制渠道库存与运费，让客服和财务追踪礼品卡及外部资金，让管理员安全地管理登录、应用故障和升级切换。顾客需要继续登录、购物、退款及访问已购数字内容；集成方需要按需订阅变化并平稳迁移旧接入；实施和 QA 人员需要明确迁移、对账及恢复的交付依据。

这些是本轮提出的目标，不代表已部署能力或已验证收益。存量经营连续性与新增能力同样重要，不能用删除历史数据、扩大权限或重复资金动作换取切换便利。

## 主要变化

### 经营资料与检索

在现有经营设置中统一维护展示名称、介绍/页头、公司名称与地址、邮件发件信息和公共/私有 metadata；敏感信息不能放入公共 metadata。商品、分类、集合、页面及共用 EditorJS 处理的属性和翻译，应兼容旧字符串列表与新嵌套对象列表，保留合法文字、层级、顺序和样式，保存反馈可信且危险内容得到一致处理。

外部图片导入要支持带查询参数、无扩展名以及不支持 HEAD 但 GET 可用的合法图片源，不能以兼容为由访问内部资源或关闭安全过滤；同一下载路径的应用品牌图也遵守安全边界。改善已有商品、订单、顾客、礼品卡搜索及新增交易查询的更新可靠性，不引入新搜索产品。

### 库存、运费与交付

每个渠道可以选择“兼容配送区域”或“仅按渠道仓库”的库存模式，让商家逐步切换，保留旧经营方式。共享仓库的真实库存不能按渠道复制。渠道还要能分别控制外部报价缓存时长和外部配送过滤，订单使用所属渠道的配置；这些选择只影响运费，不改变税费或支付通知的业务规则。

退出旧数字内容业务接口，但保留数字商品本身和已购下载权益。明确退出范围为 `digitalContent`、`digitalContents` 及其创建、更新、删除、生成下载地址的旧操作，变体和订单行关联的旧数字内容/下载字段、旧下载默认设置及不再被引用的专属类型。Dashboard 同步退出旧配置入口和调用。历史文件和权益不随接口退出而删除；新销售必须有可用履约路径，不能把尚未交付的订单留在两套流程之间。

### 资金追踪与售后

将礼品卡纳入统一交易及退款管理：成功支付时，每张实际扣款的卡都有平台交易和扣款事件，可追溯订单、原卡与来源。余额、事件、订单和结账结果保持一致，同一结账重复处理不重复扣款，不同结账不能超用余额；统一实付只计算一次礼品卡，不再把旧补偿字段累加为第二笔支付。礼品卡部分或全额退款由平台退回原卡，不向第三方支付服务商请求该部分退款；混合支付按真实来源处理。

增加面向 `TransactionItem` 的分页交易查询和财务定位入口，保留既有单笔查询。限定退出 Dummy、DummyCreditCard、Braintree、Razorpay 四类支付插件的新业务使用、配置安装及运行注册；历史资金和售后必须仍可追踪与处理，不删除 `Payment` 或全部旧支付 API。

### 登录与账号连续性

支持三种密码策略：`ALL` 允许所有用户使用密码，`CUSTOMERS_ONLY` 只允许非员工使用密码，`DISABLED` 禁用所有用户本地密码登录、依赖外部身份。API 与 Dashboard 必须一致执行，不能仅隐藏界面。策略变化不得丢失账号、订单归属或合法外部身份，收紧之前要有管理员可用的登录与恢复路径。

### 应用使用与变化通知

在保留既有扩展的基础上，首版补齐分类、页面/模型、页面类型/模型类型、菜单、促销这五类详情 Widget。员工与应用双方有权才能启动，所传上下文不附带无关个人或订单数据；扩展故障不得阻断原生操作。应用列表、详情和全局提醒要区分安装失败、主动停用、投递失败及熔断，帮助商家理解影响与恢复；不提供阈值自由调节、强制清零或从故障页盲目重放同步资金动作。

应用可以按事件、支持的渠道和最少字段订阅，不必接收整个对象。新增通知覆盖经营普通设置及地址变化、交易创建与金额/状态/退款变化，交易包括平台礼品卡和外部交易，metadata 专用通知保留。补齐 Attribute、Category、Menu、MenuItem、Page、PageType、ProductType、ShippingMethod 的 metadata 变化通知；不为补通知而给 AttributeValue 新增 metadata，其普通变化沿用原事件。以上名称用于界定业务对象，新增事件名称由后续契约明确。

事件只提供订阅者有权读取且选取的字段；私有 metadata、员工信息及渠道隔离不因通知放宽，完整卡码、密码和凭证不得进入新增通知。存量订阅有过渡安排，不能通过升级自动重置接入。

## 范围与非目标

范围包括上述核心行为、商家操作、必要配置、迁移与预检恢复工具、兼容契约及本地交付验证要求。顾客交互由现有消费者承接，本轮定义核心 API 行为、错误语义及接入说明。新增契约保持兼容，明确删除只限上述四类支付插件和旧数字内容退出范围，不顺便清理其他弃用 API。后续接口名、枚举和错误码可以规范化，但不能改变业务含义、默认值或缩减验收覆盖。

允许维护窗口，不承诺无停机升级。后续实施须先有影响报告和外部登录/支付/履约路径验证，备份数据库、媒体、应用配置及必要密钥，安排迁移、对账、恢复与开放后验证。本地交付包括 API、Dashboard、必要数据库/缓存/worker 和受控的身份、支付、运费、通知验证端；可以用受控模拟履约验证接口，不要求建设第三方产品。这些是后续交付义务，不是本阶段执行指令。

明确不做：顾客 Storefront、原生 App、支付服务商、身份产品、商家主体认证系统（含执照或税号认证）、应用市场结算分成、任意 Dashboard 页面搭建器、跨币兑换、礼品卡转账/提现/储值利息/自动延期/退款转现金、语义搜索或新增分词、推荐、独立媒体代理/CDN、新数字分发产品。不强制转换全部历史 `Payment` 为新支付来源；保留未整体弃用的内置支付、Webhook 支付、OpenIDConnect、邮件、插件扩展框架、普通数字商品和文件属性。

更多扩展挂载点、熔断阈值自助配置、全局搜索产品、旧固定 Webhook payload 最终停止时间和历史数字权益兼容下载服务最终下线不在本轮。仍需提供相应清单与迁移说明，不能以延期为由拖延本轮已明确的新增和退出内容，也不能擅自终止无到期权益。

## 本阶段任务与输出

阅读本委托、`public/business-conversations.md` 的固定补充决定、`public/prd-schema.md`，并只读调查指定 Base，输出一份符合该模板的 PRD。请自行理解需求、调查现状、关联依赖、拆分需求并组织可观察的验收条件，不输出代码实现、部署或测试报告。

模板的 Instruction 指本委托与固定沟通记录的公开正文。来源引用真实原文并附文件、章节或片段位置；组合多处信息时一并引用，Base 调查依据与业务决定分清。章节沿用模板的 1、2、4、5、6，不补第 3 章；不规定条目数或业务分组。优先级按业务影响而非开发难度判断：去掉后目标无法实现或造成不可用、数据/安全问题为 P0；目标仍可达但具体使用者需增加正常操作为 P1；无上述影响为 P2。不要求各级都有条目。

R 与 AC 标识由你自行组织，AC 一条对应一个可判定场景，不写成已执行结果；若后续修订，编号不重排、不复用。模板中的完成状态不能掩盖未知，影响范围或验收的未决项应如实标注并在“其他”说明。实际经营规模、历史证据及外部路径验证尚未提供的部分，只记录为依赖和切换前条件，不猜测事实，不借此取消已明确义务。
