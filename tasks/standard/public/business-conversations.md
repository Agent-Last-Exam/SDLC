# 固定业务沟通记录

以下是任务启动前一次性提供的合成需求材料。角色仅代表商家管理员、运营、财务、客服、集成和运维等职能视角，不对应真实人物、公司或已经发生的访谈，也不是待测 Agent 的调查结果。不安排运行中追问。各片段补充业务委托的条件和边界，与委托共同使用；没有写明的实际部署结果不能据此推定。

## 经营资料可信且可检索

### 资料保存：未编辑不等于清空

**运营：** 修改发件信息时，不能意外清掉经营地址；多个保存区也不能只给一个含糊的“成功”。

**管理员：** 展示名称和域名是两回事，改展示名称不改域名；公司名称沿用经营地址的公司名称字段。按字段更新时，省略就保留，显式清空与不合法空值要区分。保留既有长度、邮箱、按国家校验地址和 API 已定义的 null 清空行为，但前端不能把“没编辑”当成清空请求。清空地址必须显式操作并确认，历史订单地址快照不受影响。

**运营：** 信息和地址分别保存、分别反馈，失败的输入保留，重复保存不重复新增地址。邮箱不合法、发件名称含换行、地址不符合国家规则，都在对应区域说明；不能把部分成功说成整体成功。

**管理员：** 修改需要 `MANAGE_SETTINGS`；匿名经营信息查询和无私有 metadata 权限的订阅都不能看到私有字段。实际设置变化要通知应用，通知遵守后面的事件规则。

### 内容编辑：新旧内容都要可读

**内容运营：** 旧字符串列表与新版带 content、嵌套 items 和元数据的列表要一起用。层级、顺序、样式及合法链接不能被压平或丢掉。空段落、空列表、空列表项、缺少可选字段不能让后续合法内容失效，也不能导致保存、读取或索引崩溃。

**管理员：** 非法结构的新提交应定位字段错误并保留旧值；已经存在的异常内容则展示安全可读部分、记录可定位告警，不能让整页或搜索任务崩溃，也不能未经用户确认覆盖原文。文本、列表、图片地址/说明和嵌入内容统一清理危险协议、脚本及事件属性，不能只处理一种链接写法；安全链接保留。允许标签与协议边界在后续契约中明确。

**内容运营：** 预览及保存后都不能执行危险内容。供搜索使用的纯文本按阅读顺序包含各层可见文字，不包含可执行 HTML。不要强制破坏性重写全库；如需重建派生内容和索引，保留原文备份与异常清单。

### 图片与搜索：失败可处理、更新可恢复

**运营：** 图片是否可用以实际内容能否解码为准，不能只信扩展名或 Content-Type。已有视频/oEmbed 和本地上传支持的格式继续可用，普通网页不能冒充图片。

**管理员：** 默认下载上限 20 MiB、4000 万像素、总下载预算 20 秒；部署可调，但不能没有有限边界。首版不自动跟随重定向，3xx 应提示提供最终直链。默认只允许 HTTP/HTTPS 公网，遵守更严格的生产策略，拒绝回环、私网、链路本地、云元数据地址以及 DNS 解析绕过。未提供可用公开直链的鉴权资源明确失败，不代用户进入内部系统。日志隐藏 URL 的敏感查询参数。

**运营：** 超时、非成功响应、非图片、损坏、不支持格式或超限要返回可理解的字段错误；不能留下成功媒体记录或孤立文件。导入显示进行中，失败保留输入和既有图片，可修改重试。

**运维：** 搜索保留原有字段、权限、渠道隔离与空查询行为；嵌套内容、富文本属性、关联属性/页面名称、SKU、顾客信息和交易参考号变化按已有搜索语义更新。标点、引号、中文、长输入不能导致服务端崩溃。标准本地验收环境下，单次正常更新提交后 60 秒内可检索新值，这是新验收目标，不是生产 SLA。

**运营：** 索引失败要可见、可重试，中断后能续跑，异常单条不能永久卡住其他对象。全量重建覆盖已有非空旧索引，并保持查询可用；并发编辑不能被旧快照覆盖或丢掉较新的待更新状态。迁移后做必要重建，给出处理总数、失败对象和重试结果，提示不得泄露私有字段。

## 订单可接、商品可交付

### 渠道库存：有库存不等于可配送

**仓储运营：** 升级和未显式选择的新渠道默认“兼容配送区域”。渠道详情与 API 都能读写模式；只有有渠道管理权限的人可保存。界面说明当前模式、关联仓库、顺序及切换影响，旧模式仍显示配送区域要求，切换前给出可能扩大可售区域的变更摘要并要求确认。

**管理员：** 新模式中，可售库存、校验、预留、订单分配及补货只用关联当前渠道的仓库，不因国家或配送区域关系决定库存来源。但国家仍影响合法配送、税费和地址，没有配送方式仍不能完成需配送结账。可售数继续遵守在库减分配减有效预留，保留库存跟踪、预售、仓库顺序和分配策略、本仓/全仓自提及私有仓资格，不放宽自提权限。没有关联仓库时，跟踪库存且非预售的商品不能购买。

**仓储运营：** 切模式或解除仓库关系不重写已有订单有效分配及其履约、退货回库来源。未完成结账在下次报价、预留或完成时按新规则重验，预留失效和释放要一致，不能重复扣减。共享库存的并发成交也必须受同一真实存量约束。

### 外部运费：缓存和失败不能改变成交底线

**渠道运营：** 报价缓存时长以秒配置，范围 0—86400，0 表示不缓存；未指定时为 43200 秒。外部配送过滤默认开启，关闭前说明候选方式可能扩大，界面有校验和保存反馈。关闭仅跳过结账与订单的外部过滤，本地校验和外部报价继续有效。

**管理员：** 报价按应用/Webhook、渠道及报价上下文隔离。地址、数量、金额、折扣、币种、订阅所选报价数据、应用或相关配置改变，旧报价不能继续冒充有效。超时、错误和无效响应不作成功缓存，合法空列表可以缓存；报价要符合渠道币种、非负金额、标识和精度要求。

**订单客服：** 上下文匹配的未过期报价可以用，故障不能让过期报价无限续用。报价失败时保留其他合法方式，无方式则明确不可配送并允许重试，不自动变免费运费。过滤开启但失败或熔断时，受影响方式不能成交；商家显式关闭过滤才可恢复候选方式。成交前重验所选方式，涨价走已有价格变更确认，不能静默多扣。已经生成的订单保留原运费快照。

### 数字交付：退出入口不退出已购权益

**订单客服：** 退出旧业务 API 后，已购内容仍要通过只服务历史权益的兼容下载路径访问。有效链接沿用剩余次数和期限，过期或次数耗尽仍拒绝；无到期权益不能被强加失效日，也不能把受保护文件变成永久公开链接或允许猜 ID 读取他人文件。兼容服务最终下线不属于本轮。

**集成方：** 删除属于破坏性变更，必须先有消费者查询清单、替代流程及目标 schema，Dashboard 不再请求退出字段，但普通数字商品、非配送类型、文件属性、礼品卡和订单履约保留。维护前受控导出文件、校验和、商品/变体及订单行关联、下载 token、期限、剩余和已用次数、自动履约配置；核对文件、数量、订单和次数，恢复不能重复发权益或重置已用次数。

**管理员：** 已付款未交付的订单先签发权益或完成经验证交接；新数字订单由商家选定既有履约应用或外部服务承接。缺可用路径就阻断相关新销售或切换，不能影响已购下载和无关普通商品。消费者还在调用旧字段时，不能越过删除门槛。本地模拟只能验证接入，不证明生产履约已落实。

## 资金来源和处理可追溯

### 收款退款：每一笔都保留真实来源

**财务：** 保留现有加卡、移卡入口和下单扣减时机，报价、加卡或失败结账不能记成成功扣款。多卡按创建时间、再按 ID 排序消耗；单卡不超过有效余额及剩余应付，必须激活、未过期且币种一致。礼品卡是支付不是折扣，不改税基；支付应用只处理扣除礼品卡后的剩余应付。全额礼品卡按既有订单确认配置成交，不伪造 PSP 交易。

**客服：** 展示掩码卡号和币种，外部应用不能冒充平台礼品卡来源，无权者不能得到完整卡码或他人信息。退款整合进现有管理入口，能看来源、实付、已退、处理中、剩余可退、原因和事件；退款金额为正、符合币种精度，省略金额就取剩余可退。累计已退加处理中不能超过实扣，审批通过不等于退款成功，余额恢复及成功事件确认后才显示成功。

**财务：** 申请要有稳定幂等标识，重复提交、并发及异步重试不能多退，重复请求返回原结果。混合退款须明确各来源金额，不同币种不能相加；一方成功另一方失败时保留真实部分成功，重试只处理失败部分。外部资金已成功而本地失败，同样要保留资金事实并进入补偿或人工处理状态，不造成功订单、不重复扣款。

**客服：** 原卡过期或停用仍可退回余额，但不激活、不延期，界面提示仍不可消费。有资金使用的卡不能普通删除，应引导停用；找不到原卡就明确退款失败，不转现金。退货回库、取消订单、资金退款各有独立状态，取消不能隐式再退一次。

**管理员：** 退款需要 `HANDLE_PAYMENTS`，看订单另需订单权限；任意修改卡余额或状态需要 `MANAGE_GIFT_CARD`，不能用订单查看权代替资金操作授权。

### 历史账务与资金定位：不把归一当作再次收款

**财务：** 升级前盘点旧 Payment、交易、礼品卡事件和订单补偿，区分已退、未退及证据不足。可信扣款/退款证据可形成带迁移标识的账务归一记录，不再次扣余额或发消费/退款通知；旧支付和新交易并存时，同一笔钱不能变成两笔可操作资金，不强制把所有历史 Payment 转为新来源。维护窗口后启用新记账，同一订单不能双轨扣卡。

**管理员：** 支持分批、续跑和幂等重跑，按币种核对卡余额、订单实付/已退及来源关联并保留审计映射。证据不足保留只读旧账和“待核对”，不能由当前余额推算成功交易或开放不确定自动退款。财务须用可追溯线下证据录入经审核映射；核对前不宣称历史自动退款全部覆盖。

**客服：** 查交易需要组合交易 ID/token、交易或事件的 PSP 参考号、订单/结账、渠道、创建时间、来源应用及礼品卡来源。不同条件按 AND，单字段多个值按 OR。参考号不是全局唯一，精确查询不能因全文搜索索引数量上限漏掉有权交易。同一交易不要重复展示。

**财务：** 默认创建时间倒序，时间相同以唯一 ID 稳定排序，支持前后游标分页，不做无界导出。时间按 UTC 存储和筛选，界面用当前时区并说明边界，金额分币种。旧全局 ID、UUID token 继续可读；尚未成单的交易标出结账来源，应用卸载也保留历史来源。新交易入口可进入交易/订单详情，卡详情只定位本卡使用和退款，不泄其他卡或全码。

**管理员：** 列表、详情、计数都执行相同服务端权限和渠道隔离，交易查询沿用 `HANDLE_PAYMENTS`，订单深链再校验订单权限，不扩大应用访问边界。加载失败可重试，零结果展示当前筛选和清空入口。

### 支付退出：历史售后先有去处

**管理员：** 四类退出插件只清理其专属依赖，不破坏共享依赖与保留能力，更不删除插件扩展框架。旧订单、Payment、事件、币种、金额和 PSP 参考号仍能查看，不因退出插件导致启动或订单页面失败。

**财务：** 按插件与渠道盘点待结账、授权未捕获、退款、未决事件和历史售后义务。应在维护前处理，或交给已验证的既有外部处理路径并关联结果；在用插件没有已验证路径就是升级阻断，不能仅隐藏入口。

**集成方：** 外部人工处理要有受限结果登记和对账，记录执行渠道、参考号、操作者、时间及证据，明确是登记而非平台发起，不复制收入；重复登记不改已确认金额，操作须授权。旧凭证受限备份，交接后撤销；使用隔离测试工具或应用验证支付，不依赖退出的生产插件。新支付路径及回调重试、恢复都不能重复已成功的资金动作。

## 登录变化不丢合法访问

### 密码策略：按账号身份执行，不只按页面执行

**管理员：** 策略由实例部署配置控制，首版 Dashboard 只展示及说明、不在线修改。新装和升级未配置均为 ALL；未知值应使启动或配置检查失败并提示合法值。当前 `is_staff=true` 就属于员工，包括超级管理员和有购物记录的员工，不能按是否购物重新分类。

**账号管理职能：** 匿名 shop 可以查询策略及外部认证方式，不泄露账号是否存在。策略只限制本地密码，授权应用 token、外部认证及匿名购物不因此禁用；激活、邮件确认、节流、CSRF 与权限校验继续有效。受限员工不显示密码及找回入口，无外部方式就提示联系管理员；查询策略失败也不能默认开放密码。

### 账号恢复：不能借旧链接或旧会话绕过

**管理员：** 限制覆盖登录、设置/修改密码、重置邮件、带密码注册和员工密码邀请。被禁止的密码写入原子拒绝；无密码顾客注册与外部身份创建/登录仍按原规则继续。公开找回保持防枚举，受限账号不发重置邮件，旧重置或邀请链接不能恢复可用本地密码会话。

**运维：** 收紧时受影响本地访问及刷新会话失效，无法辨别来源的旧会话也安全失效并要求重登。不能清除账号、密码哈希、订单归属和外部身份关联。放宽不复活失效会话，但可使用保留密码重新登录。顾客升格员工后立即受员工策略约束，外部身份不能只凭可控邮箱匹配获得员工权限。

**管理员：** 切换前盘点受影响账号，实际验证至少一个有管理权限的外部账号登录、回调及刷新，提供无密码邀请指引并演练配置恢复。找不到经验证的管理员路径不能宣称可上线。外部服务故障不自动放宽策略；只有授权运维可通过部署配置恢复 ALL，并记录操作。

## 应用可用且可控

### 扩展体验：新位置与旧入口一起可用

**运营：** 五类新增详情 Widget 要与对象已有更多操作入口配套。界面保留 Page/Model 既有称呼，API 仍用 Page、PageType；保留全部已有挂载点、目标和默认 POPUP，不让旧应用重配才可用。

**集成方：** Manifest 可声明标签、地址、权限、挂载位置及适用 GET/POST 选项。非法位置、目标、地址、选项或越权声明在安装/更新时定位字段错误，不部分替换既有扩展及权限。详情传对象 ID、已有列表传选中 ID，有渠道上下文传当前渠道，不额外附带无关数据。

**管理员：** 停用、卸载或撤权后入口和令牌访问同步失效。所有实际可达新旧入口体验一致，不出现重复入口，无扩展不展示空容器。超时或 iframe 来源不匹配只显示局部错误及重试，不阻断原生保存；不向错误来源发送凭证，也不在 URL 或日志暴露长期 token。

### 故障管理：未知不等于健康

**管理员：** 需要看到状态变化时间、受影响同步事件、最近失败原因和投递详情入口；未启用监控、仅观察、数据未知与正常不能混为一谈。状态请求失败要显示未知且可刷新，而不是显示健康。

**运维：** 首版沿用 Base 默认阈值及自动恢复语义，调查现有状态、观察与阻断行为，不重新发明阈值或把恢复观察说成任意限流方案。升级不自动开启新阻断。保留查看详情、既有异步投递重试以及停用/启用；不是所有事件或其他应用都会随某应用的同步故障一起停用。

**管理员：** 无详细日志权限的员工只看必要影响提示，不能直接越权查询或操作。日志不含密码、完整卡码或长期凭证。资金重放不作为恢复按钮，运费故障按前面的报价与过滤规则处理。

### 变化通知：少给数据，不漏真实变化

**集成方：** 保留现有 Shop、订单、商品、变体、仓库、渠道、礼品卡等事件；新增范围按业务委托，不把建议名当现有接口。通用 metadata 写入、对象内嵌 metadata、批量写入都要覆盖，不能只处理一个入口。

**管理员：** 新对象在创建事件中携带初始 metadata，不额外伪造修改。以已提交状态为准，失败、回滚、值未变或删除不存在的 key 不产生新的逻辑更新；批量部分失败只通知成功对象。同次业务提交，同对象同类变化只产生一个逻辑事件；网络重试可重复投递同一标识。

**集成方：** 用对象、发生时间及可比较版本/序号理解先后，不要求全局有序。注册和投递都按最小领域权限限制，撤权后不能再拿数据。过渡期原通用更新对 metadata 的触发保留，说明可能同时出现专用事件，消费者按类型处理。删除或过期对象通知仍能依据快照或删除标识解析，不能因查不到对象无限重试。

### 订阅过渡：先验证再切换

**集成方：** 新增事件仅提供 subscription payload，没有合法 query 就拒绝注册；旧事件继续支持既有固定 payload 和自定义 query。旧事件集合、签名、目标 URL、启用状态及字段含义不自动改变，不要求一次性重装应用。新增字段和事件在 Manifest、Webhook 创建/更新、事件列表、样例及 Dashboard 编辑器中一致可见。

**管理员：** 创建/修改时校验 query 的事件匹配、字段及权限，失败不能覆盖有效订阅。界面能看事件、模式、渠道、投递记录及迁移提示，管理需要 `MANAGE_APPS` 或已有应用所有者权限。预览样例并用隔离样例验证，不以真实资金动作测连接。交付旧订阅清单、新 query 示例、影响及切换恢复说明，单个 Webhook 可以先验证再切，旧固定格式不在本轮硬定停止日。

**运维：** 异步投递按至少一次处理：提交后可靠登记，崩溃不能丢掉已确认的变化；失败有限重试，耗尽可见并可授权重试。提供稳定事件标识、时间、对象及验签说明，排队不等于送达。停用后不新投递，重新启用只恢复明确未成功范围，不能无提示重放全部历史。同步请求保留结果语义，任何重试都不能重复资金动作。

## 受控切换与恢复

### 维护窗口：保护在途资金和新增事实

**管理员：** 先出不含明文密钥的影响报告、验证外部路径及完成受控备份，维护时停止入口写入、暂停或排空任务，并记录在途支付回调和待投递事件。迁移、对账、必要索引重建与验证完成后再开放流量，不能把“保护写入”理解为继续无约束接单。

**运维：** 维护期间外部回调需可持久接收，或由已验证的发送方重试，不能吞掉资金结果。API、worker 和 Dashboard 固定到交付源码对应版本或镜像摘要，未知来源的 latest 不能证明交付；Dashboard 生成代码和真实调用依据同一目标 schema。

**财务：** 开放前失败可恢复一致的数据库、媒体、配置和构建版本；开放后有新订单或外部资金动作，先暂停、保留增量并对账，再前向修复或可重放恢复，不可直接回滚旧数据库抹掉新资金。恢复要有责任人、检查、日志和验证，维护时长与 RTO 通过演练测量，不虚构生产承诺。

### 验证与外部依赖：要求不能冒充结果

**实施职能：** 后续设计需给出配套前后端契约、完整目标 schema 与差异、消费者迁移说明，具体接口命名由设计规范化，不改变已给定业务语义。后续验证覆盖多渠道、共享与独立资源、员工/顾客/无权应用、混合资金、旧账、新旧订阅、异常历史内容及不同数字权益，不用一个正常样本代替连续性验证。每条验收条件须有结果或明确失败原因，所有 P0 通过且无未解决数据、权限、资金阻断才满足交付；产品参数确实无法达到时，提交有证据的变更说明，不静默放宽。

**管理员：** 真实在用四类插件的商家/渠道、外部管理员实际登录结果，由商家管理员和运维补齐；旧数字字段及固定 payload 消费者清单由集成方确认；历史事件完整性和经审核账务证据由财务确认；选用外部支付/履约路径及可用性由集成方与实施负责人验证；真实存量规模和可接受维护窗口由负责人确认。材料未提供这些实际答案，不要编造。

**实施职能：** 这些是部署前依赖，不是在本次 Agent 运行中追加回答的计划。可以据此定义有条件需求，但证据缺失不能宣称可生产切换。标准本地验收环境的配置和负载也需在实施验证时明确；静态代码不是运行成功证据。
