# PRD：Saleor 3.23 剪枝后精简交付需求

版本：2.0  
责任：产品  
状态：需求范围与验收条件已定义，已完成剪枝边界确认  
基线：Saleor Core 3.22.0、Saleor Dashboard 3.22.9  目标：剪枝后的 Saleor 3.23 交付树

> 本文是面向交付和实施的精简版 PRD。它只描述剪枝后继续保留的业务需求；已从目标中移除的需求不在本文中重新展开。原始追踪版 PRD 仍保留在 `PRD/prd.md`，用于历史对照。

## 1. 业务背景与目标

Saleor 3.23 的本次交付围绕一条完整的商业交易链路展开：客户创建 checkout、获得可用配送方式、完成支付、生成订单，商户随后可以基于渠道、仓库和订单状态完成履约与售后操作。系统同时需要为 App、支付服务和 Webhook 集成方提供稳定的 GraphQL、权限、迁移和事件合同。

本版本的产品目标是：

1. 让 checkout 配送、库存、支付和订单状态在 Core、Dashboard 与外部集成之间保持一致。
2. 让商户能够配置自动完成策略、诊断商品可售性并安全执行订单交易操作。
3. 保留对运营有直接价值的主体搜索、App Extension、Webhook 和 Dashboard 列表能力。
4. 收紧输入校验和身份安全，减少错误数据、越权操作和不明确的兼容行为。
5. 保证公开 GraphQL、migration、generated client、权限和历史数据升级可以被验证和回归。

## 2. 用户与场景

### 2.1 Storefront 与集成开发者

- 根据 checkout 地址、商品、渠道和支付状态取得可用配送选项。
- 处理配送方式失效、支付不完整、库存不足和 API 校验失败。
- 使用交易、订单、商品、客户和 App Extension 的公开 GraphQL 合同。

### 2.2 商户运营人员

- 配置密码登录、仓库库存规则和已支付 checkout 自动完成策略。
- 查看商品在不同渠道的可售性原因，并根据诊断结果修正商品配置。
- 查看订单金额和交易状态，执行 capture、refund 或 mark as paid。

### 2.3 客服、订单和履约管理员

- 搜索 checkout、客户、员工、商品、订单和礼品卡。
- 查看礼品卡交易、支付余额、订单历史和配送元数据。
- 在权限允许的范围内完成订单、履约和基础元数据操作。

### 2.4 App、支付和 Webhook 集成方

- 安装和更新符合当前 manifest 合同的 App Extension。
- 接收同步或异步业务事件，并根据 delivery 状态进行重试或故障处理。
- 适配当前 schema 的必填字段、错误码、弃用字段和权限规则。

## 4. 需求条目

### R01 显式计算 checkout 配送选项

- 来源：Target Checkout delivery/API 变化及配对剪枝 patch。  
- 优先级：P0  
- 需求描述：Storefront 必须能够针对当前 checkout 主动计算、展示和更新配送选项，并在完成 checkout 前重新确认配送方式仍然有效。
**业务目的：**让 Storefront 在提交订单前获得一组与当前 checkout 状态一致的配送选项，避免使用缓存或过期的配送方式完成订单。

**用户故事：**作为 Storefront 开发者，我希望在地址、商品或渠道发生变化后重新计算配送选项，并知道哪一个选项当前可用、已选择或已失效，这样我可以给客户展示准确的运费和配送方式。

**触发与输入：**用户提供有效的 checkout 标识；checkout 至少包含可计算配送所需的渠道、商品和地址信息。地址、行项目、渠道或 shipping webhook 结果发生变化时，客户端可以重新发起计算。

**业务规则：**

- 系统根据当前 checkout 的地址、商品、渠道和同步配送服务结果计算选项。
- 返回结果必须标明可选配送项和当前选择；配送项只能属于当前 checkout。
- 更新配送方式和完成 checkout 时都必须重新检查配送项是否仍然可用、是否已过期。
- 计算或更新失败时不得保存半成品选择，也不得创建半成品订单。
- 旧客户端仍可按兼容规则读取旧配送字段；新客户端以当前 delivery 合同为准。

**验收条件：**

- AC-R01-01：给定地址、商品和渠道均有效的 checkout，发起配送计算后，返回当前可用的配送选项、当前选择和每项可展示的价格/状态信息。
- AC-R01-02：给定 checkout 地址或商品发生变化，重新计算后，旧的不可用配送项不再被标记为可选择。
- AC-R01-03：给定已选择配送方式在完成前变为过期或不可用，完成请求被阻止，并返回可区分的配送失效原因。
- AC-R01-04：给定配送计算因地址不完整、shipping 服务错误或 checkout 不存在而失败，系统不改变原有有效选择，并返回字段级错误。
- AC-R01-05：给定兼容客户端使用旧配送标识、当前客户端使用新配送标识，两种合法请求都只能更新属于该 checkout 的配送方式。

### R02 礼品卡纳入 Transaction 支付链路

- 来源：Target Gift Card payment/Transaction 变化及配对剪枝 patch。  
- 优先级：P0  
- 需求描述：礼品卡支付必须纳入统一 Transaction 生命周期，支持初始化、授权、取消、扣款、退款、幂等和 Dashboard 可追踪展示。
**业务目的：**让礼品卡支付与普通交易共享一致的授权、扣款、取消、退款和历史记录模型，使 checkout、订单和 Dashboard 能看到同一笔支付事实。

**用户故事：**作为商户或支付集成方，我希望礼品卡余额被当作一种可追踪的 transaction payment method，这样我可以安全地完成订单并在取消或售后时恢复或退回金额。

**触发与输入：**用户在 checkout 或订单中提交礼品卡支付；系统收到初始化、授权、取消、扣款或退款请求；Dashboard 查询交易或礼品卡支付明细。

**业务规则：**

- 礼品卡必须存在、启用、未过期、币种匹配且余额足够。
- 同一 checkout/order 的重复请求必须保持幂等，不能重复扣减余额或生成冲突授权。
- checkout 阶段的授权可以取消；订单阶段已完成的礼品卡扣款可以按可退余额退款。
- 交易事件、礼品卡余额和订单/checkout 支付状态必须在同一业务结果中保持一致。
- 权限不足、礼品卡状态不合法和金额超限必须返回明确错误，不得静默转换为普通支付。

**验收条件：**

- AC-R02-01：给定有效礼品卡且余额、币种和有效期均满足要求，支付初始化成功并生成可追踪的交易记录。
- AC-R02-02：给定礼品卡已停用、过期、币种不匹配或余额不足，支付请求失败，余额和订单支付状态均不被错误修改。
- AC-R02-03：给定同一支付请求被重复提交，最终只产生一次有效授权/扣款和一次余额变化。
- AC-R02-04：给定 checkout 尚未完成，取消礼品卡授权后，授权状态和可用余额恢复到可解释状态。
- AC-R02-05：给定订单存在已完成的礼品卡扣款，退款金额不超过可退余额，交易历史、礼品卡余额和订单退款状态保持一致。
- AC-R02-06：Dashboard 查看订单交易时，可以区分礼品卡支付方式、金额和相关事件，并在操作失败时展示可识别的错误。

### R03 Transaction 基础查询合同

- 来源：Target Transaction 查询变化；阶段 04-A 删除日期/事件过滤和排序后的保留合同。  
- 优先级：P1  
- 需求描述：保留按订单、checkout、交易 ID、PSP reference 和 app identifier 定位交易的基础查询合同，不提供已剪枝的日期/事件过滤、排序及专用索引。
**业务目的：**保留完成订单运营所需的最小交易查询能力，让商户可以按订单、支付服务商和应用定位交易。

**用户故事：**作为客服或支付集成方，我希望通过稳定的基础条件找到相关交易，而不依赖特定日期、事件排序或实现专用索引。

**业务规则：**

- 根级交易查询支持按订单/checkout 关联、交易 ID、PSP reference 和 app identifier 等主体条件过滤。
- 查询结果遵循现有分页和权限规则；客户、staff、App 只能看到其权限范围内的交易。
- 交易详情必须支持订单金额、支付方式、状态和事件展示所需的基础字段。
- 输入为空、类型错误、越界分页或无权限时返回稳定的 GraphQL/API 错误。

**验收条件：**

- AC-R03-01：给定订单、支付服务商或应用的合法查询条件，返回准确的交易集合，并遵守分页边界。
- AC-R03-02：给定礼品卡交易、普通订单交易和多交易订单，查询结果能通过 ID、关联对象和支付服务商准确定位。
- AC-R03-03：给定无权限身份或不属于当前对象的交易 ID，系统不泄露交易详情，并返回权限或不存在语义。
- AC-R03-04：给定非法过滤类型、空分页项或越界分页，系统在执行查询前返回明确校验错误。

### R04 可配置密码登录模式

- 来源：Target password login mode、Dashboard authentication settings 和配对剪枝 patch。  
- 优先级：P0  
- 需求描述：商店必须支持 ENABLED、CUSTOMERS_ONLY、DISABLED 三种密码登录模式，并让 Core 认证、密码流程和 Dashboard 入口读取同一生效配置。
**业务目的：**让商户可以明确控制客户和 staff 是否可以使用密码登录，同时让 Storefront、Dashboard 和密码修改流程使用同一配置。

**支持模式：**`ENABLED` 允许受支持用户使用密码；`CUSTOMERS_ONLY` 只允许客户使用密码；`DISABLED` 禁止密码认证及相关密码入口。外部认证入口按自身配置独立处理。

**业务规则：**

- 模式变更保存后，登录、密码重置、密码修改和 Dashboard 登录页立即读取最新配置。
- `CUSTOMERS_ONLY` 不能被 staff 用来获得后台能力；staff 必须使用允许的外部认证或其他管理入口。
- `DISABLED` 下不得通过旧密码、旧 token 或隐藏接口绕过配置。
- Dashboard 必须展示当前模式、权限限制、加载状态和保存错误。

**验收条件：**

- AC-R04-01：设置为 `ENABLED` 后，符合账户状态的客户可以使用密码登录，密码重置和修改流程保持可用。
- AC-R04-02：设置为 `CUSTOMERS_ONLY` 后，客户密码登录可用，staff 密码登录不能获得 staff 会话或后台能力。
- AC-R04-03：设置为 `DISABLED` 后，客户和 staff 的密码登录、重置或修改请求均被拒绝，并返回明确原因。
- AC-R04-04：Dashboard 打开登录或商店设置页面时，展示的认证入口与服务端模式一致，不显示已经禁用的入口。
- AC-R04-05：配置保存失败或无权限时，页面保留原值并显示错误，不把未保存的状态当作生效配置。

### R05 仓库-渠道库存可用性统一

- 来源：Target warehouse-channel stock availability 变化及配对剪枝 patch。  
- 优先级：P0  
- 需求描述：系统必须根据渠道与仓库关系计算商品可售性，并在商品、checkout、订单、履约和草稿订单入口复用一致的库存规则。
**业务目的：**建立一致的库存可售判断，避免商品页显示可售、checkout 却无法购买，或不同履约入口对同一库存给出不同结果。

**用户故事：**作为商户，我希望通过渠道和仓库关系控制库存可用性，并在 checkout、订单、履约、草稿订单和商品查询中看到相同的结果。

**业务规则：**

- 新库存计算方式以仓库与渠道的直接关联为主要事实源。
- 既有商店未打开新设置时，历史兼容行为继续有效，升级不能改变已有可售结果。
- checkout、order、fulfillment、draft order 和 Product availability 必须复用同一套库存可用性语义。
- 地址参数在新计算方式下不能绕过渠道/仓库关系，也不能让同一商品在不同入口得到冲突结果。
- 关系变更、库存不足、预留失败和权限不足必须有可解释结果。

**验收条件：**

- AC-R05-01：升级前未修改库存设置的商店，在 checkout、订单和履约场景中的既有库存结果保持不变。
- AC-R05-02：给定一个商品、渠道和多个仓库，打开新计算方式后，只有与该渠道直接关联且有可用库存的仓库参与可售计算。
- AC-R05-03：同一商品、渠道和库存状态分别通过商品查询、checkout、订单、履约和草稿订单检查时，返回一致的可售/不可售结论。
- AC-R05-04：库存预留或分配成功后，各入口反映相同的剩余可用量；失败时不产生超卖或部分预留。
- AC-R05-05：客户端继续传入旧地址参数时，请求保持兼容，但地址不能改变新计算方式下由渠道/仓库关系决定的结果。

### R06 主体业务对象搜索

- 来源：Target search patch；阶段 04-B1/B2 删除 Page/User 高级搜索后的保留范围。  
- 优先级：P1  
- 需求描述：保留 Checkout、Gift Card、Product、Order、Customer、Staff 的主体搜索和基础 Page 查询字段，提供稳定分页、权限和 Dashboard 一致搜索语义。
**业务目的：**让客服和运营人员可以快速定位主体业务对象，同时确保搜索结果、分页和索引更新在 Core 与 Dashboard 中一致。

**当前对象范围：**Checkout、Gift Card、Product、Order、Customer、Staff，以及基础 Page 查询所需的 title/slug/content 搜索字段。

**业务规则：**

- 搜索支持合法关键词、空输入、分页和主体对象权限；空输入不得触发不可控的全量查询。
- 对象创建、修改、归档或关联字段变化后，搜索结果在约定的最终一致性窗口内更新。
- 订单、商品、礼品卡和 checkout 的搜索结果必须返回正确对象、稳定分页和必要的展示字段。
- 客户和 staff 搜索遵守隐私与 staff 权限，不因搜索接口暴露不应可见的地址或身份信息。
- Dashboard 的搜索输入、弹窗搜索和列表搜索应使用同一套查询语义，并明确显示空结果、加载和错误状态。

**验收条件：**

- AC-R06-01：给定客户、staff、订单、商品、礼品卡或 checkout 的合法关键词，返回匹配对象且结果不包含无权限数据。
- AC-R06-02：给定对象的名称、编码、邮箱或主体标识发生变化，后续搜索可以定位新值，旧值不会持续作为唯一结果。
- AC-R06-03：给定分页、重复关键词、大小写差异或组合关键词，结果顺序、数量和分页游标稳定且可解释。
- AC-R06-04：给定空关键词、过长关键词、非法输入或搜索服务异常，系统返回明确的空态/校验/错误状态，不阻塞其他列表操作。
- AC-R06-05：Dashboard 在列表、弹窗和筛选器中执行同一主体搜索时，展示结果与 Core 查询一致。

### R08 App Extension 与 manifest 合同

- 来源：Target App Extension、manifest、双向表单和 self-hosted catalog 变化。  
- 优先级：P1  
- 需求描述：App 安装、迁移、扩展渲染、表单响应和 self-hosted catalog 必须遵循 mountName、targetName、settings 等当前 manifest 合同。
**业务目的：**让 App 安装、扩展渲染、表单响应和 self-hosted catalog 使用统一的 manifest 结构，降低不同版本 App 与 Dashboard 之间的兼容成本。

**业务规则：**

- Extension 使用当前的 mount、target 和 settings 结构；可选字段缺省时采用稳定默认行为。
- manifest 的 identifier、权限、target 和 settings 必须在安装前完成校验。
- 重复 identifier、无效权限、非法 target 或无法解析的设置必须拒绝安装/更新，并返回可定位错误。
- migration 要保留已有扩展数据；读取旧记录时，系统应转换到当前合同，不要求客户端继续提交旧字段。
- Dashboard 的 popup/form response 必须处理缺省值、成功响应、验证错误、权限错误和 App 关闭等状态。
- self-hosted catalog 不依赖不可用的旧 marketplace 地址，目录加载失败时仍要给出可理解的空态或错误态。

**验收条件：**

- AC-R08-01：给定 manifest 缺少可选安装字段，App 仍可完成安装，且生成的扩展配置具有稳定默认值。
- AC-R08-02：给定重复 identifier、无效权限或非法 target，安装/更新被拒绝，已有有效扩展数据不被破坏。
- AC-R08-03：给定迁移前的扩展记录，执行 migration 后扩展仍可查询、编辑和渲染，settings 数据不丢失。
- AC-R08-04：给定 App 返回有效或无效 form response，Dashboard 分别展示成功结果或字段级错误，不把错误响应保存为成功状态。
- AC-R08-05：给定 self-hosted 环境没有旧 marketplace 服务，扩展目录仍能加载可用数据或显示明确的失败原因。

### R09 已支付 checkout 自动完成

- 来源：Target automatic checkout completion 变化及配对剪枝 patch。  
- 优先级：P1  
- 需求描述：商户可以按渠道配置自动完成规则；后台任务只处理满足支付、客户、地址、配送、库存和金额条件的 checkout，并对失败执行幂等重试。
**业务目的：**减少商户手工完成已支付 checkout 的操作，同时防止未满足客户、地址、配送、库存或金额条件的 checkout 被错误转成订单。

**配置项：**商户按渠道设置是否启用、延迟时间和 cutoff；配置必须明确适用渠道和生效范围。

**自动完成条件：**checkout 已达到支持的 fully paid 状态；存在必要客户/邮箱；地址和配送信息完整；商品仍可售；订单总额满足业务规则；checkout 尚未被完成或重复处理。

**业务规则：**

- 配置保存只表示规则已保存，不表示某个 checkout 已完成。
- 调度任务按批次寻找符合条件的 checkout，并为单个 checkout 执行幂等完成。
- 完成前必须再次检查支付、库存、配送、地址和金额，避免任务排队期间状态变化造成错误订单。
- 任务失败必须记录可重试状态；重试不能重复创建订单、重复扣款或重复发送完成事件。
- Dashboard 显示当前配置、保存错误和可观察的订单状态，不在前端模拟后台任务结果。

**验收条件：**

- AC-R09-01：给定合法的开关、延迟和 cutoff 组合，渠道配置保存成功，重新打开页面可以看到相同配置。
- AC-R09-02：给定支付未完成、缺少客户/地址/配送、商品不可售或总额不符合规则的 checkout，任务运行后不创建订单。
- AC-R09-03：给定各受支持支付模式下满足全部条件的 checkout，任务按渠道配置完成 checkout，并产生唯一订单结果。
- AC-R09-04：给定任务第一次执行失败，条件修复后再次执行可以成功；多次重试不会重复创建订单或改变已完成订单金额。
- AC-R09-05：给定配置无权限、范围非法或保存冲突，Dashboard 保留原配置并展示错误，不显示虚假的成功状态。

### R10 Product Doctor 商品可售性诊断

- 来源：Target Dashboard Product Doctor 和商品可售性数据变化。  
- 优先级：P1  
- 需求描述：商品编辑页必须按渠道展示影响可售性的发布、库存、仓库、配送区域和时间配置事实，并区分阻断错误、警告和不适用检查。
**业务目的：**让商户能够解释商品为什么不能在某个渠道销售，并把可修复问题与非问题条件区分开，减少依赖人工排查。

**诊断范围：**渠道发布状态、商品/变体库存、仓库关联、配送区域适用性、时间配置和其他直接影响可售性的事实。

**业务规则：**

- 诊断按渠道返回事实和问题等级，至少区分 error、warning、skipped/不适用。
- 未发布、无库存或渠道配置不完整时，应指出实际阻断原因，不返回与当前商品无关的噪音。
- 不需要配送的商品跳过配送区域检查，但仍继续检查库存和其他核心条件。
- 诊断结果遵守渠道、商品和 staff 权限；无权限不能通过错误信息推断受限数据。
- 商品或渠道正在编辑时，页面必须显示加载/刷新状态，避免把旧结果当成最新结论。

**验收条件：**

- AC-R10-01：给定商品关联多个渠道，商户可以按渠道名或币种筛选并分页查看每个渠道的问题计数和明细。
- AC-R10-02：给定渠道未发布或商品不可售，诊断显示直接阻断原因，不把正常的依赖项重复计为错误。
- AC-R10-03：给定商品不需要配送，诊断将配送区域检查标记为不适用，同时继续返回库存和发布状态结论。
- AC-R10-04：给定用户权限不足、查询失败或商品正在编辑，页面显示对应错误/加载状态，不覆盖用户当前编辑内容。

### R12 订单金额、支付和交易操作

- 来源：Target Dashboard order/payment redesign、Transaction 和 legacy payment 变化。  
- 优先级：P0  
- 需求描述：Dashboard 必须展示可信的订单金额分解和交易余额，并安全执行 mark as paid、capture、refund 等受权限和金额边界约束的操作。
**业务目的：**为商户提供可信的订单金额和支付操作，使 capture、refund、mark as paid 与交易状态之间不存在超额、重复或权限绕过。

**订单金额展示：**订单摘要应区分商品金额、折扣、税费、配送、礼品卡、已授权、已扣款、已退款和剩余待付金额；各项相加关系应可解释。

**操作规则：**

- capture 金额不能超过当前可捕获授权金额。
- refund 金额不能超过当前可退款金额；多笔交易需要合并计算已使用额度。
- mark as paid 只在订单状态、权限和现有支付记录允许时展示和执行。
- 交易操作必须幂等；重复提交不能重复扣款、退款或生成冲突事件。
- 成功操作返回刷新后的订单/交易事实；失败操作保留原状态并展示 typed error。

**验收条件：**

- AC-R12-01：给定包含折扣、礼品卡、税费和多笔支付的订单，金额摘要各组成项与服务端计算一致，剩余余额不重复计算。
- AC-R12-02：给定用户具有支付权限且订单允许人工收款，mark as paid 操作可执行；无权限或不适用状态下操作不可用。
- AC-R12-03：给定订单存在部分或全部授权，capture 输入等于边界值时按规则成功，超过可捕获金额时被拒绝且状态不变。
- AC-R12-04：给定订单存在多笔交易，refund 输入不超过可退款余额时成功，超过余额或重复提交时被拒绝/幂等处理。
- AC-R12-05：给定支付操作成功，Dashboard 刷新后显示新的订单状态、交易事件和余额；给定失败，页面不显示虚假的完成状态。

### R13 配送元数据快照与基础编辑

- 来源：Target shipping metadata denormalization、metadata dialogs 变化；阶段 01 剪枝边界。  
- 优先级：P1  
- 需求描述：保留配送元数据在订单创建时的快照、历史读取、迁移和基础编辑；不交付独立 metadata dialog、路由和专用入口。
**业务目的：**保留订单履约所需的配送元数据，并确保历史订单记录的是创建时事实，而不是被源对象后续变化追溯修改。

**业务规则：**

- checkout 或 draft order 使用的配送方式元数据，在订单创建时复制为订单/履约可读取的快照。
- 源配送方式后续被修改、停用或删除时，已创建订单的快照不被回写。
- checkout、draft order、order 和 fulfillment 只暴露当前业务需要的基础 metadata 读写能力。
- metadata 操作遵守对象权限和字段校验；非法键值或无权限修改不得产生部分写入。
- migration 后历史订单仍可读取已有元数据；没有元数据的历史记录返回稳定空值。

**验收条件：**

- AC-R13-01：给定带配送元数据的 checkout 或 draft order，创建订单后可以从订单/履约读取创建时的相同快照。
- AC-R13-02：给定订单已创建，修改或删除源配送方式后，订单历史快照保持不变。
- AC-R13-03：给定合法基础 metadata 更新，用户在权限范围内可以保存并读取新值；无权限或非法值不会改变原值。
- AC-R13-04：给定旧数据执行 migration，历史订单元数据可读取，migration 不产生重复记录或数据丢失。

### R14 Dashboard 列表、筛选和导航一致性

- 来源：Target Dashboard list/filter/navigation changes。  
- 优先级：P1  
- 需求描述：列表页面必须正确合并锁定筛选、普通筛选、URL 状态和批量操作条件，并在层级导航、长文本和异步状态下保持可理解的一致行为。
**业务目的：**让商户在高频列表操作中保持筛选条件、层级路径和批量动作的一致，避免“页面显示一组数据、操作作用于另一组数据”的风险。

**业务规则：**

- URL、弹窗或页面上下文提供的锁定条件必须与普通筛选分开管理，普通筛选不能覆盖锁定条件。
- 仓库、分类和分配类层级数据需要去重，并保持稳定的父子路径。
- 导出、批量操作、礼品卡筛选和排序必须读取当前页面的有效筛选，而非过期缓存。
- 长关键词输入不能破坏布局；页面应保持稳定宽度并提供截断或完整值提示。
- loading、empty、permission、error 和返回列表状态需要保持导航上下文。

**验收条件：**

- AC-R14-01：给定带锁定渠道/仓库条件的分配页面，修改其他筛选后锁定条件仍然生效。
- AC-R14-02：给定用户取消仓库选择或切换分类层级，列表不出现重复项，面包屑和父子关系正确。
- AC-R14-03：给定当前列表已有筛选，执行导出或批量操作时，服务端收到的条件与页面当前筛选完全一致。
- AC-R14-04：给定长搜索关键词，输入框、结果列表和提示不发生重叠或跳动，用户仍能确认完整关键词。

### R15 Webhook 延迟求值和异步事件载荷

- 来源：Target Webhook promise/async event changes。  
- 优先级：P1  
- 需求描述：同步 webhook 只计算订阅实际选择的字段；允许的订单类事件在异步任务边界构建 payload，并隔离不同 delivery 的失败和重试。
**业务目的：**降低同步请求因构建无关事件载荷而产生的延迟，并让异步事件、失败重试和多 App delivery 之间相互隔离。

**业务规则：**

- 同步 webhook 只解析订阅查询实际选择的字段，不为未选择字段执行额外计算。
- 订单、draft order、fulfillment 等允许异步处理的事件，在异步任务边界构建完整 payload。
- promise、调用次数、超时、retry 和 circuit breaker 遵循现有上限，不能通过重复解析放大负载。
- 单个 App 或 shipping webhook 的失败只影响该 delivery；其他订阅继续按规则处理。
- Dashboard 展示 delivery 状态、重试和错误，不假设异步 payload 在 mutation 返回时已经存在。

**验收条件：**

- AC-R15-01：给定只订阅异步事件的 App，触发业务操作后，不提前执行无关同步通知。
- AC-R15-02：给定会产生较大订单事件 payload 的 mutation，请求在不等待完整异步 payload 的情况下完成，worker 随后构建并发送有效 payload。
- AC-R15-03：给定商品折扣价格等已定义业务事件满足触发条件，订阅方收到一次合同正确的 delivery；无实质变化的保存不重复触发。
- AC-R15-04：给定一个 App delivery 失败和另一个 delivery 成功，失败 delivery 按策略重试，成功 delivery 不被阻断。
- AC-R15-05：Dashboard 查看 delivery 时，可以区分 pending、成功、失败和重试中状态，并支持在权限范围内单条重试。

### R16 内容输入与身份认证安全

- 来源：Target EditorJS 和 OIDC hardening 变化。  
- 优先级：P0  
- 需求描述：系统必须在保存前校验和清理富文本及外链，并按 provider 合同处理 OIDC refresh token 和既有用户身份关联，防止绕过和敏感信息泄露。
**业务目的：**阻止不安全内容进入系统，并保证 OIDC、密码和外部链接处理不会产生权限绕过或浏览器安全风险。

**业务规则：**

- EditorJS 内容先校验结构，再清理 URL、链接属性和嵌套深度；未知字段、非法 scheme 和过深结构不得绕过校验。
- 合法的 `http`、`https`、`mailto`、`tel` 等链接按产品规则保存；外部新窗口链接必须具备安全的 rel 行为。
- Google OIDC 在需要 refresh token 时使用兼容的离线授权参数；不同 provider 不互相套用错误参数。
- OIDC 首次关联既有用户时，系统必须按当前身份策略处理旧密码路径，不能让旧密码绕过已建立的外部身份约束。
- 安全校验失败不得保存部分危险内容，也不得在错误响应中泄露 token 或敏感身份信息。

**验收条件：**

- AC-R16-01：提交包含未知字段、非法链接或超过深度限制的内容时，请求被拒绝，数据库不保存危险部分。
- AC-R16-02：渲染合法外链时，链接协议和安全属性符合规则；非法 scheme 被拒绝或清理，不能控制来源页面。
- AC-R16-03：Google OIDC 授权 URL 在需要 refresh token 的配置下使用离线访问参数，其他 provider 仍使用各自合同。
- AC-R16-04：既有用户首次关联 OIDC 身份后，旧密码不能绕过当前身份策略；同一 OIDC 身份后续登录保持稳定。

### R17 GraphQL/API 输入约束与兼容语义

- 来源：Target GraphQL/API compatibility changes。  
- 优先级：P0  
- 需求描述：GraphQL/API 必须在执行前校验输入、权限和组合关系，明确处理删除/弃用合同，并同步 Core schema、Dashboard generated types 和错误语义。
**业务目的：**通过统一输入校验、权限校验和弃用语义，减少 API 调用方对隐式行为的依赖，并让删除、导出和敏感字段访问可预测。

**业务规则：**

- 数值、时间、分页、枚举、required input 和 Federation representation 在执行前校验类型、范围和组合关系。
- staff 删除、属性更新、App 安装、导出和税务字段查询必须按权限执行，不能因 GraphQL 层返回 HTTP 200 就视为成功。
- 当前公开 schema 只承诺现行支付、数字商品、App、订单、商品和导出合同；已弃用字段按明确的 deprecated 或迁移语义处理。
- 失败 mutation 不产生部分写入；错误应包含可供客户端分支处理的字段/code/message。
- Core schema、Dashboard generated hooks/types 和文档必须同步更新，避免客户端继续生成已不支持的操作。

**验收条件：**

- AC-R17-01：提交负数时间、越界分页、错误类型或无效 Federation entity 时，请求在执行前被拒绝并返回明确校验错误。
- AC-R17-02：提交缺失 required 字段的 mutation 时不产生写入；有权限用户可以删除合法 staff，无权限或自删请求被拒绝。
- AC-R17-03：调用方访问当前不再承诺的旧合同，系统返回明确的不存在、deprecated 或迁移错误，不静默执行旧逻辑。
- AC-R17-04：具有导出权限的用户可以使用当前 API 导出商品、礼品卡和 voucher；无权限用户不能通过更换查询入口绕过权限。
- AC-R17-05：对 Checkout/Order 敏感税务字段的读取遵守 HANDLE_TAXES 等权限，未授权身份不能获得数据。
- AC-R17-06：订单条件查询、数组输入和组合过滤对合法输入返回准确结果，对空项、错误类型和越界值返回稳定错误。

### R18 Dashboard 配置和展示一致性

- 来源：Target Dashboard configuration/display changes。  
- 优先级：P1  
- 需求描述：Dashboard 必须基于最新服务端事实处理配置加载、缓存更新、单位/时间展示和 draft-order 操作状态，避免过期或错误数据驱动错误操作。
**业务目的：**修复配置页、商品页、订单历史和草稿订单中的数据展示与操作状态问题，使 Dashboard 不根据过期、缺失或错误格式的数据执行错误操作。

**业务规则：**

- 页面必须区分 loading、已加载空数据、权限错误、网络错误和可重试状态。
- 渠道、商店和商品数据到达后，只更新仍与当前编辑上下文相关的字段，不覆盖用户正在输入的值。
- 重量、媒体状态、折扣金额和订单日期分组按服务端真实数据、单位、locale 和 timezone 展示。
- 停用渠道、无可售商品或缺少必要配置时，禁用不适用的 draft order 动作，并说明原因。
- mutation 成功后更新相关缓存或重新读取服务端事实；失败时保留原状态。

**验收条件：**

- AC-R18-01：打开渠道或商店设置时注入加载延迟，页面不崩溃、不闪烁错误值；数据到达后表单正确回填并可保存。
- AC-R18-02：给定不同单位重量、媒体失败、折扣事件和跨日期边界订单，Dashboard 展示值与 API 原始数据一致，分组不受 locale/timezone 错误影响。
- AC-R18-03：给定停用渠道、无可售商品渠道和正常渠道，draft order 页面分别禁用不适用动作并说明原因，正常渠道仍可操作。
- AC-R18-04：给定任一配置 mutation 失败，页面不把失败值写入缓存，并允许用户在修正后重试。

## 6. 其他

### 6.1 产品原则和约束

- **交易链路优先**：配送、库存、支付、订单和履约相关行为不能因界面或单点功能调整而断裂。
- **同一事实源**：同一商品、渠道、仓库、交易和订单状态在不同入口应返回一致结果。
- **失败可解释**：过期、无权限、余额不足、输入非法和配置不完整必须返回可区分的错误或状态。
- **兼容可迁移**：历史数据可完成 migration；兼容字段有明确的读取或弃用语义。
- **产品与实现分离**：依赖升级、测试适配、生成工具和内部重构只有在影响产品合同时才进入需求验收。

### 6.2 迁移、兼容和验收规则

- migration 必须可从空数据库执行，并能保留已有订单、交易、扩展、库存和元数据的业务语义。
- Core schema 变更必须同步 generated schema；Dashboard 操作、类型和错误映射必须与当前 schema 一致。
- Base 验证使用 environment patch 与最终剪枝 test patch；Target 使用同一测试树并增加剪枝 code patch。
- 冻结的 F2P/P2P 选择必须全部通过；不得删除断言、扩大 skip、隐藏错误或用测试专用生产 stub 代替真实行为。
- 验收结果：F2P `5365/5365`、P2P `15013/15013`、reward `1`。对应 patch、tree、冻结 selection 和验证证据见 `../evidence/`。
